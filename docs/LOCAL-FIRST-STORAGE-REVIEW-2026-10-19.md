## 권장 방향

**Android 앱 내부에 글·방문 기록·사진을 저장하고, 사용자가 선택한 외부 위치로 백업하는 방식**을 권한다. 새 개인 기록의 필수 경로에서 Supabase와 자체 회원가입을 제거하는 방향이다. 기본 저장은 인터넷·광고 로딩·클라우드 로그인과 무관하게 동작해야 한다.

처음부터 여러 기기 간 자동 병합과 공동 편집까지 만들지 않는다. 첫 버전은 주 기기 한 대를 기준으로 복구 가능한 전체 백업을 제공하고, 다음 단계에서 Google Drive 자동 백업을 붙이는 순서가 적합하다. iOS 확대 시 iCloud 등 플랫폼별 백업을 검토하되 Android와 iOS 사이의 자동 동기화를 보장하는 것으로 소개하지 않는다.

현재의 기존 공동 기록은 보존 대상이다. 운영비 우선 선택을 공동 기록 삭제·개인 소유권 자동 이전의 승인으로 해석하지 않는다. 공동 편집과 웹/여러 기기의 즉시 동기화를 유지하려면 별도 서버 또는 더 복잡한 동기화 구조가 계속 필요하다.

## 가능한 대안 비교

| 대안 | 운영 비용 구조 | 현재 앱에서의 전환 작업 | 판단 |
|---|---|---|---|
| 기기 저장 + 파일 백업 | 개인 기록용 자체 DB·사진 저장/전송 서버를 운영하지 않음. 사용자의 기기/백업 공간 사용 | 로컬 DB·파일 저장·백업/복구, 세션 의존 제거, Android 패키징 | **현재 우선 권장**. 초기 개발은 필요하지만 사용자 증가에 따른 자체 사진 비용을 줄임 |
| 기기 저장 + 사용자 클라우드 | 위 구조에 사용자의 Drive 등 연결. 용량은 사용자 계정의 한도/정책에 따름 | OAuth·업로드 재시도·백업 세대·복원·연결 해제. 자동 동기화는 추가 충돌 처리 필요 | 두 번째 단계. 자동 백업부터 시작 |
| Firebase Auth + Firestore + Storage | 관리형 인증·DB·사진 저장. 무료 구간 이후 사용량에 따른 비용 | 현재 PostgreSQL 함수·RLS·검색/집계·저장 계약을 Firestore 모델/규칙/서버 처리로 재설계 | Supabase 대체는 가능하지만 비용 최소화만을 위한 첫 선택으로 권하지 않음 |
| PostgreSQL + 자체 API + 비공개 R2/S3 | DB·API·인증·스토리지·메일·백업의 비용을 각각 관리 | SQL 일부 재사용 가능. `auth.uid()`, Storage 정책, RPC 노출·권한 경계를 교체 | 공동 편집·웹 동기화를 유지하면서 Supabase에서 벗어날 때 검토 |
| VPS에 DB/API/파일 직접 운영 | 서버 요금 외 패치·백업·모니터링·복구 운영 필요 | 인증·배포·객체 저장·장애 대응까지 직접 책임 | 소규모 개인 기록 앱의 첫 출시에는 운영 부담이 큼 |

Firebase Cloud Storage는 현재 Blaze 종량제 연결이 필요하다. 무료 사용량이 남더라도 결제 연결 없이 사진을 계속 운영할 수 있다는 전제로 선택하면 안 된다. Firestore도 읽기·쓰기·저장량 등의 쿼터와 과금 구조를 확인해야 한다. [Firebase Storage 현행 요건](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024?hl=en), [Firestore 사용량](https://firebase.google.com/docs/firestore/quotas).

Cloudflare R2는 인터넷 전송에 대한 egress 요금이 없고 Standard 저장·요청의 무료 구간을 제공하지만, 초과 저장과 요청 등은 유료다. 또한 인증·DB·권한 확인 API까지 대신해 주는 서비스는 아니다. 공유 기능이 필요해지는 단계의 사진 저장 후보로 남긴다. [R2 공식 요금](https://developers.cloudflare.com/r2/pricing/).

## 권장 구조의 구성

| 데이터/기능 | 저장·처리 위치 |
|---|---|
| 역·호선·노선도 | 버전이 있는 정적 데이터를 앱에 포함. 이후 필요 시 작은 갱신 파일 다운로드 |
| 방문 날짜·장소명·메모·태그·사진 메타데이터 | 앱 내부 SQLite DB |
| 첨부 사진 | 앱의 비공개 영구 파일 영역에 복사. 캐시나 갤러리의 임시 URI만 보관하지 않음 |
| 사진 썸네일 | 기기에서 생성. 서버 이미지 변환·서명 URL 없이 조회 |
| 검색·기간·태그·통계 | 로컬 DB 질의와 인덱스. 기존 검색 의미와 페이지 정렬 유지 |
| 백업 | 글·태그·사진·스키마 버전·파일 목록을 포함한 복구용 묶음을 기기 밖에 저장 |
| 클라우드 연결 | 백업을 선택한 사용자만 Drive 등 권한 연결 |
| 광고 | 네이티브 광고 SDK가 광고 네트워크와 통신. 기록 저장소와 분리 |

Android 패키징은 현재 React 화면과 노선도·사진 전처리를 재사용할 수 있는 Capacitor 경로를 우선 기술 검증한다. SQLite 플러그인/브리지의 현재 Android·Capacitor 버전 지원, 영구 파일 접근, 앱 재시작과 업데이트 후 유지, 광고 SDK 호환성을 확인한 뒤 라이브러리를 확정한다. [Capacitor 개요](https://capacitorjs.com/docs), [파일 시스템 API](https://capacitorjs.com/docs/apis/filesystem).

**브라우저의 localStorage만으로 사진 보관 앱을 만드는 안은 권하지 않는다.** IndexedDB도 웹 저장소 정책과 사용자 삭제 영향을 받으므로 백업 없는 장기 보관 수단으로 취급하지 않는다. 네이티브 앱의 DB/파일과 웹 미리보기용 저장을 구분한다. [MDN 저장 한도·삭제 정책](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

이 구조로 개인 기록용 자체 DB·사진 서버 비용은 없앨 수 있다. 다만 스토어 개발자 등록·도메인·지원/배포·광고/오류 수집 운영과 개발 유지보수 비용까지 0원이 되는 것은 아니다. 사용자 클라우드 용량이 부족하면 백업이 실패할 수 있으므로 성공/실패 상태를 표시해야 한다.

## 백업과 동기화를 구분한다

백업은 특정 시점의 복구 가능한 사본이고, 동기화는 여러 기기의 변경을 합쳐 일관된 상태로 만드는 기능이다. 첫 버전은 백업/복원과 주 기기 변경을 지원한다. 다른 기기에서 같은 백업 파일에 동시에 쓰는 기능은 제공하지 않는다.

Google Drive의 `appDataFolder`는 앱만 접근하는 숨김 영역을 제공하지만 그 안의 파일은 공유할 수 없다. 따라서 개인 자동 백업에는 적합한 후보지만 커플 공동 편집 저장소가 저절로 되지는 않는다. [Google Drive 공식 제약](https://developers.google.com/workspace/drive/api/guides/appdata).

Android 앱 전용 파일은 앱 삭제 시 제거된다. OS 자동 백업도 앱당 25MB 한도가 있어 사진 기록 앱의 전체 백업을 맡길 수 없다. **백업/복원은 출시 필수 기능으로 올리고 새 폰에서 사진까지 복구되는 것을 검증한다.** [Android 앱 파일 수명](https://developer.android.com/training/data-storage/app-specific), [Auto Backup 한도](https://developer.android.com/identity/data/autobackup).

출시 전 필요한 백업 계약은 다음과 같다.

1. DB의 일관된 시점과 연결된 사진을 함께 담고 스키마 버전·개수·크기·검증용 해시를 기록한다. 장기 교환용 데이터 형식과 복구용 형식을 구분한다.
2. 내보내기는 앱 샌드박스 밖의 사용자가 고른 위치/공유 경로에 완료된 경우에만 성공으로 표시한다. 같은 폰 안의 앱 폴더 사본은 기기 분실 대비가 아니다.
3. 복원 전 파일 목록·크기·경로·해시·버전을 검증하고 현재 데이터의 백업을 제안한다. 임시 영역에 복원한 뒤 검증 성공 시 전환하며, 실패하면 현재 기록을 보존한다.
4. 기본 복원은 주 기기 이전을 위한 전체 복원으로 명확히 안내한다. 자동 병합은 후속 설계다. 생성 ID와 사진 ID를 보존해 중복/누락을 식별한다.
5. 마지막 성공 백업 시간과 그 이후 변경 여부를 표시한다. 백업 연결 실패·용량 부족·권한 철회·일부 사진 누락을 숨기지 않는다.
6. 암호화 백업은 검증된 구현과 복구 수단을 사용한다. 앱 삭제로 사라지는 기기 키 하나에만 의존하면 새 기기에서 풀 수 없으므로 암호/복구 키와 분실 안내를 함께 설계한다.

자동 백업은 파일 백업 검증 후 Drive부터 추가한다. 백그라운드 실행 제한을 고려해 가능한 시점에 실행하고 실제 성공 시각을 표시한다. 일정 간격의 업로드가 반드시 완료된다고 약속하지 않는다.

## 기존 코드의 이전 범위

현재는 단순히 Supabase URL이나 SDK를 바꾸는 수준의 결합이 아니다. `SessionProvider`의 로그인/기록 공간, `record-rpc.ts`의 저장·revision·작업 영수증, `photo-storage.ts`의 업로드/서명 URL, `station-master.ts`와 화면의 직접 조회가 모두 연결돼 있다.

| 현재 경로 | 전환 시 필요한 변경 |
|---|---|
| `src/auth/SessionProvider.tsx`, `src/auth/guards.tsx` | 새 개인 모드의 로컬 소유자/저장소 준비 상태를 로그인과 분리. 백업 계정 연결을 앱 사용의 필수 조건으로 두지 않음 |
| `src/lib/record-rpc.ts`, `src/lib/record-card-query.ts` | 저장/조회 인터페이스를 분리하고 SQLite 구현 추가. 본문·태그·사진 메타데이터의 원자성·revision·오류 의미 보존 |
| `src/lib/photo-storage.ts`, `src/screens/records/PhotoField.tsx` | 비공개 파일 저장·로컬 썸네일·유실 파일 처리. DB/파일의 서로 다른 실패를 대비하는 준비/확정·정리 절차 |
| `src/lib/station-master.ts`, 방문 집계·역 상세·타임라인·프로필 | 실제 UUID/역 코드 연결을 유지한 정적 마스터와 로컬 질의로 전환 |
| 라우트·프로필·안내 | 로그인 없는 시작, 로컬 데이터 용량·백업 상태·복원·전체 삭제·광고 개인정보 선택 제공 |
| 기존 Supabase SQL/권한 테스트 | 과거 서버 계약 검증으로 보존. 새 로컬 저장 경로의 재시작·업데이트·실패 복구 검증을 대체하지 않음 |

PostgreSQL의 저장 함수와 RLS는 SQLite에 그대로 실행할 수 없다. 현재 UI·지도·입력 검증·사진 재인코딩 등은 재사용하지만, 저장 트랜잭션과 파일 일관성은 새 구현에서 다시 검증해야 한다.

### 기존 데이터 보호

- 유효한 기존 프로젝트와 데이터 유무부터 확인한다. 현재 DNS 문제만으로 데이터가 없다고 판단하지 않는다.
- 기존 개인 기록은 본인 인증 후 글·메타데이터·사진을 내보내고 로컬에서 개수·날짜·사진 해시를 대조한다.
- 기존 공동 기록은 기존 권한 안에서 별도 공동 기록 보관본으로 다룬다. 작성자·공동 공간 식별을 보존하고 자동으로 개인 원본 소유로 바꾸지 않는다.
- 로컬 보관본은 이후 상대의 수정·공유 해제와 자동 동기화되지 않는다는 점을 명시한다. 공동 편집을 유지해야 하는 사용자에게는 별도 서버 경로가 필요하다.
- 실제 복원·사용자 확인과 기존 보관/삭제 정책의 이행 전에는 원격 데이터나 계정을 삭제하지 않는다. 기존 계정의 탈퇴/삭제 대응도 전환 완료 전까지 남는다.

## 광고 수익화와의 관계

AdMob 연동은 자체 기록 서버가 있어야만 가능한 구조가 아니다. 로컬 기록 앱도 광고 네트워크 SDK로 광고를 요청할 수 있다. 따라서 서버 사진 비용을 줄이면서 타임라인 한 곳의 광고를 시험하는 방향은 유지할 수 있다. [Google 광고 SDK 도입 안내](https://developers.google.com/admob/android/next-gen/quick-start).

광고 통신은 계속 발생하므로 앱 전체를 인터넷이 전혀 필요 없는 앱으로 소개하지 않는다. 오프라인·광고 없음·동의 처리 실패 중에도 기록 저장/열람은 동작하게 한다. 일기·사진·역/장소 기록을 광고 요청 매개변수나 분석 이벤트로 전달하지 않는다.

자체 회원가입을 줄여도 광고 SDK의 데이터 처리, 개인정보 안내, 필요한 지역 동의, 스토어 신고, app-ads.txt와 광고 심사는 남는다. 광고·오류 수집 SDK를 실제 추가한 뒤 신고 내용을 갱신한다. [광고 동의 흐름](https://developers.google.com/admob/android/privacy), [광고 소유 검증](https://support.google.com/admob/answer/14538460?hl=en).

## 진행 순서

1. **작은 기술 검증:** Android 패키지에서 SQLite와 비공개 사진 저장·썸네일·앱 재시작·광고 테스트 호환성 확인.
2. **로컬 기록의 완결:** 저장·수정·검색·기간/태그·역별 집계·기록 삭제. 디스크 부족·중단·업데이트 후 보존 검증.
3. **전체 백업·복원:** 새 설치/다른 기기에서 사진까지 복구. 손상된 백업·버전 불일치·복원 실패·기존 기록 보존 검증.
4. **기존 데이터 이전:** 개인/공동 기록을 구분해 내보내기와 대조. 실제 원격 데이터 확인 전 삭제 없음.
5. **공개 출시 준비:** 로컬 보관 범위 안내·지원/개인정보 페이지·실기기 QA·스토어/광고 심사.
6. **후속:** Google Drive 자동 백업, 그다음 사용자 요구가 확인될 때 다중 기기 동기화나 선택 공유를 별도 설계.

앞선 출시 검토에서 Supabase 운영 연결을 첫 번째 공통 관문으로 둔 것은 **현재 서버 구조를 그대로 출시할 경우**의 판단이다. 이번 사용자 우선순위에서는 새 개인 모드의 출시 관문을 **기기 영구 저장과 검증된 백업/복원**으로 바꾼다. 기존 서버 데이터 이전의 확인 절차는 계속 필요하다.
