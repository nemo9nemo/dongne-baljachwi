# UI 변경 내역 및 기존 기획 대비 검토

작성일: 2026-10-05\
대상: 현재 로컬 작업 파일. 비교 기준은 UI 작업 전 코드(`02f94ad`, 이후 문서 커밋 `81a8498`은 앱 코드를 변경하지 않음)와 사용자의 요청 및 앞선 제안 보고서다.

## 1. 검토 결론

**현재 상태는 기존 커플 앱의 일부 화면을 간소화한 단계다. 사용자가 원한 ‘혼자 사용이 기본이고 함께 사용은 선택’인 제품으로 전환된 상태는 아니다.**

실제 UI 변경은 기록 목록 카드, 기록 작성·수정 폼, 타임라인의 태그 필터에 집중되어 있다. 가입·온보딩·기본 홈·하단 메뉴·지도·프로필·공유 구조는 그대로다. 가입 화면만 확인하면 이번 UI 변경이 보이지 않는 것이 맞다.

앞서 “1차 UI 수정 적용”으로 보고한 내용은 아래 일부 변경을 뜻한다. 전체 개인 기록 기획이나 UIUX 보고서의 모든 시안을 구현했다는 의미로 해석하면 실제 코드와 다르다.

## 2. 사용자 요구와 보고서 제안을 구분

| 구분 | 기준 |
|---|---|
| 사용자가 명확히 요구한 제품 방향 | 혼자 사용하는 것이 주이고, 누군가와 공유해 사용하는 것이 부 |
| 사용자가 명확히 요구한 디자인 방향 | 심플하고 깔끔한 스타일. 지나치게 많은 텍스트·컬러와 조잡한 구성 지양 |
| 사용자가 요구한 실행 방식 | 기능·UI 수정, 내용이 드러나는 단계별 커밋, 전체 흐름 테스트, 미정 사항은 사용자 확인 후 진행 |
| 분석 보고서가 제안한 구체 설계 | 개인 소유 원본과 선택 공유 모음, 최근 기록 홈, 기록/지도/내 정보 메뉴, 장소 중심 카드 제목, 검색·필터 재배치 |
| 확인이 필요한 정책 | 기존 공동 기록 처리 방식, 초기 공유 권한, 관리자 계정 정보·대시보드 범위 |

구체적인 화면 구성과 권한 모델은 사용자의 방향을 구현하기 위한 제안이다. 보고서에 적혔다는 이유만으로 모든 세부안이 사용자에게 확정된 것으로 간주하지 않는다. 다만 개인 사용을 기본으로 해야 한다는 요구 자체는 명확하다.

## 3. 어디가 어떻게 바뀌었는가

| 화면·요소 | 변경 전 | 현재 적용 | 사용자가 볼 수 있는 차이 |
|---|---|---|---|
| 기록 카드의 보조 정보 | 날짜 옆 감정·날씨 이모지, 태그 칩 최대 3개와 추가 개수 표시 | 목록의 이모지·태그 칩 제거 | 사진·날짜·메모가 더 눈에 들어옴. 감정·날씨·태그 데이터는 삭제하지 않음 |
| 목록 위 역명 링크 | 테두리와 좌우 여백이 있는 칩 형태, 반경 20% | 테두리 제거, 좌우 여백 축소, 기존 컨트롤 반경 토큰 적용 | 별도 역명 텍스트 링크로 보임. 클릭하면 역 상세 이동 유지 |
| 카드 썸네일 | 원본 사진 비율을 목록에 적용 | 폭 88px, 비율 1:1, `object-fit: cover` | 세로·가로 사진이 동일한 정사각형으로 표시됨. 원본 파일을 자른 것은 아님 |
| 작성·수정 폼 순서 | 역 → 날짜 → 감정 → 날씨 → 사진 → 일기 → 태그 → 저장 | 역 → 날짜 → 사진 → 일기 → 접힌 선택 항목 → 저장 | 먼저 사진과 기록을 작성할 수 있음 |
| 감정·날씨·태그 입력 | 모두 상시 노출 | ‘감정 · 날씨 · 태그 (선택)’을 열어 입력 | 기본 화면의 선택 버튼 10개와 태그 입력이 숨겨짐. 접어도 입력값 유지 |
| 타임라인 태그 필터 | 태그 버튼과 사용 횟수가 항상 표시 | ‘태그로 찾기’를 열 때 표시, 선택 후 요약에 선택 태그 표시 | 초기 목록이 간결해짐. 펼치면 기존 버튼·사용 횟수는 남음 |

카드 변경은 공용 `RecordCard`를 사용하므로 **타임라인과 역 상세의 기록 목록 모두**에 적용된다. 역 상세 목록은 기존에도 별도 역명 링크를 표시하지 않았으므로 그 화면에서는 링크 외형 변경이 보이지 않는다.

관련 코드: `src/components/RecordCard.tsx`, `RecordCard.module.css`, `src/screens/records/RecordEditorScreen.tsx`, `record-editor.module.css`, `src/screens/timeline/TimelineScreen.tsx`, `timeline.module.css`.

### UI와 함께 수정한 동작

- 사진 동기화가 실패하면 실패한 사진을 저장 완료로 취급하지 않고 이탈 경고를 유지한다.
- 타임라인 필터 변경 중 이전 요청·추가 페이지의 늦은 결과가 새 목록에 섞이지 않도록 한다. 조회 중 상태를 완료된 목록 캐시로 저장하지 않는다.
- 일기 길이 초과 오류 안내를 서버 제한과 같은 1,000자로 수정했다. 허용 길이를 새로 줄인 변경은 아니다.

## 4. 기존 기획과 다른 부분

| 요구·제안 | 실제 상태 | 판단·영향 |
|---|---|---|
| 혼자 사용하는 경험이 기본 | 주요 화면이 여전히 `RequireCouple` 안에 있음 | **핵심 요구 미반영.** 신규 사용자가 연결 없이 바로 개인 기록을 사용할 수 없음 |
| 공유는 필요할 때 선택 | 커플 만들기/합류 온보딩과 초대 흐름 유지 | 공유가 부가 기능으로 분리되지 않았음 |
| 개인 사용자에게 관계 대기 상태를 표시하지 않음 | 멤버가 1명이면 노선도·프로필에 ‘상대 초대 대기 중’ 표시 | 혼자 쓰는 사람을 미완성 상태로 보이게 하는 기존 경험이 남음 |
| 개인 기록 서비스에 맞는 문구 | 가입 화면에 ‘둘만의 발자취를 남길 계정을 만들어요.’ 유지 | 사용자가 밝힌 방향과 직접 충돌. 이번 UI 작업은 가입 화면을 수정하지 않았음 |
| 최근 기록 중심 홈 — 보고서 제안 | 기본 경로는 여전히 `/lines` | 시작 경험은 기록 회고보다 노선도 탐색 중심 |
| 기록/지도/내 정보 메뉴 — 보고서 제안 | 노선도/타임라인/프로필 유지 | 메뉴 이름·순서와 정보 구조 미적용 |
| 장소를 카드 주 제목으로, 날짜는 보조 — UIUX 보고서 제안 | 역명은 카드 바깥 링크, 카드 안의 굵은 제목은 날짜 | **카드 위계 미적용.** 칩 외형만 바뀌었고 장소 중심 카드로 재구성하지 않음 |
| 개인 카드에서 작성자 숨김 — 보고서 제안 | 모든 카드에 작성자 표시 유지 | 개인·공유 화면 구분이 없어 반복 정보가 남음 |
| 검색과 필요할 때 여는 필터 — 보고서 제안 | 기존 태그 필터를 접는 방식만 구현 | 본문·장소 검색, 기간 필터, 통합 필터 UI는 없음 |
| 내 정보에서 개인 설정을 우선 — 보고서 제안 | 사귄 날·디데이·커버리지·추천·커플 연결 해제 유지 | 프로필은 기존 커플 제품 구조 그대로 |
| 일반 화면의 색 사용 절제 | 전역 색 토큰·지도·추천 영역 변경 없음 | 새로운 팔레트를 도입한 작업은 아님. 노선도 기능색 유지와 추천 영역 정리는 구분해야 함 |
| 개인 소유권과 선택한 기록만 공유 | DB·RPC·사진 접근 정책이 기존 커플 기준 | 화면 간소화만으로 개인 프라이버시·선택 공유를 제공하지 않음 |
| 관리자 계정과 접속 시 대시보드 | 관리자 역할·계정·라우트 미구현 | 추가 요청은 미완료. 계정 이메일과 범위 확인 필요 |

근거: `src/App.tsx`의 `RequireCouple` 및 기본 `/lines` 이동, `src/auth/guards.tsx`, `src/components/AppShell.tsx`의 메뉴·대기 배너, `src/screens/auth/SignUpScreen.tsx:79`, `src/screens/profile/ProfileScreen.tsx`, 기존 Supabase 마이그레이션.

## 5. 차이가 남은 이유와 평가

**정책 확인으로 보류한 항목:** 기존 공동 기록의 개인 소유권 이전·복제 여부와 공유 권한은 데이터 및 접근 범위를 바꾸므로 임의로 확정하지 않았다. 이 결정과 연결되는 개인 데이터 구조·가입 흐름·공유는 보류했다.

**아직 구현하지 않은 UI 항목:** 카드의 장소 제목, 메뉴·홈·프로필 재구성, 검색, 지도 컨트롤 정리는 미적용이다. 이 전체를 데이터 이전 정책 때문이라고 설명하는 것은 부정확하다. 일부는 화면 설계 확정 또는 별도 구현 작업이 남은 것이다.

**기존 기능 보호를 위해 남긴 항목:** 역별 탐색 링크와 기존 공동 목록의 작성자 표시는 유지했다. 그러나 최종 개인 UI에서도 그대로 유지해야 한다는 결정은 아니다. 특히 테두리를 없앤 역명 링크의 발견성은 실제 사용 확인이 필요하다.

현재 결과는 심플함 요구에 일부 부합하지만, 제품 구조와 화면 위계를 포함한 전체 목표를 충족하지 않는다. 숨긴 정보를 찾기 어려워지지 않았는지, 정사각형 크롭이 장소 사진의 중요한 부분을 가리지 않는지도 확인해야 한다.

## 6. 사용자가 직접 확인할 순서

1. 가입 화면: 기존 문구가 남아 있고 이번 시각 변경이 없음을 확인한다.
2. 기존 연결 계정 로그인 → 타임라인: 역명 링크, 사진 비율, 이모지·태그 없는 카드, 작성자 표시를 확인한다.
3. ‘태그로 찾기’를 열고 선택·해제한다. 사용 가능한 태그가 없으면 필터 영역이 표시되지 않는다.
4. 역 상세 기록 목록: 공용 카드 변경이 동일하게 적용되는지 확인한다.
5. 기록 작성: 사진·일기가 먼저 나오고 선택 항목은 접혀 있는지 확인한다.
6. 감정·날씨·태그 선택 → 접기 → 다시 열기: 값 유지와 저장 결과를 확인한다.
7. 노선도·프로필: 초대 대기·사귄 날 등 기존 공동 사용 구조가 남아 있음을 확인한다.

새 계정은 기존 연결 온보딩을 거쳐야 하므로, 지금 상태를 개인 사용의 최종 흐름으로 평가하면 안 된다.

## 7. 후속 진행 제안

| 순서 | 작업 | 진행 전 필요한 결정 |
|---|---|---|
| 1 | 개인 원본·기존 공동 기록·공유 권한의 데이터 계약 확정 | 공동 기록 유지/복제/이전, 읽기 전용/기여자 권한 |
| 2 | 계약에 맞는 DB·RPC·Storage·캐시 변경과 권한 테스트 | 1번 확정 |
| 3 | 연결 없는 개인 가입·기록 시작, 개인 문구와 선택 공유 동선 | 개인 진입 흐름 확정 |
| 4 | 카드 제목·홈·메뉴·내 정보 재구성 | 기록 홈 여부와 구체 화면안 검토 |
| 5 | 검색·필터·지도 정보 노출 정리 | 1차 검색 범위와 필터 항목 |
| 별도 | 관리자 계정·대시보드 | 계정 이메일, 생성 환경, 조회·관리 권한 및 지표 |

문구만 개인 서비스처럼 바꾸면서 데이터는 공동으로 노출되는 상태를 최종 결과로 제공하지 않는다. 보고서의 후속 제안은 승인·구현 완료 항목이 아니다.

## 8. 검증·커밋 상태와 검토 한계

- 이전 구현 검증: 빌드 성공, lint 기존 경고 5개, DB 테스트 178/178, 세션·외부 응답을 모킹한 브라우저 회귀 통과.
- 브라우저 회귀 범위: 선택 입력 유지·저장 요청, 사진 실패 이탈 경고, 필터 응답 역전, 모바일 가로 넘침. 전체 운영 가입·공유·권한 테스트 완료를 의미하지 않는다.
- Supabase 복구 후 인증 health/settings의 HTTP 200과 이메일 가입 활성화는 확인했다. 실제 사용자의 가입·메일 인증·기록 저장 전체 완료는 별도다.
- 코드 변경은 아직 커밋되지 않았다. 생성된 `81a8498`은 조사·보고서·구현 범위 문서 커밋이며 UI 코드 커밋이 아니다. 일부 staging과 working tree 변경이 남아 있다.
- 이번 검토는 실제 코드 차이와 보고서를 대조한 정적 검토다. 새 사용성 실험이나 전체 실화면 비교를 수행한 것으로 보고하지 않는다.
- 이번 요청에서는 이 Markdown 파일만 생성했으며 앱 코드를 추가 변경하지 않았다.
