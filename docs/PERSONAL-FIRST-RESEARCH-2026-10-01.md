## 1. 변경된 제품 방향

**동네 발자취는 내가 다녀온 곳을 사진과 짧은 메모로 쌓는 개인 기록 서비스다. 원하면 선택한 기록을 공유하거나 특정 모음을 함께 작성할 수 있다.**

개인 사용은 완성된 기본 경험이고, 공유는 추가 선택이다. 혼자 쓰는 사람이 “상대 초대 대기” 상태로 취급되어서는 안 된다. 연인뿐 아니라 친구·가족·여행 동행도 선택적으로 함께 사용할 수 있다.

이 문서는 앞선 `DEVELOPMENT-GUIDE-2026-10-01.md`의 커플 중심 제품 정의와 일부 우선순위를 대체한다. 사진 원자성·요청 경쟁·만료 URL·실 서비스 검증에 관한 기술 분석은 계속 유효하지만, 구현 계약은 개인 소유권 기준으로 다시 설계해야 한다. 기존 PRD는 과거 방향의 기록으로 유지하며 실제 구현 전 새 버전으로 정리한다.

애플리케이션 코드·SQL·기존 문서는 수정하지 않았다. 조사 결과와 수정 권고를 이 문서에 작성했다.

### 조사에서 얻은 설계 판단

좋은 참고 지점은 기능의 개수보다 **기록 시작과 공유 시작이 분리되는 구조**다. 개인 기록을 만들기 위해 공유 상대를 정할 이유가 없다. 지도는 기억을 찾아가는 수단이며 사진과 메모가 내용이다. 통계와 공유는 필요한 순간에 열면 된다.

공유도 구분해야 한다. 이미지 내보내기는 결과 전달, 읽기 공유는 열람 권한, 함께 기록하기는 쓰기 권한이다. 이 셋을 같은 “공유” 스위치 하나로 처리하면 사용자도 권한도 복잡해진다.

## 3. 권장 최종 화면과 사용 흐름

### 3.1 세 개의 탭

> **2026-10-06 최신 결정:** 아래 ‘기록 홈·일반 지도 기본’은 당시 조사 제안이며 채택하지 않는다. 사용자는 노선도를 메인으로 유지하기로 했다. 실제 개발 방향은 [후속 개발 실행 계획](DEVELOPMENT-ROADMAP-2026-10-06.md)을 따른다. 개인 소유권·선택 공유 정책은 별도 결정 대상으로 남아 있다.

**기록 / 지도 / 내 정보**를 권장한다. 로그인 후 기본 화면은 기록 목록이다. 기존 노선도는 지도 화면 안의 `지도 | 노선도` 선택으로 유지한다. 마지막 선택을 기억하되 첫 사용자는 일반 지도로 시작한다.

이것은 조사 서비스의 우열을 단정한 결과가 아니라 현재 사용자의 “개인 사용·심플함”에 맞춘 설계 권고다. 노선도 차별성은 유지하되, 첫 화면에서 수백 개 빈 역을 읽어야만 기록을 시작하는 부담을 줄인다.

| 화면 | 기본으로 보이는 것 | 필요할 때 여는 것 |
|---|---|---|
| 기록 | 제목·검색·최근 기록·기록 추가 | 필터 시트, 기간 이동, 기록 모음 |
| 지도 | 내 방문 핀·검색·기록 추가 | 노선도 전환, 호선 선택, 전체 핀 보기 |
| 작성 | 장소/역·날짜·사진·짧은 메모·저장 | 더 보기 안의 감정·날씨·태그, 공유 모음 선택 |
| 상세 | 사진·장소·날짜·메모 | 더보기의 수정/삭제/이미지 저장, 모음에 추가 |
| 내 정보 | 이름·방문 장소 수·기록 수 | 공유 모음 관리, 캐시 비우기, 내보내기, 계정 설정 |

사진 카드의 기본 정보는 썸네일·장소·날짜·메모 한두 줄이면 충분하다. 개인 기록에서 작성자 이름은 숨긴다. 공동 모음에서는 작성자와 공유 상태를 보여준다. 방문 수집률·추천 역·감정·날씨·태그를 모든 카드에 동시에 노출하지 않는다.

### 3.2 첫 사용자

가입·이메일 확인 → 내 기록 화면 → “첫 발자취 남기기” → 장소와 날짜 → 선택적으로 사진·메모 → 저장.

커플 생성·사귄 날·초대 코드 입력은 이 과정에서 제거한다. 이름 입력도 가입에 이미 있다면 다시 요구하지 않는다. 아직 공유 기능을 사용하지 않았으면 초대 배너나 공유 모음 전환기는 나타나지 않는다.

### 3.3 혼자 사용하는 일상

합정 근처에서 카페를 다녀온 뒤 장소를 선택하고 사진과 짧은 메모를 저장한다. 날짜는 오늘이 기본이다. 다음에 기록 목록 검색이나 지도 핀에서 다시 찾는다. 기록을 추가하는 데 태그 분류·감정 선택·다른 사람 연결을 요구하지 않는다.

### 3.4 선택적으로 함께 사용

1. 개인 기록을 충분히 사용한 뒤, 내 정보나 모음 화면에서 “함께 기록할 모음 만들기”를 선택한다.
2. “주말 산책” 같은 모음을 만들고 사람을 초대한다. 사람 수 2명·연애 관계·한 사람 한 모음으로 묶지 않는다.
3. 기존 기록을 선택하여 모음에 추가한다. 개인 기록 전체가 자동 공유되지 않는다.
4. 모음 안에서 새 기록을 작성하면 그 모음에 추가된다는 표시를 보여준다. 개인 화면에서 작성하면 기본은 나만 보기다.
5. 공유를 중단해도 개인 원본은 남는다. 상대의 기록 소유권까지 내게 이전되지는 않는다.

홈의 “내 기록”과 “공유받은 모음”을 섞지 않는 편을 권장한다. 내 기록은 내가 소유한 원본을 뜻하고, 모음에는 다른 사람의 기록도 표시된다. 지도·통계·검색은 선택한 범위를 따른다.

## 4. 현재 프로젝트에서 수정해야 할 점

### 4.1 진입과 세션 — 최우선

**근거:** `src/App.tsx`의 주요 화면은 `RequireCouple` 아래에 있다. `guards.tsx`는 커플이 없으면 온보딩으로 보낸다. `SessionProvider.tsx`는 커플 조회가 끝나기 전 로그인 상태를 대기시킨다.

**수정:** 주요 화면의 진입 조건은 로그인으로 바꾼다. 개인 프로필과 선택적 공유 모음 조회를 분리한다. 공유 모음 조회가 실패해도 개인 기록 화면은 사용할 수 있어야 한다. 새 온보딩은 있더라도 건너뛸 수 있는 첫 기록 안내만 제공한다.

**완료 기준:** 멤버십이 0개인 신규 사용자도 작성·조회·사진 업로드를 할 수 있다. 공유 기능 장애가 개인 홈을 막지 않는다.

### 4.2 개인 소유권과 선택 공유 — 문구보다 먼저 변경

**근거:** `records.couple_id`는 NOT NULL이다. 사진·태그도 couple_id를 보유하고 `current_couple_id()` 기반 RLS를 사용한다. 작성자 `author_id`는 현재 공동 기록의 최초 작성자 정보이며 개인 소유권 계약이 아니다.

**권장 모델:** 개인 기록 원본 + 선택적 공유 모음 참조.

| 데이터 | 역할 |
|---|---|
| `records.owner_id` | 개인 원본 소유자. 작성자/수정자와 의미를 분리 |
| `collections(id, owner_id, title)` | 필요한 순간 만드는 공유 가능한 기록 모음 |
| `collection_members(collection_id, user_id, role)` | viewer/contributor 권한. 소유자는 collections에서 판정 |
| `collection_records(collection_id, record_id, added_by)` | 선택된 원본을 모음에 연결. 같은 원본 중복 삽입 방지 |
| `collection_invites` | 특정 모음에 대한 초대. 역할·만료·취소·사용 상태 관리 |

일반 개인 기록에는 모음이 필요 없다. 모든 사용자에게 가상의 “1인 커플”이나 공유 공간을 자동 생성해 기존 구조를 숨기는 방식은 권장하지 않는다. 개인 원본을 공유 모음으로 옮기지 않고 연결하면 공유 해제 후에도 개인 기록이 유지된다.

모음에 연결된 기록은 수정 결과도 반영되는 살아 있는 공유다. 복사본 공유가 아니다. UI에서 이를 설명하고 소유자가 자신의 기록을 어느 모음에서 공유하는지 확인할 수 있게 한다. 일부 내용만 공유하고 싶으면 별도 복제/스냅샷 기능이 필요하므로 1차 범위에서 제외한다.

**권한 기본값:** 소유자만 원본 수정·삭제·사진 변경. viewer는 보기만, contributor는 자기 기록을 모음에 추가하고 자기 원본만 수정한다. 모음 소유자는 다른 사람의 기록을 모음에서 제외할 수 있지만 원본을 삭제하지 못한다. 개인 기록을 다른 모음에 공유하는 것은 원본 소유자의 명시적 선택으로 제한한다. 초기부터 “모든 참가자가 모든 원본 편집” 권한은 도입하지 않는다.

**완료 기준:** 개인 기록은 모음 참가자에게도 기본적으로 보이지 않는다. 연결된 기록·사진·태그만 해당 모음에서 보인다. 모음 제거·탈퇴가 원본을 삭제하지 않는다. 이름·프로필 조회도 공유 관계만으로 필요한 정보에 한정한다.

### 4.3 RPC·RLS·Storage·집계를 함께 전환

**근거:** `upsert_record`, 사진 경로, 기록/태그/사진 정책과 방문/태그 집계가 모두 커플 경계에 연결되어 있다. 화면에서 가드만 제거하면 저장은 실패한다.

**수정 대상:** `couple-rpc.ts`, `record-rpc.ts`, `database.types.ts`, `photo-storage.ts`, 관련 SQL, `record-card-query.ts`, 노선도 방문 로더, 프로필 통계.

기록 저장 RPC는 `auth.uid()`를 소유자로 설정하고 모음 추가 요청은 별도 인가를 확인한다. 사진 경로는 신규 기록에 `{owner_id}/{record_id}/{photo_id}`를 권장한다. 업로드/수정/삭제는 원본 소유자만 허용하고 조회는 개인 소유권 또는 해당 원본에 대한 유효한 모음 열람권으로 판단한다. 공유 사진 읽기를 경로 첫 세그먼트 = 현재 사용자 검사만으로 구현하면 공유자가 사진을 볼 수 없다.

공유 조회는 사진/태그/집계까지 동일한 접근 범위를 적용한다. 사용자에게 읽기 권한이 있는 전체 데이터를 한 번에 가져와 프론트에서 걸러내는 방식을 피한다. 내 기록 집계와 모음 집계를 별도로 요청하고 보안 경계는 서버에서 보장한다.

이미 발급된 서명 URL은 공유 해제 순간에 즉시 무효화된다고 가정하지 않는다. 만료 기간·재검증·로컬 캐시 제거의 보장 범위를 정한다. 다운로드한 이미지의 회수까지 약속하지 않는다.

### 4.4 캐시 — 사용자와 조회 범위로 분리

**근거:** `screen-cache.ts`는 하나의 coupleId로 캐시를 구분한다. 개인과 여러 공유 모음이 공존하면 한 커플이라는 전제가 맞지 않는다.

**수정:** 캐시 키를 `userId + scope(personal 또는 collectionId) + filter`로 변경한다. URL과 React state의 조회 범위도 맞춘다. 공유 권한 변경·탈퇴 시 해당 범위 캐시를 비우고 읽기를 차단한다. 요청 세대 검사로 늦은 응답이 다른 사용자나 모음에 들어가지 않게 한다.

**완료 기준:** 모음 A에서 개인 화면/B로 전환해도 목록·지도 핀·통계가 섞이지 않는다. 로그아웃 시 개인/공유 캐시를 모두 정리한다.

### 4.5 장소 기록의 단위 — 단계적으로 확장

**근거:** 현재 필수 위치는 `station_id`다. 지도 핀은 실제 방문한 가게가 아니라 역 좌표다. “다녀온 곳 기록”으로 소개하면서 정확한 장소 핀처럼 보여주면 기대와 맞지 않는다.

**1차 권장:** 역을 지역 묶음으로 유지하고 선택적 `place_name`을 추가한다. “합정역 · ○○카페”로 표시한다. 장소명을 입력하지 않아도 역 기록으로 저장 가능하다. 핀은 역 기준임을 설명한다.

**2차 선택:** 장소 ID·좌표·주소와 수동 입력을 지원한다. `station_id`를 선택값으로 바꾸고 방문 위치 계약을 재정의한다. 단순 텍스트 장소와 정확한 좌표 장소를 구별한다. API 검색·좌표의 이용 조건은 해당 단계에서 공식 문서로 확인한다.

장소 데이터가 없는 기존 기록을 역 좌표의 특정 가게 방문으로 자동 변환하지 않는다. 전국 검색·자동 GPS 추적을 개인 전환의 필수 범위에 넣지 않는다.

### 4.7 심플하고 깔끔한 디자인 원칙

- 기본 화면의 주요 행동은 “기록 추가” 하나로 둔다. 보조 동작은 헤더/더보기에 배치한다.
- 중립 배경과 한 가지 강조색을 사용한다. 노선 색상은 노선도·호선 정보에만 사용한다.
- 개인 상태에서는 공유 배지·작성자·참가자 아바타를 숨긴다. 공유 모음에서만 분명하게 표시한다.
- 태그 칩을 헤더 전체에 늘어놓기보다 검색 옆 필터 시트로 옮긴다. 선택된 필터만 요약한다.
- 통계는 작은 요약으로 두고 수집률과 추천을 첫 화면의 중심에서 내린다.
- 공백·사진 비율·타이포·버튼 높이를 기존 `tokens.css`로 일관되게 맞춘다. 폰트를 무작정 줄여 밀도를 낮추려 하지 않는다.
- 확장 필드를 접어도 기존 감정/날씨가 있는 기록을 몰래 지우지 않는다. 수정 시 값은 유지하고 필요하면 펼쳐 보여준다.

정적 코드와 공식 자료를 기반으로 한 방향이다. 실제 화면의 최종 간격·대비·사진 크기는 모바일 프로토타입에서 검증한다.

## 5. 공유 기능의 단계

| 단계 | 제공 범위 | 이유 |
|---|---|---|
| 개인 MVP | 내 기록·지도·사진·검색, 기존 PNG 저장 | 혼자 사용하는 핵심을 먼저 완성 |
| 선택 공유 | 로그인한 특정 사람에게 모음 열람 초대 | 개인 원본과 공유 권한을 분명하게 구분 |
| 함께 기록 | 모음 참가자가 자신의 기록을 추가 | 공동 사용 지원, 원본 소유권 유지 |

공유 모음은 웹에서도 간단히 볼 수 있게 하되 첫 버전은 로그인 기반을 권장한다. 비로그인 링크는 클라이언트에 service role을 두거나 기존 anon 테이블 조회를 열어서 구현하지 않는다. 별도 제한된 조회 경로와 토큰 검증이 필요하다.

## 6. 기존 데이터 이전 계획

기존 공동 데이터에 `owner_id = author_id`를 일괄 적용하는 것은 승인된 소유권 정책이 아니다. 상대가 수정하거나 사진을 추가한 공동 기록을 최초 작성자 한 명의 개인 기록으로 조용히 귀속시키지 않는다.

1. 기록·사진·태그·모든 FK·Storage 경로와 현재 권한을 조사하고 백업한다. 운영 데이터 존재 여부는 이번 조사에서 확인하지 않았다.
2. 신규 개인 모델과 기존 커플 모델을 일정 기간 병행 가능한 새 마이그레이션으로 추가한다.
3. 새 가입자는 개인 흐름으로 진입시킨다. 기존 사용자는 기존 공유 기록을 열람할 수 있게 보존한다.
4. 기존 커플 공간은 참여자 권한이 유지되는 레거시 공유 모음으로 대응한다. 기존 기록은 이전 정책이 결정될 때까지 별도 레거시 소유 모델로 보존한다.
5. 개인 복사본 제공, 명시적 소유자 합의, 공동 기록 전용 모음 유지 중 실제 데이터와 사용자 기대에 맞는 정책을 결정한다. 복사 시 저장 용량·중복 기록·사진 복제/참조 정리를 따로 설계한다.
6. 개인·공유 정책과 Storage 조회를 검증한 뒤 구 가드/RPC/커플 전용 화면을 순차적으로 제거한다.

가장 단순한 개발을 위해 데이터가 없다고 가정하거나, UI 교체와 동시에 구 테이블을 삭제하지 않는다. 이전 기간의 해제/탈퇴도 레거시 기록 보존 정책과 함께 정의한다. 파괴적 이전은 실제 구현 단계에서 구체적인 대상과 결과를 검토해야 한다.

## 8. 검증 기준

- 멤버십이 없는 계정이 가입 직후 기록·사진을 저장하고 목록·지도를 볼 수 있다.
- 사용자의 개인 기록은 공유 모음 참가자에게도 자동으로 노출되지 않는다.
- 두 기록 중 한 건만 공유하면 사진·태그·검색·방문 통계에서도 한 건 범위만 노출된다.
- 열람자는 수정하지 못하고, 기여자는 다른 사람의 원본을 변경/삭제하지 못한다.
- 모음 탈퇴/삭제 후 개인 원본은 남는다. 공유 링크/서명 URL/다운로드의 철회 범위를 안내와 맞춘다.
- 동일 원본을 여러 모음에 연결해도 개인 통계가 중복 집계되지 않는다.
- 권한 철회 후 캐시·늦은 요청·다른 탭이 이전 공유 내용을 계속 제공하지 않는지 확인한다. 오프라인/기존 다운로드까지 즉시 회수한다고 주장하지 않는다.
- 사진 실패·기록 부분 성공·재시도·새로고침에서 사용자 입력과 완료 상태가 정확하다.
- 기존 공동 데이터는 이전 전후 사용자별 조회 결과와 Storage 객체 수를 대조한다.
- 모바일에서 기본 작성 화면의 주요 필드·저장 버튼을 쉽게 찾고, 숨긴 선택 항목도 키보드로 접근한다.

이번 작업은 자료 조사와 정적 분석이며 새 코드에 대한 테스트 실행은 없다. 앞선 가이드의 DB 178/178 통과는 기존 커플 모델의 결과이므로 개인 모델 검증으로 재사용하지 않는다.

## 9. 1차 변경 범위 권고

우선 **커플 연결 없이 사용 / 개인 소유권 / 최근 기록 홈 / 단순한 작성 / 선택 모음 공유**에 집중한다. 장소는 역 기반을 유지하면서 이름 메모만 확장한다. 노선도는 탐색 모드로 남기고 감정·날씨·태그·통계·추천의 기본 노출을 줄인다.

결과적으로 사용자는 서비스를 “누군가와 연결해야 열리는 공간”이 아니라 “내가 쌓아두고 필요한 때 함께 보는 장소 기록장”으로 이해해야 한다.
