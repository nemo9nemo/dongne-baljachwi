# 기기 저장·코드 공유·개인 맵 전환 구현

2026-10-20. 기본 앱을 로그인 없는 기기 저장 모드로 전환했다. 기존 Supabase 앱은 별도 빌드 모드로 보존했고 원격 데이터·계정을 삭제하거나 변경하지 않았다.

## 구현한 동작

| 영역 | 현재 구현 |
|---|---|
| 실제 앱 | `/`에서 새 개인 맵으로 시작. 샘플 기록을 자동 생성하지 않는다. `/design/mockup.html`은 기존 디자인 목업으로 별도 유지 |
| 저장 | 브라우저는 IndexedDB, 네이티브는 SQLite 메타데이터와 앱 전용 사진 파일. 사진 준비 실패·저장 실패 시 기존 기록 보존 |
| 기록 | 역·날짜·장소명·글·태그·감정·날씨·최대 10장 사진 작성/수정/삭제. 수정 revision 검사와 다른 탭 변경 알림. 날짜·메모·파일 크기 검증 |
| 보기 | 실제 646역 노선도, 방문 집계, 역 검색·노선 필터, 역별 기록, 타임라인 검색·정확 태그·기간 필터, 50개 단위 표시, 사진 보기 |
| 사진 | JPG/PNG/WebP 원본 10MB 이하. 2048px JPEG 재인코딩과 EXIF 제거. 기기에서 320px 목록 썸네일 생성. HEIC는 기존과 같이 명시적 거부 |
| 맵 | 개인 맵 생성·선택·이름 변경·삭제. 기존 맵을 덮어쓰지 않고 독립 보관 |
| 공유 | 1:1 읽기 전용. 10분 유효 코드 → 양쪽 확인 문자 → 원본 기기 승인 → WebRTC로 해당 맵의 기록·사진 전송 |
| 동기화 | 두 앱이 연결돼 있을 때 원본 변경을 가져옴. 사진 해시 검증과 필요한 파일만 전송. 완전히 받은 스냅샷만 확정하고 오래된 응답/해제된 연결 응답 차단 |
| 연결 해제 | 각 기기에 완전히 받은 기록·사진을 유지한 채 독립 개인 맵으로 전환. 이후 수정·삭제는 이전 상대에게 반영하지 않음. 원래 작성자·출처 보존 |
| 오프라인 해제 | 로컬에서 즉시 개인 맵 전환. 연결 서버에 해제 요청을 재시도하고 상대가 다시 조회할 때 개인 맵 전환. 양쪽이 동시에 완료됐다고 표시하지 않음 |
| 백업 | AES-256-GCM + PBKDF2-SHA256 암호화 파일. 사진 해시·스키마·파일 크기를 검증해 새 개인 맵으로 복원. 기존 맵을 덮어쓰지 않으며 연결 토큰은 백업에서 제외 |
| 백업 범위 | 전체/현재 맵 및 기간 선택. 파일 한 개당 사진 256MB 제한. 암호 분실 복구는 제공하지 않음. 표시 시각은 백업 파일 생성 시각이며 외부 보관 완료를 보장하지 않음 |
| Android | Capacitor 8 프로젝트, SQLite·Filesystem·Share 플러그인 연결. 웹 자산을 패키지에 포함하고 네이티브 백업은 공유 시트로 내보냄 |

## 연결 서버의 역할

`scripts/sharing/broker.mjs`는 코드·승인·연결 상태와 SDP를 중계한다. 기록·사진 업로드 API는 없다. 연결 토큰·코드는 해시로 보관하고 SDP는 메모리에만 둔다. 기본 파일은 무시되는 `tmp/share-connections.json`이다. 연결 승인 정보는 재시작 후 복원한다. 승인된 연결은 명시적 해제까지 유지하며, 닫힌 연결 메타데이터는 오프라인 상대의 확인을 위해 30일 보관한다.

다른 연결의 토큰 사용·허용되지 않은 Origin·잘못된 신호를 거부한다. 생성/참여/신호/조회 요청의 속도와 본문 크기를 제한한다. 직접 연결이 어려운 네트워크에는 선택적으로 coturn REST 방식의 1시간 TURN 자격 증명을 발급할 수 있다. TURN 영구 비밀은 클라이언트 번들에 넣지 않는다. 실제 TURN 배포와 다른 통신망 간 연결은 아직 확인하지 않았다.

## 확인한 검증

- 실제 앱 브라우저 통합 12개 통과: 로그인 없는 시작과 Supabase 요청 없음, 사진 저장·재시작, 암호화 백업·다른 브라우저 복원, 잘못된 암호에서 기존 데이터 보존, 실제 두 브라우저 WebRTC 사진 전송, 원본 변경 동기화, 해제 후 양쪽 독립 수정, 모바일 넘침/런타임 오류, 다른 탭 revision 충돌, 큰 맵과 비공개 맵 격리·재연결, 사진 전송 중단과 재시도, 오프라인 해제 재전달.
- 연결 서버 검사 8개 통과: 코드/승인 전 접근·기기 역할·다른 연결 토큰·신호 범위·해제·Origin·TURN 자격 증명·재시작/만료. 마지막 타입/보존 정책 정리 이후에도 재검증했다.
- 기존 서버 앱 브라우저 회귀 23개 통과. 노선도 정합성/재생성 검사와 회귀 8개 통과.
- 기존 DB 계약 276/276 통과(현재 스키마 203, 전환 전 이력 73). 운영 서버에 적용한 검증은 아니다.
- 타입·프로덕션 빌드 및 `cap sync android` 통과. SQLite·Filesystem·Share 3개 플러그인 연결 성공. lint 오류 0, 기존 버튼 Fast Refresh 경고 1개.
- 추가한 CLI의 개발 도구 취약점을 피하도록 8.4.3에 고정했다. 기존 Tailwind 3 도구 체인의 7개 감사 항목은 남아 있으며 강제 메이저 전환은 하지 않았다.
- Android SDK·JDK가 현재 환경에서 확인되지 않았다. APK/AAB 빌드·설치·실제 두 휴대폰 검증은 수행하지 않았다. 브라우저 통합 결과를 실기기 검증으로 간주하지 않는다.

## 실행과 빌드

```sh
npm ci
npm run dev
```

기본 실제 앱은 `http://localhost:5173/`. 개발 Vite에 연결 서버가 함께 붙어 별도 Supabase 설정 없이 코드 연결을 확인할 수 있다. 서로 다른 브라우저 프로필/시크릿 창은 서로 다른 기기 저장소로 동작한다. 두 탭은 같은 기기로 취급한다.

```sh
npm run test:local
npm run test:sharing
npm run android:sync
```

Windows에서 브라우저 검증은 기본 Edge, CI에서는 `TEST_BROWSER_CHANNEL=chromium`을 사용한다. 검증 스크립트는 임시 서버를 띄우고 종료 시 중지한다.

Android SDK·JDK·Android Studio 준비 후 `npm run android:sync`, `npm run android:open`으로 빌드/설치를 이어간다. 현재 앱 식별자는 `com.nemo9.dongnebaljachwi`이며 첫 스토어 등록 전에 확정해야 한다. 앱 전용 DB/사진과 연결 토큰의 불완전한 OS 백업 복원을 막고 앱의 명시적 전체 백업을 사용하도록 Android 백업 규칙을 설정했다.

## 배포 설정

- 웹 정적 파일: 기존 `npm run build`의 `dist`를 호스팅한다.
- 연결 서버: `npm run share:server`. 기본 `127.0.0.1:8787`; HTTPS 역방향 프록시 뒤에서 운영한다. 영구 상태 파일은 웹 루트 밖의 쓰기 가능한 경로로 지정한다. 현 구현은 단일 프로세스용이며 여러 서버가 같은 상태 파일을 동시에 쓰도록 운영하지 않는다.
- `VITE_SHARE_SERVER`: 웹/Android 앱에서 접근 가능한 HTTPS 연결 서버 origin. 비워두면 현재 origin을 사용하므로 정적 호스팅과 Android에서는 운영용 주소를 설정해야 한다.
- `SHARE_ALLOWED_ORIGINS`: 웹 앱 origin과 네이티브 origin `https://localhost` 등을 명시한다. iOS 프로젝트를 추가할 때는 해당 origin도 확인한다.
- `SHARE_TURN_URLS`, `SHARE_TURN_SECRET`: 필요한 경우 서버에서만 설정한다. 릴레이 트래픽은 비용과 대역폭을 점검해야 한다.
- 기존 서버 앱: `VITE_STORAGE_BACKEND=supabase`로 빌드하면 이전 라우트/인증/권한 흐름을 사용한다. Supabase 키 설정과 실제 프로젝트 연결은 별도로 필요하다.

## 남은 출시 작업

실기기에서 재시작·디스크 부족·사진 선택/공유·백업/복원·네트워크 전환을 검증하고 APK/AAB 서명 및 스토어 자료를 준비해야 한다. 공개 HTTPS 연결 서버와 필요 시 TURN을 배포하고 운영 제한을 점검해야 한다. 기존 서버 데이터가 있으면 실제 연결·내보내기·대조 후 이전해야 한다.

광고 SDK·실제 광고 단위·동의 화면·공개 개인정보/지원 페이지·app-ads.txt는 아직 추가하지 않았다. 자동 Drive/iCloud 백업, 여러 기기 동시 편집, 공동 작성도 이번 읽기 전용 공유 범위 밖이다. 기존 Supabase 모드의 고급 작성/조회 편의 일부는 새 기기 저장 UI로 추가 이전할 수 있다.
