# 동네 발자취 출시 준비 및 광고 수익화 검토

검토일: 2026-10-19. 검토 코드: `d12dc82`. 코드·설정·기존 검증 기록과 아래 공식 정책을 검토했다. 이번 검토에서 테스트를 새로 실행하거나 운영 서버·스토어·광고 계정을 변경하지 않았다.

후속 사용자 선택은 **운영비 최소화·개인 기록 우선**이다. 이 문서의 Supabase 운영 점검은 10월 19일 구현을 그대로 출시할 경우의 기준이다. 10월 20일에는 기본 앱의 기기 저장·코드 공유·개인 맵 전환을 구현했다. 최신 상태는 [구현 결과](IMPLEMENTATION-2026-10-20.md), 판단 근거는 [기기 저장·개인 백업 검토](LOCAL-FIRST-STORAGE-REVIEW-2026-10-19.md)를 따른다.

## 판단

핵심 기록 기능은 구현됐지만 **현재 상태를 공개 출시 가능으로 판단하기는 어렵다.** 먼저 실제 운영 서버, 계정 삭제·개인정보 안내, 사진 백업·비용 통제, 실제 모바일 검증을 마쳐야 한다. 스토어 출시는 별도 앱 패키징도 필요하다.

수익화의 제안 방향은 **웹에서 사용성 확인 → Android 비공개 테스트 → Android 공개 출시와 AdMob 광고 검증 → iOS 확대 검토**다. Android 우선은 현재 웹 코드와 Windows 개발 환경을 고려한 제안이며 확정된 플랫폼 결정은 아니다. 광고 노출을 늘리기 위해 기록 흐름을 늘이거나 핵심 기능을 광고 시청에 묶지 않는다.

Apple도 앱 내 계정 삭제를 요구한다. **D21의 탈퇴 부분은 후속 편의 기능에서 스토어 출시 필수 작업으로 우선순위를 올려야 한다.** [Google Play 계정 삭제](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en), [Apple 5.1.1(v)](https://developer.apple.com/app-store/review/guidelines/#data-collection-and-storage).

Supabase DB 백업에는 Storage 파일 자체가 포함되지 않는다. 사진 보관 앱에서는 DB 백업 설정만으로 복구 준비가 완료되지 않는다. [Supabase 백업 범위](https://supabase.com/docs/guides/platform/backups).

현재 목록 썸네일은 `src/lib/photo-storage.ts`에서 `createSignedUrl(..., { transform: ... })`를 사용하고, 재시도도 같은 변환 경로다. Supabase의 현재 요금 안내상 이미지 변환은 Free에서 제공되지 않는다. **운영 프로젝트가 Free라면 썸네일이 정상 동작한다고 가정하면 안 된다.** 프로젝트 요금제는 아직 확인하지 못했으며, 지원 요금제 사용과 사전 생성 썸네일의 비용을 비교해야 한다. [Supabase 요금 항목별 지원](https://supabase.com/docs/guides/platform/billing-on-supabase), [변환 사용량과 대안](https://supabase.com/docs/guides/platform/manage-your-usage/storage-image-transformations).

이메일 인증이 가입을 막는 관문이므로 실제 도메인의 SMTP·발송 제한·확인 링크도 점검해야 한다. 현재 호스팅 설정은 미확인이다. Supabase는 운영 시 자체 SMTP와 인증 요청 남용 방지 점검을 안내한다. [Supabase 운영 체크리스트](https://supabase.com/docs/guides/deployment/going-into-prod).

## 광고 배치 제안

출시 초기에는 광고 네트워크 하나, 광고 위치 하나로 시작한다. **타임라인에 충분한 기록이 있을 때 목록 중간의 독립 영역에 인라인 배너 한 개**를 제안한다. 예를 들어 기록 6개 이후를 초기 실험값으로 삼을 수 있으나 정책상 정해진 개수가 아니며 사용성 결과에 따라 조정한다. 추후 수익/유지율이 확인되면 명확한 광고 표시를 갖춘 네이티브 광고 카드를 검토한다.

| 화면 | 초기 배치 | 이유 |
|---|---|---|
| 노선도/지도 | 광고 없음 | 확대·이동·역 선택이 이어지는 주 조작 화면 |
| 타임라인 | 독립 인라인 영역 한 곳 | 돌아보는 흐름에서 시험. 검색 입력·필터·기록 카드·하단 탭과 충분히 분리 |
| 기록 작성/수정·저장 결과 | 광고 없음 | 작성 중 이탈과 저장 성공 혼동 방지 |
| 기록 상세·사진 전체 보기 | 광고 없음 | 개인 기록과 사진 감상에 집중 |
| 로그인·권한·오류·빈 상태·탈퇴 | 광고 없음 | 아직 콘텐츠가 없거나 필수 작업을 처리하는 상태 |

광고가 기록 카드처럼 보이도록 복제하지 않고 광고 영역임을 명확히 표시한다. 지도 위 오버레이나 하단 탭 바로 위 고정 배너를 기본 배치로 삼지 않는다. Google은 조작 요소 근처 배너를 권장하지 않고 콘텐츠를 덮는 배너를 금지한다. [배너 배치 지침](https://support.google.com/admob/answer/6275345?hl=en).

초기 전면·앱 시작 광고는 도입하지 않는 안을 권한다. 특히 기록 입력 중 갑자기 뜨는 전면 광고는 사용 흐름과 정책 모두에 문제가 된다. 보상형 광고는 나중에 꾸미기 같은 명확한 선택 보상이 생겼을 때 검토하고 저장·복구·탈퇴 같은 필수 동작에는 연결하지 않는다. [전면 광고 지침](https://support.google.com/admob/answer/6201362?hl=en).

### 광고 도입 순서와 개인정보

1. AdMob 계정·지급 정보·앱 ID·광고 단위 준비. Android/iOS의 실제 채택 SDK 버전과 브리지의 지원 상태를 확인한다.
2. **테스트 광고만으로** 배치·복귀·광고 없음/네트워크 실패·키보드·회전·접근성을 검증한다. 실제 광고를 개발 중 클릭하지 않는다. [Google 테스트 안내](https://support.google.com/admob/answer/3342099?hl=en).
3. 앱 데이터와 광고 SDK 데이터를 구분해 목록화한다. 이메일·사진·일기·장소/역 기록은 광고 타기팅용 매개변수나 광고 분석 로그로 전달하지 않는 설계를 채택한다.
4. 개인정보 방침과 스토어 신고에 SDK의 실제 데이터 처리를 반영한다. 광고 ID를 쓰지 않아도 IP·진단 등 다른 처리가 남을 수 있다. 채택 SDK/버전의 공식 공개 내용을 확인한다. [Google SDK 데이터 공개 안내](https://developers.google.com/admob/android/privacy/play-data-disclosure), [Apple App Privacy](https://developer.apple.com/app-store/app-privacy-details/).
5. 필요한 지역의 동의 상태를 SDK 초기화/요청 전에 처리하고 설정에서 선택을 변경할 수 있게 한다. EEA·영국·스위스에는 Google 인증 CMP 요건을 확인하며 UMP를 우선 검토한다. 비맞춤 광고만 선택했다고 모든 동의 검토가 끝나는 것은 아니다. iOS ATT는 다른 회사 앱/웹에 걸친 추적을 하는 경우 검토한다. [Google CMP 요건](https://support.google.com/admob/answer/13554116?hl=en), [UMP 흐름](https://developers.google.com/admob/android/privacy), [Apple 5.1.2](https://developer.apple.com/app-store/review/guidelines/#data-use-and-sharing).
6. 개발자 도메인 루트의 `/app-ads.txt`를 실제 발급 정보로 제공하고 스토어의 개발자 웹사이트와 연결한다. SPA HTML로 응답하지 않는지도 확인한다. 신규 앱은 해당 소유 검증과 준비 상태 심사를 완료해야 광고를 정상적으로 충분히 송출할 수 있다. [AdMob 소유 검증](https://support.google.com/admob/answer/14538460?hl=en), [app-ads.txt 설정](https://support.google.com/admob/answer/9363762?hl=en).
7. 원격으로 광고를 끌 수 있는 운영 수단을 두고, 광고 준비/승인 대기나 로딩 실패가 기록 앱 사용을 차단하지 않게 한다.

## 수익을 판단할 숫자

이 앱은 개인 추억을 기록하는 용도여서 매일 여러 번 여는 사용 습관을 아직 확인하지 못했다. 설치 수보다 **재방문하는 사용자 수와 실제로 보게 되는 광고 수**를 먼저 확인해야 한다.

`월 광고 매출 ≈ DAU × 사용자당 하루 광고 요청 기회 × 30 × 실제 노출 전환율 × eCPM ÷ 1,000`

eCPM은 실제 광고 1,000회 노출당 매출이다. 아래는 **시장 단가 예측이 아닌 계산 예시**이며 광고 기회가 수익으로 이어지는 비율을 80%로 가정했다. 이는 SDK의 매칭률 지표 하나와 같은 뜻이 아니다.

| 일일 활성 사용자(DAU) | 1인당 하루 광고 기회 | 실제 월 노출 가정 | eCPM 1,000원 가정 | eCPM 3,000원 가정 |
|---:|---:|---:|---:|---:|
| 100 | 3 | 7,200 | 7,200원 | 21,600원 |
| 1,000 | 3 | 72,000 | 72,000원 | 216,000원 |
| 10,000 | 3 | 720,000 | 720,000원 | 2,160,000원 |

이는 비용·세금 등을 차감하기 전 예시다. 제안한 한 곳의 광고만으로 하루 3회 기회를 얻는다는 보장도 없다. 같은 DAU에서도 타임라인을 거의 열지 않으면 결과는 더 작아진다. 실제 수익은 국가·광고 형식·계절·수요·동의·무효 트래픽 조정에 따라 달라진다.

사진 압축·썸네일은 이미 구현돼 있지만 저장량은 누적되고 재열람에는 다운로드 비용이 생긴다. **월 광고 매출 − 서버/DB·사진 저장·전송·메일·모니터링 등 운영비**를 함께 계산한다. 유료 사용자 유입은 실제 유지율과 사용자당 광고 수익을 확인한 뒤 판단한다.

최초 베타에서 볼 지표는 가입→첫 기록 저장 전환, 7일/28일 재방문 및 주간 기록 횟수, 저장/사진 업로드 성공률, 사용자당 저장량·월 전송량이다. 광고 도입 뒤에는 노출 사용자 비율·실제 노출 수·eCPM·활성 사용자당 매출과 광고 도입 전후의 재방문 변화를 함께 본다.

1. **운영 연결과 데이터 보호:** 유효한 Supabase 확인, 테스트 환경 적용, 실제 권한·사진·복구 검증, 이메일 발송·사용량 확인.
2. **출시 필수 기능:** 탈퇴의 개인/공동 데이터 정책과 서버 처리, 공개 개인정보·지원·삭제 요청 페이지, 스토어 데이터 신고 초안.
3. **Android 베타 준비:** 패키징 기술 검증, 인증 딥링크·기기 사진 선택·뒤로 가기·안전 영역·실기기 QA. 해당 시 비공개 테스트 요건 충족.
4. **광고 검증:** 타임라인 한 곳의 테스트 광고, 동의/신고·app-ads.txt·광고 비활성화 수단, 광고 실패 시 정상 사용 확인.
