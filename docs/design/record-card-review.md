# 기록 카드 이미지 저장 — 디자인 검토 + 조판 스펙

> 대상: `docs/specs/10-record-card-image.md` 구현분
> · 렌더: `src/screens/records/record-image-render.ts`
> · 시트: `src/screens/records/RecordImageDialog.tsx` + `record-image.module.css`
>
> 이 문서는 두 가지를 겸한다.
> ① **검토 노트** — 페르소나(PRD §2) 관점에서 무엇이 되고 무엇이 아쉬운지.
> ② **조판 스펙** — 디자이너가 TS를 직접 못 고치므로, 개발자가 그대로 옮길 수 있는 정확한 값 표.
>
> 시트 CSS(`record-image.module.css`)는 **이 문서 작성과 함께 이미 수정했다**(§5).
> 카드 조판(§3·§4)은 TS 상수라 **개발자 이관 대상**이다.
>
> 재검토하지 않은 확정 사항(2026-08-20 사용자 결정): 워터마크 문구 "동네 발자취" 고정 /
> 카드 색은 생성 시점 앱 테마를 따름(다크=검정+흰 테두리, 라이트=흰+검정 테두리) /
> 감정·날씨는 이모지 없이 텍스트 라벨만. 아래 제안은 전부 **이 세 전제 안에서** 찾은 최선이다.

## 1. 한 줄 판단

**"기능은 다 됐다. 그런데 지금 이 PNG는 카톡방에 올리고 싶어지는 물건은 아니다."**

기능 요구사항(F-01~F-16)은 충실히 구현돼 있다. 문제는 전부 조판 층위에 있고, 원인은 하나로
모인다 — **카드가 "정보를 빠짐없이 담은 요약본"으로 조판돼 있지 "보여주고 싶은 한 장"으로
조판돼 있지 않다.** 공유 대체재(PRD §3)라는 이 기능의 목적에서는 그 차이가 전부다.

| 판정 | 항목 |
|---|---|
| 결함(반드시 수정) | 다크 모드 "+N" 배지가 안 보인다 · 감정/날씨·태그 칩이 두 테마 모두에서 사실상 안 보인다 · 미리보기 매트가 결과와 다르게 보인다(둥근 모서리·이중 테두리) · 가로 모드에서 미리보기 비율이 찌그러진다 |
| 개선(강력 권장) | 사진 블록 고정 560 → 적응형 · 타이포 4단계로 정리 · 워터마크를 앱 워드마크 규격으로 · 사진 크롭 앵커 |
| 유지(잘 돼 있다) | 4:5 2160×2700 · 사진 1/2/3/4 슬롯 규칙 · "+N" 정책 · 일기 어절 줄바꿈·말줄임 · 시트의 접근성 골격 |

## 2. 페르소나 관점 검토

> **지하철로 데이트하는 20~30대 커플.** 주말에 지하철로 이동하며 데이트하고, 흩어진 장소·사진을
> 한눈에 보고 싶어 하며, 100일·1주년에 그동안의 데이트를 돌아보는 걸 좋아한다. (PRD §2)

장면을 구체적으로 놓고 봤다. **금요일 밤, 성수에서 데이트를 마치고 집에 온 20대 여성이 기록을
쓰고 "이미지로 저장"을 눌러 그 PNG를 남자친구와의 카톡방에 던진다.** 그리고 1주년에는 인스타
스토리에 올린다. 이 두 장면에서 카드가 통과해야 하는 것은 세 가지다.

### 2.1 되는 것

- **4:5 · 2160×2700은 정확한 선택이다.** 카톡 대화방 썸네일은 세로가 길수록 크게 잡히고,
  인스타 스토리(9:16)에 4:5를 얹으면 위아래에 여백이 남아 오히려 "카드"로 읽힌다. 정사각형이나
  1:1로 갔으면 둘 다 손해였다. 재검토 필요 없다.
- **흑백 카드는 이 서비스에서 맞다.** 사진 색이 뭐가 오든 카드가 사진을 이긴다. 카톡방은
  배경이 흰색/파스텔이라 흰 카드+검정 테두리가 자연스럽게 얹히고, 다크 모드 사용자가 만든
  검정 카드는 인스타 스토리에서 강하다.
- **텍스트 전용 감정·날씨는 오히려 톤에 맞다.** "설렘 · 맑음"이라는 **단어**가 이모지보다
  차분하고, 흑백 심플모던과 충돌하지 않는다. 기기 간 렌더 문제(AC-13)도 같이 사라졌다.
  다만 지금 스타일은 이 장점을 못 살리고 있다(§2.2).
- **일기가 잘렸음을 미리보기에서 알려 준다**(F-09/§2.2). 커플이 쓴 문장이 소리 없이 잘리는
  것만큼 이 서비스에서 나쁜 일은 없다.

### 2.2 안 되는 것 — 왜 올리고 싶어지지 않는가

**① 사진이 작다. 카드의 41%뿐이고, 그마저 고정값이다.**
`PHOTO_BLOCK_HEIGHT = 560`은 1350 높이의 41%다. 나머지 59%는 텍스트와 여백이다.
그런데 실제 사용 패턴은 반대다 — 데이트 일기는 대개 한두 줄이고("한강 산책."), 사진이 본체다.
지금 구조에서는 일기가 한 줄이든 다섯 줄이든 사진은 똑같이 560이라, **짧은 일기를 쓴 사람의
카드에는 일기와 태그 사이에 130px짜리 빈 구멍이 생긴다.** 그 구멍은 "여백"이 아니라 "덜 만든
것"으로 읽힌다. 카톡방에 올리기 직전에 손이 멈추는 지점이 정확히 여기다.
→ §3.3 적응형 사진 높이.

**② 감정·날씨 칩과 태그 칩이 사실상 보이지 않는다.**
칩 배경이 `palette.fill`(라이트 `--gray-100` / 다크 `--gray-800`)이고 카드 배경은 순백/순검정이다.
대비가 **1.05:1(라이트) / 1.5:1(다크)** — 알약 모양이 눈에 잡히지 않는다.
결과적으로 "설렘 맑음"이 그냥 본문 사이에 떠 있는 글자로 보인다. 이모지를 뺀 지금, 칩의 형태가
유일하게 "이건 감정·날씨 라벨이다"를 말해 주는 신호인데 그 신호가 꺼져 있는 셈이다.
→ §3.4. **감정·날씨는 채움(칠한 알약), 태그는 윤곽(선 알약).** 흑백 안에서 색이 아니라
형태로 두 층위를 가른다 — `tokens.css` 상단 주석이 primary/danger를 색이 아니라
"채움 vs 윤곽"으로 가른 것과 같은 논리이고, 그래서 앱과 같은 계열로 읽힌다.

**③ 위계가 눌려 있다.** 지금 크기는 64 / 34 / 32 / 30 / 28 — **28~34 사이에 네 단계가 몰려 있고,
날짜(34)가 일기(32)보다 크다.** 메타데이터가 본문보다 크면 카드가 "정보 나열"로 읽힌다.
1080 폭 카드를 480 폭 앱으로 환산(÷2.25)하면 각각 14.2 / 15.1 / 13.3 / 12.4px로,
전부 앱의 sm~md 사이에 뭉쳐 있다. 위계가 없다.
→ §3.1. **72 / 34 / 30 / 28 네 단계.** 환산하면 32 / 15.1 / 13.3 / 12.4 = 앱의 display / md /
sm / xs와 정확히 겹친다. 같은 서비스에서 나온 조판이라는 게 수치로 성립한다.

**④ 워터마크가 브랜드가 아니라 각주다.** 지금은 전폭 실선 + 가운데 정렬 28px/500 muted.
이 카드는 링크를 못 뿌리는 비공개 서비스의 **유일한 출구**다(스펙 §1). 카톡방에서 이 카드를
본 제3자가 "이거 뭐야?"라고 물을 수 있어야 기능이 제 값을 한다. 그런데 지금 워터마크는
"저작권 표시" 톤이라 아무도 안 읽는다.
→ §3.5. 앱 워드마크(`system.md` §6: 14px/700/자간 0.18em/`--color-text` + 발자국 마크) 규격을
그대로 스케일업해 **좌측 정렬 서명 블록**으로 만든다. 카드 전체가 좌측 축 정렬인데 워터마크만
가운데인 것도 축이 깨지는 지점이었다.

**⑤ 다크 모드에서 "+N" 배지가 안 보인다.** → §4 결함 D-1.

**⑥ 세로 사진 1장이 가로 띠로 잘린다.** 936×560(1.67:1) 커버 크롭이고 앵커가 정중앙(0.5)이라,
폰 세로 사진(3:4)에서는 **위아래가 잘려 얼굴이 프레임 밖으로 나간다.** 데이트 사진은 대개 인물이
있고 인물은 화면 위쪽 1/3에 있다.
→ §3.3. 크롭 앵커 0.5 → **0.38**(위쪽을 더 남긴다). 실측 비교에서 얼굴이 살아남았다.
적응형 높이가 도입되면 1장·짧은 일기 카드는 936×690(1.36:1)까지 커져 문제 자체가 크게 줄어든다.

### 2.3 "다시 가볼만한 역"과 같은 집안으로 보이는가

지금은 **반쯤만** 그렇다. 아래 제안을 적용하면 네 지점이 맞물린다.

| 앱 요소 | 카드의 대응 | 관계 |
|---|---|---|
| `profile.module.css` `.chip` (추천 역) — 윤곽 알약 + pill 반경 | 태그 칩(윤곽) | 같은 조형 |
| `ui.module.css` `.buttonPrimary`(채움) vs `.button`(윤곽) | 감정·날씨(채움) vs 태그(윤곽) | 같은 "채움/윤곽" 위계 문법 |
| `ui.module.css` `.title` — 700 / 자간 -0.02em | 역명 700 | 같은 제목 처리 |
| `Wordmark` `.brand` — 700 / 0.18em / 발자국 마크 | 카드 서명 블록 | 같은 로고타입 |
| `--space-*` 4px 배수 | 카드 값 전부 4px 배수(§3) | 같은 격자 |

## 3. 카드 조판 스펙 (개발자 이관 — `record-image-render.ts`)

논리 좌표계 1080×1350, 출력은 ×2 = 2160×2700 (F-06, 변경 없음).
아래 값은 전부 **논리 px**이고 전부 4의 배수다.

### 3.1 타이포 — 4단계로 줄인다

| 역할 | 현재 | **제안** | 근거 |
|---|---|---|---|
| 역명 (display) | `700 / 64` | **`700 / 72`** | 카드의 후크. ÷2.25 = 32px ≈ 앱 `.title`(26)보다 한 단계 위 = 포스터 헤드라인 |
| 일기 (body) | `400 / 32`, 행간 50 | **`400 / 34`, 행간 52** | ÷2.25 = 15.1 ≈ `--font-size-md`(16). 행간 1.53 |
| 날짜·감정·날씨 (meta) | 날짜 `400/34`, 칩 `500/30` | **날짜 `400/30`, 칩 `500/30`** | 같은 층위면 같은 크기. ÷2.25 = 13.3 ≈ `--font-size-sm`(14) |
| 태그·워터마크 (caption) | `500 / 28` | **`500 / 28` / 워터마크만 `700 / 28→30`** | ÷2.25 = 12.4 ≈ `--font-size-xs`(12) |

- **자간은 역명에 주지 않는다.** `ctx.letterSpacing`은 브라우저 지원이 갈려 AC-13(기기 간
  동일성)을 깬다. 워터마크만 **글자별 수동 전진**으로 트래킹한다(§3.5).
- **역명 오버플로 2단계 처리(신규)**: `measureText(역명) > CONTENT_WIDTH`이면 폰트를
  **72 → 56**으로 한 단계 내리고, 그래도 넘치면 기존대로 `…` 말줄임.
  ("남한산성입구(성남법원·검찰청)" 같은 긴 역명이 지금은 그냥 잘린다. 56px면 15자까지 들어간다.)

### 3.2 세로 리듬 — 앵커 공식

```
PAD = 72                      (변경 없음)
CONTENT_WIDTH = 936           (변경 없음)

y = 72
  역명    (700/72)  → y += 92            → 164     [현재 80]
  날짜    (400/30)  → y += 42            → 206     [현재 74]
  칩 있으면 y += CHIP_HEIGHT(60) + 36    → 302     [현재 56+36=92]
  칩 없으면 y += 20                      → 226     [현재 36]

푸터(아래에서 위로 고정)
  WATERMARK_TOP = 1350 - PAD - 34               = 1244
  RULE_Y        = WATERMARK_TOP - 28            = 1216
  TAGS_TOP      = 태그 있음 ? RULE_Y - 36 - TAG_HEIGHT(52) : RULE_Y   = 1128
  NOTE_BOTTOM   = TAGS_TOP - 36                 = 1092 (태그 없으면 1180)
```

### 3.3 사진 블록 — 고정 560 → 적응형

**핵심 변경.** 일기 줄 수를 **사진을 그리기 전에** 먼저 재고, 남는 세로를 사진에 준다.

```ts
// 1) 일기를 먼저 랩핑한다 (사진 그리기 전으로 순서 이동)
ctx.font = font(400, NOTE_FONT_SIZE)               // 34
const wrapped = note === '' ? [] : wrapText(ctx, note, CONTENT_WIDTH)

// 2) 사진 블록 높이를 역산한다
const noteH   = Math.min(wrapped.length, NOTE_MAX_LINES) * NOTE_LINE_HEIGHT  // 5 * 52
const photoH  = clamp(NOTE_BOTTOM - y - PHOTO_NOTE_GAP - noteH, PHOTO_MIN, PHOTO_MAX)

// 3) 사진을 그린 뒤
y += photoH + PHOTO_NOTE_GAP
// 4) 일기는 y부터 상단 정렬, maxLines = floor((NOTE_BOTTOM - y) / NOTE_LINE_HEIGHT)
```

| 상수 | 현재 | **제안** |
|---|---|---|
| `PHOTO_BLOCK_HEIGHT` | `560` 고정 | **삭제 → 위 공식** |
| `PHOTO_MIN` / `PHOTO_MAX` | — | **`520` / `780`** |
| `PHOTO_NOTE_GAP` | `44` | **`48`** |
| `NOTE_MAX_LINES` (사진 있을 때) | 없음 | **`5`** |
| `PHOTO_GAP` | `16` | 유지 |
| `PHOTO_RADIUS` | `24` | 유지 |
| 크롭 앵커 (`drawCover`) | `(rect.h - drawH) / 2` | **`(rect.h - drawH) * 0.38`** |

실측 결과(사진 2장·칩·태그 3개 기준, `NOTE_BOTTOM = 1092`):

| 일기 줄 수 | 사진 블록 높이 | 1장일 때 비율 |
|---|---|---|
| 0줄 | 742 | 1.26:1 |
| 1줄 | 690 | 1.36:1 |
| 2줄 | 638 | 1.47:1 |
| 3줄 | 586 | 1.60:1 |
| 4줄 | 534 | 1.75:1 |
| 5줄 이상 | 520 (하한 적용 → 실제로 들어가는 건 4줄) | 1.80:1 |

→ **짧은 일기(대다수)는 사진이 커지고, 긴 일기는 잘리지 않고 다 들어간다.** 지금은 3줄에서
무조건 `…`로 끊기는데, 제안안에서는 5줄까지 살아남는다. 커플이 쓴 문장이 더 많이 남는다.

**사진 없는 카드**(F-04 폴백·사진 미첨부): 일기가 유일한 콘텐츠이므로 **`400 / 44`, 행간 68**로
키워 상단 정렬한다. 34px로 두면 1350 높이 카드에 두 줄만 떠 있어 "실패한 카드"로 보인다.

| 상수 | 값 |
|---|---|
| `NOTE_FONT_SIZE_SOLO` / `NOTE_LINE_HEIGHT_SOLO` | **`44` / `68`** |

슬롯 규칙(1=전체 / 2=좌우 / 3=좌 전체높이+우 상하 / 4=2×2)은 **그대로 유지한다.**
3장에서 빈 칸을 남기지 않는 처리는 옳은 판단이었다.

**"+N" 배지**

| 항목 | 현재 | **제안** |
|---|---|---|
| 높이 | `CHIP_HEIGHT`(56) 공용 | **`BADGE_HEIGHT = 48`** (칩 높이가 바뀌어도 안 따라 커지게 분리) |
| 폰트 | `700 / 32` | **`700 / 30`** |
| 좌우 패딩 | `20` | **`22`** |
| 글자색 | `palette.bg` | **`palette.onScrim`(항상 흰색)** ← 결함 D-1 |
| 스크림 | `rgb(0 0 0 / 62%)` | 유지 |

### 3.4 칩 — 채움 vs 윤곽

| | 감정·날씨 | 태그 |
|---|---|---|
| 형태 | **채움(solid)** | **윤곽(outline)** |
| 배경 | `palette.text` | 없음 |
| 테두리 | 없음 | `palette.muted`, `lineWidth 2` (알약 안쪽으로 1px 인셋) |
| 글자 | `palette.bg` | `palette.muted` |
| 높이 | `CHIP_HEIGHT` **60** (현재 56) | `TAG_HEIGHT` **52** (신규, 현재는 56 공용) |
| 폰트 | `500 / 30` (유지) | `500 / 28` (유지) |
| 좌우 패딩 | **30** (현재 24) | **26** (현재 24) |
| 칩 간격 | `16` (유지) | `12` (유지) |

- 좌우 패딩을 높이의 절반(30 / 26)에 맞춘다. 알약은 패딩이 반경보다 작으면 글자가 둥근 끝에
  밀려 붙어 보인다. 지금 24는 그 경계선이었다.
- 태그 `+N` 칩도 같은 윤곽 스타일, 글자·테두리 `palette.muted`.
- 상한 5개(F-10)와 "폭 넘치면 초과분에 합산" 처리는 그대로 좋다.

### 3.5 프레임 · 서명 블록

| 항목 | 현재 | **제안** | 이유 |
|---|---|---|---|
| 카드 테두리 | `lineWidth 2`, `strokeRect(1,1,W-2,H-2)` | **`lineWidth 3`, `strokeRect(1.5,1.5,W-3,H-3)`** | 카톡 썸네일(≈480px 표시)로 줄면 2px는 0.9px가 돼 렌더 아티팩트로 보인다. 3px면 의도된 프레임으로 읽힌다 |
| 카드 모서리 | 직각 | **직각 유지** | 둥글게 하려면 알파가 필요한데, PNG→JPEG 변환 경로에서 검게 뭉개진다. 전면 배경이 안전하다 |
| 구분선 | 전폭 `PAD..W-PAD`, `lineWidth 1`, `palette.border` | **`PAD..PAD+120`, `lineWidth 3`, `palette.text`** | 전폭 순검정/순백 실선은 카드 테두리와 경쟁한다. 짧은 좌측 룰은 편집 디자인의 서명 장치이고 좌측 축을 지킨다 |
| 룰→워터마크 간격 | 24 | **28** | |
| 워터마크 | `500 / 28`, `palette.muted`, **가운데 정렬** | **`700 / 30`, 자간 `0.18em`(수동 트래킹), `palette.text`, 좌측 정렬 `x = PAD + 52`** | 앱 워드마크(`system.md` §6) 규격 그대로. 각주가 아니라 로고 |
| 발자국 마크 | 없음 | **34×34 영역, 지름 15 원 2개.** 앞 중심 `(PAD+9.5, WATERMARK_TOP+7.5)` 불투명 / 뒤 중심 `(PAD+24.5, WATERMARK_TOP+26.5)` `globalAlpha 0.5` | 앱 `.brandMark`(대각선 원 2개)를 그대로 옮김. 캔버스 원 두 개라 에셋이 필요 없다 |

자간은 `ctx.letterSpacing`을 쓰지 않는다(브라우저 지원 편차 → AC-13 위반). 글자별로 그린다:

```ts
let cx = PAD + 52                       // 마크(34) + 간격(18)
for (const ch of WATERMARK_TEXT) {
  ctx.fillText(ch, cx, WATERMARK_TOP)
  cx += ctx.measureText(ch).width + 30 * 0.18   // 5.4px
}
```

## 6. 검토했지만 채택하지 않은 것

| 안 | 왜 안 하는가 |
|---|---|
| **사진 풀블리드 히어로**(사진을 카드 상단에 여백 없이 꽉 채우기) | 존재감은 커지지만 **크롭 비율은 오히려 나빠진다**(1080×620 = 1.74:1 > 지금 1.67:1). 세로 여백 예산이 그대로라 폭만 늘어난다. 게다가 여백 없는 사진은 카드 테두리를 삼켜, 흰 배경 채팅방에서 "카드"로 안 읽힌다 |
| **카드 모서리 둥글게 + 알파** | 채팅앱/스토리에서 예쁘지만, PNG→JPEG 재인코딩 경로에서 투명 모서리가 검게 남는다. 되돌릴 수 없는 사고라 안 한다 |
| **1장일 때만 3:4 세로 슬롯(가운데 정렬)** | 좌측 축 정렬 카드에서 가운데 정렬된 사진 하나는 오히려 실수처럼 보인다. 적응형 높이(§3.3)가 같은 문제를 부작용 없이 푼다 |
| **일기 세로 중앙 정렬** | 사진이 있을 땐 영역이 좁아 상단 정렬과 차이가 없고, 사진이 없을 땐 짧은 글이 카드 한복판에 떠 더 나빠진다(실측 확인). 상단 정렬 + 사진 없을 때 폰트 확대가 낫다 |
| **태그와 워터마크를 한 줄에** | 세로 58px을 벌 수 있지만 긴 태그와 충돌하고 워드마크가 약해진다 |
| **감정·날씨에 자체 SVG 아이콘 세트**(스펙 §9 대안) | 텍스트 라벨 확정으로 결론 남. 이모지는 태그 쪽에서 별도로 다룬다 |

## 7. 검증 방법

카드 조판은 앱 로그인 없이 검증하려고 `record-image-render.ts`의 레이아웃을 그대로 옮긴
독립 하니스에서 **현재안 / 제안안을 같은 데이터로 나란히 렌더**해 비교했다. 시나리오는
2장·긴 일기·태그3 / 1장(세로 원본) / 4장+2 / 사진 없음·짧은 일기 / 3장·짧은 일기 /
감정·날씨 없음·태그 없음 여섯 가지 × 라이트·다크.

시트는 실제 `tokens.css` + `ui.module.css` + `record-image.module.css`를 그대로 물려
mobile / tablet / desktop / landscape 네 폭 × 라이트·다크로 렌더하고,
비율·넘침·터치 타깃을 `getBoundingClientRect`로 실측했다(§5.2 표가 그 값이다).
D-4(비율 찌그러짐)는 이 실측에서 발견했다.

`npm run build` 통과 확인.
