# 디자이너 브리프 — 동네 발자취

> 시안 작업을 시작하기 전에 필요한 프로젝트 맥락만 정리한 문서다. **색·타이포·레이아웃 같은
> 시각적 결정은 의도적으로 다루지 않는다** — 그건 디자이너의 몫이다. 이미 확정돼 있는
> 시각 자산(토큰 시스템)이 있다는 사실만 5장에서 언급하고, 값 자체는 옮겨 적지 않는다.

## 1. 서비스가 뭔가

연인이 함께 다녀온 데이트 장소를 **지하철 노선도 위에** 기록하고, 사진과 일기로 추억을
남기는 **커플 전용** 데이트 아카이브 서비스다. 수도권 지하철 기준.

경쟁 서비스(커플 다이어리류)와의 유일한 차별점은 "지하철 노선도라는 공간 축"이다. 장소를
목록이 아니라 **노선도 위의 지점**으로 기록한다는 것이 이 서비스의 정체성이고, 그래서
노선도가 앱의 기본(첫) 화면이다.

핵심 문장(기획서 배경): "시간이 지나면 언제 어디를 갔는지 기억이 흐려진다" — 이 문제를
노선도 위에 다녀온 역을 채워나가는 방식으로 해결한다. 빈칸을 채우는 수집의 재미도 의도된
장치다(방문한 역은 채워진 스탬프, 안 간 역은 빈 원).

전체 기획 원문은 `docs/PRD.md`에 있다. 이 문서는 그 요약이 아니라 **디자인 작업에 필요한
범위만 뽑은 것**이므로, 뉘앙스가 필요하면 PRD를 직접 참고하는 게 낫다.

## 2. 누가 쓰는가

- 사용자 단위가 **개인이 아니라 커플**이다. 로그인은 개인 계정이지만, 데이터(기록)는 두 사람이
  공동 소유한다 — 상대가 쓴 기록도 내가 수정·삭제할 수 있다.
- 초대 코드로 커플을 연결한다(소셜 로그인 아님). 상대가 아직 합류하지 않은 "1인 상태"가
  정상적인 중간 상태로 존재한다.
- 모바일 우선이지만 데스크톱도 동일하게 지원해야 한다(기획서 명시 요구사항).

## 3. 핵심 사용 흐름 (기획서 시나리오)

1. 노선도(기본 화면)에서 다녀온 역이 스탬프로 표시된 걸 본다.
2. 역을 탭해 역 상세로 들어가 그 역의 기록 목록을 본다.
3. "기록 추가"로 새 데이트 기록을 쓴다 — 역(자동 채움)·날짜·감정·날씨·사진·일기·태그.
4. 저장하면 기록 상세로 이동하고, 노선도로 돌아가면 그 역에 스탬프가 찍혀 있다.
5. 타임라인에서 시간순으로 전체 기록을 훑어보거나 태그로 필터한다.
6. 프로필에서 "함께한 지 N일", 총 데이트 수, 방문 역 커버리지 %를 확인하고, "안 가본 역"
   추천을 보고 다음 데이트 장소를 정한다.

## 4. 화면 구성과 지금 상태

PRD가 정의한 화면은 7개다. 진행 상태를 정확히 알아야 시안이 필요한 지점을 판단할 수 있어
같이 적는다.

| 화면 | 설명 | 상태 |
|---|---|---|
| 인증 / 커플 연결 | 로그인·가입·초대코드 발급/입력 | 구현 완료 |
| 노선도 (기본 화면) | 전체 노선을 겹쳐 그린 SVG. 방문=채워진 스탬프, 미방문=빈 원 | **2호선만** 파일럿 구현. 나머지 노선 도식 좌표 미제작 |
| 역 상세 | 특정 역의 기록 목록, "기록 추가" 진입점 | 미착수 |
| 지도 보기 | 노선도의 보조 토글, 카카오맵 기반 실제 지도 | 미착수 |
| 기록 작성/수정 | 이 앱에 데이터가 들어오는 유일한 입구 | 구현 완료 |
| 기록 상세 | 사진 전체·일기 전문 열람, 수정/삭제/이미지 저장 메뉴 | 구현 완료 |
| 타임라인 | 전체 기록을 시간순으로, 태그 필터 | 미착수 |
| 커플 프로필 | 이름·디데이·통계(데이트 수/방문 역 수/커버리지%)·안 가본 역 추천, 커플 설정(로그아웃/연결해제) | 설정 영역만 구현. 통계·추천은 미착수 |
| 기록 카드를 이미지로 저장 | 기록 상세의 부가 기능 | 미착수 |

**시안이 특히 필요한 지점**: 역 상세·지도 보기·타임라인·프로필 통계 — 아직 화면 자체가
없어서 백지에서 시작해야 한다. 반대로 인증/노선도(2호선)/기록 작성·수정/기록 상세는 이미
동작하는 화면이 있으니, 새로 그리기보다 **다듬는 리뷰**의 대상에 더 가깝다.

## 5. 이미 있는 것 (참고 자료)

- **클릭 가능한 목업 프로토타입**: 목데이터·로그인 없이 화면 구조와 인터랙션만 보여주는
  React 프로토타입이 있다. 화면 흐름 참고용으로만 쓴다 — 실 데이터/인증이 없어서 구현
  근거로는 쓰지 않는다(근거는 어디까지나 `docs/PRD.md`와 `docs/specs/`).
- **동작하는 실제 화면 4개**: 인증/커플연결, 노선도(2호선), 기록 작성/수정, 기록 상세는
  지금 앱에서 실제로 눌러볼 수 있다. 새로 시안을 그리기 전에 먼저 켜서 보는 걸 권한다.
- **이미 확정된 시각 자산이 있다**: 색상·타이포·간격·그림자 등은 토큰 시스템으로 이미
  구현돼 있고(`src/styles/tokens.css`), 라이트/다크 모드도 지원한다. 값 자체를 여기 옮기지
  않는다 — 필요하면 그 파일과 `docs/design/system.md`를 직접 열어서 확인하고, 유지할지
  바꿀지는 디자이너가 판단한다.
- **기존 디자인 노트**: `docs/design/` 아래 인증 화면·앱 프레임에 대한 기존 작업 기록이
  있다(`auth-screens.md`, `app-frame.md`).

## 6. 구조적 제약 (색·스타일이 아니라 "이렇게는 못 만든다"에 해당하는 것들)

- **순수 SPA, 서버 미들웨어 없음**: 화면이 Supabase를 직접 호출한다. 서버 사이드 렌더링이나
  이미지 최적화 프록시 같은 걸 전제로 한 디자인은 못 쓴다.
- **모바일 우선 반응형 + 데스크톱 카드 프레임**: 데스크톱에서는 앱이 고정 폭 카드(≈480px)
  안에 담기고 바깥은 배경 톤이 채운다. 모바일은 풀블리드다. 두 레이아웃을 별도로 설계할
  필요는 없고, 하나의 반응형 구조가 양쪽을 커버해야 한다.
- **노선도는 직접 그린 SVG**: 실제 지리 좌표가 아니라 가독성을 위해 왜곡한 도식이다(디자이너
  또는 개발자가 좌표를 직접 배치). 자동 생성 지도가 아니라는 점이 노선도 화면 디자인에
  중요한 전제다.
- **접근성 하한선**: 본문 대비 4.5:1, UI 요소 3:1(WCAG), 터치 타깃 44×44px 이상, 색만으로
  상태를 구분하지 않기(형태·텍스트 병행), 키보드만으로 전 기능 접근 가능. 이건 스펙에
  못박힌 요구사항이라 시안 단계에서부터 감안이 필요하다.
- **사용자가 올리는 사진**: 기록당 최대 10장, 원본 상한 10MB, 업로드 전 리사이즈(긴 변
  2,048px). 즉 사진 그리드/뷰어를 설계할 때 "장수가 0~10장으로 가변"이라는 걸 전제해야 한다.
- **일기(`note`)는 평문**: 마크다운·링크 해석을 하지 않는다. 줄바꿈만 보존한다. 긴 글이 들어올
  수 있다는 전제(최대 1,000자)로 레이아웃을 잡아야 한다.

## 7. 참고 문서

- `docs/PRD.md` — 기획 원문 (최종 소스)
- `docs/specs/` — 화면별 상세 스펙(사용자 시나리오·기능 요구사항·완료 조건). 특정 화면을
  맡기 전에 해당 번호의 스펙을 먼저 읽는 걸 권한다 (예: 역 상세 = `04-station-detail.md`).
- `docs/decisions/` — 되돌리기 어려운 결정 기록(ADR). 노선도 좌표를 왜 정적 파일로
  관리하는지 등.
- `docs/design/system.md`, `auth-screens.md`, `app-frame.md` — 기존 디자인 작업 기록.
