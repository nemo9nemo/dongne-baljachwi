# 역 상세 화면

> 근거: PRD §4 "역 상세 — 해당 역의 기록 목록 + 기록 추가 버튼", §3 "역별 기록 보기 (P0)"
> 전제: `00-data-model.md`, `02-station-master.md`, `03-line-map.md`

## 1. 목적 / 배경

노선도는 "어디를 갔는가"를 한눈에 보여주지만, 스탬프 하나에는 여러 번의 데이트가 겹쳐 있다.
역 상세는 그 스탬프를 **풀어서 보는 화면**이다. "홍대입구 3회"라는 뱃지를 눌렀을 때
그 세 번이 각각 언제, 어떤 기분이었는지 보여주지 못하면 노선도는 그냥 통계 그래프가 된다.

동시에 이 화면은 **기록 작성의 주 진입점**이다. PRD §2의 사용자 시나리오는
"노선도에서 홍대입구역을 누른다 → 기록 추가를 누른다"로 시작한다. 즉 역이 먼저 정해지고
기록이 따라온다. 이 순서가 이 앱의 기본 입력 흐름이다.

## 2. 사용자 시나리오

### 2.1 정상 흐름

1. 노선도(또는 지도 보기, 프로필의 추천 칩)에서 홍대입구를 탭한다.
2. 역 상세로 이동한다. 상단에 **역명 + 소속 호선 배지들 + 방문 요약**(총 N회, 마지막 방문일).
3. 그 아래 해당 역의 기록이 **최신순 카드 목록**으로 나열된다.
   각 카드: 날짜 / 감정·날씨 아이콘 / 대표 사진 썸네일 / 일기 앞부분 / 태그 최대 3개 / 작성자.
4. 카드를 탭하면 기록 상세로 이동한다 (`06-record-detail.md`).
5. 화면 하단 고정 버튼 "이 역에 기록 추가"를 누르면 기록 작성 화면으로 이동하며,
   **역이 이미 선택된 상태**로 열린다 (`05-record-editor.md`).
6. 뒤로 가면 노선도의 직전 뷰포트로 복귀한다.

### 2.2 예외 흐름

| 상황 | 동작 |
|---|---|
| 이 역에 기록 0건 (미방문 역) | 빈 상태: "아직 이 역에는 발자취가 없어요" + "첫 기록 남기기" 버튼(주 액션으로 강조) |
| 기록 로드 실패 | 역 헤더(역명·호선)는 마스터 캐시로 즉시 표시하고, 목록 영역만 에러 + 재시도. 기록 추가 버튼은 **활성 유지** |
| 존재하지 않는/비활성 역 ID로 진입 | "존재하지 않는 역입니다" + 노선도로 돌아가기. 단 `is_active=false`여도 **기록이 있으면 정상 표시**한다 (폐역의 추억도 기록이다) |
| 오프라인 | 마스터 캐시로 헤더 표시 + 기록 목록은 에러 상태. 기록 추가는 막는다(작성 화면에서 저장 실패가 뻔함) |
| 기록이 매우 많음 (수십 건) | 무한 스크롤 페이지네이션 (F-06) |
| 커플 미연결 | 이 화면에 도달하지 않는다 |

## 3. 기능 요구사항

| ID | 요구사항 | 우선순위 | 비고 |
|----|---------|---------|------|
| F-01 | 역명, 소속 호선 배지(전부), 총 방문 횟수, 마지막 방문일을 헤더에 표시한다 | Must | 환승역은 호선 배지가 여러 개 |
| F-02 | 해당 역의 기록을 `visited_on` 내림차순으로 나열한다. 동일 날짜는 `created_at` 내림차순 | Must | 타이브레이커를 정해두지 않으면 목록 순서가 요청마다 흔들린다 |
| F-03 | 기록 카드에 표시할 것: 날짜, 감정·날씨 아이콘, 대표 사진 썸네일, 일기 발췌, 태그 최대 3개, 작성자 이름 | Must | PRD §5.3 "기록 카드에 태그 최대 3개 미리보기" |
| F-04 | 대표 사진 = `sort_order`가 가장 작은 사진. 사진이 없으면 썸네일 영역 자체를 생략한다 | Must | 빈 회색 박스를 남기지 않는다 |
| F-05 | 일기 발췌는 최대 2줄, 넘치면 말줄임 | Should | |
| F-06 | 기록 목록은 20건 단위 키셋 페이지네이션 (무한 스크롤) | Must | `(visited_on DESC, id DESC)` 기준 |
| F-07 | 하단 고정 "이 역에 기록 추가" 버튼. 누르면 역이 선택된 상태로 작성 화면 진입 | Must | PRD §4 |
| F-08 | 카드 탭 → 기록 상세로 이동 | Must | |
| F-09 | 이 화면은 고유 URL을 가진다 (새로고침·뒤로가기 보존) | Must | URL 경로 명명은 개발자 결정 |
| F-10 | 기록 상세에서 삭제 후 돌아오면 목록에서 해당 카드가 사라져 있어야 한다 | Must | 목록 캐시 무효화 |
| F-11 | 태그가 3개를 넘으면 "+N" 표시 | Should | |
| F-12 | 이 역의 기록에만 필터/정렬 UI를 두지 않는다 | Must | 역 단위 기록은 보통 한 자릿수. 전체 필터는 타임라인(`08`)이 담당 |
| F-13 | 헤더의 호선 배지를 탭하면 노선도로 돌아가 그 호선이 필터된 상태로 연다 | Could | 있으면 좋지만 없어도 흐름이 끊기지 않음 |

## 4. 데이터 모델

### 4.1 읽는 것

**신규 테이블 없음.** `records`, `record_photos`, `record_tags`, `profiles`,
`stations`, `station_lines`, `lines`를 읽는다.

**쿼리 계약 — 화면 진입 시**

| # | 대상 | 조건 | 반환 |
|---|---|---|---|
| 1 | 마스터(캐시) | `stations.code` 또는 `id` | 역명, 소속 호선 목록 |
| 2 | `couple_station_visits` | `station_id = ?` | `visit_count`, `last_visited_on` |
| 3 | `records` + 조인 | `station_id = ?`, 키셋 20건 | 아래 shape |

3번의 응답 shape (프론트/백엔드 계약):

```
RecordCard {
  id: uuid
  visited_on: date            // "YYYY-MM-DD"
  mood: 'happy'|'love'|'excited'|'calm'|'sad' | null
  weather: 'sunny'|'cloudy'|'rainy'|'snowy'|'windy' | null
  note_excerpt: string | null // 서버에서 자르지 않고 note 전문을 보내되,
                              // 목록 전용이면 앞 200자만 (아래 주석 참조)
  author: { id: uuid, display_name: string }
  photo_count: int
  cover_photo: { storage_path: string, width: int, height: int } | null
  tags: string[]              // tag 표기 그대로, 최대 3개 + total_tag_count
  total_tag_count: int
}
```

- `note`는 최대 2,000자다. 20건이면 최악 40KB — 그대로 보내도 문제없는 크기지만,
  목록에서 2줄만 쓰므로 **앞 200자만 전송**한다. 이유는 대역폭이 아니라, 목록 응답에
  일기 전문이 실려 다니면 캐시·로깅 등에 불필요하게 사적인 내용이 퍼지기 때문이다.
- `cover_photo`는 `storage_path`만 보내고, **서명 URL은 클라이언트가 필요할 때 발급**한다
  (`00-data-model.md` §4.6). 20건×서명 URL을 서버가 미리 만들면 유효기간 관리가 꼬인다.
- 서명 URL은 화면에 보이는 카드 것만 발급한다 (일괄 발급 금지).

### 4.2 쓰는 것

**없다.** 읽기 전용 화면이다. 작성은 `05`, 삭제는 `06`이 담당한다.

### 4.3 RLS로 보장할 접근 범위

| 대상 | 범위 |
|---|---|
| `records` | `couple_id = current_couple_id()`. **URL에 임의의 `station_id`를 넣어도 다른 커플의 기록은 절대 보이지 않는다** — 이 화면의 보안 요건은 이 한 줄이다 |
| `record_photos`, `record_tags` | 동일 |
| `profiles` (작성자 이름) | 본인 + 같은 커플 멤버만 (`00-data-model.md` §4.1) |
| Storage `record-photos` | 경로 첫 세그먼트 = `current_couple_id()` |
| `stations`, `lines` | 전원 읽기 (역 정보는 공개 데이터) |

> 주의: 역 자체는 공개 데이터이므로 **"이 역이 존재하는가"는 누구나 알 수 있다.**
> 격리해야 하는 건 "이 커플이 이 역에 몇 번 갔고 무엇을 기록했는가"다. 이 화면은 그 둘을
> 한 화면에 섞어 놓으므로, 기록 관련 모든 쿼리가 예외 없이 RLS를 타는지 확인해야 한다.

## 5. 상태 정의

| 상태 | 화면 |
|---|---|
| 로딩 | 헤더(역명·호선)는 마스터 캐시로 **즉시** 표시. 목록 영역만 스켈레톤 카드 3개 |
| 빈 상태 | 일러스트/문구 "아직 이 역에는 발자취가 없어요" + "첫 기록 남기기" 주 버튼. 하단 고정 버튼과 중복되면 하단 버튼은 숨긴다 |
| 목록 에러 | 목록 영역만 에러 + 재시도. 헤더·기록 추가 버튼은 살아 있다 |
| 부분 성공 (기록은 왔으나 방문 요약 실패) | 목록 정상 표시, 헤더의 "총 N회"는 목록 길이로 대체하지 않고 **표시를 생략**한다 (잘못된 숫자를 보여주지 않는다) |
| 사진 로드 실패 | 해당 카드의 썸네일 자리만 대체 표시. 카드 전체를 에러로 만들지 않는다 |
| 추가 페이지 로딩 | 목록 하단 스피너 |
| 마지막 페이지 도달 | 스피너 제거, 추가 문구 없음 |
| 오프라인 | 헤더 표시 + 목록 에러 + 기록 추가 버튼 비활성(사유 툴팁) |

## 6. 비기능 요구사항

- **응답 목표**: 기록 20건 조회 p95 300ms 이하 (커플당 총 기록 5,000행 기준).
  인덱스 `(couple_id, station_id)` 필수 (`00-data-model.md` §4.5).
- **첫 픽셀**: 헤더는 마스터 캐시에서 오므로 네트워크 대기 없이 표시되어야 한다.
  "역명이 로딩 스켈레톤으로 보이는" 상태를 만들지 않는다.
- **이미지**: 썸네일은 원본이 아니라 변환 이미지로 요청한다 (Supabase Storage 변환 파라미터).
  카드 썸네일 기준 폭 이하로 다운스케일 + DPR 2배까지만.
  `width`/`height`를 미리 알고 있으므로 **레이아웃 시프트(CLS) 0**을 목표로 한다.
- **스크롤 복원**: 기록 상세에 갔다 돌아오면 목록 스크롤 위치가 유지된다.
- **접근성**: 카드는 링크 역할로 노출하고, 접근 가능한 이름은
  "2026년 8월 11일 홍대입구 기록, 설렘, 맑음, 사진 2장" 형태로 구성한다.
  감정·날씨 이모지는 장식이 아니라 정보이므로 `aria-label`을 붙인다(이모지 자체를
  스크린리더가 읽는 방식에 의존하지 않는다).
- **브라우저**: `03-line-map.md` §6과 동일.

## 7. 확장 포인트

| 지점 | 지금 | 이유 |
|---|---|---|
| 기록 카드 컴포넌트의 데이터 shape | `RecordCard` (§4.1) | 이 shape를 타임라인(`08`)이 **그대로 재사용**한다. 두 화면의 카드가 갈라지면 유지보수가 두 배가 된다. 차이는 "역명을 보여주는가"뿐이므로 필드에 `station`을 옵셔널로 둔다 |
| 목록 정렬 | 방문일 내림차순 고정 | 정렬 축이 늘어나면 키셋 커서 정의만 추가하면 된다. 지금은 UI를 만들지 않는다 |
| 역 헤더의 부가 정보 | 호선/방문 요약 | 후일 "이 역 주변 추천" 등이 붙어도 헤더 영역만 확장 |
| 진입 경로 | 노선도 / 지도 / 추천 칩 | 진입 경로에 무관하게 같은 URL로 열리도록 해서, 경로가 늘어나도 화면을 고치지 않는다 |

**만들지 않는 것**: 역 즐겨찾기, 역별 메모, 역 단위 통계 그래프.

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 홍대입구에 기록 3건, When 노선도에서 홍대입구를 탭하면, Then 역 상세가 열리고 헤더에 "총 3회"와 마지막 방문일이 보이며 카드 3개가 최신순으로 나열된다.
- **AC-02** Given 환승역(홍대입구), When 역 상세를 열면, Then 소속 호선 배지 3개가 모두 표시된다.
- **AC-03** Given 같은 날짜에 기록 2건, When 목록을 두 번 새로고침하면, Then 두 번 모두 같은 순서로 표시된다 (타이브레이커 검증).
- **AC-04** Given 기록이 0건인 역, When 역 상세를 열면, Then 빈 상태 문구와 "첫 기록 남기기" 버튼이 보인다.
- **AC-05** Given 역 상세, When "이 역에 기록 추가"를 누르면, Then 작성 화면이 열리고 역 필드가 해당 역으로 채워져 있으며 변경 가능하다.
- **AC-06** Given 기록 25건인 역, When 스크롤을 끝까지 내리면, Then 추가 5건이 로드되고 중복·누락이 없다.
- **AC-07** Given 카드 탭으로 기록 상세 진입 후 삭제, When 뒤로 돌아오면, Then 목록에서 해당 카드가 사라져 있다.
- **AC-08** Given 사진이 없는 기록, When 카드를 보면, Then 썸네일 영역이 없고 레이아웃이 깨지지 않는다.
- **AC-09** Given 태그가 5개인 기록, When 카드를 보면, Then 태그 3개 + "+2"가 표시된다.
- **AC-10** Given 커플 A 사용자, When 커플 B만 기록이 있는 역의 상세를 열면, Then 기록 0건(빈 상태)이 표시된다.
- **AC-11** Given 기록 목록 요청 실패, When 화면을 보면, Then 역명 헤더는 정상 표시되고 목록만 에러 상태이며 재시도가 동작한다.
- **AC-12** Given 목록을 스크롤한 뒤 기록 상세에 갔다가 돌아오면, Then 스크롤 위치가 유지된다.
- **AC-13** Given 스크린리더 사용, When 카드에 포커스하면, Then 날짜·역명·감정·날씨·사진 수를 읽어준다.

## 9. 미결정 항목

> ❓ **폐역(`is_active=false`)에 기록이 있을 때의 표시**. 현재는 "정상 표시"로 정했으나,
> 폐역임을 사용자에게 알려야 하는지(배지 등) 미정. 노선도에는 표시되지 않으므로
> 타임라인에서만 도달 가능해진다.

> ❓ **일기 발췌 200자 / 2줄**은 임의값. 디자이너의 카드 레이아웃 확정 후 조정.

> ❓ **호선 배지 탭 동작 (F-13)**. Could로 두었으나, 환승역에서 "이 역이 어느 노선 소속인지"
> 시각적으로만 보여줄지 인터랙션까지 줄지 미정.

> ❓ **같은 역·같은 날짜에 기록 2건**을 허용할지. 현재 스키마에는 제약이 없어 허용된다.
