# 기록 작성 / 수정

> 근거: PRD §4 "기록 작성/수정 — 역·날짜·감정·날씨·태그·사진·일기 입력",
> §3 "기록 작성/수정 (P0)", "감정·날씨 아이콘 (P0)", "자유 태그 (P0)", "실 데이터 저장 (P0)",
> §5.2, §5.3
> 전제: `00-data-model.md`, `02-station-master.md`, `04-station-detail.md`

## 1. 목적 / 배경

이 앱에 데이터가 들어오는 **유일한 입구**다. 다른 모든 화면(노선도 스탬프, 타임라인,
프로필 통계, 지도 핀, 추천)은 여기서 만들어진 `records`의 파생물이다.

프로토타입에서 가장 결정적으로 미완성인 부분이기도 하다 — PRD §7은 "사진 업로드는 브라우저
로컬 미리보기만 되고 저장되지 않는다"고 명시한다. 즉 이 스펙의 실질적 난이도는 입력 폼이
아니라 **사진을 Supabase Storage에 안전하고 실패 없이 올리는 것**, 그리고 **업로드가
부분 실패했을 때 사용자의 일기를 잃지 않는 것**이다.

PRD §5.2가 강조하는 설계 의도는 "입력 마찰 최소화"다. 그래서 이 폼에서 **필수 입력은
역과 날짜 둘뿐**이다. 나머지는 전부 선택이다.

## 2. 사용자 시나리오

### 2.1 정상 흐름 — 작성 (PRD §2 시나리오 그대로)

1. 역 상세에서 "이 역에 기록 추가"를 누른다 → 작성 화면. 역은 이미 채워져 있다.
2. 날짜는 **오늘**로 기본 채워져 있다. 그대로 두거나 바꾼다.
3. 감정 아이콘 5개 중 "설렘"을 탭한다 (한 번 더 탭하면 해제).
4. 날씨 아이콘 5개 중 "맑음"을 탭한다.
5. 사진 추가 버튼 → 갤러리에서 2장 선택 → 썸네일이 즉시 미리보기로 뜬다.
6. 일기를 짧게 쓴다.
7. 태그 입력에 "카페" 입력 후 Enter → 칩 생성. "산책" 입력 후 Enter → 칩 생성.
8. "저장"을 누른다. 업로드 진행률이 보이고, 완료되면 **기록 상세 화면**으로 이동한다.
9. 노선도로 돌아가면 그 역에 스탬프가 찍혀 있다.

### 2.2 정상 흐름 — 수정

1. 기록 상세 → "수정" → 같은 폼이 기존 값으로 채워져 열린다.
2. 사진 1장을 삭제하고 1장을 추가한다. 순서를 바꾼다.
3. 저장 → 기록 상세로 복귀. `last_edited_by`가 나로 갱신된다.

### 2.3 예외 흐름

| 상황 | 동작 |
|---|---|
| 역 미선택 상태로 저장 | 저장 버튼 비활성. 역 필드에 인라인 안내 |
| 미래 날짜 선택 | 날짜 선택기에서 오늘 이후를 선택 불가로 막는다 (에러 문구보다 선택 자체를 막는 게 낫다) |
| 사진 용량 초과 | 선택 즉시 거부 + "10MB 이하 이미지만 올릴 수 있어요". 다른 사진은 정상 유지 |
| 지원하지 않는 형식(HEIC 등) | 브라우저가 디코딩 가능하면 통과, 실패 시 "이 사진 형식은 지원되지 않아요" 안내 후 거부 (§9 결정) |
| 사진 11장째 추가 | 추가 버튼 비활성 + "사진은 최대 10장까지" |
| 업로드 중 일부 실패 | **기록은 저장하고**, 실패한 사진만 카드에 재시도 표시 (F-16) |
| 저장 중 네트워크 끊김 | 폼 내용을 로컬에 임시 보관하고 "저장하지 못했어요, 다시 시도" — 입력값은 절대 날리지 않는다 |
| 작성 중 화면 이탈 시도 | 변경사항이 있으면 확인 모달 ("작성 중인 내용이 있어요") |
| 수정 중 상대가 같은 기록을 먼저 수정 | 마지막 저장이 이긴다 + 저장 후 안내. **⚠ 2026-08-12: 미구현.** 참조하던 "F-19"는 실제로는 §3.4 EXIF 항목이라 번호가 잘못됐었다(정정함). `upsert_record`가 충돌 신호(예: 버전/`updated_at` 비교)를 반환하지 않아 클라이언트가 애초에 감지할 방법이 없다 — "저장 후 안내"를 하려면 RPC 계약에 낙관적 잠금을 추가해야 한다. 별도 F-ID로 분리해 백엔드와 함께 재설계 필요 |
| 수정 중 상대가 그 기록을 삭제 | 저장 시 대상 없음 → "이 기록은 삭제되었어요" + 폼 내용을 새 기록으로 저장할지 제안 |
| 커플 미연결 | 이 화면에 도달하지 않는다 |
| 오프라인 | 저장 불가. 폼은 열리고 입력은 되지만 저장 버튼에 오프라인 사유 표시 |

## 4. 데이터 모델

### 4.1 쓰는 것

`records`, `record_tags`, `record_photos` (`00-data-model.md` §4.5~4.7이 정본)
+ Supabase Storage 버킷 `record-photos`.

### 4.2 저장 계약 — `upsert_record` RPC

본문과 태그는 **하나의 SQL 함수**로 처리한다. 이유: 태그는 별도 테이블이고, 수정 시
"기존 태그 전체 삭제 후 재삽입"이 필요한데 이것이 클라이언트에서 2회 요청으로 쪼개지면
중간 실패 시 태그가 사라진 기록이 남는다.

**요청**
```
upsert_record({
  record_id:  uuid | null,   // null이면 신규
  station_id: uuid,          // 필수
  visited_on: date,          // 필수, 미래 불가
  mood:       slug | null,
  weather:    slug | null,
  note:       string | null, // 최대 1000자
  tags:       string[]       // 정규화 전 원문. 최대 10개. 서버가 다시 정규화
})
```

**응답**
```
{ record_id: uuid, created: boolean, updated_at: timestamptz }
```

**서버 측 검증 (클라이언트 검증을 신뢰하지 않는다)**

| 검증 | 실패 코드 |
|---|---|
| 호출자가 커플 멤버 | `NOT_IN_COUPLE` |
| (수정 시) 대상 기록이 내 커플 소유 | `RECORD_NOT_FOUND` — 남의 기록인지 없는 기록인지 구분하지 않는다 |
| `station_id`가 존재 | `STATION_NOT_FOUND` |
| `visited_on <= 오늘` | `INVALID_DATE` |
| `mood`/`weather`가 허용값 | `INVALID_ENUM` |
| `note` 길이 | `NOTE_TOO_LONG` |
| 태그 개수·길이 | `INVALID_TAGS` |

**동작**
- 신규: `records` INSERT (`couple_id = current_couple_id()`, `author_id = auth.uid()`)
- 수정: `records` UPDATE (`author_id` 불변, `last_edited_by = auth.uid()`)
- 태그: 해당 `record_id`의 `record_tags` 전 행 삭제 → 정규화 후 재삽입

### 4.3 사진 저장 계약

RPC로 묶지 않는다. 파일 업로드는 시간이 오래 걸려 트랜잭션에 넣을 수 없다.

1. 클라이언트가 `photo_id`(uuid)를 생성한다.
2. Storage에 `{couple_id}/{record_id}/{photo_id}.{ext}`로 업로드한다.
3. 성공한 것만 `record_photos`에 INSERT한다 (`couple_id`는 트리거가 채운다).
4. `sort_order`는 클라이언트가 지정한 최종 순서를 그대로 보낸다.

**수정 시 삭제**: `record_photos` 행 삭제 → Storage 객체 삭제.
Storage 삭제가 실패해도 사용자에게는 성공으로 보인다 (DB 행이 없으면 화면에 안 뜬다).
고아 객체는 배치가 정리한다 (`00-data-model.md` §4.6).

### 4.4 RLS로 보장할 접근 범위

| 대상 | 정책 |
|---|---|
| `records` INSERT | `couple_id = current_couple_id()` **AND** `author_id = auth.uid()` |
| `records` UPDATE | `couple_id = current_couple_id()`. `author_id` 변경은 트리거가 차단 |
| `record_tags`, `record_photos` | `couple_id = current_couple_id()` |
| Storage 업로드 | 경로 첫 세그먼트 = `current_couple_id()`. **다른 커플 폴더에는 쓸 수 없다** |
| Storage 삭제 | 동일 |

> 이 화면은 **쓰기가 발생하는 유일한 지점**이므로 RLS 검증의 초점이다. 특히 Storage
> INSERT 정책이 빠지면, 커플 A가 커플 B의 폴더에 파일을 올려 용량을 소진시키거나
> 콘텐츠를 주입할 수 있다. 읽기 정책만 걸고 쓰기 정책을 잊는 것이 전형적인 실수다.

| 수정 초기 로딩 | 폼 전체 스켈레톤. 기존 사진은 썸네일 자리 확보 후 순차 로드 |
| 입력 중 | 저장 버튼 활성. 변경 감지 플래그 on |
| 검증 실패 | 해당 필드 인라인 에러 + 첫 에러 필드로 스크롤·포커스 |
| 저장 중 (본문) | 버튼 스피너, 폼 비활성 |
| 저장 중 (사진 업로드) | 진행률 "2/3 업로드 중". 이때 **취소 버튼은 제공하지 않는다** (본문은 이미 저장됨) |
| 저장 성공 | 기록 상세로 이동 + 토스트 "기록을 저장했어요" |
| **부분 성공** (본문 O, 사진 일부 X) | 기록 상세로 이동 + 경고 토스트 "사진 1장을 올리지 못했어요". 상세 화면에 재시도 진입점 |
| 저장 실패 (본문) | 폼에 머무름 + 상단 에러 배너 + 입력값 전부 보존 |
| 삭제된 기록 수정 시도 | 모달 "이 기록은 삭제되었어요. 새 기록으로 저장할까요?" |
| 오프라인 | 저장 버튼 비활성 + 사유 표시. 입력은 계속 가능 |

**임시 저장(초안)**: 폼 내용은 저장 실패·앱 종료에 대비해 로컬에 보관하고, 같은 진입
지점으로 다시 들어오면 "작성 중이던 내용이 있어요. 이어서 쓸까요?"를 제안한다.
사진 파일은 로컬 초안에 포함하지 않는다 (용량 문제). 초안은 저장 성공 시 삭제한다.

## 6. 비기능 요구사항

- **저장 응답**: 본문+태그 RPC p95 500ms 이하.
- **업로드**: 사진 1장(리사이즈 후 ~1.5MB) 업로드가 4G에서 5초 이내. 10장 동시 업로드 시
  동시 요청은 **2~3개로 제한**한다 (모바일에서 전량 병렬은 실패율을 올린다).
- **클라이언트 리사이즈**: 10장 처리에 메인 스레드를 3초 이상 붙잡지 않는다.
- **입력 지연**: 일기 입력·태그 입력에서 키 입력 반응 지연 50ms 이하 (자동완성 쿼리는 디바운스).
- **접근성**:
  - 감정·날씨 토글은 `radiogroup` 역할 + 각 항목에 텍스트 레이블(이모지만 두지 않는다).
  - 태그 칩 추가/삭제는 `aria-live`로 알린다.
  - 사진 순서 변경은 드래그 외에 **버튼 방식 대안**을 반드시 제공한다 (드래그만 있으면
    키보드·스크린리더 사용자가 대표 사진을 정할 수 없다).
  - 모든 입력에 연결된 `<label>`. 날짜는 네이티브 date 입력 동작을 보장.
- **모바일**: 키보드가 올라와도 저장 버튼과 현재 입력 필드가 가려지지 않는다.
- **브라우저**: `03-line-map.md` §6과 동일.

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 역 상세에서 진입, When 작성 화면이 열리면, Then 역은 채워져 있고 날짜는 오늘이며 저장 버튼이 활성이다.
- **AC-02** Given 역만 선택하고 나머지를 전부 비운 상태, When 저장하면, Then 성공한다 (감정·날씨·사진·일기·태그 모두 선택 항목임을 검증).
- **AC-03** Given 감정 "설렘"을 선택한 상태, When 같은 아이콘을 다시 탭하면, Then 선택이 해제되고 저장 시 `mood`가 null이다.
- **AC-04** Given 날짜 선택기, When 내일을 고르려 하면, Then 선택할 수 없다.
- **AC-05** Given 태그 입력에 `"  #카페  "` 입력 후 Enter, When 칩을 보면, Then `카페` 칩 1개가 생기고 저장 후 `tag_norm='카페'`다.
- **AC-06** Given 태그 `카페`가 이미 있는 상태, When 다시 `카페`를 입력하고 Enter, Then 칩은 1개로 유지되고 에러가 나지 않는다.
- **AC-07** Given 태그 10개, When 11번째를 추가하려 하면, Then 추가되지 않고 상한 안내가 뜬다.
- **AC-08** Given 12MB 사진 선택, When 추가하면, Then 거부되고 안내가 뜨며 다른 사진은 유지된다.
- **AC-09** Given 4,000×3,000 px 사진 업로드, When Storage 객체를 확인하면, Then 긴 변이 2,048px 이하이고 EXIF GPS가 없다.
- **AC-10** Given 사진 3장 중 2번째만 업로드 실패, When 저장이 끝나면, Then 기록은 저장되어 있고 사진 2장이 붙어 있으며 실패 안내가 표시된다.
- **AC-11** Given 사진 순서를 바꿔 저장, When 역 상세 카드를 보면, Then 첫 번째로 옮긴 사진이 대표 썸네일이다.
- **AC-12** Given 상대가 작성한 기록, When 내가 수정해 저장하면, Then 성공하고 `author_id`는 상대 그대로, `last_edited_by`는 나로 기록된다.
- **AC-13** Given 수정 화면에서 사진을 삭제하고 **저장하지 않고 나가면**, Then 사진은 그대로 남아 있다.
- **AC-14** Given 입력 중 뒤로가기, When 변경사항이 있으면, Then 이탈 확인 모달이 뜬다.
- **AC-15** Given 저장 요청이 네트워크 오류로 실패, When 화면을 보면, Then 일기·태그·선택값이 모두 그대로 남아 있고 재시도할 수 있다.
- **AC-16** Given 커플 A 사용자, When 커플 B의 Storage 경로로 업로드를 시도하면, Then Storage 정책에 의해 거부된다.
- **AC-17** Given 커플 A 사용자, When `upsert_record`에 커플 B의 `record_id`를 넘기면, Then `RECORD_NOT_FOUND`가 반환된다.
- **AC-18** Given 기록 저장 성공, When 노선도로 이동하면, Then 해당 역에 스탬프가 반영되어 있다 (방문 집계 미캐시 검증).
- **AC-19** Given 키보드만 사용, When 폼을 조작하면, Then 감정·날씨 선택, 태그 추가/삭제, 사진 순서 변경이 모두 가능하다.

> ✅ **결정 완료 (2026-08-25) — HEIC/HEIF 사진 처리**: **(b) 브라우저가 디코딩 가능할 때만

> (iOS Safari처럼) 디코딩할 수 있으면 성공적으로 JPEG/WebP로 재인코딩되어 저장되고, 디코딩
> 못 하는 브라우저(Android Chrome 등)에서는 캔버스 처리가 실패하므로 그 시점에 "이 사진
> 형식은 지원되지 않아요. 다른 사진을 선택하거나 카메라 설정에서 '호환성 우선(JPEG)'
> 모드로 바꿔주세요" 같은 안내로 거부한다. 즉 새로운 코드 경로가 아니라 **기존 F-18
> 파이프라인의 실패 케이스에 안내 문구를 추가하는 것**으로 (b)를 구현할 수 있어, 번들
> 증가 없이 iOS 사용자 대부분(HEIC 원본을 그대로 올려도 통과됨)을 커버한다. 참고로 iOS는
> 기본 설정("자동" 모드)에서 웹 업로드 시 HEIC을 JPEG로 자동 변환해 보내는 경우가 많아,
> 실제로 원본 HEIC이 그대로 도달하는 비율은 우려보다 낮다. (a) 전면 거부는 이 자동 완화
> 효과를 무시하는 과도한 제약이고, (c) 라이브러리 도입은 이미 캔버스 파이프라인이 하는
> 일을 중복 구현하는 비용이라 기각했다.

> ✅ **결정 완료 (2026-08-25) — 업로드 크기 상한(10MB / 2,048px / 1.5MB) 근거**: **세 값
> 모두 그대로 유지**하고, 근거를 명시한다. 스마트폰 카메라 원본은 보통 3~8MB 수준이라
> 10MB는 대부분의 촬영본을 통과시키면서 파노라마·초고화소 등 극단적 이상치만 걸러내는
> 여유값이다. 2,048px는 모바일 화면 표시폭(DPR 3배 기준 실사용 표시폭을 넉넉히 상회)과
> 기록 상세 전체화면 뷰어 모두에서 화질 손실이 체감되지 않는 상한이며, 이 서비스가
> 인쇄물 수준 해상도를 요구하지 않는다. 1.5MB 목표는 §6의 "4G에서 5초 이내 업로드"
> 목표를 만족하는 크기다. 세 값은 임의로 고른 게 아니라 "촬영 관행 × 표시 해상도 ×
> 업로드 속도 목표"의 교차점에서 역산한 값이라는 것이 확정의 근거다.

> ✅ **결정 완료 (2026-08-25) — 초성 검색(F-08) 지원 범위**: **클라이언트 캐시에서
> 필터링한다.** 서버(Postgres) 측 전용 인덱스·컬럼은 만들지 않는다.
>
> **근거**: 역 마스터는 수도권 기준 약 700행, 전국 확장 시에도 약 1,100행 수준이라(§9가
> 이미 이 규모를 스스로 언급) 클라이언트가 이미 캐시해 둔 마스터 전체를 순회하며 초성을
> 비교해도 체감 지연이 없다. 서버에 별도 인덱스 컬럼을 만들면 적재 배치·RLS·캐시 무효화
> 로직이 하나씩 늘어나는데, 얻는 성능 이득이 이 규모에서는 없다 — `CLAUDE.md`의 "나중에
> 쓸 것 같아서 만드는 최적화 금지" 원칙과도 일치한다.

> ✅ **결정 완료 (2026-08-25) — 글자 수 카운터 80% 노출 시점**: **80%(800/1,000자)를
> 그대로 유지**한다.

> **근거**: F-24의 취지는 "항상 카운터를 띄우면 짧게 써야 한다는 압박을 준다"는 것이므로,

> 사용자가 절대 도달하지 않는 지점(짧은 일기가 압박 없이 자유롭게 써지는 구간)과, 실제로

> 이다. 더 정밀하게 조정할 실사용 데이터가 없으므로 임의값이었던 80%를 그대로 확정한다.
