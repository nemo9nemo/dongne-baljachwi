# 커플 프로필 (요약 통계 & 안 가본 역 추천)

> 근거: PRD §4 "프로필 — 커플 요약 통계, 다음에 가볼만한 역 추천",
> §3 "커플 프로필 — 이름·디데이·총 데이트 수·방문 역 수·커버리지 % (P0)",
> "안 가본 역 추천 (P1)", §5.5
> 전제: `00-data-model.md`, `01-auth-couple-link.md`, `02-station-master.md`

## 1. 목적 / 배경

노선도와 타임라인이 "개별 기록"을 보여준다면, 프로필은 **누적된 결과를 한 문장으로 요약**한다.
PRD §2의 페르소나가 기념일에 돌아보는 화면이고, 커버리지 %는 §1이 말한 "빈칸을 채우는 수집의
재미"를 숫자로 만든 장치다.

"안 가본 역 추천"은 이 앱이 **과거 기록 도구를 넘어 다음 데이트를 제안하는 도구**가 되는
유일한 지점이다. PRD §2 시나리오의 마지막 문장이 이것이다 — "프로필 화면에서 다음에
가볼만한 역에 뜬 성수역을 보고 다음 데이트 장소를 정한다."

동시에 이 화면은 **커플 설정의 유일한 위치**다. 이름 변경, 사귄 날 수정, 연결 해제,
로그아웃이 여기서 이뤄진다 (PRD §4에 설정 화면이 별도로 없다).

## 2. 사용자 시나리오

### 2.1 정상 흐름

1. 하단 탭에서 "프로필"을 누른다.
2. 상단에 두 사람의 이름과 **디데이**("함께한 지 372일")가 보인다.
3. 통계 3개가 나열된다: **총 데이트 수 / 방문 역 수 / 커버리지 %**.
4. 그 아래 "다음에 가볼만한 역" 섹션에 역 칩이 최대 4개.
5. "성수" 칩을 탭한다 → 성수역이 선택된 상태로 **기록 작성 화면**이 열린다 (PRD §5.5).
6. 하단에 설정 항목: 내 이름 변경 / 사귄 날 수정 / 로그아웃 / 커플 연결 해제.

### 2.2 예외 흐름

| 상황 | 동작 |
|---|---|
| 기록 0건 | 통계는 모두 0으로 정상 표시(숨기지 않는다). 추천은 폴백 규칙으로 4개 제시 (F-14) |
| 상대 미합류 (멤버 1명) | 이름 자리에 "상대 초대 대기 중" + 초대 코드 다시 보기 진입점 (`01` F-18) |
| 통계 로드 실패 | 통계 카드만 에러 + 재시도. 이름·디데이는 이미 가진 커플 정보로 표시 |
| 추천 로드 실패 | 추천 섹션만 숨기거나 재시도 표시. 통계는 정상 |
| 마스터 미적재 | 커버리지 % 분모가 없다 → **커버리지를 "-"로 표시**한다. 0%로 표시하면 거짓 정보 |
| 추천할 역이 없음 (모든 역 방문) | 축하 문구로 대체 ("수도권을 모두 다녀왔어요!") |
| 오프라인 | 캐시된 값을 stale 표시로 노출. 설정의 파괴적 동작 비활성 |
| 커플 미연결 | 이 화면에 도달하지 않는다 |

### 3.3 안 가본 역 추천 (PRD §5.5)

| ID | 요구사항 | 우선순위 | 비고 |
|----|---------|---------|------|
| F-13 | 기록이 **없는** 역 중 최대 **4개**를 칩으로 제시한다 | Must | PRD §5.5 명시 |
| F-14 | 후보 집합 = `in_mvp_scope` AND `is_active` AND 이 커플 기록 0건 | Must | |
| F-15 | 정렬 규칙 (우선순위 순): ① 이미 방문한 역과 **같은 노선**인 역 우선 ② 그 노선에서 방문 역과의 `seq` 거리가 가까운 순 ③ 동률은 안정적 무작위 | Must | 근거는 아래 "추천 규칙 근거" |
| F-16 | 기록이 0건일 때는 ①②를 적용할 수 없으므로 후보 전체에서 안정적 무작위 4개 | Must | 신규 커플도 빈 섹션을 보지 않는다 |
| F-17 | 무작위 시드는 `couple_id + 오늘 날짜(KST)`다 | Must | 같은 날 새로고침하면 같은 추천, 다음 날은 다른 추천. 매 렌더마다 바뀌면 "고르는 재미"가 아니라 노이즈가 된다 |
| F-18 | 같은 노선에서 연달아 4개가 나오지 않도록, 노선당 최대 2개로 제한한다 | Should | 4칩이 전부 2호선이면 추천의 의미가 약하다 |
| F-19 | 칩 탭 → **기록 작성 화면**이 해당 역으로 채워진 채 열린다 | Must | PRD §5.5 "누르면 바로 그 역의 기록 작성으로 이어진다" |
| F-20 | 칩에 역명과 소속 호선을 함께 표시한다 | Should | 어디쯤인지 감이 와야 선택된다 |
| F-21 | "다시 추천받기" 버튼은 두지 않는다 | Must | F-17의 일간 고정과 모순된다. 매일 바뀐다는 것이 이 섹션의 리듬 |

**추천 규칙 근거**: PRD §5.5는 "전국 역 마스터가 선행되어야 하며, 그전까지는 최근 방문이
뜸해진 역을 우선 보여주는 방식으로 축소해 시작할 수 있다"고 쓴다. 그런데 "최근 방문이
뜸해진 역"은 **이미 방문한 역**이므로 "안 가본 역 추천"이라는 기능명과 모순된다.
마스터 데이터는 `02-station-master.md`로 확보되므로, 축소 대안을 쓰지 않고 원래 정의
("기록이 없는 역")를 그대로 구현한다. 다만 700개 후보에서 무작위로 4개를 뽑으면 강원도
근처 역이 나올 수 있어 쓸모가 없으므로, **생활권 근접성**을 방문 이력에서 추론하는 것이
F-15의 목적이다.

## 4. 데이터 모델

### 4.1 읽는 것

**신규 테이블 없음.**

| 출처 | 내용 |
|---|---|
| `couples` | `started_on`, `status` |
| `couple_members` + `profiles` | 두 사람의 `display_name` |
| `records` | 총 개수 |
| `couple_station_visits` 뷰 | 방문 역 목록 (통계 + 추천 계산 입력) |
| 마스터 캐시 | 역·노선·`seq`·`in_mvp_scope` |

### 4.2 통계 쿼리 계약 — `couple_summary` 뷰

통계 3개를 위해 클라이언트가 여러 쿼리를 조합하지 않도록 뷰 하나로 제공한다.

```
couple_summary {
  couple_id: uuid
  total_records: int        // 총 데이트 수
  visited_station_count: int
  first_visited_on: date | null
  last_visited_on: date | null
}
```

- **커버리지 분모는 이 뷰에 넣지 않는다.** 분모는 커플과 무관한 마스터 상수이고, 클라이언트가
  이미 마스터를 캐시하고 있으므로 로컬에서 센다. 커플별 뷰에 마스터 집계를 조인하면
  매 조회마다 700행 스캔이 붙는다.
- 분모는 마스터 캐시와 함께 `app_settings`에 미리 계산해 실어도 된다
  (`mvp_station_count`). → §9 확인 항목.
- `security_invoker = true` 필수.

### 4.3 추천 계산 위치

**클라이언트에서 계산한다.** 근거:

| 항목 | 서버(SQL 함수) | 클라이언트 |
|---|---|---|
| 필요 데이터 | 이미 서버에 있음 | 마스터(캐시됨) + 방문 목록(수백 행) — **이미 다 가지고 있다** |
| 추가 왕복 | 1회 | 0회 |
| 규칙 변경 비용 | 마이그레이션 | 배포 |
| 규모 한계 | 없음 | 후보 1,100 × 방문 수백 = 수십만 연산. 브라우저에서 수 ms |

전국(1,100역)으로 확장해도 클라이언트 계산이 성립한다. 데이터가 100배가 되는 경우는
지하철 도메인에 존재하지 않는다.

**계산 절차 (계약)**
1. 방문 역 집합 `V` = `couple_station_visits`의 `station_id`
2. 후보 `C` = MVP 범위 활성 역 − `V`
3. `V`가 비었으면 → `C`에서 시드 무작위 4개 (F-16)
4. `V`의 각 역이 속한 노선 집합 `L`을 구한다
5. `C`의 각 역에 점수 부여: 소속 노선이 `L`에 포함되면, 그 노선에서 가장 가까운 방문 역과의
   `|seq 차이|`를 거리로 삼는다. 여러 노선에 속하면 **최솟값**을 쓴다. `L`에 없으면 무한대
6. 거리 오름차순 → 동률은 시드 무작위로 정렬
7. 노선당 최대 2개 제한(F-18)을 적용하며 위에서부터 4개 선택

### 4.4 쓰는 것

| 동작 | 대상 | 정책 |
|---|---|---|
| 이름 변경 | `profiles.display_name` UPDATE | `id = auth.uid()` — **본인 것만** |
| 사귄 날 수정 | `couples.started_on` UPDATE | `id = current_couple_id()` — 둘 다 가능 |
| 연결 해제 | `dissolve_couple()` RPC | `01-auth-couple-link.md` §4.3 |

### 4.5 RLS로 보장할 접근 범위

| 대상 | 범위 | 비고 |
|---|---|---|
| `couples` SELECT/UPDATE | `id = current_couple_id()` | 사귄 날은 공동 정보이므로 양쪽 수정 가능 |
| `couple_members`, `profiles` SELECT | 같은 커플만 | 상대 이름 표시 |
| `profiles` UPDATE | `id = auth.uid()` | **상대 이름은 못 바꾼다.** 커플 내부에서도 개인 소유가 명확한 유일한 필드 |
| `couple_summary` 뷰 | `couple_id = current_couple_id()`, `security_invoker = true` | 누락 시 전 커플의 기록 수·방문 역 수가 노출된다 |
| `couple_station_visits` 뷰 | 동일 | |
| 마스터 | 전원 읽기 | 추천 후보 집합은 공개 데이터 |

> 이 화면은 **커플 단위 집계 수치**를 다룬다. 개별 기록보다 민감도가 낮아 보이지만,
> "언제부터 사귀었는지 / 얼마나 자주 만나는지"는 그 자체로 사적인 정보다. 집계 뷰에
> `security_invoker`가 빠지면 개별 기록은 안 보여도 **모든 커플의 관계 통계가 노출**된다.

## 5. 상태 정의

| 상태 | 화면 |
|---|---|
| 로딩 | 이름·디데이는 커플 정보만 있으면 즉시 표시. 통계 카드와 추천 칩만 스켈레톤 |
| 정상 | 전체 표시 |
| 빈 상태 (기록 0건) | 통계 "0 / 0 / 0%"를 **그대로 표시**한다. 숨기면 다음에 볼 때 갑자기 나타나 혼란. 추천은 폴백으로 4개 |
| 통계 실패 | 통계 카드만 에러 + 재시도 |
| 추천 실패/불가 (마스터 없음) | 추천 섹션 숨김 |
| 커버리지 계산 불가 (분모 0) | "-" 표시. 0%로 표시하지 않는다 |
| 추천 후보 없음 | "수도권을 모두 다녀왔어요!" 축하 표시 |
| 상대 미합류 | 이름 자리에 대기 상태 + 초대 코드 진입점. 통계·추천은 정상 동작 |
| 이름/사귄날 저장 중 | 해당 항목만 비활성 + 스피너. 실패 시 이전 값 복원 + 토스트 |
| 해제 진행 중 | `01` §5 |
| 오프라인 | 캐시 값 stale 표시. 이름 변경·사귄날 수정·해제 비활성 |

## 6. 비기능 요구사항

- **응답 목표**: `couple_summary` 조회 p95 300ms 이하 (기록 5,000행 기준).
- **추천 계산**: 후보 1,100 × 방문 500 규모에서 메인 스레드 점유 50ms 이하.
  넘으면 사전 인덱싱(노선별 역 배열)을 캐시한다.
- **왕복 예산**: 화면 진입 시 2회 (`couple_summary`, `couple_station_visits`).
  커플 정보·프로필은 앱 부팅 시 이미 가지고 있다.
- **정확성**: 기록 추가/삭제 후 프로필에 진입하면 통계가 **즉시 반영**되어야 한다
  (집계를 캐시하지 않는다).
- **접근성**:
  - 통계 수치는 레이블과 함께 읽히도록 구성한다 ("총 데이트 수, 42회").
  - 디데이는 숫자만 크게 두지 말고 텍스트 대안을 함께 제공한다.
  - 추천 칩은 링크/버튼 역할과 "○○역 기록 작성하기"라는 접근 가능한 이름을 갖는다.
  - 연결 해제는 색만으로 위험을 표현하지 않는다.
- **브라우저**: `03-line-map.md` §6과 동일.

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given `started_on`이 2025-08-05이고 오늘이 2026-08-11일 때, When 프로필을 열면, Then 디데이가 372일로 표시된다 (사귄 날을 1일째로 계산).
- **AC-02** Given 기록 42건이 서로 다른 역 30곳에 분포, When 프로필을 열면, Then 총 데이트 수 42, 방문 역 수 30이 표시된다.
- **AC-03** Given 같은 역에 3건의 기록, When 통계를 보면, Then 총 데이트 수는 3 증가하고 방문 역 수는 1만 증가한다.
- **AC-04** Given MVP 범위 활성 역이 712개이고 방문 역이 42개일 때, When 커버리지를 보면, Then 5.9%로 표시된다.
- **AC-05** Given 방문 역 1개 / 전체 712개, When 커버리지를 보면, Then "0%"가 아니라 0.1%(또는 "0.1% 미만")로 표시된다.
- **AC-06** Given 마스터 데이터가 비어 있을 때, When 프로필을 열면, Then 커버리지가 "-"로 표시된다.
- **AC-07** Given 2호선 역들을 여러 번 방문한 커플, When 추천을 보면, Then 추천 4개 중 다수가 2호선 인접 역이다.
- **AC-08** Given 추천 4개, When 각 칩의 노선을 확인하면, Then 같은 노선이 3개 이상 나오지 않는다.
- **AC-09** Given 오늘 추천 목록, When 같은 날 화면을 5번 새로고침하면, Then 추천이 동일하다.
- **AC-10** Given 어제 본 추천, When 날짜가 바뀐 뒤 다시 보면, Then 추천이 달라진다.
- **AC-11** Given 추천에 나온 역, When 그 역에 기록을 작성하고 프로필로 돌아오면, Then 그 역은 더 이상 추천에 나타나지 않는다.
- **AC-12** Given 기록 0건인 신규 커플, When 프로필을 열면, Then 통계는 0으로 표시되고 추천 칩 4개가 정상 표시된다.
- **AC-13** Given 추천 칩 "성수", When 탭하면, Then 기록 작성 화면이 성수역이 선택된 채로 열린다.
- **AC-14** Given 상대가 아직 합류하지 않은 커플, When 프로필을 열면, Then 상대 이름 자리에 대기 상태와 초대 코드 진입점이 보인다.
- **AC-15** Given 프로필, When 내 이름을 바꾸면, Then 저장되고 기록 카드의 작성자 표시에 반영된다.
- **AC-16** Given 프로필, When 상대의 이름 변경을 시도하면, Then 그런 UI가 없고 RLS로도 불가능하다.
- **AC-17** Given 두 사람 중 한 명이 `started_on`을 수정하면, Then 상대의 화면에서도 디데이가 바뀐다.
- **AC-18** Given 커플 A 사용자, When `couple_summary`를 조회하면, Then 커플 A의 행만 반환된다.
- **AC-19** Given 기록을 삭제한 직후, When 프로필을 열면, Then 총 데이트 수가 즉시 1 감소해 있다.
- **AC-20** Given 스크린리더 사용, When 통계 영역을 읽으면, Then 각 수치가 레이블과 함께 읽힌다.

## 9. 미결정 항목

> ✅ **결정 완료 (2026-08-25) — "총 데이트 수"의 정의**: **기록 건수 그대로 유지한다**
> (F-06 변경 없음). "서로 다른 날짜 수"로 바꾸지 않는다.
>
> **근거**: `04-station-detail.md`·`05-record-editor.md` §9가 이미 "같은 역·같은 날 중복
