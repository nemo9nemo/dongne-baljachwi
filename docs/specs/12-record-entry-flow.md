# 기록 작성 흐름 개선 — 재방문 맥락 · 연속 작성 · 촬영일 제안

> 근거: PRD §5.2 "별도 텍스트 필드보다 **입력 마찰이 적어서**, 일기를 짧게 쓰거나 아예 안 쓴
> 기록도 기록다워 보이게 하는 효과", PRD §2 "다음 데이트 장소를 정할 때 아직 안 가본 곳을
> 참고하고 싶어 한다", PRD §1 "시간이 지나면 언제 어디를 갔는지 기억이 흐려진다"
> 전제: `05-record-editor.md`(이 문서는 05를 **대체하지 않고 확장한다**),
> `04-station-detail.md`, `06-record-detail.md`, `00-data-model.md`
>
> **05와의 관계**: 폼의 필드·검증·저장 계약은 전부 `05`가 정본이다. 이 문서는 그 폼의
> **주변 흐름**(작성 전 맥락 제공, 저장 후 이어짓기, 사진 선택 시 날짜 제안)만 정의한다.
> 충돌하는 서술이 있으면 `05`가 우선하고, 이 문서가 명시적으로 `05`의 F-ID를 지목해
> 갱신하는 경우만 예외다.

## 1. 목적 / 배경

`05-record-editor.md` §1은 이 화면을 "데이터가 들어오는 유일한 입구"로 정의하고, 그
설계 원칙을 "입력 마찰 최소화"로 못 박았다. 그런데 지금까지 그 마찰은 **폼 안쪽**에서만
줄여 왔다(필수 입력 2개, 감정·날씨 아이콘, 태그 Enter 입력). 폼 **바깥쪽**의 마찰 셋은
아직 아무도 손대지 않았다.

| # | 마찰 | 지금 상태 | 결과 |
|---|---|---|---|
| 1 | **재방문 시 맥락 부재** | 같은 역에 또 갔는데 지난번에 뭘 했는지 보려면 폼을 버리고 역 상세로 나가야 한다 | 귀찮아서 확인을 건너뛴다 → 같은 태그를 다르게 쓰거나, 같은 카페를 또 "발견"한다 |
| 2 | **몰아쓰기 시 왕복** | 저장하면 기록 상세로 간다(`05` F-03). 다음 기록을 쓰려면 목록 → FAB → 역 검색 → 날짜 선택을 처음부터 반복 | 밀린 3~4건 중 한두 개만 쓰고 포기 → PRD §1의 "장기간 누적" 가치가 깎인다 |
| 3 | **날짜 재입력** | 날짜 기본값이 항상 "오늘"이라, 지난 데이트를 몰아 쓸 때마다 날짜 선택기를 연다 | 위 2와 곱해져서 마찰이 커진다 |

세 마찰 모두 **누적 사용자에게만 보이는 문제**다. 기록 1건을 쓸 때는 아무 문제가 없고,
50건째를 쓸 때부터 이탈로 이어진다. PRD §1이 내세우는 핵심 가치가 정확히 "장기간 누적"
이므로, 이 셋은 부가 기능이 아니라 핵심 가치의 보호 장치다.

## 2. 사용자 시나리오

### 2.1 정상 흐름 — 재방문 맥락 (마찰 1)

1. 홍대입구역 상세에서 "이 역에 기록 추가"를 누른다.
2. 폼이 열리고, 역 필드 바로 아래에 접힌 한 줄이 보인다:
   **"이 역 4번째 방문 · 마지막은 3개월 전 (5월 12일)"**
3. 탭하면 펼쳐지고 최근 3건이 나온다:
   - `5월 12일 😍 #카페 #산책 — 연남동 골목 카페에서...` (지연)
   - `3월 2일 😊 #전시 — 상수 쪽 작은 갤러리...` (나)
   - `1월 14일 😆 #맛집` (지연)
4. "아 저번엔 카페 갔었지" 하고 태그에 "맛집"을 넣는다. 폼은 그대로 유지된 채다.

### 2.2 정상 흐름 — 연속 작성 (마찰 2·3)

1. 7월 12일 성수역 기록을 저장한다 → 기록 상세로 이동(`05` F-03 그대로).
2. 상세 화면 상단에 배너: **"저장했어요 · 이어서 기록 추가"**
3. 누르면 작성 폼이 다시 열린다. **날짜는 7월 12일**(방금 저장한 날짜)로 채워져 있고,
   역은 비어 있으며 역 검색 입력에 포커스가 가 있다.
4. "합정"을 입력해 고르고, 날짜를 7월 19일로 한 번 조정하고, 사진 3장을 올린다.
5. 사진을 올린 순간 날짜 필드 아래에 제안 칩: **"사진 촬영일 7월 19일로 바꾸기"** →
   이미 맞춰놨으므로 무시한다.
6. 저장 → 다시 상세 + 배너. 밀린 4건을 이 리듬으로 끝낸다.
7. 마지막에 뒤로 가면 **연속 작성을 시작하기 전의 목록 화면**으로 돌아간다
   (상세 화면이 4개 쌓여 있지 않다).

### 2.3 예외 흐름

| 상황 | 동작 |
|---|---|
| 이 역에 과거 기록 0건 | 재방문 맥락 영역을 **아예 렌더하지 않는다**. "기록이 없어요" 같은 빈 상태 문구도 두지 않는다 |
| 과거 기록 조회 실패 | 영역을 조용히 숨긴다. 에러 표시도, 재시도 버튼도 두지 않는다 — 폼의 본질(입력·저장)을 방해하지 않는다 |
| 오프라인에서 폼 진입 | 재방문 맥락은 표시하지 않는다(`05` §2.3대로 저장 자체가 불가한 상태다) |
| 수정 모드로 진입 | 재방문 맥락은 표시하되 **수정 중인 기록 자신은 목록에서 제외**한다 |
| 역을 여러 번 바꿈 | 마지막 선택 기준으로만 조회한다(디바운스). 이전 요청 결과가 늦게 도착해도 무시한다 |
| 연속 작성 중 이탈 시도 | `05` F-04(변경 있으면 확인 모달)가 그대로 적용된다. 연속 작성이라고 완화하지 않는다 |
| 연속 작성 폼에서 저장하지 않고 뒤로 | 확인 후 이탈 → 연속 작성 시작 전 목록으로 복귀(직전 기록 상세로 돌아가지 않는다) |
| EXIF 촬영일이 없거나 파싱 실패 | 제안 칩을 띄우지 않는다. 에러 아님 |
| EXIF 촬영일이 미래 | 제안하지 않는다(`05` F 미래 날짜 금지와 정합) |
| 선택한 사진들의 촬영일이 서로 다른 날 | 가장 이른 날짜를 제안하되, "선택한 사진이 여러 날에 걸쳐 있어요" 안내 한 줄을 함께 표시한다. **막지는 않는다** |
| 커플 미연결 | 이 화면에 도달하지 않는다 |

### 2.4 커플 관점에서의 데이터 경계

| 질문 | 답 |
|---|---|
| 재방문 맥락에 상대가 쓴 기록도 나오나? | **나온다.** 커플 공동 아카이브이므로 구분하지 않는다. 다만 각 항목에 작성자 이름을 표시해 "누구의 시선인지"는 잃지 않는다(`06` F-03과 같은 원칙) |
| 새 데이터가 생기나? | **생기지 않는다.** 기존 `records`/`couple_station_visits`를 읽기만 한다 |
| 연속 작성으로 만든 기록의 소유권은? | 일반 기록과 동일하다. `author_id = auth.uid()`, 상대도 수정·삭제 가능(`00` §4.5) |
| 촬영일·EXIF가 서버에 저장되나? | **저장되지 않는다.** 읽기만 하고 버린다. `05` F-19(EXIF 제거)는 그대로 유효하다 |

## 3. 기능 요구사항

### 3.1 재방문 맥락 — "이 역의 지난 발자취"

| ID | 요구사항 | 우선순위 | 비고 |
|----|---------|---------|------|
| F-01 | 작성 폼에 역이 선택되어 있으면, 그 역의 **이 커플 과거 기록 요약**을 역 필드 바로 아래에 표시한다 | Must | 역 필드와 붙여야 "이 역"이라는 맥락이 성립한다 |
| F-02 | 기본 상태는 **접힌 한 줄**이다: `이 역 {N}번째 방문 · 마지막은 {상대표기} ({절대날짜})` | Must | 예: "이 역 4번째 방문 · 마지막은 3개월 전 (5월 12일)". 상대표기만 두면 정확한 날짜를 못 보고, 절대표기만 두면 얼마나 됐는지 감이 안 온다 |
| F-03 | `{N}`은 **지금 쓰는 기록을 포함한 순번**이다(과거 3건이면 "4번째 방문") | Must | 사용자가 지금 만들고 있는 것이 몇 번째인지가 알고 싶은 값이다 |
| F-04 | 한 줄을 탭하면 최근 **최대 3건**이 펼쳐진다. 각 항목: 날짜 / 감정 이모지 / 태그 최대 3개 / 일기 앞 40자 / 작성자 이름 | Must | 3건은 "지난번 + 그 전"을 떠올리기에 충분하고, 폼을 밀어내지 않는 상한이다 |
| F-05 | 펼침 항목에 **사진 썸네일은 넣지 않는다** | Must | 서명 URL 발급이 항목당 추가되고, 저신호 환경에서 폼이 무거워진다. 사진이 보고 싶으면 역 상세가 있다 |
| F-06 | 펼침 항목은 **탭해도 이동하지 않는다**(읽기 전용) | Must | 작성 중 이탈은 `05` F-04의 확인 모달을 부르고 입력 흐름을 끊는다. "참고"가 목적이지 "탐색"이 목적이 아니다 |
| F-07 | 과거 기록이 0건이면 영역 전체를 렌더하지 않는다(빈 상태 문구 없음) | Must | 처음 가보는 역에서 "기록이 없어요"는 정보가 아니라 잡음이다 |
| F-08 | 과거 기록이 3건을 넘으면 펼침 하단에 `이 역 기록 {M}건 모두 보기`를 둔다 | Could | 이건 이동이 허용되는 유일한 지점이다 — 명시적 의도가 있는 탭이므로 `05` F-04 확인 모달을 정상적으로 거친다 |
| F-09 | 역을 바꾸면 요약이 새 역 기준으로 갱신된다. 갱신 중에는 이전 역의 요약을 보여주지 않는다 | Must | 잘못된 역의 과거를 보여주는 것이 아무것도 안 보여주는 것보다 나쁘다 |
| F-10 | 수정 모드에서는 수정 대상 기록 자신을 목록·방문 횟수에서 제외한다 | Must | "이 역 4번째 방문"인데 그중 하나가 지금 이 기록이면 숫자가 어긋난다 |
| F-11 | 조회 실패 시 영역을 숨기고 저장 흐름에 아무 영향을 주지 않는다 | Must | 이 기능은 **보조 정보**다. 실패가 입력을 막으면 안 된다 |

| ID | 요구사항 | 우선순위 | 비고 |

| F-19 | 연속 작성 횟수를 세거나 표시하지 않는다 | Must | 게이미피케이션의 자리는 노선도 스탬프(`03`)다. 입력 폼에 카운터를 붙이면 "더 써야 한다"는 압박이 된다 |

## 4. 데이터 모델

### 4.1 서버 측 변경

**없다.** 신규 테이블·뷰·RPC·RLS 정책이 없다. 세 기능 모두 기존 계약만 쓴다.

### 4.2 재방문 맥락 쿼리 계약

| # | 대상 | 조건 | 반환 |
|---|---|---|---|
| 1 | `couple_station_visits` (`00` §4.9) | `station_id = ?` | `visit_count`, `last_visited_on` |
| 2 | `records` + `record_tags` + `profiles` | `station_id = ?`, `visited_on DESC, id DESC` 상위 3건 | 아래 shape |

```
StationContextItem {
  id: uuid
  visited_on: date
  mood: slug | null
  note_head: string | null      // 앞 40자만 전송
  tags: string[]                // 최대 3개
  author: { id: uuid, display_name: string }
}
```

- `note_head`를 **40자로 자르는 이유**는 대역폭이 아니라 노출 범위다. `04` §4.1이 목록
  응답에서 200자로 자른 것과 같은 논리이며, 여기서는 표시 영역이 한 줄이라 40자면 충분하다.
- **사진 관련 필드를 일절 포함하지 않는다**(F-05). `cover_photo`를 넣지 않는 것이 계약이다.
- 인덱스는 `records(couple_id, station_id)`(`00` §4.5)를 그대로 쓴다. 신규 인덱스 없음.

**왕복 예산**: 폼 진입 시 최대 **+2회**. 단, 역 상세에서 진입한 경우(`04` → `05`)는
직전 화면이 이미 두 값을 모두 갖고 있으므로 **넘겨받아 0회로 시작**하고, 사용자가 역을
바꿀 때만 조회한다.

### 4.3 RLS로 보장할 접근 범위

| 대상 | 정책 |
|---|---|
| `records`, `record_tags` | `couple_id = current_couple_id()` — 폼에서 **임의의 `station_id`를 지정해도** 다른 커플의 과거 기록은 0행이다 |
| `couple_station_visits` 뷰 | 동일 (`security_invoker = true`) |
| `profiles` | 본인 + 같은 커플 |

> 이 화면은 원래 **쓰기 전용 화면**이었다(`05` §4.4). 이 스펙이 처음으로 읽기 경로를
> 추가하므로, 폼에서 나가는 조회도 예외 없이 RLS를 타는지 확인해야 한다. 특히
> "역을 바꾸면 그 역의 과거를 보여준다"는 동작은 **사용자가 임의의 `station_id`를 폼에서
> 지정할 수 있다**는 뜻이므로, 파라미터 검증이 아니라 RLS가 경계임을 다시 못 박는다.

### 4.4 연속 작성 / 촬영일 제안

둘 다 **서버 계약 변경이 없다.** 연속 작성은 `05` §4.2의 `upsert_record`를 그대로 호출하고,
촬영일 제안은 파일을 읽는 클라이언트 로직이라 네트워크 호출 자체가 없다.

## 5. 상태 정의

### 5.1 재방문 맥락 영역

| 상태 | 화면 |
|---|---|
| 역 미선택 | 영역 없음 |
| 조회 중 | 접힌 한 줄 자리에 **높이가 같은 스켈레톤**. 폼 아래 요소가 밀리지 않아야 한다 |
| 과거 0건 | 영역 없음(F-07) |
| 접힘(기본) | 한 줄 요약 + 펼침 어포던스 |
| 펼침 | 최근 3건 + (4건 이상이면) "모두 보기" |
| 조회 실패 | 영역 없음. 에러·재시도 표시 없음(F-11) |
| 역 변경 중 | 이전 역의 요약을 즉시 제거하고 스켈레톤으로 교체(F-09) |
| 오프라인 | 영역 없음 |

### 5.2 연속 작성 배너

| 상태 | 화면 |
|---|---|
| 저장 직후 도달 | 배너 노출. 사진 부분 실패 시(`05` §5) 경고 영역과 **함께** 표시되며, 경고가 위에 온다 |
| 목록에서 진입 | 배너 없음 |
| 배너 탭 | 즉시 폼으로 전환(현재 화면 replace). 로딩 없음 — 신규 폼이라 조회할 것이 없다 |
| 화면 이탈 후 재진입 | 배너 없음(F-14) |

### 5.3 촬영일 제안 칩

| 상태 | 화면 |
|---|---|
| 사진 없음 / EXIF 없음 / 날짜 동일 / 미래 | 칩 없음 |
| 제안 가능 | 날짜 필드 아래 칩 1개 |
| 칩 탭 | 날짜 필드 값이 바뀌고 칩은 사라진다. 취소용 되돌리기는 두지 않는다(날짜 선택기로 언제든 바꿀 수 있다) |
| 사진 목록 변경(추가·삭제) | 제안을 다시 계산한다 |
| 여러 날에 걸침 | 칩 + 안내 한 줄(F-23) |

## 6. 비기능 요구사항

- **재방문 맥락 조회**: p95 **300ms 이하**(커플당 총 기록 5,000행 기준, `04` §6과 동일 목표).
  이 조회가 폼의 첫 입력 가능 시점을 지연시켜서는 안 된다 — **폼은 조회와 무관하게
  즉시 입력 가능**해야 한다.
- **레이아웃 시프트**: 재방문 맥락 영역은 조회 전/후 높이가 같아야 한다(접힌 한 줄 기준).
  `docs/PROGRESS.md` 표7 No.15가 기록한 타임라인 레이아웃 시프트 결함과 같은 유형의
  회귀를 만들지 않는다.
- **역 변경 디바운스**: 역 검색에서 후보를 고른 시점에만 조회한다. 타이핑 중에는 조회하지
  않는다(`05` §6의 "키 입력 반응 지연 50ms 이하"를 깨지 않기 위해).
- **EXIF 파싱 비용**: 사진 1장당 파싱에 **50ms를 넘기지 않는다.** 파일 전체가 아니라
  앞부분(APP1 세그먼트 범위)만 읽는다 — 10장을 선택했을 때 메인 스레드를 붙잡으면
  `05` §6의 "10장 리사이즈에 3초 이상 붙잡지 않는다" 예산을 잠식한다.
- **접근성**:
  - 재방문 맥락의 접힘/펼침은 `aria-expanded`를 가진 버튼이며, 펼침 내용은 목록 구조로
    노출한다. 감정 이모지에는 `05` §6과 동일하게 텍스트 레이블을 붙인다.
  - 연속 작성 배너는 저장 성공 안내와 액션을 겸하므로 `aria-live`로 알린다.
  - 촬영일 제안 칩은 버튼이며, 적용 결과(바뀐 날짜)를 `aria-live`로 알린다.
  - 세 기능 모두 **키보드만으로 도달·조작 가능**해야 한다.
- **브라우저**: `03-line-map.md` §6과 동일.

## 7. 확장 포인트

| 지점 | 지금 | 왜 열어두는가 |
|---|---|---|
| 재방문 맥락의 표시 항목 | 날짜·감정·태그·발췌·작성자 | `StationContextItem` shape 하나만 늘리면 항목이 추가된다. 사진을 넣기로 결정이 바뀌어도 필드 추가로 끝난다 |
| 재방문 맥락의 조회 축 | 역(`station_id`) | "같은 태그의 지난 기록" 같은 축이 생겨도 조회 조건만 바뀌고 표시 컴포넌트는 그대로다 |
| 연속 작성 프리필 규칙 | 날짜만 이월 | 이월 대상이 늘어도(예: 태그) 프리필 객체 하나만 확장된다. 지금 늘리지 않는 이유는 F-16 |
| 진입점 | 기록 상세 배너 | `05` §7이 이미 "진입 경로마다 프리필 파라미터만 다르다"고 정의했다. 이 배너는 네 번째 진입 경로일 뿐 폼은 동일하다 |
| 촬영일 파싱 | `DateTimeOriginal`만 | 다른 메타데이터로 확장하려면 F-25(프라이버시 원칙)를 먼저 재검토해야 한다 — 의도적으로 좁게 잠근 지점이다 |

**만들지 않는 것**: 사진 여러 장을 촬영일별로 **자동 분할해 여러 기록으로 만드는 기능**
(어떤 사진이 어느 기록에 가야 하는지 앱이 알 수 없고, 잘못 나뉘면 되돌리기가 더 비싸다),
작성 폼 안에서의 과거 기록 수정, 재방문 맥락의 필터·정렬, OS 공유 시트 연동(§9).

## 8. 완료 조건 (Acceptance Criteria)

**재방문 맥락**
- **AC-01** Given 홍대입구에 과거 기록 3건, When 그 역으로 작성 폼을 열면, Then "이 역 4번째 방문 · 마지막은 {상대표기} ({날짜})"가 한 줄로 보인다.
- **AC-02** Given 그 상태에서 한 줄을 탭하면, Then 최근 3건이 날짜·감정·태그·발췌·작성자와 함께 펼쳐지고 **사진 썸네일은 없다**.
- **AC-03** Given 과거 기록 0건인 역, When 폼을 열면, Then 재방문 맥락 영역이 화면에 존재하지 않는다(빈 상태 문구도 없다).
- **AC-04** Given 폼에서 역을 A에서 B로 바꾸면, Then 요약이 B 기준으로 갱신되고 갱신 중 A의 내용이 보이지 않는다.
- **AC-05** Given 상대가 작성한 과거 기록, When 펼치면, Then 그 항목에 상대의 이름이 표시된다.
- **AC-06** Given 기존 기록을 수정 모드로 열었을 때, Then 그 기록 자신은 목록에 없고 방문 횟수에도 포함되지 않는다.
- **AC-07** Given 재방문 맥락 조회가 실패하는 상황, When 폼을 보면, Then 영역이 숨겨지고 저장은 정상적으로 동작한다.
- **AC-08** Given 커플 A 사용자, When 커플 B만 기록이 있는 역을 폼에서 선택하면, Then 재방문 맥락 영역이 나타나지 않는다.
- **AC-09** Given 폼을 여는 순간, When 재방문 맥락이 아직 로딩 중이면, Then 일기·태그 등 다른 필드는 이미 입력 가능하고 로딩 완료 후에도 레이아웃이 밀리지 않는다.

**연속 작성**
- **AC-10** Given 기록을 저장해 상세로 이동한 직후, When 화면을 보면, Then "이어서 기록 추가" 배너가 보인다.
- **AC-11** Given 타임라인에서 기존 기록 상세로 진입, When 화면을 보면, Then 배너가 보이지 않는다.
- **AC-12** Given 7월 12일 기록을 저장한 뒤 배너를 탭하면, Then 새 폼의 날짜가 **7월 12일**이고 역은 비어 있으며 역 검색 입력에 포커스가 있다.
- **AC-13** Given 감정·날씨·태그·사진을 채워 저장한 뒤 배너로 새 폼을 열면, Then 그 값들이 모두 비어 있다.
- **AC-14** Given 배너로 연속 3건을 저장한 뒤, When 뒤로가기를 **한 번** 누르면, Then 연속 작성을 시작하기 전의 목록 화면으로 돌아간다.
- **AC-15** Given 연속 작성 폼에 입력한 뒤 뒤로가기를 누르면, Then `05` F-04의 이탈 확인 모달이 뜬다.
- **AC-16** Given 사진 일부 업로드 실패로 저장된 기록, When 상세로 이동하면, Then 실패 경고와 연속 작성 배너가 모두 보이고 경고가 위에 있다.

**촬영일 제안**
- **AC-17** Given 날짜가 오늘인 폼, When 7월 19일에 촬영된 사진을 추가하면, Then "사진 촬영일 7월 19일로 바꾸기" 칩이 보이고 **날짜는 아직 바뀌지 않았다**.
- **AC-18** Given 그 칩을 탭하면, Then 날짜 필드가 7월 19일이 되고 칩이 사라진다.
- **AC-19** Given 7월 19일과 7월 20일에 찍힌 사진을 함께 추가하면, Then 제안 날짜는 **7월 19일**이고 "여러 날에 걸쳐 있어요" 안내가 함께 보인다.
- **AC-20** Given EXIF가 없는 스크린샷을 추가하면, Then 칩이 나타나지 않고 어떤 에러도 표시되지 않는다.
- **AC-21** Given 촬영일이 미래로 기록된 사진, When 추가하면, Then 제안이 표시되지 않는다.
- **AC-22** Given 촬영일 제안을 적용해 저장한 뒤, When Storage 객체의 EXIF를 확인하면, Then GPS를 포함한 EXIF가 남아 있지 않다(`05` AC-09 회귀 검증).
- **AC-23** Given 사진 10장을 한 번에 선택, When 추가하면, Then 촬영일 파싱 때문에 화면이 멈추지 않고 `05` §6의 리사이즈 예산이 유지된다.

>    iPhone이므로, 구현해도 절반은 혜택을 받지 못하는 기능이 된다.
> 3. (a)+(c)는 `docs/decisions/001-tech-stack.md`가 확정한 **"순수 SPA"** 전제를 바꾸는
>    일이다(사실상 PWA 전환). 스펙 문서에서 결정할 사안이 아니라 **ADR이 필요한 결정**이다.
>    또한 `11-offline-photo-cache.md` §9의 콜드 스타트 오프라인 항목과 **같은 결정에
>    묶여 있다** — 서비스워커를 도입한다면 두 기능을 함께 설계해야 한다.
>
> **대신 이번에 채택한 대안**: 원 아이디어의 핵심은 "OS 공유 시트"라는 특정 수단이 아니라
> **"사진을 고르는 순간부터 기록 작성이 시작되게 하라"**는 것이다. 그중 PWA 없이 지금
> 실현 가능한 부분을 F-20~F-26(촬영일 제안)으로 가져왔다 — 사진을 올리면 그 사진이
> 언제 찍혔는지를 앱이 알아채고 날짜를 대신 채워주는 것이, 실제로 사용자가 손으로 하던
> 일 하나를 없앤다. 진입 경로 자체의 단축은 홈 화면 추가(A2HS)로 부분적으로 얻어지지만,
> 이는 별도 기능이 아니라 브라우저 기본 동작이라 스펙 대상이 아니다.
>
> **사용자에게 확인할 것**:
> - Android 사용 비중이 어느 정도인가? (iOS 위주면 이 기능의 기대 효용이 크게 낮아진다)
> - 서비스워커/PWA 전환(= 배포·캐시 무효화 복잡도 증가, ADR-001 개정)을 감수할 의사가
>   있는가? 있다면 `11` §9의 콜드 스타트 오프라인과 **묶어서 한 번에** 판단해야 한다.

> ❓ **미결정 — 재방문 맥락 펼침 항목 수 3건의 적정성(F-04)**
>
> 3건은 "지난번과 그 전전번"을 떠올리기에 충분하다는 판단에서 나온 값이며 실측 근거가
> 없다. 같은 역을 10회 이상 방문한 커플에게 3건이 부족한지는 실사용에서 확인한다.
> F-08("모두 보기")이 탈출구 역할을 하므로 정보 도달 불가 상태는 아니다.

> ❓ **미결정 — 촬영일 제안(F-20)의 우선순위를 Must로 올릴지**
>
> 지금은 Should다. 이 기능은 EXIF 파싱이라는 새 코드 경로를 요구하는 유일한 항목이므로,
> 구현 비용이 예상보다 크거나(라이브러리 도입이 필요하다는 판단이 서면) `05` §6의 성능
> 예산을 위협하면 **이번 범위에서 빼도 나머지 두 기능은 독립적으로 성립한다.**
> 개발자가 비용을 실측한 뒤 planner에게 알려주면 그때 확정한다.
