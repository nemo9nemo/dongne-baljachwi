# 노선도 화면 (기본 화면)

> 근거: PRD §4 "노선도 (기본 화면)", §5.1 "노선도 화면", §3 "노선도 기반 기록 표시 (P0)"
> 전제: `00-data-model.md`, `02-station-master.md`

## 1. 목적 / 배경

이 서비스의 정체성 그 자체다. PRD §1의 배경은 "노선도 위에 다녀온 역을 채워나가는 방식이
실제 데이트 동선과 맞아떨어지고, 빈칸을 채우는 수집의 재미를 준다"는 것이다. 경쟁 서비스
분석(§6)에서도 차별점으로 유일하게 반복되는 것이 "지하철 노선도라는 공간 축"이다.

이게 없으면 이 앱은 "장소 태그가 붙은 커플 다이어리"가 되고, 비트윈·커플 다이어리류와
구분되지 않는다.

핵심 설계 난제는 두 가지다.
1. **도식 좌표를 어디서 관리하는가.** 실제 노선도는 지리적 정확성을 버리고 가독성을 위해
   왜곡한 도식이다. 위경도로 그리면 노선도가 아니라 그냥 지도가 된다. → ADR-003
2. **환승역의 방문 표시.** 한 역이 여러 호선에 동시에 그려진다. 홍대입구에 기록이 있으면
   2호선·경의중앙선·공항철도 세 군데 모두에 스탬프가 찍혀야 하는가? → F-08

## 2. 사용자 시나리오

### 2.1 정상 흐름

1. 로그인 후 하단 탭 기본값으로 노선도 화면에 진입한다.
2. 수도권 전체 노선이 한 화면에 겹쳐 그려진다. 초기 뷰는 전체가 보이도록 맞춰져 있다.
3. 다녀온 역은 **해당 호선 색으로 채워진 스탬프**, 안 간 역은 **빈 원**이다.
4. 2회 이상 방문한 역에는 **숫자 뱃지**가 붙어 있다.
5. 사용자가 손가락으로 확대해 홍대입구 부근을 본다. 확대되면 역 이름 라벨이 나타난다.
6. 홍대입구를 탭한다 → 역 상세 화면으로 이동한다 (`04-station-detail.md`).
7. 뒤로 가면 **직전의 확대/이동 상태가 유지된 채** 노선도로 돌아온다.
8. 상단 셀렉트박스에서 "2호선"을 고른다 → 2호선만 선명하게 남고 나머지는 흐려진다.
9. 헤더의 토글로 "지도 보기"로 전환한다 (`07-map-view.md`).

### 2.2 예외 흐름

| 상황 | 동작 |
|---|---|
| 기록이 0건 (신규 커플) | 노선도는 정상적으로 그려지고 전 역이 빈 원. 하단에 "첫 발자취를 남겨보세요" 안내 |
| 역 마스터 미적재 | 노선도를 그릴 수 없다. "역 정보를 불러오지 못했습니다" + 재시도 |
| 마스터는 있으나 방문 집계 로드 실패 | **노선도는 그린다.** 스탬프 없이 전 역 빈 원 + "방문 정보를 불러오지 못했어요" 배너 + 재시도. 화면 전체를 죽이지 않는다 |
| 도식 좌표가 없는 역 (신규 개통) | 노선도에 표시하지 않는다. 대신 화면 하단에 "노선도에 아직 표시되지 않은 역 N개" 안내를 두고 목록으로 접근 가능하게 한다 (기록이 사라져 보이면 안 됨) |
| 브라우저 새로고침 | 호선 필터는 URL 쿼리로 유지된다(F-15). **뷰포트는 초기 전체 보기로 리셋된다**(F-21 — 보존은 SPA 세션 내 화면 전환에만 적용) |
| 오프라인 | 마스터 캐시가 있으면 노선도는 그린다. 방문 집계는 마지막 캐시를 stale 표시로 노출 |
| 커플 미연결 | 이 화면에 도달하지 않는다 (온보딩으로 리다이렉트, `01` §5) |

## 4. 데이터 모델

### 4.1 읽는 것

| 출처 | 내용 | 형태 |
|---|---|---|
| 정적 자산 (리포지토리) | 노선도 도식 좌표 + 폴리라인 | §4.2 |
| Supabase `station_master_public` 뷰 | 역 `code`/`name_short`/소속 호선 | `02` §6 |
| Supabase `lines` | `code`/`name`/`sort_order`/`color_token` | |
| Supabase `couple_station_visits` 뷰 | `station_id`, `visit_count`, `last_visited_on` | `00-data-model.md` §4.9 |

**쿼리 계약**: 화면 진입 시 Supabase 왕복 **2회** (마스터가 캐시된 경우 1회).
1. `app_settings.master_version` (캐시 검증) — 캐시 히트 시 여기서 끝
2. `couple_station_visits` 전량 (`select station_id, visit_count`) — 커플당 최대 수백 행

방문 집계는 **캐시하지 않는다.** 기록 추가 직후 스탬프가 즉시 반영되어야 하기 때문이다.

### 4.2 노선도 도식 좌표 (정적 자산)

DB가 아니라 **리포지토리에 버전 관리되는 데이터 파일**로 둔다. 근거는 ADR-003.

논리적 shape (파일 포맷은 개발자 결정):

```
{
  "viewBox": { "width": number, "height": number },
  "lines": [
    {
      "lineCode": "L-1002",              // lines.code 와 조인
      "polyline": [[x, y], [x, y], ...], // 도식 좌표계
      "stationCodes": ["S-201", ...]     // 이 선분 위 역 순서
    }
  ],
  "stations": [
    {
      "stationCode": "S-239",            // stations.code 와 조인
      "x": number, "y": number,
      "labelAnchor": "top" | "bottom" | "left" | "right"
    }
  ]
}
```

- 조인 키는 **`code`(문자열 자연키)**이지 uuid가 아니다. uuid는 재적재 시 바뀔 수 있고,
  사람이 좌표 파일을 손으로 편집할 수 없게 만든다.
- **정합성 검증이 필수다**: CI에서 "정적 파일의 모든 `stationCode`/`lineCode`가 DB에
  존재하는가", "DB의 `in_mvp_scope` 역 중 좌표 파일에 없는 것은 무엇인가"를 검사하고
  후자는 경고(빌드 실패 아님 — 신규 개통역이 좌표 작업 전에도 배포를 막으면 안 됨).

### 4.3 쓰는 것

**없다.** 이 화면은 읽기 전용이다.

### 4.4 RLS로 보장할 접근 범위

| 대상 | 범위 |
|---|---|
| `lines`, `stations`, `station_lines`, `station_master_public` | 로그인 사용자 전원 읽기 (`02` §4.7) |
| `couple_station_visits` | **`couple_id = current_couple_id()` 행만.** 뷰는 `security_invoker = true`여야 한다 — 아니면 이 화면이 전 커플의 방문 데이터를 받아온다 |

> 이 화면의 유일한 격리 대상은 **방문 집계**다. 역 목록 자체는 공개 정보다.
> 즉 "다른 커플이 어디 갔는지"는 새어 나가면 안 되고, "홍대입구역이 존재한다"는 상관없다.

## 5. 상태 정의

| 상태 | 화면 |
|---|---|
| 최초 로딩 (마스터 캐시 없음) | 노선도 영역에 스켈레톤. 헤더/탭/셀렉트박스는 즉시 표시(비활성) |
| 마스터 캐시 히트 | 노선도를 **즉시** 그린다 (전 역 빈 원 상태) → 방문 집계 도착 시 스탬프를 채운다 |
| 방문 집계 로딩 중 | 전 역 빈 원. 스탬프 자리에 로딩 표시를 하지 않는다 (700개가 깜빡이면 최악) |
| 빈 상태 (기록 0건) | 전 역 빈 원 + 하단 안내 "첫 발자취를 남겨보세요" (역 검색/선택으로 유도) |
| 마스터 로드 실패 | 노선도 영역 전체를 에러 상태로 대체 + 재시도 버튼 |
| 방문 집계 실패 (부분 성공) | 노선도 정상 + 상단 배너 "방문 정보를 불러오지 못했어요" + 재시도. 탭 이동은 정상 동작 |
| 오프라인 | 캐시된 마스터로 렌더 + "오프라인" 표시. 방문 집계는 마지막 값 stale 표시 |
| 좌표 미보유 역 존재 | 하단에 "노선도에 아직 표시되지 않은 역 N개" 링크 |

## 6. 비기능 요구사항

- **렌더 성능 목표**: 역 **1,100개 + 노선 25개**를 그린 상태에서 팬/줌이 60fps를 유지한다.
  (전국 확장 시의 상한. 수도권 700 기준으로는 여유가 있어야 한다.)
- **성능 설계 제약** (구현 방식은 개발자 몫이지만, 목표 달성을 위해 스펙이 요구하는 것):
  - 팬/줌은 **개별 요소의 좌표를 다시 계산하지 않는다.** 뷰포트 변환 하나로 처리한다.
  - 라벨은 확대 레벨 임계값 이하에서 **DOM에서 제거**한다 (숨김이 아니라).
  - 방문 집계 갱신 시 전체를 다시 그리지 않는다.
- **초기 로드 예산**: 노선도 첫 픽셀까지 4G 기준 2.5초 이내. 정적 좌표 파일은 gzip 후 100KB 이하.
- **접근성**:
  - 노선도는 시각적 표현이므로, 동일 정보에 도달하는 **대체 경로**를 반드시 제공한다 —
    역 검색(이름으로 찾아 역 상세로 이동). 노선도만이 유일한 진입로가 되면 스크린리더
    사용자는 기록을 만들 수 없다.
  - 각 역 요소는 포커스 가능하고 `역명 + 방문 N회 / 미방문`을 읽어준다.
  - 색만으로 방문/미방문을 구분하지 않는다 (채움 vs 테두리라는 형태 차이가 이미 있음).
  - 셀렉트박스는 네이티브 select 동작(키보드 조작)을 보장한다.
- **브라우저**: iOS Safari 16+, Android Chrome 최신 2버전, 데스크톱 Chrome/Safari/Edge 최신 2버전.
- **데스크톱**: 휠 줌, 드래그 팬, 셀렉트박스 키보드 조작이 모두 동작해야 한다 (PRD §1 "데스크톱에서도 동일하게 사용 가능").

## 7. 확장 포인트

| 지점 | 지금 | 이유 |
|---|---|---|
| 도식 좌표 파일 | 수도권 1개 파일 | 전국 확장 시 권역별 파일 분할 + 지연 로드가 가능하도록 파일 단위를 권역으로 잡아둔다. 지금은 분할하지 않는다 |
| 역 심볼 상태 | 방문 / 미방문 / 환승 | 심볼 상태를 데이터에서 파생하는 구조이므로, "추천 역 강조"(`09`)나 "최근 방문" 같은 상태가 추가되어도 렌더 구조 변경이 없다 |
| 필터 축 | 호선 단일 선택 | 필터를 "선택된 노선 집합 → 강조 대상 역 집합"으로 다루면, 후일 태그·기간 필터가 붙어도 같은 흐림 처리 로직을 쓴다. 지금은 호선만 구현 |
| 뷰포트 상태 | 화면 내 보존 (SPA 세션 한정 — 새로고침 시 리셋, F-21) | URL에 담을 수 있는 형태(중심·배율)로 유지하면 후일 공유 링크로 확장 가능. 지금은 URL·스토리지 어디에도 넣지 않는다 |

**만들지 않는 것**: 노선도 편집 UI, 사용자별 노선도 커스터마이징, 3D/애니메이션 전환.

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 로그인·커플 연결 완료, When 앱에 진입하면, Then 기본 화면이 노선도이고 전체 노선이 한 화면에 보인다.
- **AC-02** Given 홍대입구에 기록 1건, When 노선도를 보면, Then 홍대입구가 채워진 스탬프로 표시되고 **2호선·경의중앙선·공항철도 어느 쪽에서 봐도** 방문 상태다.
- **AC-03** Given 성수역 방문 1회, When 노선도를 보면, Then 스탬프는 있고 숫자 뱃지는 **없다**.
- **AC-04** Given 성수역 방문 3회, When 노선도를 **확대해서** 보면, Then 숫자 뱃지 "3"이 표시된다. (2026-08-12 개정: 기본 배율에서는 숫자 대신 방문 횟수 기반 채움 농도로 빈도를 표현한다 — §5.1 참고. 숫자는 라벨과 같은 확대 임계값에서만 나타난다.)
- **AC-05** Given 셀렉트박스에서 "2호선" 선택, When 화면을 보면, Then 2호선은 선명하고 나머지 노선은 흐려진다.
- **AC-06** Given 2호선 필터 적용 상태, When 흐려진 4호선 역을 탭하면, Then 해당 역 상세로 정상 이동한다.
- **AC-07** Given 축소 상태, When 화면을 보면, Then 역 이름 라벨이 표시되지 않는다. When 임계값 이상으로 확대하면, Then 라벨이 나타난다.
- **AC-08** Given 노선도를 확대·이동한 상태에서 **호선 필터를 바꾸지 않은 채**, When 역을 탭해 상세로 갔다가 뒤로 돌아오면, Then 직전 확대·위치가 그대로 복원된다. 하단 탭 전환·지도 보기 왕복으로 떠났다 돌아온 경우도 같다. (**2026-08-21 개정**: 보존 범위를 SPA 세션 내 화면 전환으로 한정. 브라우저 새로고침은 이 AC의 대상이 아니다 — AC-15)
- **AC-09** Given 기록 0건인 신규 커플, When 노선도에 진입하면, Then 전 역이 빈 원이고 첫 기록을 유도하는 안내가 보인다.
- **AC-10** Given 방문 집계 요청이 실패, When 화면을 보면, Then 노선도는 정상 렌더되고 배너로 실패를 알리며 재시도가 가능하다.
- **AC-11** Given 역 1,100개가 렌더된 상태, When 팬/줌을 연속 조작하면, Then 프레임 드랍 없이 부드럽게 동작한다 (성능 프로파일로 검증).
- **AC-12** Given 키보드만 사용, When Tab으로 이동하면, Then 셀렉트박스·지도 토글·역 검색에 도달할 수 있고 역 검색으로 임의의 역 상세에 진입할 수 있다.
- **AC-13** Given 스크린리더 사용, When 역 요소에 포커스하면, Then 역 이름과 방문 여부/횟수를 읽어준다.
- **AC-14** Given 정적 좌표 파일에 DB에 없는 `stationCode`가 있을 때, When CI 검증을 실행하면, Then 실패한다.
- **AC-15** Given 노선도를 확대·이동한 상태, When 브라우저를 새로고침하면, Then 뷰포트는 초기 전체 보기로 리셋된다. And 호선 필터만 URL 쿼리로 유지된다(F-15). **이는 결함이 아니라 §7·F-21에 따른 명세 동작이다.**
- **AC-16** Given "전체" 필터로 확대해 둔 뒤 역 상세로 이동, When 돌아온 시점의 호선 필터가 "2호선"이면, Then 저장된 확대 상태를 복원하지 않고 2호선에 맞춘 자동 뷰포트(F-14)가 적용된다. And 이후 필터를 다시 "전체"로 되돌려도 앞서 확대해 둔 화면은 되살아나지 않고 전체 보기로 맞춰진다(F-21a).

> 단계에서 쓰는 참고 이미지**로 격하해 계속 활용한다(자동 추출 소스로는 채택하지 않음).
> C(LOOM+GTFS)는 이번에도 **채택하지 않는다** — 2026-08-12 결론과 같지만 이번엔 유지보수
> 비용까지 따져도 결론이 바뀌지 않았다는 것까지 확인했다. 전국 확장처럼 규모가 수 배로
> 커져 수작업 자체가 물리적으로 불가능해지는 시점이 오면 C를 다시 검토할 여지는 남겨둔다.
>
> **검증 비용에 대한 별도 판단**: 어느 방법을 택하든 "간격이 자연스러운가, 환승역이 안
> 겹치는가"라는 시각적 정확성은 사람이 봐야 하고 이 비용은 사라지지 않는다(`03` §4.2 정합성
> 검증은 코드 존재 여부만 잡지 미감을 판단하지 않는다). D를 택했다고 이 비용이 줄지는
> 않는다 — 다만 D는 **좌표 오탈자·조인 키 실수 같은 저수준 실수**를 스크립트가 DB에서 직접
> 값을 읽어와 원천 차단하는 부수 효과가 있다.
>
> **신규 개통역 반영 주기·운영 주체와의 연동 (`02-station-master.md` §9)**: 같은 문제의
> 다른 얼굴이라 이번에 같이 정리했다 — 결정 내용은 `02-station-master.md` §9에 기록했다.
> 요지는 "역 마스터 재적재(`stations:load`)와 노선도 좌표 재생성(방법 D의 시드 스크립트)을
> **하나의 운영 이벤트**로 묶는다"는 것이다. 1인 개발 체제라 "운영 주체가 누구인가"는 의미가
> 약해 고정 주기 대신 **트리거 조건**(개통 소식을 인지했을 때)으로 정의했다.
>
> **1차 실행 계획 — 파일럿 우선, 실측 후 확대**: 방법 선택과 무관하게 실제 시간 비용이
> 검증되지 않았으므로, "전부 한 번에 간다"가 아니라 작은 파일럿으로 먼저 실측한다.
>
> 1. **파일럿 대상**: 3호선(44역) 전 구간. 이미 완료된 2호선 파일(본선·성수지선·신정지선)과
>    교대·을지로3가·충무로·종로3가 등 **다수 지점에서 환승 연결이 생겨**, 이 방법에서 가장
>    리스크가 큰 지점인 "환승역이 파일 경계를 넘어 자연스럽게 이어지는가"를 초기에 검증할 수
>    있다. 노선 하나 완주 규모라 파일럿이 끝나면 그대로 배포 가능한 산출물이 된다(버리는
>    작업이 없다).
> 2. **측정 항목**: 스크립트 작성 소요, 3호선 초기 배치 스크립트 실행 1회 소요, 이후 사람이
>    보정한 시간을 **역당 평균 / 환승역당 평균**으로 나눠 기록한다(`docs/PROGRESS.md`에 실측
>    치 반영). 이 숫자로 나머지 노선의 예상 소요를 역산한다 — "전 노선 다 해보니 이만큼
>    걸리더라"가 아니라 사전에 예산을 세울 수 있게 하는 것이 파일럿의 목적이다.
> 3. **파일럿 판정 기준**: 역당 평균 보정 시간이 순수 수작업 대비 눈에 띄게(체감상 뚜렷하게)
>    낮으면 D를 그대로 확대 적용. 별 차이가 없다면(스크립트의 초기 골격이 기대만큼 도움이
>    안 됐다는 뜻) A(순수 수작업 + B 참고 이미지)로 사실상 회귀하되, 스크립트는 "좌표 오탈자
>    방지용 스캐폴딩"으로만 남긴다 — 두 결론 모두 이번 파일럿에서 확정한다.
> 4. **확대 우선순위 (파일럿 통과 시)**: 서울 1~9호선(2호선 완료·3호선 파일럿 후)을 1차
>    완주 목표로 잡는다. 순서는 환승 밀집도가 높아 조사 리스크가 큰 노선을 먼저 — 3호선 →
>    4호선/7호선(강남·사당권 환승 밀집) → 나머지 1·5·6·8·9호선 → 광역철도(경의중앙선,
>    수인분당선, 공항철도 등 나머지 24개 노선). **이 우선순위는 `02-station-master.md` §9
>    "MVP 범위의 정확한 경계"(커버리지 % 분모 정의)와는 별개 문제다** — 그 항목은 여전히
>    미결정으로 남겨둔다. 여기서 정하는 것은 "무엇을 언제 그릴지"는 순서일 뿐, "무엇을
>    분모에 넣을지"는 아니다.

> ✅ **결정 완료 (2026-08-31) — 도식의 "노선도다움": 옥토리니어 스냅 후처리 패스를 추가한다
> (B안 채택).** 2026-08-24에 확정한 방법 D(자체 시드 스크립트 + 수작업 보정)는 좌표를
> **어디서 조달할지**를 정한 것이고, 이번 결정은 그렇게 조달한 좌표를 **어떤 도형 규칙으로
> 배치할지**를 정한 것이다. 방법 D를 뒤집지 않는다 — 그 위에 얹는 후처리다.
>
> **문제**: 방법 D의 산출물은 실 위경도를 유사변환(회전+등배율+평행이동)한 것이라 선분
> 각도가 제각각이다. 그 결과 화면이 "노선도"가 아니라 "지도를 축소한 그림"으로 보인다.
> 서울시 공식 노선도를 포함해 실제로 통용되는 도시철도 노선도는 거의 전부 **옥토리니어**
> 도식이다 — 선이 0°/45°/90°로만 꺾인다. §1이 이 서비스의 정체성을 "지하철 노선도라는 공간
> 축"으로 못박은 이상, 도식이 노선도처럼 보이지 않는 것은 미감 문제가 아니라 정체성 문제다.
>
> **조사한 선택지 3가지**
>
> | 안 | 내용 | 판정 |
> |---|---|---|
> | A. 전부 새로 수작업 배치 | 공식 노선도 스타일을 보고 646역을 사람이 옥토리니어로 다시 배치 | **기각.** 2026-08-24 TCO 재검토가 "순수 수작업"을 이미 기각했는데(유지보수 비용이 무한 반복) 그 결론과 정면 충돌한다. ADR-003이 좌표를 정적 자산으로 둔 이유도 재생성 가능성 때문이다 |
> | B. 실좌표 배치 유지 + 45° 스냅 후처리 패스 **(채택)** | 이미 확보한 646역 실좌표 배치(`src/data/line-map/metro-seoul.json`, `scripts/seed-line-map.mjs`)를 그대로 두고, 각 선분 각도를 45° 배수로 스냅하는 **3번째 후처리 패스**를 추가 | **채택.** 기존 `pushOutsideLoop`(루프 관통 회피)·`--resolve-crowding`(밀집 해소)과 같은 성격·같은 급의 휴리스틱이다. 신규 개통역이 생겨도 시드 → 스냅을 다시 돌리면 되므로 방법 D의 유지보수 이점이 유지된다 |
> | C. LOOM(GPL-3.0) + GTFS로 처음부터 생성 | 전용 옥토리니어 생성기로 노선도를 새로 만든다 | **미채택 유지.** 2026-08-24 표의 판단(국내 GTFS 확보 절차 미완료, 원천이 "ID체계 미표준화 파일럿 자료")이 이번에 재확인되지 않았다. 전국 확장으로 수작업이 물리적으로 불가능해지면 다시 검토한다 |
>
> **함께 배제한 것**: MIT 라이선스 오픈소스 SVG(`opensource-seoul-subway-map`)도 조사했으나
> 유지보수가 중단됐고 개별 역을 파싱할 수 없는 통짜 그림이라, "역 코드로 조인해 방문
> 스탬프를 찍는다"(§4.2)는 우리 렌더링 구조에 애초에 쓸 수 없다. 공식 노선도 이미지를
> 트레이싱하는 것은 저작권 문제로 배제한다.
>
> **파일럿 범위**: **2호선(`L-S1102`) 하나만** 먼저 적용해 결과를 확인한 뒤 나머지 32개
> 노선으로 확대한다. 2호선을 고른 이유는 (a) 유일한 순환선이라 "닫힘 제약"이라는 이
> 알고리즘의 가장 어려운 케이스를 처음에 검증할 수 있고, (b) 43역 중 21역이 환승역이라
> 15개 다른 노선과 좌표를 공유해 **환승역 참조 무결성**이라는 두 번째 리스크도 동시에
> 드러나기 때문이다. 파일럿 단계에서는 `--octolinear=<lineCode> --out=<경로>` 로
> **fixture를 덮어쓰지 않고 별도 산출물로만** 만든다.
>
> **환승역 취급**: 2호선만 스냅해도 환승역 21개는 **반드시 움직인다**(움직이지 않으면 45°
> 스냅 자체가 불가능하다 — 21개가 고정점이 되어 어떤 선분도 스냅할 수 없다). 대신 그 역을
> 지나는 **모든** 노선의 `polyline` 꼭짓점을 같은 값으로 동기화해 접합이 끊기지 않게 한다.
> 결과적으로 아직 스냅하지 않은 인접 노선에는 그 역에서 **꺾임(kink)이 생긴다** — 이건
> 파일럿의 알려진 부작용이고, 해당 노선을 스냅하는 라운드에서 해소된다.
>
> **판정 기준(다음 라운드 결정용)**: ① 2호선이 실제 노선도처럼 8각형으로 보이는가,
> ② 역 원(반지름 11) 겹침 쌍이 스냅 전보다 늘지 않는가, ③ `verify:line-map` 통과.
>
> **저작권 확인 (2026-08-31 추가 조사)**: 파일럿 통과 후 33개 노선 전체로 확대하기 전에
> "우리가 만드는 옥토리니어 도식이 남의 저작물을 침해하지 않는가"를 항목별로 확인했다.
> **결론은 문제없음이며, 기존 원칙("공식 노선도 이미지 트레이싱은 배제")은 그대로 유지한다** —
> 이번 조사는 그 원칙이 옳았다는 재확인이지 변경이 아니다.
>
> | 항목 | 확인 결과 |
> |---|---|
> | **원천 좌표 데이터** | `data.go.kr/data/15013205/standard.do`(전국도시철도역사정보표준데이터)를 직접 확인한 결과 **"이용허락범위 제한 없음"**으로 명시돼 있다. 상업적 이용을 포함해 제한이 없다. 우리 좌표는 이 데이터의 위경도를 `scripts/seed-line-map.mjs`가 변환한 것이므로 원천 단계에서 걸리는 게 없다 |
> | **옥토리니어 스타일 자체** | 1933년 Harry Beck의 런던 지하철 노선도가 확립한 **디자인 관례**이고, 이후 도쿄·뉴욕·서울 등 전 세계 교통 시스템이 각자 독자적으로 채택해왔다. 저작권은 아이디어·기법·관례가 아니라 **구체적 표현**만 보호한다 — "선을 45° 배수로만 꺾는다"는 특정 주체가 독점할 수 있는 대상이 아니다. 게다가 우리는 공식 이미지를 트레이싱하지 않고 공개 데이터의 좌표를 알고리즘으로 직접 계산하므로, 표현 자체가 독립적으로 생성된다 |

> ✅ **확대 완료 (2026-08-31) — MVP 33개 노선 646역 전부에 옥토리니어 적용, fixture 반영.**
> 파일럿(2호선 단독)이 판정 기준 3개를 모두 통과해 나머지로 확대했다. 확대 과정에서 파일럿
> 때는 드러나지 않았던 문제 두 가지가 나와 알고리즘 자체를 바꿨다.
>
> **① 환승역 좌표를 무엇이 결정하는가 — "처리 순서"를 없앴다.** 파일럿 방식(노선 하나를
> 스냅하고 환승역이 움직이면 다른 노선 polyline을 따라 옮긴다)을 33번 반복하면 **마지막에
> 만진 노선이 이긴다**. 좌표 파일 구조상 역당 좌표는 언제나 1개라 "노선마다 다른 좌표"가
> 물리적으로 생기지는 않지만(`stations[]`가 역당 한 행), 결과적으로 노선 절반이 옥토리니어가
> 아니게 된다. 그래서 **모든 노선이 동시에 조금씩 움직이는 완화(relaxation)**로 바꿨다 —
> 선분마다 "45°에 놓이려면 양 끝이 어디로 가야 하는가"를 구해 역마다 평균내 감쇠 이동하고,
> 이걸 이동량이 0.02 미만이 될 때까지 반복한다(실측 1,997라운드, 2초). 어느 노선도 특권이
> 없으므로 순서 문제가 정의상 사라진다. 그 뒤 노선을 **환승역 많은 순서**로 돌며 정확한 45°로
> 확정하는 2단계를 얹었다(환승역이 많은 노선일수록 나중에 처리되면 제약에 갇혀 망가진다).
>
> 처음 구현한 "노선별 이상 배치를 통째로 만들어 평균낸다"는 방식은 **발산했다** — 체인을 첫
> 역부터 누적해 다시 그리면 앞쪽 오차가 뒤로 갈수록 증폭돼 56역짜리 5호선의 끝이 수백 px씩
> 휘둘렸다(라운드당 최대 이동 42 → 133). 선분 단위 국소 보정은 양 끝 보정이 크기가 같고
> 부호가 반대라 무게중심이 보존되고, 오차가 확산될 뿐 증폭되지 않는다.
>
> **② 45° 스냅은 도심을 압축해 역을 포갠다.** 스냅만 하면 서로 다른 노선의 역이 **거리 0으로
> 정확히 겹치는** 쌍이 7개 생겼다(겹침 쌍 39 → 57). 밀집 해소를 별도 패스로 두면 그 순간
> 각도가 격자에서 벗어나므로, **완화 반복 안에 반발항으로 넣었다**(26 단위 미만으로 가까워진
> 쌍을 밀어낸다, 격자 해싱으로 O(N²) 회피). 2단계가 다시 겹침을 만드는 구간은 "1단계 좌표 ↔
> 정확한 격자 좌표" 사이를 보간해 겹침이 안 생기는 최대 비율만 쓰고, 그래도 안 되면 그 구간은
> 1단계 결과를 그대로 둔다.
>
> **기존 `--resolve-crowding`(2차 패스)은 이 패스 뒤에 이어 돌리지 않는다.** 실측 결과
> 겹침 쌍 11 → 13, 격자 이탈 56 → 63으로 **양쪽 다 나빠졌고** 2호선 8각형이 13선분 어긋남으로
> 무너졌다. 그 패스는 루프 타원의 특정 반경에 놓인 역만 접선 방향으로 미는 국소 규칙이라
> 옥토리니어 결과와 전제가 맞지 않는다. 루프 좌표를 처음부터 다시 만드는 경우가 아니면
> 이제 쓸 일이 없다(코드는 재생성 경로 때문에 남겨둔다).
>
> **실측 결과 (전/후)**
>
> | 지표 | 스냅 전 | 스냅 후 |
> |---|---|---|
> | 격자(45° 배수)에서 1° 넘게 벗어난 선분 | 713 / 747 | **56 / 747** |
> | 평균 각도 편차 | 11.28° | **0.27°** (최대 11.8°) |
> | 역 원(반지름 11)이 겹치는 쌍 | 39 | **11** (그중 10쌍이 20~22 단위 = 1px 미만 접촉) |
> | 최단 선분 길이 | 0.5 | **21.1** |
> | viewBox | 8252 × 7561 | 8218 × 7686 |
> | 좌표 파일 (gzip) | — | **13.9KB** (§6 예산 100KB) |
>
> 남은 56개 이탈 선분의 대부분은 **확정된 환승역 두 개가 노선상 바로 이웃한 구간**(45곳)이다 —
> 자유도가 0이라 어떤 알고리즘으로도 45°로 만들 수 없고, 양 끝을 옮기려면 다른 노선을 깨야
> 한다. 2호선 본선 43선분은 전부 정확히 격자 위에 있다.
>
> **제외한 노선: 없다.** 33개 전부 반영했다. 부수 효과로 `polyline`에서 역이 아닌 점(2호선
> 루프의 곡선 보간점 87개, 성수/신정지선의 정체불명 접속점 각 1개 — 실측해 보니 분기역이
> 아니라 이전 패스가 남긴 찌꺼기였다)이 사라져, 이제 모든 노선이 `polyline.length ===
> stationCodes.length`(순환선만 +1)를 만족한다.
>
> **남은 것(이번 범위 밖)**: `labelAnchor`는 옮기지 않았다 — 선분 방향이 크게 바뀌었으므로
> 라벨 표시 임계값(F-07) 이상으로 확대했을 때의 라벨 배치는 디자이너가 따로 봐야 한다.
> 성수지선·신정지선은 분기역(성수·신도림)이 `stationCodes`에 없어 **스냅 전에도 후에도 루프와
> 시각적으로 이어지지 않는다** — 이건 좌표가 아니라 역 마스터 쪽 문제라 별도로 다룬다.

> ✅ **결정 완료 (2026-08-25) — "전체" 선택 시 흐림 없이 모두 선명한 게 맞는가**: **유지한다
> (F-01·F-12 변경 없음, "전체" 상태에서는 흐림을 적용하지 않는다).**
>
> **근거**: 실제 서울 지하철 노선도 자체가 이미 20개가 넘는 호선을 동시에 색으로 구분해
> 보여주는 물건이고, 수도권 거주자는 매일 그걸 읽는다 — "다 선명하면 읽기 어렵다"는
> 우려는 이론적으로는 타당하지만, 실물 노선도라는 검증된 선례가 이미 그 가독성 문제를
> 해결하고 있다는 반증이 있다. 방문한 역만 채색하고 나머지를 중립색 선으로 바꾸는 대안은
> "필터를 아무것도 선택하지 않은 기본 상태"에서도 흐림과 비슷한 효과를 적용하는 셈이라,
> PRD §5.1이 명시한 "기본값은 전체 노선을 한 화면에 겹쳐 그리고"(전체 = 왜곡 없는 원래
> 노선도)라는 정의와도 어긋난다. 이 서비스의 정체성이 "지하철 노선도라는 공간 축"(§1)인
> 이상, 기본 화면을 실제 노선도의 색 체계에서 이탈시키는 결정은 근거가 더 강하지 않으면
> 채택하지 않는다. 다만 채도·선 굵기 같은 세부 계조로 가독성을 개선하는 것은 순수 시각
> 디자인 영역이라 이 정책 결정과 무관하게 디자이너가 계속 조정할 수 있다 — 그건 "전체를
> 흐리는가"라는 정책이 아니라 미감 튜닝이기 때문이다.

> ✅ **결정 완료 (2026-08-25) — 역 검색 UI의 위치**: **노선도 헤더에 넣는다.** 별도 화면을
> 만들지 않는다.
>
> **근거**: PRD §4의 하단 탭은 노선도/타임라인/프로필 3개로 고정돼 있고(화면 간 이동
> 규칙), 검색을 위해 4번째 화면이나 별도 탭을 추가하는 것은 이 구조와 충돌한다. 검색은
> "노선도를 대신하는 대체 접근 경로"(§6)라는 목적이 분명하므로, 노선도 화면 자체의 보조
> 진입점(예: 셀렉트박스 옆 검색 아이콘/버튼)으로 두는 것이 자연스럽다. 검색 결과에서 역을
> 선택하면 노선도를 확대·이동시키는 대신 **바로 역 상세로 이동**한다 — 스크린리더
> 사용자가 노선도의 시각적 탐색을 거치지 않고 목적지에 도달하는 것이 이 기능의 존재
> 이유이기 때문이다. 시각적 배치(아이콘 형태, 위치 픽셀)는 디자이너 몫으로 남긴다.

> ✅ **결정 완료 (2026-08-25) — 줌 상한 8배**: **그대로 유지한다.**
>
> **근거**: F-20이 이미 역 탭 영역 최소 44×44 CSS px를 보장하도록 요구하는데, 8배 확대는
> 강남·환승역 밀집 구간처럼 역 간격이 가장 좁은 곳에서도 이 탭 영역이 서로 겹치지 않을
> 만큼 벌어지는 수준이다(라벨 표시 임계값 F-07과도 맞물려, 8배 부근에서 라벨이 명확히
> 읽힌다). 그 이상 확대해도 좌표 자체의 정밀도(정적 좌표 파일의 값 단위)에서 추가로 얻는
> 정보가 없고, 사용자가 같은 화면 안에서 더 많이 패닝만 하게 만든다. 임의값이었던 것은
> 맞지만 뒤집을 근거(사용자 불만·QA 결함 등)가 아직 없으므로, 이번 판단에서는 확정하고
> 실사용 피드백이 쌓이면 재조정한다.

> ✅ **결정 완료 (2026-08-21) — 뷰포트 보존의 범위·우선순위 (F-21, `07` F-12)**
> 구현 단계에서 스펙에 없던 세 지점이 드러나 다음과 같이 확정했다. 더 이상 미결정이 아니다.
>
> 1. **새로고침은 보존 대상이 아니다 (F-21, AC-08 개정 + AC-15 신설).** §7 확장 포인트가
>    뷰포트를 "화면 내 보존 / URL에 넣지 않는다"로 이미 못박았으므로 새로고침 리셋은 사양이지,
>    나중에 고칠 미비점이 아니다. 다만 개정 전 AC-08 문구("역을 탭해 상세로 갔다가 뒤로
>    돌아오면 유지된다")만 읽으면 새로고침도 포함되는 것처럼 보여 QA가 결함으로 올릴 여지가
>    있었다. **AC는 QA가 그대로 체크리스트로 쓰는 문서이므로 범위를 문구에 못박고, 반증
>    조건(AC-15)까지 명시**하는 쪽을 택했다. 공유 링크 요구가 생기면 그때 URL로 승격한다.
> 2. **복원 > 자동 맞춤 (F-09·F-14 단서, `07` F-06).** 사용자가 손으로 만든 화면 상태가
>    시스템의 자동 편의 동작보다 우선한다. 복원해 놓고 곧바로 자동 맞춤이 덮으면 복원 자체가
>    무의미해지기 때문이다.
> 3. **필터가 정확히 같을 때만 복원한다 (F-21·F-21a, AC-16).** 필터가 바뀌면 화면에서
>    강조되는 대상 자체가 달라져, 옛 뷰포트는 "이전 맥락의 화면"이 된다. 이때는 F-14의 자동
>    맞춤이 사용자에게 더 나은 안내다. 필터별 뷰포트를 각각 기억하는 방식은 채택하지 않았다 —
>    되돌아왔을 때 어느 시점의 화면이 나올지 사용자가 예측할 수 없어진다.
