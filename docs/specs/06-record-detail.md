# 기록 상세

> 근거: PRD §4 "기록 상세 — 사진·일기 전문 열람, 수정/삭제/이미지로 저장"
> 전제: `00-data-model.md`, `04-station-detail.md`, `05-record-editor.md`,
> `10-record-card-image.md`

## 1. 목적 / 배경

목록 카드에서는 일기가 2줄로 잘리고 사진도 1장만 보인다. 기록 상세는 **그날 하루를 온전히
다시 보는 화면**이다. PRD §1이 말하는 "시간이 지나면 언제 어디를 갔는지 기억이 흐려진다"는
문제를 실제로 해결하는 지점이 여기다.

동시에 이 화면은 **기록에 대한 모든 파괴적 동작(수정·삭제)의 유일한 관문**이다. 커플 공동
소유 데이터라 "상대가 쓴 걸 내가 지울 수 있다"는 점이 UX적으로 위험하므로, 누가 썼는지를
항상 보이게 하고 삭제에 마찰을 둔다.

## 2. 사용자 시나리오

### 2.1 정상 흐름 — 열람

1. 역 상세 또는 타임라인의 카드를 탭한다.
2. 기록 상세가 열린다. 위에서부터:
   역명 + 날짜 / 감정·날씨 / 사진 / 일기 전문 / 태그 / "○○이(가) 기록함" + 수정 이력
3. 사진을 탭하면 전체화면 뷰어로 확대되고, 여러 장이면 좌우로 넘긴다.
4. 뒤로 가면 원래 목록의 스크롤 위치로 복귀한다.

### 2.2 정상 흐름 — 수정 / 삭제 / 이미지로 저장

- 우상단 메뉴(⋯)를 열면 **수정 / 삭제 / 이미지로 저장** 3개 항목이 나온다 (PRD §4·§5.4).
- **수정** → 작성 폼이 기존 값으로 열린다 (`05-record-editor.md`).
- **삭제** → 확인 모달 → 삭제 후 **이전 화면으로 복귀**하고 목록에서 사라져 있다.
- **이미지로 저장** → PNG 합성 후 다운로드 (`10-record-card-image.md`).

### 2.3 예외 흐름

| 상황 | 동작 |
|---|---|
| 존재하지 않거나 남의 기록 URL | "기록을 찾을 수 없어요" + **진입 출처(역 상세/타임라인)로 이동, 출처 불명이면 타임라인으로 이동**(2026-08-25 결정, §9). **"권한 없음"이라고 말하지 않는다** (RLS상 구분 불가하고, 구분해 알리면 존재 여부가 새어 나간다) |
| 상대가 방금 삭제한 기록을 열람 중 | 화면은 유지되나 수정/삭제 시도 시 "이미 삭제된 기록이에요" + 목록으로 복귀 |
| 사진 로드 실패 | 해당 사진 자리만 재시도 가능한 대체 표시. 일기·태그는 정상 |
| 서명 URL 만료 (장시간 화면 유지) | 이미지 오류 감지 시 자동으로 재발급해 다시 로드 (사용자에게 알리지 않는다) |
| 업로드 실패한 사진이 있는 기록 | 사진 영역에 "올리지 못한 사진 N장" + 재시도 진입점 (`05` F-17) |
| 삭제 도중 실패 | 화면 유지 + 에러 토스트. 기록은 그대로 |
| 오프라인 | 캐시된 텍스트는 보여주되 사진은 실패. 수정/삭제/이미지 저장 비활성 |

## 4. 데이터 모델

### 4.1 읽는 것

**신규 테이블 없음.**

**쿼리 계약 — 화면 진입 시 1회**

```
RecordDetail {
  id: uuid
  station: { id: uuid, code: string, name: string, lines: [{code, name, color_token}] }
  visited_on: date
  mood: slug | null
  weather: slug | null
  note: string | null            // 전문
  tags: string[]                 // 전체, 저장 순서
  photos: [{ id, storage_path, sort_order, width, height }]
  author: { id, display_name }
  last_editor: { id, display_name } | null
  created_at, updated_at: timestamptz
}
```

- 역 정보는 마스터 캐시에서 조인해도 되고 쿼리에 포함해도 된다. **마스터 캐시가 있으면
  `station_id`만 받아 로컬 조인**하는 쪽이 왕복과 페이로드 모두 유리하다.
- 사진의 서명 URL은 **화면에 보이는 것부터 순차 발급**한다. 5장을 한꺼번에 발급하지 않는다.
- `last_editor`는 `last_edited_by IS NOT NULL AND last_edited_by <> author_id`일 때만 채운다.

### 4.2 쓰는 것

| 동작 | 대상 |
|---|---|
| 삭제 | `records` DELETE 1건 → `record_tags`/`record_photos` CASCADE → Storage 객체 삭제 |

수정은 이 화면이 수행하지 않는다 (`05-record-editor.md`로 위임).

**삭제 계약**: 단순 DELETE로 충분하다 (RPC 불필요). RLS가 소유권을 보장하고,
CASCADE가 자식 행을 처리한다. Storage 삭제만 클라이언트가 이어서 호출한다.

### 4.3 RLS로 보장할 접근 범위

| 대상 | 정책 | 이 화면에서의 의미 |
|---|---|---|
| `records` SELECT | `couple_id = current_couple_id()` | **URL에 남의 `record_id`를 넣어도 0행.** 이 화면 보안의 전부 |
| `records` DELETE | 동일 | 남의 기록 삭제 시도는 0행 영향 |
| `record_photos`, `record_tags` SELECT | 동일 | |
| Storage 읽기(서명 URL 발급) | 경로 첫 세그먼트 = `current_couple_id()` | 사진 경로를 알아내도 커플 밖에서는 URL 발급 불가 |
| Storage 삭제 | 동일 | |
| `profiles` SELECT | 본인 + 같은 커플 | 작성자/수정자 이름 표시 |

> **DELETE가 0행에 영향을 줬을 때를 "성공"으로 처리하면 안 된다.** 남의 기록 삭제 시도와
> 이미 삭제된 기록이 모두 0행이므로, 영향 행 수를 확인해 0이면 "이미 삭제되었거나 찾을 수
> 없어요"로 처리하고 목록을 새로고침한다.

## 5. 상태 정의

| 상태 | 화면 |
|---|---|
| 로딩 | 텍스트 영역 스켈레톤. 목록에서 넘어온 경우 카드가 이미 가진 값(날짜·역명·감정·날씨)을 **먼저 그려서** 빈 화면을 만들지 않는다 |
| 정상 | 전체 표시 |
| 사진 로딩 | `width`/`height`로 자리를 미리 잡아 레이아웃 시프트 0 |
| 사진 실패 | 그 자리만 재시도 가능한 대체 표시 |
| 업로드 실패 사진 존재 | 사진 영역 하단에 "올리지 못한 사진 N장 · 다시 시도" |
| 없음/권한 없음 | "기록을 찾을 수 없어요" 전체 화면 + 타임라인으로 이동 버튼 |
| 삭제 중 | 모달 버튼 스피너, 모달 닫기 차단 |
| 삭제 성공 | 이전 화면 복귀 + 토스트 "기록을 삭제했어요" |
| 삭제 실패 (네트워크) | 모달 유지 + 에러. 재시도 가능 |
| 삭제 대상 없음 (0행) | 모달 닫고 "이미 삭제된 기록이에요" + 목록 새로고침 후 복귀 |
| 오프라인 | 텍스트는 캐시 표시, 사진 실패, 메뉴의 파괴적 항목 비활성 |

**부분 성공**: 기록 행은 지워졌는데 Storage 객체 삭제가 실패한 경우 → 사용자에게는 완전한
성공으로 보인다 (F-16). 고아 객체는 배치가 정리한다.

## 6. 비기능 요구사항

- **응답 목표**: 상세 1건 조회 p95 300ms 이하.
- **첫 픽셀**: 목록에서 진입한 경우 **네트워크 대기 없이** 날짜·역명·감정·날씨가 즉시 보인다.
- **이미지 로딩**: 첫 사진은 목록 썸네일을 저해상도 자리표시로 재사용하고 원본으로 교체한다.
  전체화면 뷰어에서만 최대 해상도를 요청한다.
- **서명 URL 유효기간 1시간**. 화면을 오래 열어두는 경우를 위해 만료 감지 후 자동 재발급.
- **접근성**:
  - 사진에 대체 텍스트를 자동 생성한다: "2026년 8월 11일 홍대입구에서 찍은 사진 1/3".
    사용자가 alt를 입력하지 않으므로 최소한의 맥락은 시스템이 제공한다.
  - 전체화면 뷰어는 Esc로 닫히고, 열릴 때 포커스가 뷰어로 이동하며 닫으면 원래 사진으로 복귀한다.
  - 메뉴(⋯)는 키보드로 열고 닫을 수 있으며, 삭제 확인 모달은 포커스 트랩을 갖는다.
  - 삭제 버튼은 파괴적 동작임을 색이 아니라 **텍스트로도** 구분되게 한다.
- **일기 렌더링**: 사용자 입력은 평문으로만 렌더한다(HTML 삽입 금지). 줄바꿈만 보존.
- **브라우저**: `03-line-map.md` §6과 동일.

## 7. 확장 포인트

| 지점 | 지금 | 이유 |
|---|---|---|
| 메뉴 항목 | 수정/삭제/이미지 저장 | 항목이 데이터 기반 목록이면 "공유"(PRD §3 P2)가 추가되어도 화면 구조 변경 없음 |
| `last_edited_by` | 마지막 수정자 1명 | 변경 이력 전체가 필요해지면 별도 이력 테이블 추가. 지금은 만들지 않는다 |
| 사진 뷰어 | 이미지 전용 | 동영상 등이 추가되면 `record_photos`가 아니라 별도 첨부 테이블로 확장 (`00` §7) |
| 태그 칩 → 타임라인 필터 | 단일 태그 | 타임라인이 다중 태그 필터를 지원하게 되어도 진입 파라미터만 배열로 확장 |
| 삭제 | 하드 삭제 | soft delete로 바꾸려면 `records`에 `deleted_at` 추가 + 모든 RLS/뷰 수정이 필요하다. **되돌리기 어려운 결정임을 인지하고 하드 삭제를 택했다** |

**만들지 않는 것**: 댓글, 좋아요, 기록 간 이전/다음 이동, 버전 히스토리, 인쇄 뷰.

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 사진 3장·일기 500자·태그 5개인 기록, When 상세를 열면, Then 사진 3장 전체, 일기 전문(잘림 없이), 태그 5개 전부가 보인다.
- **AC-02** Given 일기에 줄바꿈이 포함된 기록, When 상세를 보면, Then 줄바꿈이 보존된다.
- **AC-03** Given 일기에 `<script>alert(1)</script>` 문자열이 저장된 기록, When 상세를 보면, Then 스크립트가 실행되지 않고 문자 그대로 표시된다.
- **AC-04** Given 상대가 작성한 기록, When 상세를 열면, Then "○○이(가) 남긴 기록"으로 작성자가 표시된다.
- **AC-05** Given 내가 작성하고 상대가 수정한 기록, When 상세를 열면, Then 작성자(나)와 수정자(상대)가 모두 표시된다.
- **AC-06** Given 사진 3장, When 두 번째 사진을 탭하면, Then 전체화면 뷰어가 두 번째 사진으로 열리고 좌우 스와이프로 이동한다.
- **AC-07** Given 상세 화면, When 메뉴를 열면, Then 수정·삭제·이미지로 저장 3개 항목이 보인다.
- **AC-08** Given 상대가 쓴 기록의 삭제 모달, When 모달을 보면, Then 작성자 이름과 역명·날짜가 표시된다.
- **AC-09** Given 삭제 확인, When 삭제하면, Then 이전 목록 화면으로 돌아가고 해당 카드가 사라져 있다.
- **AC-10** Given 그 역의 마지막 기록을 삭제, When 노선도를 보면, Then 해당 역이 빈 원으로 돌아가 있다.
- **AC-11** Given 기록 삭제 후, When Storage를 확인하면, Then 해당 기록의 사진 객체가 남아 있지 않다.
- **AC-12** Given 커플 A 사용자, When 커플 B의 `record_id` URL로 접근하면, Then "기록을 찾을 수 없어요"가 표시되고 권한 관련 문구는 노출되지 않는다.
- **AC-13** Given 상대가 이미 삭제한 기록을 열어둔 상태, When 삭제를 시도하면, Then "이미 삭제된 기록이에요"가 표시되고 목록으로 복귀한다.
- **AC-14** Given 상세를 1시간 이상 열어둔 상태, When 사진을 다시 보면, Then 서명 URL이 자동 재발급되어 정상 표시된다.
- **AC-15** Given 목록 카드에서 진입, When 상세가 열리는 순간을 보면, Then 날짜·역명·감정·날씨가 로딩 없이 즉시 보인다.
- **AC-16** Given 키보드만 사용, When 메뉴를 열어 삭제를 선택하면, Then 모달에 포커스가 갇히고 Esc로 취소할 수 있다.
- **AC-17** Given 태그 칩 탭, When 타임라인이 열리면, Then 그 태그로 필터된 상태다.

## 9. 미결정 항목

> ✅ **결정 완료 (2026-08-15)**: "상대 기록도 삭제 가능"(F-11)을 그대로 유지한다. 수정과
> 동일하게 커플 공동 소유 원칙을 삭제에도 적용 — 작성자 제한 대안은 채택하지 않았다.

> ✅ **결정 완료 (2026-08-25) — 삭제 시 상대 알림 여부**: **알림 기능을 만들지 않는다.**
> 현재 스펙(알림 없음)을 그대로 확정한다.
>
> **근거**: PRD에서 알림류 기능은 전부 P2(기념일 알림)로 유보돼 있고, 이 기능 하나만을
> 위해 실시간/비동기 알림 인프라(푸시, 이메일 등)를 새로 구축하는 비용이 정당화되지
> 않는다. 완전히 무신호는 아니다 — `last_edited_by` 표시(F-04)가 이미 "누가 마지막에
> 고쳤는지"를 투명하게 보여주는 것과 같은 맥락에서, 삭제는 "목록에서 사라짐"이라는 결과
> 자체가 이미 눈에 보이는 신호다. 별도 알림 채널이 필요할 만큼 긴급하거나 놓치면 안 되는
> 정보로 보지 않는다.

> ✅ **결정 완료 (2026-08-25) — 역명 탭 → 역 상세 이동 시 복귀 동선(F-02)**: **역 상세에서
> 진입한 기록은 역명 링크를 숨긴다(비활성화).** 다른 경로(타임라인, 추천 칩 등)로 진입한
> 경우는 F-02 그대로 링크를 노출한다.
>
> **근거**: 이미 있던 화면으로 되돌아가는 링크는 아무 정보도 주지 않고 혼란만 준다.
> 기록 상세는 진입 경로를 이미 알고 있어야 하는 상태다(`25` 항목의 "기록 없음 후 이동
> 대상" 결정과 같은 메커니즘을 재사용 — 진입 시점에 출처를 함께 전달). 새 인프라를
> 추가하지 않고 기존에 필요해진 "진입 출처 추적"을 공유해서 푼다.

> ✅ **결정 완료 (2026-08-25) — 사진 대체 텍스트 자동 생성 문구**: §6에 이미 제시된 형식
> **"{연도}년 {월}월 {일}일 {역명}에서 찍은 사진 {i}/{n}"** 을 그대로 확정한다.
>
> **근거**: 스크린리더 사용자에게 최소한으로 필요한 맥락(언제·어디서·몇 번째 사진인지)을
> 담고 있어 목적에 충분하다. 사진 내용 자체를 설명하려면 이미지 캡셔닝 같은 별도 인프라가
> 필요해 이번 범위를 크게 벗어나고, 감정·날씨까지 문구에 욱여넣으면 문장이 길어져 오히려
> "몇 번째 사진인지" 같은 핵심 탐색 정보를 찾기 어렵게 만든다.

> ✅ **결정 완료 (2026-08-25) — "기록을 찾을 수 없어요" 후 이동 대상**: **진입 출처에 따라
> 분기한다.** 역 상세에서 진입했다면 역 상세로, 타임라인에서 진입했다면 타임라인으로,
> 출처를 알 수 없는 경우(직접 URL 접근 등)는 **타임라인을 기본값**으로 이동한다.
>
> **근거**: 진입 경로가 명확할 때는 사용자가 원래 하던 흐름으로 돌려보내는 것이 가장
> 자연스럽고, 진입 경로가 불분명할 때는 "전체 기록"이라는 가장 넓은 목적지인 타임라인이
> 안전한 폴백이다. 위 F-02 결정과 같은 진입 출처 추적 메커니즘을 그대로 재사용하므로
> 추가 구현 비용이 거의 없다.
