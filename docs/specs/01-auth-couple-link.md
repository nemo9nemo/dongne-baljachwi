# 계정 생성 & 커플 연결

> 근거: PRD §3 "계정/로그인 — 커플 계정 생성 및 연결 (P0)", §8 "초대 코드 방식 확정",
> `docs/decisions/001-tech-stack.md`
> 전제: `00-data-model.md` (스키마·RLS 계약)

## 1. 목적 / 배경

이 앱의 모든 데이터는 "커플"에 귀속된다. 커플이 성립하기 전에는 기록을 저장할 대상이 없다.
프로토타입은 커플 정보 1쌍이 하드코딩되어 있었고(PRD §7), 실 서비스 전환에서 **가장 먼저**
풀려야 하는 것이 이 기능이다.

이게 없으면:
- 사용자는 자기 기록을 다음에 다시 열 수 없다 (새로고침 시 초기화).
- 두 사람이 같은 아카이브를 볼 수 없다 — 서비스의 존재 이유가 사라진다.

소셜 로그인 대신 **이메일+비밀번호 + 초대 코드**를 쓰기로 확정했다(ADR-001). 초대 코드는
"둘만의 공간"이라는 제품 정서와도 맞고, 외부 심사 의존이 없다.

## 2. 사용자 시나리오

### 2.1 정상 흐름 A — 먼저 시작하는 사람 (초대자)

1. 가입 화면에서 이메일·비밀번호 입력 → 가입
2. Supabase가 확인 메일 발송 → 사용자가 메일의 링크 클릭 → 확인 완료
3. 로그인
4. 온보딩 1단계: 내 이름(`display_name`) 입력
5. 온보딩 2단계: "우리 커플 만들기" / "초대 코드 입력하기" 중 선택 → **전자 선택**
6. 사귀기 시작한 날(`started_on`) 선택 → 커플 생성
7. **초대 코드가 화면에 표시된다** (8자, 복사 버튼 + 남은 유효시간)
8. 코드를 상대에게 카카오톡 등으로 전달
9. 앱은 즉시 사용 가능하다. 상단에 "상대 초대 대기 중" 배너가 뜬다.

### 2.2 정상 흐름 B — 나중에 합류하는 사람 (합류자)

1. 가입 → 이메일 확인 → 로그인 → 이름 입력
2. 온보딩 2단계에서 "초대 코드 입력하기" 선택
3. 8자 코드 입력 → 검증 성공
4. "○○님과 연결되었습니다" 확인 화면 → 노선도 진입
5. **초대자가 그동안 쓴 기록이 전부 보인다.** 각 기록에는 작성자 이름이 붙어 있다.

### 2.3 정상 흐름 C — 연결 해제

1. 프로필 → 설정 → "커플 연결 해제"
2. 경고 모달: "해제하면 두 사람 모두 지금까지의 기록을 볼 수 없게 됩니다. 30일 후 영구
   삭제됩니다." + 총 기록 수 표시
3. 확인 문구(상대 이름 또는 고정 문구) 타이핑 요구 → 실행
4. 즉시 온보딩 화면으로 이동. 상대는 다음 요청/재접속 시 해제 사실을 알게 된다.

### 2.4 예외 흐름

| 상황 | 동작 |
|---|---|
| 이메일 확인 전 로그인 시도 | "메일함에서 확인 링크를 눌러주세요" + 재발송 버튼(60초 쿨다운) |
| 이미 가입된 이메일로 가입 | "이미 가입된 이메일입니다" + 로그인/비밀번호 재설정 링크 |
| 잘못된 코드 | "코드를 찾을 수 없어요. 대소문자 없이 8자리를 다시 확인해주세요" |
| 만료된 코드 | "만료된 코드예요. 상대에게 새 코드를 요청해주세요" |
| 이미 사용된 코드 | "이미 사용된 코드예요" |
| 내가 만든 코드를 내가 입력 | "본인이 만든 코드예요. 상대에게 전달해주세요" |
| 이미 2명인 커플의 코드 | "이미 두 사람이 연결된 커플이에요" |
| 내가 이미 커플에 속함 | 온보딩 화면 자체가 뜨지 않는다 (라우팅 단계에서 차단) |
| 코드 입력 실패 반복 | 1시간 내 실패 10회 초과 시 1시간 차단 (F-12) |
| 오프라인 | 인증/연결은 오프라인 동작을 지원하지 않는다. "네트워크 연결을 확인해주세요" + 재시도 |
| 해제 도중 실패 | 트랜잭션이므로 부분 해제 상태는 발생하지 않는다. 실패 시 원상태 유지 + 에러 표시 |

## 3. 기능 요구사항

| ID | 요구사항 | 우선순위 | 비고 |
|----|---------|---------|------|
| F-01 | 이메일+비밀번호 가입/로그인/로그아웃 (Supabase Auth) | Must | 소셜 로그인 없음 |
| F-02 | **이메일 확인을 활성화한다** | Must | 비밀번호 재설정이 유일한 계정 복구 경로이므로 오타 이메일이면 계정 영구 상실. 온보딩 1단계 추가는 감수 |
| F-03 | 비밀번호 최소 8자. 그 외 문자종류 강제 없음 | Must | 강제 규칙은 이탈만 늘리고 실제 강도 기여가 낮음 |
| F-04 | 비밀번호 재설정 (메일 링크) | Must | |
| F-05 | 가입 직후 `profiles` 행 자동 생성 (DB 트리거) | Must | `display_name` 초기값 = 이메일 로컬파트 앞 12자 |
| F-06 | 온보딩에서 `display_name` 입력/수정 (1~12자) | Must | 기록 작성자 표시에 쓰임 |
| F-07 | 커플 생성 시 `started_on`(사귄 날) 필수 입력 | Must | 디데이 계산 기준. 미래 날짜 금지 |
| F-08 | 초대 코드 발급: 8자, 커플당 **동시에 유효한 코드 1개** | Must | 재발급 시 기존 코드 즉시 무효화 |
| F-09 | 코드 문자셋: Crockford Base32 대문자 (`0-9A-Z`에서 `I L O U` 제외, 총 32자) | Must | 손으로 옮겨 적을 때의 혼동(0/O, 1/I/L) 방지 |
| F-10 | 코드 입력은 대소문자 무시, 공백/하이픈 무시, `O→0` `I,L→1` 자동 교정 | Must | 사용자가 잘못 읽어도 통과시킨다 |
| F-11 | 코드 유효기간 **72시간**. 만료 후 재발급 필요 | Must | |
| F-12 | 코드 검증 실패 rate limit: 사용자당 1시간 10회 | Must | 32^8 공간이지만 무차별 대입 자체를 막는다 |
| F-13 | 코드 검증/연결은 `redeem_invite(code)` **SECURITY DEFINER 함수 1개**로만 수행 | Must | 미연결 사용자는 RLS상 초대 행을 SELECT할 수 없다 |
| F-14 | 코드 미리보기(입력 전 상대 이름 확인) 기능은 **제공하지 않는다** | Must | 무차별 대입으로 타인 이름을 수집할 수 있는 경로가 됨. 연결 완료 후 이름을 보여준다 |
| F-15 | 자기 자신 코드 사용 금지 | Must | |
| F-16 | 이미 커플에 속한 사용자는 코드 발급/입력 불가 | Must | DB `UNIQUE(user_id)`로도 이중 방어 |
| F-17 | 초대자는 상대 합류 전에도 기록을 작성할 수 있다 | Must | 합류 시 기존 기록이 그대로 공유된다. 온보딩 이탈 방지 |
| F-18 | "상대 초대 대기 중" 배너 + 코드 재확인/재발급 진입점 | Should | 노선도·프로필 상단 |
| F-19 | 연결 해제는 한쪽이 단독으로 실행 가능 | Must | 상대 동의를 요구하면 실제 상황(이별)에서 영영 해제 불가 |
| F-20 | 해제 시: 멤버십 행 삭제 + `couples.status='dissolved'` + `dissolved_at`/`purge_after` 설정 | Must | 트랜잭션 1건 |
| F-21 | 해제 즉시 양쪽 모두 기록 접근 불가. 데이터는 30일 보존 후 배치 영구 삭제 | Must | `current_couple_id()`가 NULL을 반환하므로 자동 차단 |
| F-22 | 해제 취소(복구)는 **제공하지 않는다** | Must | 취소 권한/충돌 규칙이 복잡해지고 요구사항에 없다. 대신 F-23의 마찰로 오조작을 막는다 |
| F-23 | 해제는 2단계 확인 + 확인 문구 타이핑 필요 | Must | |
| F-24 | 해제 후 두 사람은 각각 새 커플을 만들거나 합류할 수 있다 | Must | 이전 커플 데이터는 이월되지 않는다 |
| F-25 | 세션은 브라우저에 유지되고 자동 갱신된다. 로그아웃 시 로컬 캐시 전부 삭제 | Must | 공용 PC에서 이전 커플 데이터가 남지 않도록 |

## 4. 데이터 모델

`profiles`, `couples`, `couple_members`는 `00-data-model.md` §4.1~4.3이 정본이다.
이 기능이 추가로 정의하는 것은 아래 2개다.

### 4.1 `couple_invites` — 초대 코드

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `id` | uuid | NN | PK |
| `couple_id` | uuid | NN | FK → `couples(id)` ON DELETE CASCADE |
| `code` | text | NN | UNIQUE, 정확히 8자, 문자셋 CHECK (F-09) |
| `created_by` | uuid | NN | FK → `profiles(id)` |
| `expires_at` | timestamptz | NN | 생성 + 72시간 |
| `consumed_at` | timestamptz | | 사용 시각 |
| `consumed_by` | uuid | | FK → `profiles(id)` |
| `revoked_at` | timestamptz | | 재발급으로 무효화된 시각 |
| `created_at` | timestamptz | NN | |

- **부분 유니크 인덱스**: `UNIQUE (couple_id) WHERE consumed_at IS NULL AND revoked_at IS NULL`
  → 커플당 유효 코드 1개를 DB가 강제한다 (F-08).
- 유효 판정: `consumed_at IS NULL AND revoked_at IS NULL AND expires_at > now()`
- 코드 자체를 해시로 저장하지 않는다. 이유: 유효기간 72시간·1회용·rate limit이 있고,
  발급자가 화면에서 코드를 다시 확인할 수 있어야 한다(F-18).

**RLS**
- SELECT: `couple_id = current_couple_id()` — 발급자가 자기 코드를 다시 볼 수 있게
- INSERT/UPDATE/DELETE: **클라이언트 금지.** 함수로만 변경.

### 4.2 `invite_attempts` — 무차별 대입 방어 로그

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `id` | bigint | NN | PK (identity) |
| `user_id` | uuid | NN | FK → `profiles(id)` |
| `succeeded` | boolean | NN | |
| `attempted_at` | timestamptz | NN | |

- 입력된 코드 값은 저장하지 않는다 (다른 커플의 유효 코드가 로그에 남는 걸 막기 위해).
- **RLS: 클라이언트 SELECT/INSERT 모두 금지.** `redeem_invite` 함수 내부에서만 기록.
- 30일 지난 행은 배치가 정리한다.

### 4.3 SQL 함수 계약 (프론트↔백엔드 계약의 핵심)

모두 `SECURITY DEFINER`, `search_path` 고정, 단일 트랜잭션. 프론트는 `supabase.rpc()`로 호출한다.

#### `create_couple(p_started_on date, p_display_name text)` → `{ couple_id, code, expires_at }`

| 검증 | 실패 코드 |
|---|---|
| 로그인 상태 | `UNAUTHENTICATED` |
| 호출자가 어느 커플에도 속하지 않음 | `ALREADY_IN_COUPLE` |
| `p_started_on` <= 오늘 | `INVALID_START_DATE` |
| `p_display_name` 1~12자 | `INVALID_DISPLAY_NAME` |

동작: `profiles.display_name` 갱신 → `couples` 생성(`status='active'`) →
`couple_members(role='owner')` 생성 → 코드 발급.

#### `issue_invite()` → `{ code, expires_at }`

| 검증 | 실패 코드 |
|---|---|
| 호출자가 커플 멤버 | `NOT_IN_COUPLE` |
| 커플 멤버 수가 1명 | `COUPLE_ALREADY_FULL` |

동작: 기존 유효 코드가 있으면 `revoked_at = now()` → 새 코드 발급.
코드 충돌(UNIQUE 위반) 시 최대 5회 재생성 후 `CODE_GENERATION_FAILED`.

#### `redeem_invite(p_code text, p_display_name text)` → `{ couple_id, partner_display_name }`

정규화(F-10)를 함수 내부에서도 다시 수행한다 — 클라이언트 정규화를 신뢰하지 않는다.

| 검증 (순서대로) | 실패 코드 |
|---|---|
| 로그인 상태 | `UNAUTHENTICATED` |
| 1시간 내 실패 10회 미만 | `RATE_LIMITED` (retry_after 초 포함) |
| 호출자가 어느 커플에도 속하지 않음 | `ALREADY_IN_COUPLE` |
| 코드 존재 | `CODE_NOT_FOUND` |
| 미사용·미무효·미만료 | `CODE_EXPIRED` / `CODE_USED` / `CODE_REVOKED` |
| `created_by != auth.uid()` | `OWN_CODE` |
| 대상 커플 `status='active'` | `COUPLE_DISSOLVED` |
| 대상 커플 멤버 1명 | `COUPLE_ALREADY_FULL` |

동작: `invite_attempts` 기록 → `profiles.display_name` 갱신 →
`couple_members(role='partner')` 생성 → `couple_invites.consumed_at/by` 설정.

> `CODE_NOT_FOUND`와 `CODE_EXPIRED`를 구분해 반환한다. 코드는 이미 상대가 알려준 값이라는
> 전제이고, "만료됐으니 새로 받아라"라는 안내가 UX상 훨씬 중요하다. 대신 F-12의 rate limit이
> 열거 공격을 막는다.

#### `dissolve_couple(p_confirm text)` → `{ dissolved_at, purge_after }`

| 검증 | 실패 코드 |
|---|---|
| 호출자가 커플 멤버 | `NOT_IN_COUPLE` |
| `p_confirm`이 지정 확인 문구와 일치 | `CONFIRM_MISMATCH` |

동작: `couples.status='dissolved'`, `dissolved_at=now()`, `purge_after=now()+30일` →
해당 커플의 `couple_members` 전 행 삭제 → 유효 초대 코드 `revoked_at` 설정.
**기록·사진·태그는 이 시점에 건드리지 않는다.**

#### 배치 `purge_dissolved_couples()` (service_role, 일 1회)

`purge_after < now()`인 커플의 Storage 객체 → `records` → `couples` 순으로 삭제.

### 4.4 에러 응답 형태

모든 함수는 실패 시 `{ error_code: text, message: text, retry_after: int|null }`을 던진다.
프론트는 **`error_code`로만 분기**한다. `message`는 로깅·디버깅용이고 화면 문구는
프론트가 소유한다 (다국어·톤 조정을 위해).

| 커플 생성 | 버튼 스피너 | — | `error_code`별 문구 |
| 코드 표시 | — | — | 코드 로드 실패 시 "다시 불러오기" |
| 코드 입력 | 버튼 스피너 | — | 입력 필드 하단 인라인 에러. `RATE_LIMITED`는 남은 시간 카운트다운 표시 |
| 연결 해제 | 버튼 스피너, 모달 닫기 차단 | — | 실패 시 모달 유지 + 에러 |

**부분 성공은 존재하지 않는다.** 모든 연결/해제 동작은 단일 SQL 함수 = 단일 트랜잭션이다.
"커플은 생겼는데 멤버가 안 들어간" 중간 상태가 나올 수 없다.

**세션 만료 처리**: 임의 요청이 401을 반환하면 자동 갱신 1회 시도 → 실패 시 로그아웃 후
로그인 화면으로. 작성 중이던 기록 폼 내용은 로컬에 임시 보관해 재로그인 후 복원한다.

## 6. 비기능 요구사항

- 코드 발급/검증 함수 응답 p95 500ms 이하.
- 코드 공간: 32^8 ≈ 1.1×10^12. 유효 코드 수가 수천 개 수준일 때 무작위 1회 적중 확률은
  10^-9 미만. rate limit(F-12)과 합쳐 실질 위험 없음.
- 코드 화면은 복사 버튼과 **큰 글자 표시**를 제공한다 (전화로 불러주는 사용을 가정).
- 접근성: 코드 입력 필드는 `autocomplete="off"`, `inputmode` 지정, 스크린리더가 8자를
  한 글자씩 읽도록 `aria-label`을 준다. 오류는 `aria-live="assertive"`.
- 브라우저: 최신 2개 메이저 버전의 Chrome/Safari/Edge, iOS Safari 16+, Android Chrome.
- 이메일 확인 링크는 모바일 기본 브라우저에서 열려도 세션이 이어져야 한다.

## 7. 확장 포인트

| 지점 | 지금 | 이유 |
|---|---|---|
| 인증 수단 | 이메일+비밀번호 | Supabase Auth가 소셜 provider를 나중에 추가해도 `profiles`/`couple_members` 구조는 그대로다 |
| 초대 전달 경로 | 코드 문자열만 | 딥링크(`?invite=CODE`)를 붙일 자리는 있으나 지금은 만들지 않는다 — 배포 도메인 확정 후 |
| `couple_members.role` | owner/partner | 지금은 권한 차이가 **없다**(둘 다 모든 기록 수정 가능). 차이가 필요해지면 이 컬럼으로 분기 |
| 해제 정책 | 단독 해제, 30일 보존 | `purge_after`가 컬럼이므로 기간 정책 변경이 데이터 마이그레이션 없이 가능 |
| 기록 내보내기 | 없음 | 해제 전 백업 요구가 확인되면 `10-record-card-image.md`의 클라이언트 렌더링을 확장 |

**만들지 않는 것**: 다중 기기 세션 관리 화면, 초대 코드 이력 조회, 커플 재결합 기능.

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 미가입 이메일, When 가입하면, Then 확인 메일이 발송되고 확인 전에는 로그인이 거부된다.
- **AC-02** Given 가입이 완료된 사용자, When `profiles`를 조회하면, Then 트리거로 생성된 행이 정확히 1개 존재한다.
- **AC-03** Given 커플 미소속 사용자, When `create_couple`을 호출하면, Then 커플·멤버(owner)·초대코드가 한 번에 생성되고 코드는 8자이며 `I L O U`를 포함하지 않는다.
- **AC-04** Given 유효 코드가 이미 1개 있는 커플, When `issue_invite`를 다시 호출하면, Then 이전 코드는 `revoked_at`이 채워지고 이후 그 코드로는 합류할 수 없다.
- **AC-05** Given 코드 `A3F9K2M7`, When 사용자가 `a3f9-k2m7 ` 로 입력하면, Then 정규화되어 성공한다.
- **AC-06** Given 코드 `A3F9K2M0`, When 사용자가 `A3F9K2MO`(숫자 0 대신 알파벳 O)로 입력하면, Then `O→0` 교정으로 성공한다.
- **AC-07** Given 발급 후 73시간 경과, When 코드를 입력하면, Then `CODE_EXPIRED`가 반환된다.
- **AC-08** Given 자기가 발급한 코드, When 본인이 입력하면, Then `OWN_CODE`가 반환되고 멤버 수는 1로 유지된다.
- **AC-09** Given 이미 2명인 커플의 (어떤 경로로든 얻은) 코드, When 3번째 사용자가 입력하면, Then `COUPLE_ALREADY_FULL`이 반환되고 멤버는 2명으로 유지된다.
- **AC-10** Given 1시간 내 실패 10회, When 11번째 시도를 하면, Then `RATE_LIMITED`와 `retry_after`가 반환되고 화면에 남은 시간이 표시된다.
- **AC-11** Given 초대자가 합류 전에 기록 3건을 작성, When 상대가 합류하면, Then 상대의 타임라인에 그 3건이 모두 보이고 작성자 이름이 초대자로 표시된다.
- **AC-12** Given 커플 멤버 2명·기록 다수, When 한쪽이 `dissolve_couple`을 실행하면, Then 양쪽 모두 즉시 기록 조회 결과가 0건이 되고 온보딩 화면으로 이동한다.
- **AC-13** Given 해제된 커플, When 30일이 지나기 전에 DB를 확인하면, Then `records` 행은 여전히 존재한다 (즉시 삭제되지 않음).
- **AC-14** Given 해제 후, When 두 사람이 각각 새 커플을 만들면, Then 둘 다 성공하고 서로의 새 기록은 보이지 않는다.
- **AC-15** Given 로그아웃, When 브라우저 로컬 저장소를 확인하면, Then 이전 커플의 캐시 데이터가 남아 있지 않다.

## 9. 미결정 항목

> ❓ **해제 확인 문구**: "확인 문구를 타이핑"하게 할 때 무엇을 치게 할지 정해지지 않았다.
> (a) 상대 `display_name` — 감정적으로 무겁다 / (b) "연결 해제" 고정 문구 — 무난.
> 현재 스펙은 문구를 특정하지 않고 `p_confirm` 파라미터만 정의했다.

> ❓ **이메일 확인 필수화(F-02)**: 온보딩에 1단계가 추가되고, 메일 도달률 문제(스팸함)로
> 초기 이탈이 생길 수 있다. "MVP는 확인 없이 즉시 사용"으로 뒤집을지 확인 필요.

> ❓ **코드 유효기간 72시간(F-11)**: 상대가 며칠 뒤에 가입할 수도 있다. 7일이 나은지 확인 필요.

> ❓ **`display_name` 변경 정책**: 온보딩 이후 언제든 바꿀 수 있게 할지, 바꾸면 과거 기록의
> 작성자 표시가 소급 변경되는 것(현재 설계상 소급됨)이 의도인지 미확인.

> ❓ **한 사람이 두 기기에서 동시에 코드를 발급**하는 등의 동시성은 부분 유니크 인덱스로
> 막히지만, 이때 UI가 "다른 기기에서 코드가 갱신됨"을 어떻게 알릴지 미정.
