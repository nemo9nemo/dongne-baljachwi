# 타임라인 시점 이동 (연·월 인덱스)

> 근거: PRD §2 페르소나 "**100일, 1주년 같은 기념일에 그동안의 데이트를 돌아보는 걸
> 좋아한다**", PRD §1 "시간이 지나면 언제 어디를 갔는지 기억이 흐려진다"
> 전제: `08-timeline.md`(이 문서는 08을 **대체하지 않고 확장한다**), `00-data-model.md`
>
> **08과의 관계**: 목록 렌더·카드 shape·태그 필터·키셋 페이지네이션은 전부 `08`이 정본이다.
> 이 문서는 그 목록의 **시작 지점을 옮기는 내비게이션 장치** 하나만 정의한다.

## 1. 목적 / 배경

`08-timeline.md` §1은 이 화면을 "회고가 일어나는 화면"으로 정의하고, PRD §2의
"1주년에 그동안을 돌아본다"를 그 근거로 인용했다. 그런데 지금 이 화면에서 **1년 전으로
가는 유일한 방법은 무한 스크롤을 끝까지 내리는 것**이다.

주 1회 데이트를 기록하는 커플이라면 1년 전 기록은 대략 50건 아래에 있고, `08` F-03의
20건 단위 페이지네이션 기준으로 **최소 3번의 추가 로드 + 그만큼의 스크롤**을 거쳐야
닿는다. 3년이 쌓이면 이 비용은 선형으로 늘어난다.

즉 이 화면은 **오래 쓸수록 자기가 내세운 목적(회고)을 수행하기 어려워지는 구조**다.
PRD §1의 핵심 가치가 "장기간 누적"인 이상, 누적될수록 나빠지는 이 성질은 방치할 수 없다.

### 1.1 이것은 "필터"가 아니다 (범위 경계를 먼저 못 박는다)

`08` §7은 **만들지 않는 것**으로 "검색(전문 검색), **날짜 범위 필터**, 감정·날씨 필터,
정렬 변경 UI"를 명시했다. 이 스펙은 그 결정을 뒤집지 않는다.

| | 날짜 범위 필터 (만들지 않음) | 이 스펙의 시점 이동 (만듦) |
|---|---|---|
| 사용자 입력 | 시작일·종료일 두 값 | 없음. 존재하는 달을 **고르기만** 한다 |
| 결과 집합 | 범위 안으로 **좁혀진다** | 좁혀지지 않는다. 여전히 "선택 시점 이전 전부" |
| 상태 | 필터 상태가 유지·조합됨(태그와 곱해짐) | 커서 위치일 뿐. 스크롤하면 그냥 이어진다 |
| 해제 개념 | "필터 해제"가 필요 | 없음. "맨 위로"만 있으면 된다 |

한 문장으로: **결과를 걸러내는 게 아니라, 읽기 시작하는 위치를 옮긴다.**

## 2. 사용자 시나리오

### 2.1 정상 흐름

1. 1주년을 앞두고 타임라인을 연다. 최신 기록부터 20건이 보인다.
2. 헤더의 "기간 이동"을 누른다 → 바텀시트가 열린다.
3. 시트에는 기록이 있는 연도만 나열되고, 각 연도 아래 기록이 있는 달이 건수와 함께 있다.
   ```
   2026   8월(3)  7월(5)  6월(2)  5월(4)  ...
   2025   12월(6) 11월(2) ... 8월(4) ...
   ```
4. "2025년 8월(4)"을 누른다.
5. 시트가 닫히고, 목록이 **2025년 8월의 가장 최근 기록부터** 다시 그려진다.
   스크롤은 맨 위다.
6. 목록 상단에 "최근 기록으로 돌아가기"가 고정되어 있다.
7. 아래로 스크롤하면 2025년 7월, 6월… 평소처럼 이어진다.
8. 카드를 눌러 기록 상세에 갔다 돌아와도 2025년 8월 위치가 유지된다.

### 2.2 예외 흐름

| 상황 | 동작 |
|---|---|
| 기록이 적음(첫 페이지가 20건 미만) | "기간 이동" 진입점을 **표시하지 않는다**(F-10) |
| 기록 0건 | 진입점 없음. `08` §5의 빈 상태 그대로 |
| 시트 조회 실패 | 시트 안에 에러 + 재시도. 목록은 아무 영향 없음 |
| 시트를 열었는데 달이 1개뿐 | 그 달만 표시한다(정상). 이동해도 결과가 같을 뿐 오류가 아니다 |
| 태그 필터가 걸린 상태 | 시트의 달 목록도 **그 태그가 붙은 기록 기준**으로 계산된다(F-06) |
| 점프한 뒤 태그 필터를 바꿈 | 점프가 해제되고 목록이 맨 위(최신)부터 다시 시작한다(F-07) |
| 점프 대상 달의 기록이 그사이 전부 삭제됨 | 그 시점 이전의 다음 기록부터 보여준다. 빈 화면을 만들지 않는다 |
| 오프라인 | 진입점 비활성. 이미 로드된 목록은 `08` §5대로 stale 표시 유지 |
| 커플 미연결 | 이 화면에 도달하지 않는다 |

### 2.3 커플 관점에서의 데이터 경계

- 시트가 세는 달·건수는 **커플 공동 기록 전부**다. 누가 썼는지로 나누지 않는다
  (`00` §4.5의 공동 아카이브 원칙).
- 새로 저장되는 사용자 데이터가 **없다.** 점프 위치는 URL 쿼리(F-08)에만 존재하며
  서버에 남지 않는다 — 즉 **내가 어디를 보고 있었는지가 상대에게 공유되지 않는다.**
  이건 의도된 것이다. 열람 위치는 개인의 것이고, 기록만이 공동의 것이다.

## 4. 데이터 모델

### 4.1 신규 — `couple_record_months()` SQL 함수

**뷰가 아니라 함수로 만든다.** 이유: 태그 필터 반영(F-06)이 필요한데, 뷰에 태그 축을
넣으면 `(월 × 태그)` 조합 행이 생겨 규모가 불필요하게 커지고, 태그 없는 기본 조회에도
`GROUP BY` 축이 하나 더 붙는다. 파라미터 하나를 받는 함수가 두 경우를 모두 덮는다.

```
couple_record_months(p_tag_norm text default null)
  returns table (month date, record_count int)
```

| 항목 | 정의 |
|---|---|
| 반환 `month` | 해당 월의 **1일**(`date_trunc('month', visited_on)::date`) |
| 반환 `record_count` | 그 달의 기록 수 |
| 정렬 | `month DESC` |
| 대상 행 | `records where couple_id = current_couple_id()` |
| `p_tag_norm` 지정 시 | 그 `tag_norm`이 붙은 기록만 집계(`record_tags` EXISTS) |
| 함수 성격 | `STABLE`, **`SECURITY INVOKER`** |
| 빈 결과 | 0행(에러 아님) |

> **`SECURITY DEFINER`로 만들면 안 된다.** `00` D-12가 집계 뷰에 `security_invoker`를
> 요구한 것과 정확히 같은 이유다 — DEFINER면 이 함수가 RLS를 우회해 **전 커플의 기록
> 분포**를 반환한다. 이 함수는 기록 본문을 반환하지 않으므로 사고 규모가 작아 보이지만,
> "이 커플이 몇 년 몇 월에 몇 번 데이트했는가"는 그 자체로 사생활이다.

**인덱스**: 신규 인덱스를 만들지 않는다. `records(couple_id, visited_on DESC, id DESC)`
(`00` §4.5)를 인덱스 스캔으로 훑는 집계이며, 커플당 수천 행 규모에서 충분하다.

### 4.2 목록 조회 계약의 변경

`08` §4.1의 기록 페이지 조회에 **커서 초기값 지정**이 추가될 뿐, 쿼리 형태는 같다.

| 파라미터 | 기존 | 점프 시 |
|---|---|---|
| 커서 | 첫 페이지는 없음(최신부터) | `(visited_on, id) <= ('{선택월 말일}', {최대 id})` 로 시작 |
| 필터 | `tag_norm = ?` (선택 시) | 동일하게 유지 |
| 정렬·개수 | `visited_on DESC, id DESC` / 20 | 동일 |

- 선택한 달의 **말일**을 커서 상한으로 삼으면, 그 달의 가장 최근 기록이 첫 항목이 된다.
  별도 "해당 월 첫 레코드 id 조회" 왕복이 필요 없다.
- 그사이 그 달의 기록이 전부 삭제됐어도 조건이 `<=`이므로 자연스럽게 그 이전 기록으로
  이어진다(§2.2의 "빈 화면을 만들지 않는다"가 이 정의로 자동 충족된다).

### 4.3 쓰는 것

**없다.** 읽기 전용 기능이다.

### 4.4 RLS로 보장할 접근 범위

| 대상 | 정책 |
|---|---|
| `records` | `couple_id = current_couple_id()` — 커서·태그·월 파라미터를 어떻게 조작해도 다른 커플의 기록은 0행 |
| `record_tags` | 동일 |
| `couple_record_months()` | `SECURITY INVOKER`이므로 위 정책이 그대로 적용된다 |

> `08` §4.3이 이미 못 박았듯 **페이지네이션 파라미터 검증은 UX 문제이지 보안 경계가
> 아니다.** 이 스펙은 클라이언트가 지정할 수 있는 파라미터를 하나(시작 월) 더 늘리므로,
> 그 원칙을 다시 확인해 둔다.

## 5. 상태 정의

| 상태 | 화면 |
|---|---|
| 진입점 숨김 | 첫 페이지 20건 미만 또는 오프라인. 헤더에 버튼이 없다(비활성 버튼을 남기지 않는다) |
| 시트 로딩 | 시트가 즉시 열리고 내부만 스켈레톤(연도 2줄 정도). 시트가 열리는 것 자체를 지연시키지 않는다 |
| 시트 정상 | 연도·월·건수 목록 + 현재 위치 강조 |
| 시트 조회 실패 | 시트 안에 "기간 목록을 불러오지 못했어요 · 다시 시도". 목록은 무영향 |
| 시트에 표시할 달이 1개 | 그대로 1개만 표시(에러·빈 상태 아님) |
| 점프 중 | 시트를 먼저 닫고 목록만 스켈레톤으로 교체. `08` §5의 "필터 전환 중"과 같은 처리 |
| 점프 완료 | 목록 상단에 "최근 기록으로 돌아가기" 고정 노출 + 어느 시점인지 알 수 있는 표시 |
| 점프 상태에서 추가 페이지 로딩 | `08` §5 그대로(하단 스피너) |
| "최근 기록으로 돌아가기" 탭 | 점프 해제, 목록 최신부터 재로드, URL에서 `from` 제거, 스크롤 맨 위 |
| 점프 + 태그 필터 동시 | 태그를 바꾸는 순간 점프 해제(F-13). 반대로 점프는 태그를 해제하지 않는다 |
| 오프라인 | 진입점 숨김. 이미 점프한 상태였다면 그 목록을 stale로 유지 |

## 6. 비기능 요구사항

- **응답 목표**: `couple_record_months()` p95 **300ms 이하**(커플당 기록 5,000행 기준).
  기록 50,000건이어도 인덱스 스캔 집계라 선형이며, 이 규모에서 문제가 되면 `08` §7이
  `couple_tag_usage`에 대해 정의한 것과 같은 방식(머티리얼라이즈드 뷰 승격)으로 대응한다.
- **시트 열림 지연**: 탭에서 시트가 보이기까지 **100ms 이내**. 데이터 도착을 기다리지 않는다.
- **점프 응답**: 달 선택에서 목록 첫 픽셀까지 `08` §6의 첫 페이지 목표(p95 300ms)와 동일.
- **왕복 예산**: 타임라인 진입 시 왕복은 `08`의 **2회에서 늘어나지 않는다**(F-15).
  시트를 열 때 1회가 추가된다.
- **레이아웃 시프트**: "최근 기록으로 돌아가기" 고정 영역이 나타나고 사라질 때 목록이
  튀지 않도록 자리를 예약한다. `docs/PROGRESS.md` 표7 No.15의 회귀를 반복하지 않는다.
- **접근성**:
  - 시트는 모달 다이얼로그로 노출하고 **포커스 트랩**을 가지며 Esc로 닫힌다.
  - 연도는 그룹 제목, 각 달은 버튼이고 접근 가능한 이름은 "2025년 8월, 기록 4건"이다.
  - 점프 실행 후 `aria-live`로 알린다: "2025년 8월로 이동했어요. 기록 4건."
  - 진입점과 "최근 기록으로 돌아가기"는 키보드로 도달 가능해야 한다.
  - 건수를 색·크기로만 구분하지 않는다(숫자 텍스트가 이미 있으므로 자연히 충족).
- **브라우저**: `03-line-map.md` §6과 동일.

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 2024~2026년에 걸쳐 기록 60건, When "기간 이동"을 누르면, Then 기록이 있는 연도만 내림차순으로, 각 연도 아래 기록이 있는 달만 건수와 함께 나열된다.
- **AC-02** Given 2025년 3월에 기록이 하나도 없을 때, When 시트를 보면, Then 2025년 목록에 3월이 존재하지 않는다.
- **AC-03** Given 시트를 열었을 때, Then 현재 목록 최상단 카드가 속한 달이 화면 안에 보이고 강조되어 있다.
- **AC-04** Given "2025년 8월(4)"을 선택하면, Then 시트가 닫히고 목록 첫 항목이 2025년 8월의 가장 최근 기록이며 스크롤은 맨 위다.
- **AC-05** Given 점프한 상태에서 아래로 스크롤하면, Then 2025년 7월, 6월 순으로 20건 단위로 이어지고 중복·누락이 없다.
- **AC-06** Given 점프한 상태, When 화면을 보면, Then "최근 기록으로 돌아가기"가 목록 상단에 고정되어 있다.
- **AC-07** Given 점프한 상태에서 "최근 기록으로 돌아가기"를 누르면, Then 목록이 최신 기록부터 다시 시작하고 URL에서 `from`이 사라진다.
- **AC-08** Given "카페" 태그가 걸린 상태, When 시트를 열면, Then 카페 태그가 붙은 기록이 있는 달만 그 건수로 표시된다.
- **AC-09** Given 태그 필터 + 점프가 동시에 걸린 상태, When 다른 태그 칩을 누르면, Then 점프가 해제되고 새 태그의 최신 기록부터 표시된다.
- **AC-10** Given 점프 상태에서 카드를 눌러 기록 상세에 갔다가 뒤로 오면, Then 같은 점프 위치와 스크롤이 유지된다.
- **AC-11** Given 전체 기록이 12건인 커플, When 타임라인을 열면, Then "기간 이동" 진입점이 보이지 않는다.
- **AC-12** Given 기록 0건, When 타임라인을 열면, Then `08`의 빈 상태만 보이고 진입점이 없다.
- **AC-13** Given 커플 A 사용자, When `couple_record_months()`를 직접 호출하면, Then 커플 A의 달만 반환된다(`SECURITY INVOKER` 검증).
- **AC-14** Given URL에 `?from=1999-01`처럼 기록이 없는 시점을 직접 넣어 접근하면, Then 에러 없이 "그 시점 이전 기록 없음" 상태가 되고 "최근 기록으로 돌아가기"로 복귀할 수 있다.
- **AC-15** Given 점프 대상 달의 기록이 다른 기기에서 모두 삭제된 뒤, When 그 달로 점프하면, Then 빈 화면이 아니라 그 시점 이전의 다음 기록부터 표시된다.
- **AC-16** Given 타임라인 진입, When 네트워크 요청을 세면, Then 시트를 열기 전까지 `08` 대비 추가 요청이 0건이다.
- **AC-17** Given 키보드만 사용, When 진입점 → 시트 → 달 선택을 수행하면, Then 전 과정이 조작 가능하고 Esc로 시트를 닫을 수 있으며 이동 결과가 음성으로 안내된다.
- **AC-18** Given 시트 조회만 실패, When 화면을 보면, Then 시트 안에만 에러가 뜨고 뒤의 목록은 그대로다.

## 9. 미결정 항목

> ✅ **결정 완료 (2026-08-26) — 상시 스크러버가 아니라 "버튼 → 바텀시트"다(F-01).**
>
> **선택지**: (a) 목록 우측에 상시 노출되는 세로 스크러버(연·월 눈금)
> (b) 헤더 버튼 → 바텀시트 (c) 월 구분 헤더(`08` F-07)를 sticky로 만들고 탭하면 시트
>
> **근거**: (a)는 모바일 세로 화면에서 카드 폭을 잡아먹고, 스크롤 제스처와 스크러버 드래그가
> 같은 방향으로 경쟁해 오조작이 잦다. 무엇보다 `08` F-16의 가로 스크롤 태그 칩과 함께
> 두면 한 화면에 스크롤 가능한 영역이 셋(세로 목록·가로 칩·세로 스크러버)이 되어 조작
> 모델이 무너진다. (c)는 우아하지만 발견성이 낮다 — 월 헤더가 눌릴 수 있다는 걸 알아야
> 쓸 수 있다. (b)는 발견성(항상 보이는 레이블)과 화면 절약을 동시에 만족하고, 시트라는
> 형태가 "잠깐 열어서 고르고 닫는" 이 기능의 성격과 정확히 맞는다.

> ✅ **결정 완료 (2026-08-26) — 역방향(최신 방향) 스크롤은 지원하지 않는다(F-11).**
>
> **근거**: 양방향 무한 스크롤은 (1) 위쪽 로드 시 스크롤 위치를 붙잡아 두는 앵커링,
> (2) 위·아래 두 커서의 동시 관리, (3) `08` F-10의 스크롤 위치 복원과의 상호작용,
> (4) 접근성 대안인 "더 보기" 버튼의 이중화까지 새로 설계해야 한다. 반면 얻는 것은
> "점프한 지점에서 조금 더 최신을 보고 싶다"는 좁은 요구뿐이고, 그건 시트를 다시 열어
> 한 달 위를 고르거나 F-09로 최신에 돌아가는 것으로 충족된다. `08` §9가 목록 가상화에
> 대해 내린 판단("문제가 실측되기 전에 넣으면 버그 표면적만 늘어난다")과 같은 결이다.

> ✅ **결정 완료 (2026-08-26) — 점프와 태그 필터는 곱해지지 않는다(F-13).**
>
> **근거**: 두 상태가 독립적으로 유지되면 "카페 태그 + 2025년 8월부터"라는 조합이 생기고,
> 결과가 비었을 때 사용자가 원인을 특정할 수 없다(태그 때문인지 시점 때문인지). 다만
> **한 방향만 해제**한다 — 태그를 바꾸면 점프가 풀리지만, 점프를 해도 태그는 유지된다.
> 이유는 태그가 "무엇을 보는가"(더 상위 의도)이고 점프는 "어디부터 보는가"(하위 위치)라서,
> 상위가 바뀌면 하위를 리셋하는 것이 자연스럽기 때문이다. F-06이 시트를 태그 기준으로
> 계산하는 것도 같은 위계에서 나온다.

> ❓ **미결정 — 진입점 노출 임계값(F-10)의 기준**
>
> "첫 페이지 20건 미만이면 숨김"은 추가 쿼리 0회로 판정할 수 있어서 택한 값이지, 사용성
> 근거가 있는 값이 아니다. 실제로는 "기록이 걸쳐 있는 달의 수"가 더 정확한 기준인데
> (기록 30건이 전부 한 달에 몰려 있으면 인덱스가 무용하다) 그걸 알려면 진입 시점에
> 시트 조회를 해야 해서 왕복 예산(F-15)과 충돌한다. 실사용에서 "진입점이 있는데 쓸모없다"는
> 사례가 확인되면 그때 왕복을 하나 늘릴지 재검토한다.

> ❓ **미결정 — 점프 상태를 얼마나 눈에 띄게 표시할지**
>
> §5는 "어느 시점인지 알 수 있는 표시"를 요구하지만 형태를 정하지 않았다(`08` F-07의
> 월 구분 헤더가 이미 첫 카드 위에 있으므로 그것으로 충분할 수도 있다). 중복 표시가
> 될지 필요한 신호가 될지는 실제 화면을 봐야 판단할 수 있어 **디자이너 검토 항목**으로
> 남긴다. F-09의 "최근 기록으로 돌아가기" 존재 자체는 필수다(그건 결정됐다).
