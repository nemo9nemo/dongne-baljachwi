# 역 마스터 데이터 적재

> 근거: PRD §8 "지하철역 좌표 데이터 → 공공데이터포털/TAGO API 확정",
> PRD §5.5 "전국 역 마스터 데이터가 선행되어야 함", `docs/decisions/001-tech-stack.md`
> 전제: `00-data-model.md` §4.8

## 1. 목적 / 배경

프로토타입은 역 17개가 하드코딩되어 있었다(PRD §7). 이 상태로는 세 가지가 전부 불가능하다.

1. **노선도 화면** — 전체 노선을 그리려면 역·노선·역 순서가 있어야 한다.
2. **지도 보기** — 카카오맵에 핀을 찍으려면 실 위경도가 있어야 한다.
3. **안 가본 역 추천 / 커버리지 %** — 분모가 되는 "전체 역 집합"이 있어야 계산된다.

즉 이 스펙은 **다른 모든 화면 기능의 선행 조건**이다. 동시에 사용자가 직접 보는 화면이 없는
유일한 스펙이며, 산출물은 배치 스크립트와 적재된 데이터다.

핵심 난제는 **환승역의 동일성 판정**이다. 공공데이터는 "역"을 노선별 행으로 준다. 홍대입구는
2호선·경의중앙선·공항철도 3개 행이다. 그런데 사용자에게 "홍대입구역에서 데이트했다"는 하나의
사건이다. 기록을 노선별로 3개 만들 수는 없다. 따라서 **물리적 역(`stations`)과 노선별 역
(`station_lines`)을 분리**하고, 어떤 행들이 같은 물리 역인지 판정하는 규칙을 확정해야 한다.

## 2. 사용자 시나리오

사용자 대면 화면이 없으므로 **운영자(개발자) 시나리오**로 기술한다.

### 2.1 정상 흐름 — 최초 적재

1. 운영자가 `TAGO_SERVICE_KEY`(또는 표준데이터 파일)를 준비한다.
2. 배치를 `--dry-run`으로 실행한다.
3. 배치가 원천 데이터를 내려받아 정규화하고, **적용될 변경 요약**을 출력한다:
   신규 역 N건 / 변경 M건 / 비활성화 K건 / 그룹핑 경고 J건.
4. 운영자가 요약과 그룹핑 경고 목록을 검토한다.
5. `--apply`로 재실행 → 트랜잭션 1건으로 upsert → `master_version` 증가.
6. 클라이언트는 다음 접속 시 `master_version` 변화를 감지해 로컬 캐시를 갱신한다.

### 2.2 정상 흐름 — 정기 갱신

- 원천 데이터는 연 단위 갱신이다(전국도시철도역사정보표준데이터 기준). 실시간 동기화가
  필요 없으므로 **수동 실행 배치**로 충분하다. 자동 스케줄러를 두지 않는다.
- 신규 개통역은 배치 재실행으로 추가된다.

### 2.3 예외 흐름

| 상황 | 동작 |
|---|---|
| API 키 미승인/401 | 배치가 즉시 중단하고 원인을 출력. 부분 적재 금지 |
| API 응답 항목 누락(좌표 없음) | 해당 역을 `needs_review`로 표시하고 적재하되 `is_active=false`. 좌표 없는 역은 지도·노선도에 뜨지 않는다 |
| 폐역/원천에서 사라진 역 | **삭제하지 않는다.** `is_active=false`로 내린다. 기록이 참조 중일 수 있다 (`00-data-model.md` AC-07) |
| 역명 변경 (예: "○○역 → ○○(△△)역") | `code`가 같으면 같은 역으로 보고 `name`만 갱신. 기록은 그대로 따라간다 |
| 그룹핑 애매 (동명이역/좌표 이격) | 자동 병합하지 않고 경고 목록에 남긴다. `station_merge_overrides`로 수동 결정 |
| 배치 도중 실패 | 트랜잭션 롤백. `master_version`은 증가하지 않는다 |

## 3. 기능 요구사항

| ID | 요구사항 | 우선순위 | 비고 |
|----|---------|---------|------|
| F-01 | 역 마스터를 `lines` / `stations` / `station_lines` 3테이블로 적재한다 | Must | 환승역 = `stations` 1행 + `station_lines` N행 |
| F-02 | 물리 역 그룹핑 규칙: **정규화 역명이 같고, 좌표가 서로 500m 이내**인 노선별 행들을 하나의 `stations`로 묶는다 | Must | 두 조건 모두 만족해야 함 |
| F-03 | 역명 정규화: 접미사 "역" 제거, 괄호 부기 분리, 공백 제거, NFC | Must | `총신대입구(이수)` → 비교키 `총신대입구`, 표시명은 원문 유지 |
| F-04 | 그룹핑 규칙에 걸리지 않는 케이스(동명 이역, 이격 환승)는 `station_merge_overrides` 테이블로 강제 지정/분리한다 | Must | 자동 규칙만으로 100% 맞출 수 없음을 전제 |
| F-05 | 그룹핑 경고를 배치가 출력한다: 동명이지만 500m 초과 / 500m 이내지만 이름 다름 | Must | 사람이 검토할 대상 목록 |
| F-06 | `stations.code`는 **노선번호가 가장 작은 소속 노선의 역번호**에서 파생한 안정 키다 (`S-<노선번호>-<역번호>`) | Must | 재적재해도 같은 역은 같은 code. 역번호는 노선 내에서만 유일하므로(전국 단위로는 다른 노선의 역번호와 충돌한다 — 실데이터로 2026-08-12 확인, 265건 충돌·10건 데이터 유실 실측) 노선번호로 네임스페이스한다. "최소 역번호"가 아니라 "노선번호가 가장 작은 노선의 역번호"를 쓰는 이유는, 서로 다른 노선의 역번호는 크기 비교가 무의미하고 숫자 최소를 쓰면 역번호가 더 작은 노선이 신설될 때 기존 역의 code가 흔들리기 때문이다. 상세 근거는 `scripts/station-master/grouping.mjs`의 `buildStationCode` 주석 참고 |
| F-07 | 대표 좌표는 그룹 내 노선별 좌표의 **산술 평균** | Must | 지도 핀 1개만 찍으면 되므로 |
| F-08 | `lines.sort_order`로 셀렉트박스 정렬 순서를 데이터가 결정한다 | Must | 1~9호선 → 광역/민자 순. 프론트에 순서 하드코딩 금지 |
| F-09 | `master_version` 단일 값을 두고, 적재 성공 시 증가시킨다 | Must | 클라이언트 캐시 무효화 신호 |
| F-10 | MVP 범위는 `lines.in_mvp_scope` 플래그로 데이터가 정한다 | Must | 커버리지 % 분모, 안 가본 역 추천 후보 집합 |
| F-11 | `station_lines.seq`(노선 내 역 순서)를 적재한다 | Must | 노선도 선 연결, 추천 근접도 계산. **2026-08-25 확정(§9)**: 원천 역번호 그대로 적재하며 배치가 재계산하지 않는다 — 지선·연장 구간에서 실제 지리 순서와 산발적으로 어긋날 수 있음을 알고 있고(일산선 실증), 소비처는 필요 시 실좌표 기반 재구성으로 우회한다는 원칙만 남긴다 |
| F-12 | 배치는 `--dry-run` / `--apply` 2모드를 지원하고, 기본은 dry-run | Must | 실수로 프로덕션을 덮어쓰는 사고 방지 |
| F-13 | 배치는 `service_role` 키로만 동작한다. 브라우저에서 실행 불가 | Must | `CLAUDE.md` 공통 규약 |
| F-14 | 노선도 **도식 좌표**(SVG x/y)는 이 배치의 관할이 아니다 | Must | ADR-003. `03-line-map.md`가 소유 |
| F-15 | 원천 응답 원문을 `station_source_raw`에 보관한다 | Should | 그룹핑 규칙을 바꿔 재계산할 때 API를 다시 때리지 않기 위해 |

## 4. 데이터 모델

### 4.1 `lines`

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `id` | uuid | NN | PK |
| `code` | text | NN | UNIQUE. 원천 노선번호 기반 (`L-1001` 등) |
| `name` | text | NN | 표시명. "2호선", "수인분당선" |
| `operator` | text | | 운영기관명 |
| `sort_order` | smallint | NN | 셀렉트박스 정렬 |
| `color_token` | text | NN | **색상값이 아니라 디자인 토큰 이름** (`line-2` 등). 실제 색은 `src/styles/tokens.css` 소유 |
| `in_mvp_scope` | boolean | NN | 기본 true (수도권) |
| `is_active` | boolean | NN | 기본 true |
| `created_at` / `updated_at` | timestamptz | NN | |

> `color_token`을 두는 이유: 노선 색은 노선의 속성(2호선=초록)이므로 데이터에 속하지만,
> 구체적 색상값은 디자이너 소유다(`CLAUDE.md`). 데이터는 토큰 이름까지만 정한다.

### 4.2 `stations`

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `id` | uuid | NN | PK |
| `code` | text | NN | UNIQUE. F-06 |
| `name` | text | NN | 표시명 원문 (`총신대입구(이수)`) |
| `name_short` | text | NN | 노선도 라벨용. 괄호 부기 제거 |
| `name_key` | text | NN | 그룹핑 비교용 정규화 키 (F-03) |
| `lat` / `lng` | double precision | NN | 대표 좌표 (F-07). 좌표 미확보 시 적재 보류 |
| `region_code` | text | NN | `11`(서울)/`41`(경기)/`28`(인천) 등 시도 코드 |
| `is_transfer` | boolean | NN | `station_lines` 개수 ≥ 2에서 파생, 조회 편의를 위해 물리화 |
| `is_active` | boolean | NN | |
| `needs_review` | boolean | NN | 그룹핑 경고 대상 |
| `source` | text | NN | `tago` / `standard-file` |
| `source_updated_on` | date | | 원천 데이터 기준일 |
| `created_at` / `updated_at` | timestamptz | NN | |

### 4.3 `station_lines`

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `station_id` | uuid | NN | PK(복합), FK → `stations(id)` |
| `line_id` | uuid | NN | PK(복합), FK → `lines(id)` |
| `station_no` | text | | 노선별 역번호 ("239") |
| `seq` | int | NN | 노선 내 순서. `UNIQUE (line_id, seq)` |
| `lat` / `lng` | double precision | NN | 노선별 원천 좌표 (그룹 평균 재계산용) |

### 4.4 `station_merge_overrides` — 수동 교정

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `id` | uuid | NN | PK |
| `kind` | text | NN | CHECK in (`merge`, `split`) |
| `source_keys` | text[] | NN | 원천 역번호 목록 |
| `reason` | text | NN | 왜 이렇게 정했는지 (사람이 읽는 기록) |
| `created_at` | timestamptz | NN | |

- `merge`: 규칙상 분리되지만 같은 역으로 묶어야 하는 경우 (예: 이격 환승 통로)
- `split`: 규칙상 묶이지만 다른 역인 경우 (동명이역)
- **이 테이블이 자동 규칙보다 우선한다.**

### 4.6 `app_settings` — `master_version`

| 필드 | 타입 | 제약 |
|---|---|---|
| `key` | text | PK |
| `value` | jsonb | NN |
| `updated_at` | timestamptz | NN |

- `key = 'master_version'`, `value = { "version": 7, "applied_at": "..." }`
- 클라이언트는 앱 부팅 시 이 한 행만 읽어 캐시 유효성을 판단한다.

### 4.7 RLS로 보장할 접근 범위

| 테이블 | SELECT | INSERT/UPDATE/DELETE |
|---|---|---|
| `lines`, `stations`, `station_lines` | `authenticated` 전원 허용 | **정책 없음** = `service_role`만 가능 |
| `app_settings` (`master_version`) | `authenticated` 전원 허용 | 정책 없음 |
| `station_merge_overrides`, `station_source_raw` | **정책 없음** = 클라이언트 조회 불가 | 정책 없음 |

> 마스터 데이터는 커플 데이터가 아니므로 `couple_id`가 없고 전원에게 열려 있다.
> 이는 의도된 것이다 — 역 목록은 공개 정보이며, 여기에 커플 격리를 걸 이유가 없다.
> **격리 대상은 "이 커플이 어느 역에 갔는가"(`records`)이지 "역이 존재하는가"가 아니다.**

### 4.8 원천 데이터 선택

| 후보 | 형태 | 좌표 | 환승 정보 | 갱신 | 평가 |
|---|---|---|---|---|---|
| 국토교통부 TAGO 지하철정보 (data.go.kr/15098554) | REST JSON/XML | **문서상 미확인** | 미확인 | API | ADR-001에서 확정된 소스. 실 호출 검증 필요 |
| 전국도시철도역사정보표준데이터 (data.go.kr/15013205) | XLSX 파일, 1,073행 | **포함** | **포함**(환승역 여부/환승 노선) | 연 1회 | 필요한 항목이 전부 있음. 파일이라 배치가 단순 |
| 서울교통공사 1~8호선 역사 좌표 | XLSX, 276행 | 포함 | 미포함 | 부정기 | 서울 1~8호선만. 단독으로는 부족 |

**적재 전략**: 배치를 **어댑터 구조**로 만든다 — `fetch → 정규화 → 그룹핑 → upsert` 파이프라인에서
`fetch` 단계만 원천별로 교체 가능하게 한다. 그러면 TAGO 검증 결과와 무관하게 나머지 80%를
먼저 구현할 수 있다. (과잉 추상화가 아니라, 원천이 확정되지 않았다는 현실에 대한 대응이다.)

> **TAGO 키 상태 (2026-08-11 확인)**: 프로젝트에 `.env.local`이 존재하지 않고
> `.env.example`의 `TAGO_SERVICE_KEY`는 비어 있다. **실제 호출로 승인 여부를 검증하지 못했다.**
> ADR-001에는 "사용자가 승인 완료를 확인했으나 구현 착수 시 재검증"으로 기록되어 있다.
> → §9 미결정 항목 참조.

## 5. 상태 정의

배치 실행 상태 (콘솔 출력 계약).

| 상태 | 출력 |
|---|---|
| 시작 | 원천, 모드(dry-run/apply), 대상 Supabase 프로젝트 URL |
| 수집 중 | 페이지네이션 진행률 (`n/total`) |
| 수집 실패 | HTTP 상태 + 응답 본문 앞 500자 + 중단. **부분 적재 없음** |
| 정규화 완료 | 원천 행 수 → 정규화 행 수 |
| 그룹핑 완료 | `stations` N개 / `station_lines` M개 / 경고 J건 (경고는 전체 나열) |
| 차이 요약 | 신규/변경/비활성화 각 건수 + 변경 상세 상위 50건 |
| dry-run 종료 | "적용하려면 `--apply`" |
| apply 성공 | 트랜잭션 커밋, 새 `master_version` |
| apply 실패 | 롤백 확인 메시지, `master_version` 불변 |

**클라이언트 측 상태** (마스터 데이터 소비자 공통)

| 상태 | 동작 |
|---|---|
| 캐시 히트 (`master_version` 일치) | 네트워크 요청 없이 로컬 캐시 사용 |
| 캐시 미스/버전 불일치 | 전체 마스터 재다운로드 후 캐시 교체 |
| 마스터 로드 실패 | 노선도·지도 진입 불가. "역 정보를 불러오지 못했습니다" + 재시도. 타임라인은 기록에 역명이 조인되므로 부분 동작 |
| 마스터 비어 있음 (배치 미실행) | 노선도 빈 상태. 개발 환경에서만 발생해야 하며, 프로덕션에서는 배포 전 적재가 선행 조건 |

## 6. 비기능 요구사항

- **데이터 규모**: 수도권 역 약 700 / 전국 1,073행. 전국으로 넓혀도 같은 설계가 성립한다
  (§7 참조). 100배(10만 역)는 지하철 도메인에서 발생하지 않는다.
- **전송량 예산**: 클라이언트가 받는 마스터 페이로드는 gzip 후 **150KB 이하**를 목표로 한다.
  이를 위해 클라이언트 전송 시 `stations`에서 `name_key`, `source`, `needs_review`,
  `source_updated_on`은 제외한다 (전용 조회 뷰 `station_master_public`).
- **캐시**: 로컬 저장소에 `master_version`과 함께 저장. 앱 부팅 시 `app_settings` 1행만
  조회(수 KB)해 비교 → 대부분의 접속에서 마스터 재다운로드가 발생하지 않는다.
- **배치 실행 시간**: 전량 재적재 5분 이내.
- **멱등성**: 같은 원천으로 두 번 실행하면 두 번째는 변경 0건이어야 한다.

## 7. 확장 포인트

| 지점 | 지금 | 이유 |
|---|---|---|
| 원천 어댑터 | TAGO / 표준데이터 파일 | 원천이 확정되지 않은 상태라 교체 가능성이 실재한다 |
| `in_mvp_scope` | 수도권만 true | PRD §8이 "MVP는 수도권으로 축소"로 남겨둔 항목. 전국 확장 시 플래그만 켜면 커버리지·추천이 그대로 동작한다 |
| `region_code` | 시도 코드 저장 | 지역별 커버리지(예: "서울 42%")가 요구되면 집계 축으로 바로 사용 |

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 원천 데이터가 준비되었을 때, When 배치를 `--dry-run`으로 실행하면, Then DB는 변경되지 않고 변경 요약만 출력된다.
- **AC-02** Given `--apply`로 적재 성공, When 같은 원천으로 즉시 재실행하면, Then 변경 건수가 0이다 (멱등성).
- **AC-03** Given 홍대입구(2호선/경의중앙/공항철도), When 적재하면, Then `stations` 1행 + `station_lines` 3행이 생성되고 `is_transfer = true`다.
- **AC-04** Given 이름은 같지만 좌표가 3km 떨어진 두 역, When 적재하면, Then 자동 병합되지 않고 그룹핑 경고에 나타난다.
- **AC-05** Given `station_merge_overrides`에 `split` 규칙이 있는 두 행, When 적재하면, Then 좌표가 500m 이내여도 별도 `stations`로 분리된다.
- **AC-06** Given 이미 기록이 달린 역이 원천에서 사라졌을 때, When 적재하면, Then 해당 역은 삭제되지 않고 `is_active=false`가 되며 기존 기록은 그대로 조회된다.
- **AC-07** Given 적재가 성공했을 때, When `app_settings.master_version`을 조회하면, Then 이전보다 증가해 있다.
- **AC-08** Given API 키가 무효할 때, When 배치를 실행하면, Then 아무 행도 쓰이지 않고 인증 실패 원인이 출력된다.
- **AC-09** Given 로그인한 일반 사용자, When `stations`에 INSERT를 시도하면, Then RLS로 거부된다.
- **AC-10** Given 로그인한 일반 사용자, When `station_merge_overrides`를 조회하면, Then 0행이 반환된다.
- **AC-11** Given 클라이언트가 마스터를 캐시한 상태, When `master_version`이 그대로면, Then 마스터 재다운로드 요청이 발생하지 않는다.
- **AC-12** Given `lines.sort_order`를 바꿔 적재했을 때, When 노선도 셀렉트박스를 열면, Then 코드 수정 없이 순서가 바뀌어 보인다.

> ✅ **결정 완료 (2026-08-12): 역 좌표 데이터 원천은 전국도시철도역사정보표준데이터로

> `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`(키 미승인)가 **아니라** `HTTP 400
> NO_OPENAPI_SERVICE_ERROR (returnReasonCode: 12)`였다 — 이 코드는 보통 "요청 URL이 게이트웨이에
> 등록된 서비스와 매칭되지 않음"을 뜻한다. 같은 키로 다른 오퍼레이션/가짜 서비스+가짜 키까지
> 대조 호출해본 결과 전부 동일 에러가 나서, `DEFAULT_ENDPOINT`
> (`scripts/station-master/sources/tago.mjs`의
> `http://apis.data.go.kr/1613000/SubwayInfoService/getKwrdFndSubwaySttnList`) 자체가 현재
> 유효하지 않은 경로라고 진단했다. (b) 위경도 포함 여부·(c) `seq` 포함 여부는 응답 바디까지
> 도달하지 못해 끝내 확인하지 못했다.
>
> 엔드포인트를 다시 찾는 대신 **전국도시철도역사정보표준데이터(좌표·환승 포함)로 원천을
> 확정**했다. `scripts/load-station-master.mjs`는 이제 `--source` 미지정 시 무조건
> `standard-file`을 기본값으로 쓴다 — `TAGO_SERVICE_KEY`가 `.env.local`에 남아 있어도 자동
> 선택하지 않는다. TAGO 어댑터 코드는 향후 올바른 엔드포인트를 찾으면 `--source=tago`로
> 재시도할 수 있게 남겨뒀다. 상세 배경: `docs/decisions/001-tech-stack.md`.
>
> **남은 미검증 지점**: 실제 표준데이터 CSV/XLSX 파일이 아직 저장소에 없어 `standard-file`
> 어댑터의 실 파싱 경로(컬럼 매핑, CP949 인코딩 감지)는 검증되지 않았다. 파일을 확보하는
> 대로 `--file=<경로>`로 dry-run 재검증이 필요하다.

> ❓ **노선 내 역 순서(`seq`)의 출처**. 표준데이터는 역번호를 주지만 역번호가 노선상 순서와
> 항상 일치한다는 보장이 없다(지선·연장 구간). 역번호 정렬로 시작하되, 노선도 도식 작업
> (`03-line-map.md`) 과정에서 육안 검증이 필요하다.
>
> **실증 사례 (2026-08-24, `03-line-map.md` §9 방법 D 1차 파일럿 중 확인)**: 일산선
> (`L-I4106`, 대화~지축)의 `station_lines.seq`가 실제 지리 순서와 어긋나는 것을 실측으로
> 확인했다. DB 값은 원흥(seq 1) → 지축(seq 2) → 삼송(seq 3) → 원당 → ... → 대화(seq 11)
> 순인데, 실제 노선은 대화 → 주엽 → 정발산 → 마두 → 백석 → 대곡 → 화정 → 원당 → 원흥 →
> 삼송 → 지축(3호선 접속점) 순이다. 즉 지축이 노선의 **끝 접속점**인데 seq 상으로는 두
> 번째에 끼어 있다. 같은 노선인 3호선 본선(`L-I1103`, 지축~오금, 34역)의 seq는 이 문제가
> 없었다(방향만 반대일 뿐 순서 자체는 실제 경로와 일치) — 즉 이 문제가 전체 seq에
> 조직적으로 퍼져 있다기보다는 **노선/구간별로 산발적으로 나타날 가능성**을 시사한다.
>
> 원인은 특정하지 않았다(표준데이터 원본의 역번호 채번 방식 자체 문제인지, 적재 배치의
> `numericPart(station_no)` 폴백 정렬 로직 문제인지는 미조사 — F-11 배치 코드가 seq를
> 역번호 숫자 파싱에 의존한다면, 일산선처럼 역번호 체계가 노선 방향과 어긋나는 구간에서
> 같은 문제가 재발할 수 있다).
>
> **회피책이 이미 하나 존재한다**: `03-line-map.md` §9 방법 D의 시드 스크립트
> (`scripts/seed-line-map.mjs`)는 애당초 `seq`를 신뢰하지 않고, 역들의 실좌표(위경도)로
> 최소신장트리(Prim)를 만든 뒤 트리 지름의 양 끝을 찾는 방식(DFS 2회)으로 노선 순서를
> **자체 복원**해 이 문제를 우회한다 — 분기 없는 단순 경로 노선(대부분의 광역철도)에서만
> 안전하고, 순환선(2호선)·분기선(성수/신정지선류)에는 쓸 수 없다는 전제가 있다.
>
> 이 사실은 정책 결정이 아니라 관찰 기록이었다. 아래에 정책 결정을 남긴다.

> ✅ **결정 완료 (2026-08-25) — 노선 내 역 순서(`seq`)의 출처**: **DB `station_lines.seq`는
> 원천 표준데이터의 역번호 기반 그대로 유지한다.** 적재 배치(`scripts/station-master/`)를
> 고쳐 `seq`를 재계산하지 않는다. 대신 "`seq`가 노선의 실제 지리적 순서를 100% 보장하지
> 않는다"는 사실을 스펙 레벨에서 공식 인정하고, `seq`를 직접 소비하는 모든 기능은 필요할
> 때 실좌표 기반 재계산으로 우회할 수 있다는 원칙을 F-11 비고에 남긴다.
>
> **근거**: 배치를 고쳐서 `seq` 자체를 다시 채번하려면 33개 MVP 노선 전체를 실좌표로
> 재검증해야 하는데, 일산선 실증 사례가 보여주듯 문제는 "노선 전체에 조직적으로 퍼진
> 패턴"이 아니라 **지선·연장 구간에서 산발적으로** 나타난다(3호선 본선 34역은 문제
> 없었고, 일산선 11역 중 1개 접속점만 어긋남). 즉 44역 중 1건 수준의 낮은 발생률을 고치기
> 위해 전 노선 전수 재검증이라는 큰 비용을 치르는 것은 배보다 배꼽이 크다. 더 결정적으로,
> 노선도 좌표 작업(`03-line-map.md` 방법 D)이 **이미 이 문제를 겪지 않는 방식**(실좌표
> 최소신장트리 재구성)으로 8차 파일럿까지 수작업 보정 0건을 유지하며 검증됐다 — 즉
> "고치지 않아도 실제로 문제가 되는 소비처가 없다"는 것이 실증됐다. 유일하게 남는 위험은
> `09-couple-profile.md`의 "안 가본 역 추천" 노선 내 거리 계산(`seq` 차이를 직접 씀)인데,
> 이 계산은 근사 랭킹(추천 4개를 고르는 용도)이라 순서가 국소적으로 한두 자리 어긋나도
> 추천 품질에 미치는 영향이 노선도 좌표 오류보다 훨씬 작다 — 틀린 좌표는 사용자 눈에 바로
> 보이지만, 추천 순위가 살짝 바뀌는 것은 체감되지 않는다. 향후 이 계산에서도 문제가
> 실측되면, 노선도가 쓰는 것과 같은 실좌표 기반 재구성을 재사용하면 된다(새로 설계할 필요
> 없음).

> ✅ **결정 완료 (2026-08-25) — 그룹핑 임계값 500m**: **그대로 유지한다.**
>
> **근거**: 배치를 8차례 이상 실제로 실행해 944개 물리 역으로 그룹핑했음에도, 이 기간
> 동안 발견된 데이터 이상치는 양원역 좌표 버그와 서생역 오탐(경계 박스 판정의 부작용,
> 실제로는 정상)뿐이었고 **둘 다 500m 임계값과 무관**하다 — 그룹핑 경고(F-05)로 인한
> 문제가 실증적으로 관측된 적이 없다. 종로3가·디지털미디어시티 같은 긴 환승 통로도
> 대체로 300~400m대라 500m 안에 들어온다고 알려져 있다. 값을 좁히면 정당한 환승 그룹을
> 놓치는(분리로 잘못 판정) 리스크가, 넓히면 동명이역을 잘못 합치는 리스크가 생기는데
> 지금 임계값에서 그 어느 쪽 문제도 아직 관측되지 않았으므로 조정할 근거가 없다. 향후
> 그룹핑 경고 로그에서 임계값 근처의 오탐/누락이 실제로 관측되면 그때 재조정한다.

> ✅ **결정 완료 (2026-08-25) — MVP 범위의 정확한 경계**: **`in_mvp_scope`는 행정구역
> 기준 "서울특별시 + 인천광역시 + 경기도"로 정의한다.** `stations.region_code`(이미 적재
> 중인 시/도 코드 컬럼, `02` §4.2)로 판정 가능하다.
>
> **적용 결과**
> - **성환·직산·두정(충청남도 천안/아산)**: 행정구역상 충남이므로 **`in_mvp_scope=false`가
>   맞다.** 현재 DB가 `true`로 되어 있는 것은 이 기준에 비춰보면 **정정이 필요한 상태**다.
>   ⚠ **DB 마이그레이션은 이번 판단 범위에 포함하지 않는다** — 정책만 확정하고, 실행은
>   `developer-backend`의 별도 후속 작업으로 남긴다.
> - **연천·전곡·청산(경기도 연천군)**: 행정구역상 경기도이므로 **`in_mvp_scope=true`
>   유지가 원칙적으로 맞다.** 노선도 좌표 정적 파일에서 이 3역을 제외한 기존 조치
>   (`EXCLUDE_STATION_CODES`)는 **그대로 유지한다** — 그 제외는 "이 역이 수도권에
>   속하는가"가 아니라 "공유 viewBox 종횡비가 왜곡되는가"라는 순수 렌더링 문제에 대한
>   조치이므로, DB 스코프 정의와 별개로 계속 유효하다. 즉 커버리지 %(분모)에는 포함되지만
>   노선도 그림에는 당분간 그려지지 않는 상태가 유지된다 — 이는 이미 `03-line-map.md`
>   §2.2/§5가 "좌표 미보유 역은 하단 안내 목록으로 노출"로 정의해둔 정상 동작이라 모순이
>   아니다.
>
> **근거**: "수도권"의 사전적·행정적 정의(수도권정비계획법 등)는 서울·인천·경기이고,
> `CLAUDE.md`도 이 프로젝트를 "수도권 지하철 기준"으로 명시한다. 충남 3역은 1호선이라는
> **하나의 노선 번호**를 공유할 뿐 행정구역·생활권 어느 기준으로도 수도권이 아니다 —
> PRD §2 페르소나("서울/수도권에 거주하며 주말에 지하철 타고 이동하는 커플")가 천안까지
> 데이트하러 가는 상황을 상정한다고 보기 어렵다. 반면 연천군은 비록 서울에서 멀고
> (약 60km) 노선도 좌표 작업에 실무적 문제를 일으켰지만, 행정구역상으로는 명백히
> 경기도다 — "멀어서 불편하다"는 이유로 스코프에서 빼면, 그 기준이 자의적이라 다른
> 원거리 역(예: 경기 남부·동부 끝자락)에도 같은 논리를 어디까지 적용할지 기준이 없어진다.
> region_code라는 이미 존재하는 명확한 축으로 선을 긋는 것이 유지보수 가능하고 설명
> 가능한 유일한 방법이다. 서울 1~9호선만으로 좁히는 대안은 기각했다 — 그러면 이미 수도권
> 생활권으로 통합된 광역철도(수인분당선·공항철도 등)까지 스코프 밖으로 빠져 PRD가 말하는
> "지하철로 데이트하는 커플"의 실제 이동 범위를 과소평가하게 된다.
>
> **`09-couple-profile.md` §9의 "커버리지 % 분모 범위"(구 40번)도 이 결정을 그대로
> 따른다** — 분모 정의(F-09)는 변경 없이 `in_mvp_scope=true AND is_active=true`이고,
> 이번 결정은 그 `in_mvp_scope` 자체가 무엇을 가리켜야 하는지를 확정한 것이다.
>
> **실증 사례 (2026-08-24, `03-line-map.md` §9 방법 D 4차 파일럿 중 확인)**: 1호선
> (`L-I4101`)이 `in_mvp_scope=true`인 채로 성환·직산·두정(충청남도 천안/아산)까지, 경원선
> (`L-I4102`)이 연천(경기 최북단, 서울 도심에서 직선거리 약 60km)까지 포함하고 있다.
> 노선도 좌표 파일은 모든 노선이 **하나의 viewBox를 공유**하므로(ADR-003 §5), 이 원거리
> 역들을 실좌표 그대로 배치하자 파일 전체의 종횡비가 1:1.1 대에서 **1:3**까지 벌어졌다
> (가로 3271.6 × 세로 9952.3) — 도심 밀집부(사용자 활동이 실제로 집중되는 곳)가 "전체
> 보기"에서 상대적으로 매우 작게 보이는 부작용이 있다. `CLAUDE.md`가 이 프로젝트를
> "수도권 지하철 기준"으로 전제하는데, 충남 3역·경기 최북단 1역이 상식적인 "지하철로
> 데이트하는 커플"의 활동 범위 밖이라는 정황(2026-08-24 사용자 판단)과, `in_mvp_scope`가
> 애초에 넓게 잡혀 있었을 가능성을 함께 시사한다.
>
> **잠정 조치 (정책 결정 아님)**: 노선도 좌표 정적 파일 쪽에서만, 이렇게 종횡비를 심하게
> 왜곡시키는 원거리 역을 좌표 작업 대상에서 제외하기로 했다(`scripts/seed-line-map.mjs`의
> `EXCLUDE_STATION_CODES`). `stations.is_active`/`in_mvp_scope` 등 DB 데이터는 전혀 건드리지
> 않았다 — 이건 데이터 소유 경계 밖이고, "수도권"의 정확한 경계를 다시 긋는 문제이므로
> 백엔드/기획 쪽에서 별도로 결정할 사안이다. **이 결정 자체는 여전히 미정으로 남긴다.**
> 좌표가 없는 역은 `03-line-map.md` §2.2/§5에 따라 노선도에 그려지지 않고 하단 안내 목록으로
> 노출되므로, 이 잠정 조치로 기능이 깨지지는 않는다.

> ✅ **결정 완료 (2026-08-24) — 신규 개통역 반영 트리거.** `03-line-map.md` §9의 노선도 좌표
> 조달 방법 TCO 재검토와 같은 문제의 다른 얼굴이라 함께 정리했다. 이 프로젝트는 1인 개발
> 체제라 "운영 주체가 누구인가"는 답할 실익이 거의 없다 — 대신 **"언제 실행하는가"를 고정
> 주기가 아니라 트리거 조건**으로 정의한다.
>
> - **트리거**: 신규 역 개통(또는 노선 변경) 소식을 인지했을 때, 수동으로 실행한다.
>   고정 스케줄러는 두지 않는다(이미 F-12·§2.2에서 결정된 대로 원천 자체가 연 단위 갱신이라
>   실시간 대응이 목표가 아니다).
> - **절차**: ① `stations:load --dry-run`으로 diff 확인 → ② diff가 있으면 `--apply` →
>   ③ **같은 세션에서** `03-line-map.md` §9 방법 D의 시드 스크립트를 diff가 발생한 노선에
>   대해 재실행해 신규역의 초기 도식 좌표를 채운다 → ④ `npm run verify:line-map` 경고
>   목록으로 커버리지 공백을 재확인.
> - **의미**: 역 마스터 재적재와 노선도 좌표 재생성은 **하나의 운영 이벤트**로 묶인다.
>   별개로 챙겨야 할 두 개의 일정이 아니라, ①~④를 한 번에 처리하는 단일 체크리스트다.
>   이렇게 묶지 않으면 마스터에는 있는데 노선도에는 없는 역(현재 602개, `PROGRESS.md` 표1)이
>   구조적으로 계속 재발한다.
