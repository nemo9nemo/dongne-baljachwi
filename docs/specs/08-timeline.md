# 타임라인 (전체 기록 피드)

> 근거: PRD §4 "타임라인 — 전체 기록 최신순, 태그 칩으로 필터", §3 "기록 타임라인 (P1)",
> §5.3 "타임라인 화면에서는 등장한 태그를 자동 수집해 칩 필터로 제공"
> 전제: `00-data-model.md`, `04-station-detail.md`

## 1. 목적 / 배경

노선도가 **공간 축**이라면 타임라인은 **시간 축**이다. "우리가 어디를 갔나"는 노선도가
답하지만, "우리가 뭘 하며 지냈나"는 시간순으로 훑어야 보인다. PRD §2의 페르소나는
"100일, 1주년 같은 기념일에 그동안의 데이트를 돌아보는 걸 좋아한다" — 그 회고가 일어나는
화면이 여기다.

태그 필터는 이 화면의 두 번째 축이다. PRD §5.3의 설계 의도는 명확하다: **추천 태그 사전을
만들지 않고, 사용자가 쓴 태그가 곧 필터 목록이 된다.** 이 원칙을 지키면 구현 비용이 낮고
커플마다 자기들만의 분류가 생긴다.

또한 타임라인은 **역이 정해지지 않은 상태에서 기록을 시작하는 유일한 진입점**이기도 하다
(노선도·역 상세는 역이 먼저 정해진다).

## 2. 사용자 시나리오

### 2.1 정상 흐름

1. 하단 탭에서 "타임라인"을 누른다.
2. 전체 기록이 **최신순 카드 목록**으로 나열된다. 카드는 역 상세의 카드와 같은 형태이되
   **역명이 함께 표시된다**.
3. 상단에 태그 칩들이 가로 스크롤로 나열되어 있다. 많이 쓴 태그가 앞에 온다.
4. "카페" 칩을 탭한다 → 카페 태그가 붙은 기록만 남는다. 칩은 선택 상태가 된다.
5. 다시 탭하면 해제되어 전체로 돌아온다.
6. 카드를 탭하면 기록 상세로 이동한다.
7. 스크롤을 내리면 다음 20건이 이어 붙는다.

### 2.2 예외 흐름

| 상황 | 동작 |
|---|---|
| 기록 0건 (신규 커플) | 빈 상태: "아직 발자취가 없어요" + "첫 기록 남기기" → 역 선택부터 시작하는 작성 화면 |
| 선택한 태그의 결과 0건 | (동시 삭제 등으로 발생) "이 태그의 기록이 없어요" + 필터 해제 버튼. 칩 목록은 유지 |
| 태그가 하나도 없음 | 칩 영역 자체를 표시하지 않는다 (빈 가로 스크롤 바를 남기지 않는다) |
| 목록 로드 실패 | 목록 영역 에러 + 재시도. 칩은 별도로 로드되므로 살아 있을 수 있다 |
| 칩 로드 실패 | 칩 영역만 숨기고 목록은 정상 표시 (필터 없이도 화면의 본질은 성립) |
| 추가 페이지 로드 실패 | 이미 로드된 목록은 유지 + 하단에 "더 불러오지 못했어요 · 다시 시도" |
| 오프라인 | 마지막 캐시 목록을 stale 표시로 노출 + 오프라인 배너 |
| 커플 미연결 | 이 화면에 도달하지 않는다 |

## 4. 데이터 모델

### 4.1 읽는 것

**신규 테이블 없음.** `records`, `record_tags`, `record_photos`, `profiles`, `stations`(캐시),
`couple_tag_usage` 뷰 (`00-data-model.md` §4.9).

**쿼리 계약 — 화면 진입 시 2회 (병렬)**

**① 태그 칩 목록**
```
select tag, tag_norm, usage_count
from couple_tag_usage
order by usage_count desc, last_used_at desc
limit 30
```
- `couple_tag_usage`는 `couple_id`로 이미 격리되어 있으므로 클라이언트가 조건을 붙이지 않는다.
- **캐시하지 않는다.** 기록을 추가하면 새 태그가 즉시 칩에 나타나야 한다.

**② 기록 페이지**
```
RecordCard[]  // 04-station-detail.md §4.1 의 shape + station 필드
```
| 파라미터 | 값 |
|---|---|
| 필터 | `tag_norm = ?` (선택된 칩이 있을 때만) |
| 정렬 | `visited_on DESC, id DESC` |
| 커서 | `(visited_on, id) < (cursor_visited_on, cursor_id)` |
| 개수 | 20 |

- 태그 필터가 걸리면 `record_tags`를 조인(또는 서브쿼리 `EXISTS`)한다. 인덱스는
  `record_tags(couple_id, tag_norm)` (`00-data-model.md` §4.7).
- `note`는 앞 200자만 전송한다 (`04` §4.1과 동일 이유).
- `cover_photo`는 `storage_path`만. 서명 URL은 **뷰포트에 들어온 카드만** 발급한다.

### 4.2 쓰는 것

**없다.** 읽기 전용 화면이다.

### 4.3 RLS로 보장할 접근 범위

| 대상 | 범위 |
|---|---|
| `records` | `couple_id = current_couple_id()` — **필터 파라미터를 어떻게 조작해도 다른 커플의 기록은 반환되지 않는다** |
| `record_tags` | 동일 |
| `couple_tag_usage` 뷰 | 동일 (`security_invoker = true` 필수) |
| Storage `record-photos` | 경로 첫 세그먼트 = `current_couple_id()` |
| `profiles` | 본인 + 같은 커플 |

> **이 화면은 커플의 전체 기록을 한 번에 훑는 화면**이라, RLS가 뚫리면 노출 규모가 가장 크다.
> 특히 태그 칩은 `couple_tag_usage` **뷰**를 통해 나가므로, 뷰의 `security_invoker` 누락은
> "다른 커플이 어떤 태그를 쓰는지"가 전부 보이는 결과가 된다.
>
> 또한 클라이언트가 커서·필터를 자유롭게 조작할 수 있다는 전제로 설계한다 — 페이지네이션
> 파라미터 검증은 UX 문제이지 보안 경계가 아니다. **보안 경계는 오직 RLS다.**

## 5. 상태 정의

| 상태 | 화면 |
|---|---|
| 최초 로딩 | 칩 영역 스켈레톤 + 카드 스켈레톤 3개 |
| 정상 | 칩 + 목록 |
| 빈 상태 (기록 0건) | 칩 영역 없음. "아직 발자취가 없어요" + "첫 기록 남기기" 주 버튼 |
| 빈 상태 (필터 결과 0건) | 칩은 유지, 목록 자리에 "이 태그의 기록이 없어요" + 필터 해제 버튼 |
| 목록 로드 실패 | 목록 영역 에러 + 재시도. 칩은 정상이면 유지 |
| 칩 로드 실패 (부분 성공) | 칩 영역 숨김, 목록은 정상. **화면 전체를 죽이지 않는다** |
| 추가 페이지 로딩 | 목록 하단 스피너 |
| 추가 페이지 실패 | 기존 목록 유지 + 하단에 재시도 |
| 마지막 페이지 | 스피너 제거. "끝입니다" 같은 문구는 두지 않는다 |
| 필터 전환 중 | 목록만 스켈레톤으로 교체. 칩은 즉시 선택 상태로 반응 (지연 없는 피드백) |
| 오프라인 | 마지막 캐시 목록 + stale 표시. 무한 스크롤 비활성 |

## 6. 비기능 요구사항

- **응답 목표**: 커플당 총 기록 **5,000행** 기준, 첫 페이지 20건 p95 300ms 이하.
  태그 필터가 걸린 경우도 동일. 인덱스 `(couple_id, visited_on DESC, id DESC)` 필수.
- **데이터 100배 검토**: 기록 50,000건이어도 키셋 페이지네이션은 O(log n) 인덱스 스캔이라
  성능이 유지된다. **offset 방식이었다면 뒤쪽 페이지에서 선형 열화**한다 — F-03을
  Must로 둔 이유다. 태그 칩 집계(`couple_tag_usage`)는 전체 스캔이므로 5만 건 규모에서
  느려질 수 있다. 그 시점의 대응은 §7 참조.
- **렌더 성능**: 무한 스크롤로 카드 500개가 누적되어도 스크롤이 60fps를 유지해야 한다.
  → 화면 밖 카드의 이미지는 해제하고, 목록 가상화 여부는 개발자 판단에 맡기되
  **500개 누적 시 스크롤 성능을 측정해 검증**한다.
- **이미지**: 썸네일은 변환 이미지로 요청. `width`/`height`로 자리를 잡아 CLS 0.
  서명 URL은 뷰포트 진입 시 발급하고, 벗어난 지 오래된 카드의 URL은 폐기한다.
- **접근성**:
  - 칩은 토글 버튼(`aria-pressed`)이며 키보드로 좌우 이동·선택이 가능하다.
  - 필터 변경 시 결과 건수를 `aria-live`로 알린다 ("카페 태그 기록 12건").
  - 무한 스크롤은 스크린리더 사용자가 끝을 알 수 없으므로 **"더 보기" 버튼도 함께 제공**한다.
  - 월 구분 헤더는 목록의 의미 구조로 노출한다.
- **브라우저**: `03-line-map.md` §6과 동일.

## 7. 확장 포인트

| 지점 | 지금 | 이유 |
|---|---|---|
| `RecordCard` shape | 역 상세와 공유 | 카드에 표시할 정보가 늘어나도 두 화면이 함께 따라온다 |
| 필터 파라미터 | `tag_norm` 단일 | 쿼리를 "필터 조건 집합 → where 절"로 다루면 다중 태그·기간 필터가 붙어도 페이지네이션 로직은 그대로다. **지금은 단일 태그만 구현** |
| 칩 정렬/상한 | 사용 횟수 top 30 | `couple_tag_usage` 뷰가 정렬을 담당하므로 규칙 변경이 뷰 수정으로 끝난다 |
| `couple_tag_usage` | 실시간 뷰 | 기록이 수만 건이 되면 뷰 이름을 유지한 채 머티리얼라이즈드 뷰로 교체 (`00` §7). 호출부 무변경 |
| 커서 | `(visited_on, id)` | 정렬 축이 추가되면 커서 튜플만 확장 |

**만들지 않는 것**: 검색(전문 검색), 날짜 범위 필터, 감정·날씨 필터, 정렬 변경 UI,
지도/캘린더 뷰 전환, 기록 다중 선택·일괄 삭제.

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 기록 5건(서로 다른 역·날짜), When 타임라인을 열면, Then 최신 방문일 순으로 5건이 나열되고 각 카드에 역명이 보인다.
- **AC-02** Given 같은 날짜에 기록 2건, When 목록을 두 번 로드하면, Then 두 번 모두 같은 순서다.
- **AC-03** Given 기록 45건, When 끝까지 스크롤하면, Then 20+20+5건이 순서대로 로드되고 중복·누락이 없다.
- **AC-04** Given 스크롤로 40건을 로드한 상태, When 새 기록을 추가하고 돌아오면, Then 목록에 중복 항목이 생기지 않는다 (키셋 검증).
- **AC-05** Given 태그 "카페"가 12건, "산책"이 5건, When 타임라인을 열면, Then 칩이 "카페 → 산책" 순으로 나열된다.
- **AC-06** Given 태그 칩 "카페" 탭, When 목록을 보면, Then 카페 태그가 붙은 기록만 남고 스크롤이 맨 위로 간다.
- **AC-07** Given "카페" 선택 상태, When "산책"을 탭하면, Then "카페"가 해제되고 "산책"만 선택된다 (단일 선택).
- **AC-08** Given "카페" 선택 상태, When "카페"를 다시 탭하면, Then 필터가 해제되고 전체 목록으로 돌아온다.
- **AC-09** Given 태그 `Cafe`와 `cafe`가 각각 저장된 기록, When 해당 칩을 선택하면, Then 두 기록이 모두 결과에 포함된다 (`tag_norm` 매칭).
- **AC-10** Given 태그 필터가 걸린 상태, When 스크롤로 다음 페이지를 로드하면, Then 필터가 유지된 채 이어진다.
- **AC-11** Given 기록 상세에서 태그 칩을 탭해 진입, When 타임라인이 열리면, Then 해당 태그가 선택된 상태이고 URL에 반영되어 있다.
- **AC-12** Given 기록 0건, When 타임라인을 열면, Then 칩 영역이 없고 첫 기록 유도 화면이 보인다.
- **AC-13** Given 칩 조회만 실패, When 화면을 보면, Then 칩 없이 목록이 정상 표시된다.
- **AC-14** Given 목록에서 기록 상세로 갔다가 삭제 후 돌아오면, Then 해당 카드가 사라져 있고 스크롤 위치는 유지된다.
- **AC-15** Given 커플 A 사용자, When 타임라인을 열면, Then 커플 B의 기록과 태그 칩이 전혀 나타나지 않는다.
- **AC-16** Given 커플당 기록 5,000건, When 첫 페이지를 로드하면, Then 300ms(p95) 이내에 응답한다.
- **AC-17** Given 스크린리더 사용, When 태그 칩을 선택하면, Then 결과 건수가 음성으로 안내된다.
- **AC-18** Given 키보드만 사용, When 목록 끝에 도달하면, Then "더 보기" 버튼으로 다음 페이지를 로드할 수 있다.

## 9. 미결정 항목

> ✅ **결정 완료 (2026-08-25) — 태그 다중 선택 여부(F-14)**: **단일 선택을 유지한다.**
>
> **근거**: PRD §5.3의 설계 의도는 "추천 태그 사전을 두지 않고 사용자가 쓴 태그가 곧
> 필터 목록이 되는 구조라 구현 비용이 낮다"는 것이다. 다중 선택은 AND/OR 의미 선택,
> 다중 선택 상태의 칩 UI, 전체 해제 컨트롤까지 새로 정해야 해서 이 원칙과 어긋나는
> 방향으로 복잡도를 키운다. 여러 태그를 동시에 좁혀보고 싶은 수요가 실사용에서 확인되면
> 그때 다시 검토한다 — 지금은 "구현 비용을 낮게 유지"라는 PRD의 명시적 의도를 따른다.

> ✅ **결정 완료 (2026-08-25) — 월/연도 구분 헤더(F-07)**: **넣는다. 월 단위로 확정한다.**
>
> **근거**: PRD §2 페르소나가 "100일, 1주년 같은 기념일에 그동안의 데이트를 돌아보는"
> 회고 목적으로 이 화면을 쓰므로, 시간 감각을 주는 구분 헤더가 그 목적에 직접 기여한다.
> "월 헤더가 카드보다 많아질 수 있다"는 우려는 논리적으로 성립하지 않는다 — 헤더는
> 기록이 존재하는 달에만 생기므로, 헤더 개수는 항상 "기록이 걸쳐 있는 달의 수" 이하이고
> 카드 수보다 많아지는 경우가 원천적으로 없다(데이트가 뜸한 커플은 헤더도 그만큼
> 드물어질 뿐이다). 연 단위보다 월 단위가 더 세밀한 회고 경험을 주므로 월 단위를 택한다.

> ✅ **결정 완료 (2026-08-25) — 칩 상한 30개 · "더보기" 필요성(F-17)**: **상한 30개는
> 유지하되, "더보기" 시트는 이번 범위에서 만들지 않는다.** 30개를 넘는 나머지 태그는
> 칩 목록에 노출하지 않는다.
>
> **근거**: 커플 한 쌍이 자유 태그를 30종 넘게 만드는 것은 초기 사용자 규모에서 드문
> 케이스로 예상된다. "더보기 시트"라는 별도 UI를 지금 미리 만드는 것은 §9 스스로
> 인정했듯 필요성이 불확실한 투기적 구현이라 `CLAUDE.md`의 "나중에 쓸 것 같아서 만드는
> 추상화 금지" 원칙과 정확히 충돌한다. 30개 밖으로 밀린 태그가 있어도 그 태그가 붙은
> 기록 자체가 사라지는 건 아니다 — 타임라인 목록 자체(필터 없이)나 기록 상세의 태그 칩
> 탭(`06` F-07)으로 여전히 접근 가능하므로, "더보기"가 없어도 완전히 도달 불가능한
> 상태가 되지는 않는다. 실사용 중 30개를 넘는 커플이 실제로 나타나면 그때 추가한다.

> ✅ **결정 완료 (2026-08-25) — 목록 가상화 필요 여부**: **지금은 구현하지 않는다.**
> §6이 이미 요구한 "500개 누적 시 스크롤 성능 측정"을 먼저 하고, 60fps 미달이 실측되면
> 그때 도입한다는 기존 방침을 그대로 확정한다.
>
> **근거**: 가상화는 스크롤 위치 복원(F-10)·무한 스크롤의 "더 보기" 접근성 대안(§6)과
> 상호작용이 복잡해서, 문제가 실측되지 않은 상태에서 선제적으로 넣으면 오히려 버그
> 표면적만 늘어난다. `CLAUDE.md`의 "두 번째 사용처가 생기면 그때 추출한다"는 원칙과 같은
> 결로, "성능 문제가 실측되면 그때 도입한다"가 이번 결정이다.

> ✅ **결정 완료 (2026-08-25) — FAB(새 기록) 진입 시 역 선택 흐름**: **노선도로 보내지
> 않는다.** FAB를 누르면 바로 기록 작성 화면이 "역 미선택" 상태로 열리고, 화면 안의
> 역 검색 입력(`05` F-07)에 자동으로 포커스가 간다.
>
> **근거**: 노선도로 보내면 사용자가 타임라인의 컨텍스트(스크롤 위치, 태그 필터 상태)를
> 완전히 벗어나는 화면 전환이 발생하고, 노선도 → 역 상세 → 기록 작성이라는 3단계 우회를
> 강제하게 된다. `05` F-07이 이미 "역 변경은 이름 검색으로 한다(노선도를 다시 띄우지
> 않는다)"고 정의해 뒀으므로, 이 원칙을 FAB 진입에도 그대로 적용해 새로운 흐름을 만들지
> 않는다 — 작성 폼의 첫 상호작용 지점(역 검색 필드 포커스)만 조정하면 된다.
