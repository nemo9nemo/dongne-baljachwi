# 오프라인 사진 캐시

> 근거: PRD §1 "수도권 데이트는 지하철역을 기준으로 이동", §2 페르소나 "주말에 지하철을
> 타고 이동하며 데이트한다" — **이 앱을 여는 대표적 장소가 지하철 안**이라는 사실에서
> 파생된, 기존 스펙이 한계로만 적어두고 방치한 지점을 해소한다.
> 전제: `00-data-model.md` §4.6(Storage 계약), `04-station-detail.md`, `06-record-detail.md`,
> `08-timeline.md`
> 이 문서는 화면 하나가 아니라 **여러 화면이 공유하는 이미지 표시 경로**를 정의한다.

## 1. 목적 / 배경

기존 스펙 세 곳이 오프라인 동작을 이렇게 정의해 놓았다.

- `06-record-detail.md` §2.3 — "오프라인: 캐시된 텍스트는 보여주되 **사진은 실패**"
- `08-timeline.md` §5 — "오프라인: 마지막 캐시 목록을 stale 표시로 노출"
- `04-station-detail.md` §2.2 — "오프라인: 마스터 캐시로 헤더 표시 + 기록 목록은 에러"

즉 **텍스트는 살아남고 사진만 죽는다**가 현재 확정된 동작이다. 그런데 이 서비스의 기록은
사진이 절반이다(PRD §1 "사진과 일기로 추억을 남기는"). 지하 구간에서 신호가 끊기는 것은
수도권 지하철의 일상이고, 페르소나가 앱을 여는 가장 흔한 순간이 바로 그 구간이다.
"지하철 위의 기록"을 표방하는 서비스가 정작 지하철 안에서 사진을 못 보여주는 상태다.

이 스펙은 그 간극을 **기기 로컬 이미지 캐시**로 메운다. 사진을 한 번이라도 화면에서 본 적이
있으면, 그 다음부터는 신호가 없어도 보인다.

### 1.1 이 스펙이 해결하지 **못하는** 것 (먼저 못 박는다)

이 프로젝트는 서비스워커가 없는 순수 SPA다(`docs/decisions/001-tech-stack.md`).
따라서 **완전 오프라인 상태에서 앱을 새로 여는 것(콜드 스타트)은 이 스펙으로 해결되지
않는다** — HTML·JS 번들 자체를 네트워크에서 받아야 하기 때문이다. 이 스펙이 다루는
범위는 "앱이 이미 실행 중이거나 브라우저 HTTP 캐시/bfcache로 부팅에 성공한 뒤,
**신호가 끊긴 상태에서의 사진 표시**"다. 콜드 스타트 오프라인은 §9에서 별도로 다룬다.

## 2. 사용자 시나리오

### 2.1 정상 흐름

1. 주말 저녁, 커플이 집에서 지난달 성수역 기록을 열어 사진 5장을 본다.
   → 화면에 성공적으로 표시된 사진들이 **자동으로 기기에 저장된다**(사용자에게 아무 안내도
   하지 않는다 — 별도 동작이 아니라 표시의 부수 효과다).
2. 다음 주말, 지하철 지하 구간에서 그 기록을 다시 연다.
3. 신호가 없어도 사진이 즉시 뜬다. 화면 어디에도 "캐시에서 불러왔다"는 표시는 없다.
4. 아직 한 번도 열어본 적 없는 다른 기록을 연다 → 그 사진 자리에는
   "오프라인이라 사진을 불러오지 못했어요" 대체 표시가 뜬다(기존 에러와 문구로 구분).
5. 신호가 돌아오면 그 자리의 사진이 자동으로 로드되고, 그때 캐시에 들어간다.

### 2.2 예외 흐름

| 상황 | 동작 |
|---|---|
| 캐시 미스 + 오프라인 | 사진 자리만 대체 표시. 일기·태그·감정은 정상. 카드/화면 전체를 에러로 만들지 않는다 |
| 캐시 미스 + 온라인 | 평소대로 네트워크 로드. 캐시는 관여하지 않는다 |
| 캐시 히트인데 파일이 깨져 있음 | 조용히 캐시 항목을 버리고 네트워크로 폴백한다. 오프라인이면 대체 표시 |
| 저장 공간 부족(QuotaExceeded) | **캐시 쓰기만 실패**하고 사진 표시는 정상 진행. 사용자에게 알리지 않는다 |
| 브라우저가 IndexedDB를 막아둠(프라이빗 모드 등) | 캐시 기능 전체를 비활성화하고, 앱은 캐시 없이 정상 동작한다 |
| 상대가 그 기록/사진을 삭제 | 온라인 복귀 후 해당 기록 조회 시 사라진 것을 확인하면 캐시도 삭제(F-12) |
| 로그아웃 / 커플 해제 / 다른 계정 로그인 | **캐시 전량 즉시 삭제**(F-10, F-11) |
| 커플 미연결 | 캐시할 사진 자체가 없다 |

### 2.3 커플 관점에서의 데이터 경계 (이 서비스에서 특히 중요)

| 질문 | 답 |
|---|---|
| 캐시는 커플 공유 데이터인가? | **아니다.** 순전히 **기기 로컬**이다. 내 폰의 캐시는 상대 폰에 없고, 그 반대도 같다 |
| 상대가 쓴 기록의 사진도 캐시되나? | 된다. 커플 공동 아카이브이므로 열람 권한이 있는 사진은 구분 없이 캐시한다 |
| 상대가 사진을 지우면 내 기기 캐시는? | 즉시는 아니다. 내 기기가 다음에 온라인으로 그 기록을 조회하는 시점에 정리된다(F-12). 이 **시차를 없앨 수단은 없다**(푸시 인프라가 없다) — 그래서 TTL 상한(F-09)을 함께 둔다 |
| 커플이 해제되면? | 즉시 전량 삭제한다(F-11). `current_couple_id()`가 NULL이 되어 서버 접근이 끊기는 것과 **기기 로컬도 같은 시점에 끊기게** 맞춘다 |

## 3. 기능 요구사항

### 3.1 캐시 채우기 / 읽기

| ID | 요구사항 | 우선순위 | 비고 |
|----|---------|---------|------|
| F-01 | **화면에 실제로 표시되어 로드에 성공한 이미지만** 캐시에 저장한다. 사전 프리페치(선제 다운로드)는 하지 않는다 | Must | 사용자가 모르는 사이 데이터 요금·배터리·저장공간을 쓰는 동작을 만들지 않는다. §7 참조 |
| F-02 | 캐시 키는 서명 URL이 아니라 **`record_photos.storage_path` + 변형(variant)** 이다 | Must | 서명 URL은 1시간마다 바뀌므로(`00` §4.6) URL을 키로 쓰면 캐시가 매시간 전부 미스가 난다. **이 한 줄이 이 기능의 성립 조건이다** |
| F-03 | 변형(variant)은 `thumb`(목록 썸네일 변환본)과 `full`(상세·뷰어용) 2종이며 각각 독립된 캐시 항목이다 | Must | 같은 사진이라도 목록에서 본 것과 상세에서 본 것은 다른 바이트다 |
| F-04 | 이미지 표시 경로는 **캐시 조회 → 미스 시 네트워크** 순서다. 캐시 히트 시 네트워크 요청을 보내지 않는다 | Must | 히트인데도 요청을 보내면 지하 구간에서 타임아웃 대기가 생겨 기능이 무의미해진다 |
| F-05 | 캐시에서 읽은 이미지와 네트워크에서 받은 이미지는 화면상 **구분 표시하지 않는다** | Must | "캐시됨" 뱃지는 사용자에게 아무 행동 선택지도 주지 않는 잡음이다 |
| F-06 | 오프라인 + 캐시 미스일 때의 대체 표시는 온라인 로드 실패와 **문구로 구분**한다 ("오프라인이라 사진을 불러오지 못했어요") | Must | 원인이 다르면 사용자의 다음 행동도 다르다(재시도 vs 기다리기) |
| F-07 | 온라인 복귀가 감지되면, 화면에 떠 있는 실패 상태 사진을 자동으로 다시 로드한다 | Should | 사용자가 새로고침하게 만들지 않는다 |

### 3.2 용량 · 축출

| ID | 요구사항 | 우선순위 | 비고 |
|----|---------|---------|------|
| F-08 | 캐시 상한은 변형별로 둔다: `thumb` **1,000개 또는 40MB**, `full` **60개 또는 60MB**. 먼저 도달하는 조건이 적용된다 | Must | 변형별로 나누는 이유: 단일 풀이면 큰 `full` 몇 장이 썸네일 수백 개를 밀어내 목록 화면이 먼저 죽는다 |
| F-09 | 축출 정책은 **LRU**(`last_accessed_at` 오름차순)이며, 마지막 접근 후 **30일**이 지난 항목은 용량과 무관하게 폐기한다 | Must | TTL은 용량 관리가 아니라 §2.3의 "삭제 시차" 상한을 못 박기 위한 프라이버시 장치다 |
| F-10 | 로그아웃 시 캐시를 **전량 삭제**한다 | Must | 공용/가족 기기에서 다음 사용자에게 연애 사진이 남으면 안 된다 |
| F-11 | 커플 해제가 확인되면 캐시를 전량 삭제한다 | Must | 서버 접근 차단(`current_couple_id()` = NULL)과 기기 로컬을 같은 시점에 맞춘다 |
| F-12 | 캐시 저장소에 소유자(`user_id`, `couple_id`)를 함께 기록하고, 현재 세션과 불일치하면 **읽지 않고 전량 폐기**한다 | Must | 계정 전환·재로그인 시의 최종 방어선. F-10이 실패해도(강제 종료 등) 이게 막는다 |
| F-13 | 기록 삭제·사진 삭제(수정 중 제거 포함)를 클라이언트가 수행하면, 해당 `storage_path`의 캐시 항목을 함께 삭제한다 | Must | `06` F-15 삭제 흐름의 마지막 단계로 편입 |
| F-14 | 온라인 상태에서 기록 상세 조회 결과에 없는 사진의 캐시 항목은 정리한다 | Should | 상대가 지운 사진이 내 기기에서만 계속 보이는 상태를 줄인다(§2.3) |

| ID | 요구사항 | 우선순위 | 비고 |
|----|---------|---------|------|
| F-15 | 프로필 화면(`09-couple-profile.md`) 하단에 "오프라인 사진 저장 · 사용량 NNMB · 비우기" 한 줄을 둔다 | Should | 최대 100MB를 쓰면서 사용자가 그 사실을 알 방법도 되돌릴 방법도 없는 상태를 만들지 않는다 |

## 4. 데이터 모델

### 4.1 서버 측 변경

**없다.** 테이블·뷰·RPC·RLS 정책 어느 것도 추가하거나 수정하지 않는다.
이 기능은 **이미 인가를 통과해 클라이언트가 정당하게 수신한 바이트를 기기에 보관하는 것**
뿐이므로 서버 인가 경계(`00-data-model.md` §4.6 Storage RLS)를 전혀 건드리지 않는다.

> 반대로 말하면 **이 기능은 RLS 우회 경로가 될 수 없다.** 캐시에 들어가는 유일한 경로가
> "서명 URL 발급 성공 → 다운로드 성공 → 화면 표시 성공"이고, 서명 URL 발급 자체가
> `(storage.foldername(name))[1]::uuid = current_couple_id()` 정책을 통과해야 하기 때문이다.
> 남는 위험은 인가가 아니라 **기기에 남은 잔존물**이며, 그건 F-10~F-12가 담당한다.

### 4.2 클라이언트 로컬 저장소 계약

저장소는 **IndexedDB**를 쓴다. 선택 근거는 §9 결정 블록 참조.

**스토어: `photo_cache`**

| 필드 | 타입 | 필수 | 제약 |
|---|---|---|---|
| `key` | string | ✔ | PK. `` `${storage_path}::${variant}` `` |
| `storage_path` | string | ✔ | 인덱스. `record_photos.storage_path`와 동일 값 |
| `record_id` | uuid | ✔ | 인덱스. F-13의 일괄 삭제용 |
| `variant` | string | ✔ | `'thumb'` \| `'full'` |
| `blob` | Blob | ✔ | 이미지 바이트 |
| `byte_size` | int | ✔ | 용량 집계용(매번 Blob 크기를 재지 않기 위해) |
| `content_type` | string | ✔ | |
| `cached_at` | number | ✔ | epoch ms |
| `last_accessed_at` | number | ✔ | 인덱스. LRU 축출 기준(F-09) |

**스토어: `cache_meta`** (단일 행)

| 필드 | 타입 | 설명 |
|---|---|---|
| `owner_user_id` | uuid | F-12 검증용 |
| `owner_couple_id` | uuid | F-12 검증용 |
| `schema_version` | int | 레이아웃 변경 시 증가 → 불일치면 전량 폐기 |
| `bytes_by_variant` | `{ thumb: int, full: int }` | 용량 집계 캐시(F-08 판정을 O(1)로) |

**표시 경로 계약** (모든 사진 표시 지점이 이 순서를 따른다)

```
1. cache_meta 소유자 검증 → 불일치면 전량 삭제 후 캐시 없음으로 진행 (F-12)
2. photo_cache.get(`${storage_path}::${variant}`)
   ├─ 히트 → last_accessed_at 갱신 → createObjectURL(blob)로 표시 (F-04)
   └─ 미스 ↓
3. 온라인?
   ├─ 예  → 서명 URL 발급 → 다운로드 → 표시 → 성공 시 캐시 저장 (F-01)
   └─ 아니오 → 오프라인 대체 표시 (F-06)
```

- `createObjectURL`로 만든 URL은 요소가 화면에서 사라질 때 `revokeObjectURL`한다
  (안 하면 장시간 스크롤에서 메모리가 선형 증가한다).
- 캐시 쓰기는 **표시를 막지 않는다**. 표시를 먼저 하고 쓰기는 뒤에서 진행하며, 실패해도
  무시한다(§2.2 QuotaExceeded).

### 4.3 서명 URL과의 관계

서명 URL 유효기간은 1시간이다(`00` §4.6). 캐시는 **서명 URL을 저장하지 않는다** —
바이트만 저장한다. 따라서 만료 개념이 캐시에는 존재하지 않고, `06` §2.3의
"서명 URL 만료 시 자동 재발급"은 캐시 미스 경로에서만 그대로 유효하다.

## 5. 상태 정의

| 상태 | 화면 동작 |
|---|---|
| 캐시 사용 가능 · 히트 | 즉시 표시. 로딩 스피너를 보여주지 않는다(수십 ms 안에 끝나므로 스피너가 깜빡임만 만든다) |
| 캐시 사용 가능 · 미스 · 온라인 | 기존 동작 그대로(`width`/`height`로 자리 확보 후 로드) |
| 캐시 사용 가능 · 미스 · 오프라인 | 사진 자리에 "오프라인이라 사진을 불러오지 못했어요". 재시도 버튼은 두지 않는다(눌러도 실패가 확정) |
| 온라인 복귀 감지 | 화면에 남아 있는 실패 자리를 자동 재로드(F-07). 성공하면 조용히 교체 |
| 캐시 사용 불가(IndexedDB 차단) | 캐시가 없는 것처럼 동작. 프로필의 F-15 줄은 "이 브라우저에서는 사용할 수 없어요"로 표시 |
| 캐시 쓰기 실패(용량 초과) | 화면에 아무 변화 없음. 다음 축출 라운드에서 공간을 확보한 뒤 자연히 다시 시도된다 |
| 소유자 불일치 감지 | 전량 삭제 후 "캐시 없음"으로 진행. 사용자에게 알리지 않는다 |
| 비우기 실행 중 | F-15 줄의 버튼만 비활성 + 스피너. 화면의 이미 표시된 사진은 그대로 둔다 |

## 6. 비기능 요구사항

- **캐시 조회 지연**: 항목 1개 조회 p95 **20ms 이하**. 이 값을 넘으면 캐시가 오히려
  온라인 표시를 느리게 만든다. 목록 스크롤 중에는 뷰포트에 들어온 카드 단위로만 조회한다.
- **총 용량 상한**: 100MB(F-08의 40 + 60). iOS Safari의 스토리지 축출 정책상 상한을
  더 올려도 보장되지 않으므로 늘리지 않는다.
- **메인 스레드 예산**: 캐시 쓰기(Blob 저장)는 표시 완료 후 수행하며, 스크롤 중 프레임을
  떨어뜨리지 않아야 한다. `08` §6의 "카드 500개 누적 시 60fps 유지"를 이 기능이 깨면 안 된다.
- **축출 실행 시점**: 쓰기 직전에만 상한을 확인한다. 주기적 타이머를 돌리지 않는다.
- **접근성**: 오프라인 대체 표시도 `alt`를 유지한다(`06` §6의 자동 생성 문구를 그대로 사용)
  — 스크린리더 사용자에게는 사진이 안 보이는 것과 사진이 없는 것이 원래 같은 경험이므로,
  대체 텍스트까지 사라지면 정보량이 이중으로 준다.
- **브라우저**: `03-line-map.md` §6과 동일(iOS Safari 16+, Android Chrome 최신 2버전,
  데스크톱 Chrome/Safari/Edge 최신 2버전). 전 대상 브라우저가 IndexedDB + Blob 저장을
  지원한다.
- **프라이버시**: 캐시에 사진 바이트 외의 텍스트(일기·태그)는 넣지 않는다. 일기는 이미
  기존 스펙에서 "오프라인에서도 보이는" 것으로 정의돼 있고, 그 캐시는 이 스펙의 범위가
  아니다 — 여기서 범위를 넓히면 삭제 책임 지점이 둘로 갈라진다.

## 7. 확장 포인트

| 지점 | 지금 | 왜 열어두는가 |
|---|---|---|
| 캐시 채우기 시점 | 표시 성공 시에만(F-01) | "최근 기록 N건의 썸네일 선제 다운로드"를 붙이려면 이 스토어에 쓰는 진입점 하나만 추가하면 된다. 지금 만들지 않는 이유는 §9 참조 |
| 변형(variant) 종류 | `thumb` / `full` 2종 | 카드 이미지 저장(`10`)이 쓰는 해상도가 따로 필요해지면 값 하나 추가로 끝난다 |
| 저장 대상 | 사진 바이트 | 같은 키 구조로 다른 첨부(`00` §7의 음성 메모 등)를 담을 수 있다. 지금은 이미지 전용 |
| 콜드 스타트 오프라인 | 미지원 | 서비스워커 도입이 필요하고, 그건 SPA 전제(ADR-001)를 건드리는 별도 결정이다. §9 참조 |
| 사용량 노출 위치 | 프로필 화면 한 줄(F-15) | 후일 설정 화면이 생기면 그 줄만 옮기면 된다 |

**만들지 않는 것**: 캐시 on/off 토글, 기록 단위 "오프라인 저장" 핀 고정 UI,
캐시 동기화 상태 표시, 오프라인 기록 작성·큐잉(`05` §5는 이미 "오프라인에서 저장 불가"로
확정돼 있다 — 이 스펙은 **읽기 전용 기능**이며 쓰기 경로를 건드리지 않는다).

## 8. 완료 조건 (Acceptance Criteria)

- **AC-01** Given 온라인에서 기록 상세를 열어 사진 3장이 모두 표시된 상태, When 네트워크를 끊고 같은 기록을 다시 열면, Then 사진 3장이 모두 표시된다.
- **AC-02** Given 한 번도 열어본 적 없는 기록, When 오프라인에서 그 상세를 열면, Then 일기·태그·감정은 보이고 사진 자리에는 "오프라인이라 사진을 불러오지 못했어요"가 표시된다.
- **AC-03** Given 사진을 캐시한 뒤 1시간이 지나 서명 URL이 만료된 상태, When 오프라인에서 그 사진을 보면, Then 정상 표시된다(캐시는 URL이 아니라 바이트를 저장했음을 검증).
- **AC-04** Given 목록 썸네일만 캐시된 사진, When 오프라인에서 그 기록의 상세를 열면, Then 상세용 원본은 캐시 미스로 대체 표시되고 목록으로 돌아가면 썸네일은 정상 표시된다(변형 분리 검증).
- **AC-05** Given 캐시에 사진이 들어 있는 상태, When 로그아웃하면, Then IndexedDB의 `photo_cache`가 비어 있다.
- **AC-06** Given 사용자 A의 캐시가 남아 있는 기기, When 사용자 B로 로그인해 기록을 열면, Then A의 캐시는 전량 폐기되어 있고 A의 사진이 어떤 화면에도 나타나지 않는다.
- **AC-07** Given 커플이 연결 해제된 직후, When 앱을 다시 열면, Then 캐시가 비어 있다.
- **AC-08** Given 기록을 삭제한 직후, When IndexedDB를 확인하면, Then 그 `record_id`의 캐시 항목이 남아 있지 않다.
- **AC-09** Given `full` 캐시가 상한(60개)에 도달한 상태, When 새 사진을 상세로 열면, Then 가장 오래 접근하지 않은 항목이 밀려나고 새 항목이 들어가며 썸네일 캐시는 줄어들지 않는다.
- **AC-10** Given 저장 공간이 가득 차 캐시 쓰기가 실패하는 상황, When 온라인에서 사진을 보면, Then 사진은 정상 표시되고 에러 문구가 나타나지 않는다.
- **AC-11** Given 프라이빗 모드처럼 IndexedDB를 쓸 수 없는 브라우저, When 앱 전체를 사용하면, Then 모든 화면이 캐시 없이 정상 동작한다.
- **AC-12** Given 오프라인에서 사진이 실패한 화면을 열어둔 상태, When 신호가 복구되면, Then 사용자가 아무 조작을 하지 않아도 사진이 표시된다.
- **AC-13** Given 캐시에 데이터가 있는 상태, When 프로필 화면을 보면, Then 사용량(MB)이 표시되고 "비우기"를 누르면 0MB가 된다.
- **AC-14** Given 캐시 히트로 사진 20장이 표시된 목록, When 스크롤해서 화면 밖으로 내보내면, Then object URL이 해제되어 메모리 사용량이 선형 증가하지 않는다.

## 9. 미결정 항목

> ✅ **결정 완료 (2026-08-26) — 저장소는 IndexedDB, 서비스워커/Cache API는 쓰지 않는다.**
>
> **근거**: (1) Cache API는 요청 URL을 키로 삼는데, 이 앱의 사진 URL은 1시간마다 바뀌는
> 서명 URL이라 키가 매번 달라진다 — 서비스워커에서 쿼리스트링을 잘라내는 정규화 로직을
> 따로 짜야 하고, 그건 "요청을 가로채는 코드"라는 가장 디버깅하기 어려운 종류의 부채다.
> (2) 서비스워커를 도입하는 순간 등록·업데이트·강제 갱신·구버전 고착 같은 배포 문제군이
> 통째로 따라오는데, 이는 `docs/decisions/001-tech-stack.md`가 확정한 "순수 SPA" 전제를
> 건드리는 결정이라 ADR 없이 스펙에서 정할 사안이 아니다. (3) IndexedDB는 Blob을 그대로
> 저장할 수 있고 대상 브라우저 전부가 지원하며, 애플리케이션 코드 안에서 열고 닫히므로
> 로그아웃 시 전량 삭제(F-10) 같은 프라이버시 요구를 확실하게 구현할 수 있다.

> ✅ **결정 완료 (2026-08-26) — 선제 프리페치는 하지 않는다(F-01).**
>
> **근거**: "최근 기록 N건을 미리 받아둔다"는 원 아이디어가 더 강력해 보이지만, 그 순간
> **사용자가 요청하지 않은 다운로드**가 생긴다 — 셀룰러 요금·배터리·저장공간을 예고 없이
> 쓰는 동작이고, 이를 정당화하려면 "Wi-Fi에서만" 같은 조건이 필요한데 브라우저에서
> 연결 종류 판별(`navigator.connection`)은 iOS Safari에서 아예 지원되지 않아 조건을
> 신뢰성 있게 걸 수 없다. 반면 표시 시점 캐싱만으로도 원 시나리오("예전 데이트 기록을
> **다시** 보려고")의 대부분을 덮는다 — 다시 본다는 것은 한 번은 봤다는 뜻이기 때문이다.
> 실사용에서 "한 번도 안 본 기록을 지하철에서 열고 싶다"는 요구가 확인되면 §7의 확장
> 지점으로 다시 검토한다.

> ❓ **미결정 — 콜드 스타트 오프라인(앱 자체가 안 뜨는 문제)**
>
> §1.1대로 이 스펙은 "앱은 떴는데 사진만 안 뜨는" 구간만 해결한다. 지하 구간에서 앱을
> **처음 여는** 경우는 HTML·JS 번들 로드부터 실패하므로 이 스펙과 무관하게 아무것도
> 보이지 않는다. 이를 해결하려면 서비스워커로 앱 셸을 캐싱해야 하고, 그것은 사실상
> PWA 전환이라 `ADR-001`(순수 SPA)의 재검토가 필요하다. 사용자에게 확인할 것:
> - 실사용에서 "지하철에서 앱을 켰는데 아무것도 안 뜬다"가 실제로 반복되는가,
>   아니면 대부분 앱을 이미 열어둔 채 내려가는가?
> - 서비스워커 도입(= 배포·캐시 무효화 복잡도 증가)을 감수할 만한 빈도인가?
>
> 확인 전까지는 도입하지 않는다. 도입하기로 하면 스펙이 아니라 **ADR로 먼저 기록**한다.

> ❓ **미결정 — 총 용량 상한 100MB의 적정성(F-08)**
>
> 40MB/60MB 배분은 "썸네일 ~40KB × 1,000장", "상세 원본 ~1MB × 60장"이라는 추정에서
> 역산한 값이며 실측 근거가 없다. 실사용 후 (a) 캐시 히트율, (b) 실제 축출 빈도를 보고
> 조정한다. 상수 2개(항목 수·바이트)만 바꾸면 되도록 구현할 것.
