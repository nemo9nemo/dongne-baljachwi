# 동네 발자취 — 프로젝트 분석 및 개발 가이드

작성일: 2026-10-01 · 기준: 현재 로컬 `master`의 문서와 소스 코드

## 1. 결론과 분석 범위

최종 결과물은 **두 사람이 함께 사용하는 비공개 데이트 아카이브 반응형 웹 앱**이다. 노선도를 채우는 공간 탐색, 사진과 일기의 기록, 타임라인을 통한 회고가 하나의 흐름으로 이어져야 한다. 일반 지도 검색 서비스나 공개 SNS로 확장하는 것은 현재 제품 방향과 맞지 않는다.

현재는 목데이터 프로토타입 단계가 아니다. 인증·초대·커플 연결, Supabase 저장, 노선도·지도·타임라인·프로필·PNG 저장까지 구현되어 있다. 다음 개발의 중심은 화면을 더 만드는 것보다 **공동 기록의 일관성, 실패해도 보존되는 사진, 오래 쌓인 추억의 탐색**이어야 한다.

분석 근거는 `docs/PRD.md`, 기능 스펙 00~13, ADR, `docs/PROGRESS.md`, 실제 React/SQL/배치 코드다. PRD의 과거 “미착수” 표시는 현재 구현 상태를 나타내지 않는다. 외부 노션이나 운영 서버는 조회하지 않았다. 코드에서 확인한 사실과 그로부터 도출한 위험, 신규 제안을 아래에서 구분한다.

실제 로그인·두 기기 사용·운영 DB·Storage·카카오 지도·모바일 화면 검증은 수행하지 않았다. 따라서 운영 서비스의 장애 발생 여부나 배포 상태를 단정하지 않는다. 애플리케이션 코드와 SQL은 수정하지 않고 이 문서만 추가했다.

## 2. 최종 아웃풋의 형태

### 2.1 사용자가 받는 경험

| 영역 | 최종 형태 | 사용자가 얻는 결과 |
|---|---|---|
| 시작 | 이메일 가입·확인 → 로그인 → 커플 생성 또는 초대 참여 | 둘만 접근하는 공동 공간 |
| 홈 | 수도권 노선도, 호선 선택, 확대·이동, 방문 스탬프·횟수 | 어디를 함께 갔는지 한눈에 파악 |
| 보조 지도 | 방문 역의 실제 좌표 핀, 전체 핀 보기 | 기록의 지리적 위치 확인 |
| 역 상세 | 역 정보·방문 기록·작성 진입 | 특정 동네의 추억 탐색 |
| 작성 | 역·날짜 필수, 감정·날씨·태그·일기·사진 선택 | 짧은 기록도 부담 없이 축적 |
| 기록 상세 | 사진·일기 전문, 수정·삭제, 카드 PNG 다운로드 | 회고·관리·이미지 보관 |
| 타임라인 | 최신순 기록, 월 구분, 태그 필터, 기간 이동 | 공간과 별개로 과거 추억 탐색 |
| 프로필 | 이름·사귄 날·통계·미방문 역 후보·계정 관리 | 축적 성취와 다음 데이트의 단서 |

공동 기록은 작성자와 무관하게 커플 양쪽이 열람·수정·삭제한다. 최초 작성자와 마지막 수정자는 구분한다. 커플 생성 후 상대가 합류하기 전 상태도 지원한다. 커플 해제는 접근 차단과 데이터 정리 정책을 함께 갖춰야 한다.

PNG는 개별 기록의 파생 산출물이다. 여러 기록과 원본 사진을 복원할 수 있는 전체 백업과는 기능이 다르다.

### 2.2 핵심 사용자 여정

1. 가입·이메일 확인·커플 연결을 마친다.
2. 노선도에서 역을 선택하거나 타임라인의 작성 버튼으로 시작한다.
3. 역과 방문일을 지정하고 선택 정보를 입력한다. 사진은 기기에서 축소·JPEG 변환하며 EXIF를 제거한다.
4. 저장하면 기록 상세에서 결과를 확인한다. 노선도 스탬프, 방문 횟수, 목록, 프로필 통계도 같은 기록을 반영한다.
5. 상대의 기기에서도 변경을 확인할 수 있어야 한다. 동시 수정에서는 조용한 덮어쓰기 대신 충돌을 설명한다.
6. 기록이 많아지면 태그와 연월 이동으로 과거를 찾는다. 재방문과 몰아쓰기는 기존 정보를 참고하며 이어서 작성한다.

5번의 동기화·충돌 안내와 6번의 일부 흐름은 현재 보완이 필요하다. 기존 스펙 11~13의 오프라인 사진 열람은 실행 중인 앱의 네트워크 단절을 다룬다. 서비스워커/PWA 미도입 결정을 유지하므로 완전 오프라인 콜드 스타트와 오프라인 저장을 약속하지 않는다.

## 3. 현재 동작 구조와 구현 수준

### 3.1 구조

- `src/App.tsx`: React 데이터 라우터. 인증과 커플 유무 가드 뒤에서 화면을 제공한다. 작성 중 이탈 방지에 `useBlocker`를 사용한다.
- `src/auth/SessionProvider.tsx`: Auth 세션, 멤버십, 커플·프로필 정보를 읽고 컨텍스트로 제공한다.
- 화면과 `src/lib/*`: Supabase JS로 DB/RPC/Storage를 직접 호출한다. 별도 앱 API 서버는 없다.
- SQL 마이그레이션: RLS·컬럼 권한·RPC가 인가 경계다. 프론트 가드는 사용자 경험을 담당하며 인가를 대신하지 않는다.
- 노선도: DB 역 마스터와 정적 도식 좌표 JSON을 역 코드로 연결한다. 지도는 실제 위경도를 사용한다.
- `screen-cache.ts`: 방문 집계와 목록·스크롤을 메모리에 보관한다. 로컬 작성·삭제에서 캐시를 무효화하거나 일부 제거한다.
- 사진: 본문·태그 RPC 저장 → Storage 업로드 → 사진 메타데이터 동기화 순서다. DB와 Storage는 하나의 트랜잭션이 아니다.
- 타임라인: `(visited_on, id)` 키셋으로 20건씩 조회한다. 목록용 뷰는 일기를 200자로 잘라 반환한다.
- 카드 이미지: 클라이언트에서 합성해 PNG로 내보낸다. Vercel 설정은 SPA 경로를 `index.html`로 되돌린다.

### 3.2 구현되어 유지할 부분

인증 가드, 커플별 캐시 구분, 본문·태그의 원자적 RPC 저장, RLS 격리, 목록 전용 일기 발췌 뷰, 키셋 페이지네이션, 사진 용량 축소, 입력 초안·이탈 확인, 지도/목록 복귀 상태 보존은 이미 있다. 이 기능을 “신규 구현” 항목으로 중복 계획하지 않는다.

추천도 목데이터가 아니다. `station-recommendation.ts`는 활성 MVP 미방문 역을 후보로 삼고, 방문 역과의 `seq` 차이·일일 시드·노선별 상한으로 선정한다. 다만 정확한 이동 거리나 소요시간을 계산하는 추천은 아니다.

### 3.3 실행한 검증

| 명령 | 결과 | 확인 범위 |
|---|---|---|
| `npm run lint` | 종료 코드 0, 경고 5건 | 정적 린트. 경고를 무조건 오류로 간주하지 않음 |
| `npm run test:db` | 178/178 통과 | PGlite에서 전체 마이그레이션·RLS·RPC 계약 |

빌드와 브라우저 검증은 이번 분석에서 실행하지 않았다. DB 테스트는 Auth 서비스, 실제 PostgREST 에러 봉투, Storage 서명/변환/업로드를 재현하지 않는다(`supabase/tests/README.md`). 통과한 테스트가 최신 기획을 검증하는지도 별도로 확인해야 한다.

## 4. 우선 개선 항목: 실제 수정 방향과 근거

우선순위는 **제안**이다. P0는 출시 전 데이터·공동 사용 신뢰성, P1은 핵심 사용성, P2는 계측 후 확장으로 정의한다. 기존 PRD의 기능 우선순위 표와 구별한다.

### G-01 · P0 · 사진 메타데이터 교체를 원자적으로 처리

**확인 사실:** `RecordEditorScreen.tsx`의 `syncPhotos()`는 순서가 바뀐 기존 사진을 DELETE한 뒤 별도 INSERT로 복원한다. INSERT 실패 시 재시도를 제공하지만 삭제된 행은 그 사이 복원되지 않는다. 본문은 먼저 저장되어 있다.

**영향:** 사진 순서를 바꾸는 작업이 실패하면 원본 객체가 있어도 사진이 기록 목록에서 빠질 수 있다. 재시도 전에 사용자가 닫으면 복구가 진행되지 않는다.

**수정 방향:** Storage 업로드는 기존처럼 선행하되, 최종 사진 목록의 추가·삭제·순서 변경은 하나의 `sync_record_photos` RPC에서 트랜잭션으로 처리한다. 기록의 커플 소유권, 사진 ID·경로의 귀속, 개수·순서·크기·타입을 서버에서 검증한다. 같은 요청 재시도는 같은 최종 상태를 만들도록 한다. 임시 슬롯 또는 삭제 후 재삽입을 사용하더라도 RPC 안에서 끝내 유니크 제약의 중간 충돌을 피한다.

**경계:** Storage와 SQL까지 원자적이라고 설명하면 안 된다. DB 반영 성공 후에만 제거 대상 객체를 정리하고, 업로드 성공/메타데이터 실패 객체는 유예 후 정리한다. 기존 Storage RLS를 유지한다.

**변경 대상:** 에디터, 사진 RPC 래퍼·타입, 새 SQL 마이그레이션, DB 테스트, 스펙 05의 사진 저장 계약.

**완료 기준:** 순서 교체 중 SQL 실패 시 기존 메타데이터가 그대로 유지된다. 재시도에서 중복 행이 생기지 않는다. 다른 커플 기록·경로로 요청하면 거부된다.

### G-02 · P0 · 두 기기 사이 변경과 커플 상태를 재검증

**확인 사실:** `screen-cache.ts`는 같은 브라우저의 저장·삭제에서 갱신된다. `SessionProvider.tsx`의 커플 조회는 세션 사용자 변경과 명시적 `reload`에 의존한다. `src` 검색에서 Realtime 구독·포커스 복귀 재조회·BroadcastChannel이 확인되지 않았다.

**추론되는 위험:** 상대가 초대에 합류하거나 기록을 추가·삭제·수정해도 이미 열린 화면과 캐시에 즉시 반영되지 않을 수 있다. 서버 RLS의 차단과 화면에 남은 과거 데이터는 별개의 문제다.

**수정 방향:** 먼저 앱 포그라운드 복귀·온라인 복귀에서 세션/멤버십을 재검증하고, 변경 세대 번호 또는 캐시 신선도 기준으로 목록·통계를 재조회한다. 상시 실시간성이 필요한지는 두 기기 검증 후 결정한다. 필요하면 Realtime 이벤트는 재조회 신호로 사용하고 커플 해제 감지는 별도 검증 경로를 둔다.

오래된 응답이 새 사용자·커플의 상태나 캐시에 들어가지 않도록 모든 로더에 요청 세대/소유자 검사를 둔다. 캐시 변수만 비우면 이미 마운트된 화면의 React state는 갱신되지 않으므로 구독 가능한 갱신 신호가 필요하다. 갱신 중에도 스크롤을 유지하고 작성 중 폼은 덮어쓰지 않는다.

**완료 기준:** A가 작성한 기록을 B의 앱 복귀 후 확인한다. A가 해제하면 B의 온라인 상태 재검증 후 가드가 이동하고 커플 캐시가 비워진다. 계정 전환 중 늦은 응답이 이전 기록을 다시 넣지 않는다. “오프라인 기기의 즉시 삭제”는 보장하지 않는다.

### G-03 · P0 · 사진 부분 실패가 남아 있으면 이탈 보호

**확인 사실:** 저장 후 `photoBaselineRef`를 실패 사진까지 포함한 ID 목록으로 갱신한다. `dirty`는 폼 값과 사진 ID 목록을 비교한다. 사진 내용·성공 여부는 비교하지 않는다.

**추론되는 위험:** 본문은 저장됐지만 사진이 실패한 상태에서 `dirty=false`가 되어 닫기/이탈 경고가 사라질 수 있다. 미업로드 사진 Blob은 메모리에 있어 초안 텍스트로 복구되지 않는다.

**수정 방향:** 본문 변경과 미완료 사진 저장을 별도 상태로 관리한다. 실패한 새 사진 또는 메타데이터 동기화 실패가 남으면 경고와 재시도를 유지한다. 안내는 “기록 본문 저장됨, 사진 N장 미완료”로 구분하고 재시도는 본문을 다시 덮어쓰지 않게 분리한다.

**완료 기준:** 사진 실패 후 뒤로가기·새로고침에서 경고가 뜬다. 재시도 성공 후 경고가 해제된다. 본문만 저장하고 나가는 선택은 결과를 명확히 설명한다.

### G-04 · P0 · 명세·SQL·테스트의 규칙 불일치 정리

**확인 사실 1:** 스펙 01 F-11은 초대 유효기간 7일로 확정했지만 `20260811120100_couple_link.sql`은 `interval '72 hours'`이며 테스트도 72시간을 기대한다. 프론트 초대 화면 주석은 7일 기준이다.

**수정 방향:** 7일 결정을 기준으로 새 마이그레이션에서 코드 발급 함수와 테스트를 수정한다. 기존 발급 코드는 만료 시각을 유지하고 새 발급부터 적용하는 방안을 권장한다. 저장소와 운영 함수 정의가 같은지는 배포 전 별도로 확인한다. 과거 마이그레이션을 덮어써 이력을 숨기지 않는다.

**확인 사실 2:** 스펙 05·에디터·최신 SQL은 일기 최대 1,000자인데 `record-rpc.ts`의 `NOTE_TOO_LONG` 안내는 2,000자다.

**수정 방향:** 안내를 1,000자로 정정하고 입력/서버/오류 메시지를 같은 계약으로 점검한다. 한국어·이모지의 JS 길이와 SQL `char_length` 차이도 경계 사례로 확인한다.

**완료 기준:** 신규 초대는 7일 만료, 만료·재발급 경계 테스트가 최신 스펙과 일치한다. 일기 1,000자·1,001자 결과와 안내가 일치한다. 테스트 통과 수보다 테스트가 검증하는 규칙을 리뷰한다.

### G-05 · P0 · 동시 수정의 유실 방지

**확인 사실:** 최신 `upsert_record`는 기존 버전을 인자로 받지 않고 기록을 UPDATE한다. 스펙 05의 예외 흐름도 충돌 안내 미구현을 명시한다.

**수정 방향:** 로딩 시 버전을 기억하고 저장 RPC에 기대 버전을 전달하는 낙관적 잠금을 추가한다. 버전 불일치 시 트랜잭션을 실패시키고 입력을 보존한 채 최신 내용 확인/명시적 덮어쓰기 선택을 제공한다. 사진 교체도 같은 기록 버전 체계에 포함한다.

**주의:** 낙관적 잠금 도입 후에도 직접 UPDATE가 자유롭게 열려 있으면 RPC 밖에서 규칙을 우회할 수 있다. 컬럼 권한·쓰기 경로와 트리거를 함께 검토하고 본문/태그/사진 변경의 잠금 순서를 정한다. 우선 버전 비교만 추가하고 자동 병합·편집 이력은 뒤로 미룬다.

**완료 기준:** A/B가 같은 버전을 열고 A 저장 후 B 저장하면 B 입력이 보존되고 충돌을 알린다. B의 재시도가 사진만 복구하면서 A의 본문을 조용히 덮어쓰지 않는다.

### G-06 · P0 · 서버 데이터 정리의 운영 경로 구현

**확인 사실:** 스펙 01은 해제 30일 후 정리 배치, 스펙 00은 고아 Storage 정리를 요구한다. SQL에는 `purge_after`가 있지만 확인한 마이그레이션·스크립트에 실제 정리 잡 구현은 없다. 별도 운영 환경에 잡이 있는지는 미확인이다.

**수정 방향:** 서버 전용 잡으로 만료 커플과 고아 객체 정리를 분리한다. service role은 서버에만 둔다. 커플 정리는 Storage → DB 순서로 진행하며 실패 시 대상과 재시도 상태를 남긴다. 고아 정리는 업로드 시각 유예를 두어 업로드와 DB 등록 사이의 정상 객체를 지우지 않는다. 실행 전 대상 산출과 dry-run을 제공한다.

**완료 기준:** 보존기간 전 데이터는 유지된다. 부분 실패 후 다시 실행해 정리된다. 진행 중 업로드와 활성 기록 사진은 제외된다. 실행 결과·실패 수를 운영자가 확인한다. 실제 삭제 작업은 이 분석에서 수행하지 않는다.

### G-07 · P1 · 타임라인 요청 경쟁과 확장성 개선

**확인 사실:** `TimelineScreen.tsx`의 초기 조회·추가 페이지는 요청 세대 검사 없이 상태를 갱신한다. 태그 후보 ID를 `record_tags`에서 전부 받아 `.in('id', candidateIds)`로 전달한다. 사진·태그 추가 조회와 썸네일 서명 요청도 별도로 발생한다.

**영향:** 빠른 태그 전환 중 이전 응답이 새 필터 결과를 덮거나, 이전 필터의 추가 페이지가 새 목록에 합쳐질 가능성이 있다. 태그 데이터가 서버 반환 상한을 넘으면 후보 누락, 큰 URL, 불필요한 요청이 발생할 수 있다.

**수정 방향:** 커플·태그·시작월을 조회 키로 만들고 요청 세대를 확인한다. 첫 조회와 추가 페이지 모두 이전 키 응답을 버린다. 태그 조건은 서버에서 `EXISTS`로 처리하며 커서와 페이지 크기를 함께 적용하는 조회 RPC를 검토한다. 읽기 RPC는 `SECURITY INVOKER`와 RLS를 유지한다. 목록용 사진 개수·대표 사진·태그 요약을 묶을지는 실측 후 결정한다.

**완료 기준:** 지연을 달리한 태그 A/B 요청에서 마지막 선택만 표시된다. 이전 필터 페이지가 섞이지 않는다. 5,000건 데이터에서 태그 결과와 페이지 합계가 정확하다. 요청 수는 DB/RPC·서명·이미지를 분리해 측정한다.

### G-08 · P1 · 서명 URL 만료와 이미지 실패 복구

**확인 사실:** `photo-storage.ts`는 3,600초 서명 URL을 발급하고 목록 캐시는 URL을 보관한다. `RecordCard.tsx`의 이미지에는 실패 시 재발급 경로가 없다.

**수정 방향:** URL 문자열 대신 저장 경로와 만료 정보를 이미지 로더가 관리한다. 캐시 복귀 시 만료 여부를 확인하고, 온라인 이미지 실패는 재발급을 최대 1회 시도한다. 권한 재검증 실패면 재시도를 중지한다. 이후 G-10의 Blob 캐시와 하나의 표시 경로로 통합한다.

**완료 기준:** 장시간 후 목록 복귀에서도 사진이 다시 표시된다. 404·네트워크 실패에서 무한 재시도가 없다. 사진 오류가 기록 카드 전체를 막지 않는다.

### G-09 · P1 · 역 범위와 커버리지 지표 통일

**확인 사실:** 프로필 분모는 활성 MVP 역 수지만 분자는 `visits.rows.length`다. StationPicker는 `is_active`만 필터링한다. 노선도의 좌표 없는 역 목록도 활성 여부만 본다. 역 범위와 도식 표현 범위는 동일하지 않다.

**영향:** 범위 밖 기록이 포함되면 “수도권 커버리지” 분자와 분모의 모집단이 달라진다. 단순히 퍼센트를 100으로 자르는 것은 계산 오류를 가린다.

**수정 방향:** 총 기록 수·전체 방문 역 수는 유지하되 커버리지 분자는 활성 MVP 집합과 방문 집합의 교집합으로 계산한다. 작성 가능 범위를 MVP로 제한할지, 범위 밖 기록을 허용하고 통계만 분리할지는 스펙으로 명시한다. 기본 검색은 MVP 우선, 다른 역은 명시적 확장으로 제공하는 방안을 권장한다.

도식 없는 MVP 역은 검색·역 상세로 접근 가능해야 한다. 노선도에 역 이름 검색을 제공해 밀집된 SVG에서 찾기 어려운 역과 미도식 역을 같은 진입점으로 연결한다. 범위 밖 전체 역을 단순 “좌표 준비 중”으로 나열하지 않는다.

**완료 기준:** 범위 밖 방문·폐역·미도식 MVP 역을 넣어도 통계 의미가 유지된다. 사용자가 검색한 역의 상세와 기록 추가에 도달한다.

### G-11 · P1/P2 · 추천의 설명 가능성과 노선도 품질

**확인 사실:** 추천의 거리 기준은 `seq` 차이다. 진행 문서에는 일부 노선 `seq`가 실제 순서와 다르다는 기록이 있다. 노선도 시드는 최소신장트리 복원으로 이를 보완하지만 추천은 그 복원 결과를 쓰지 않는다.

**수정 방향:** 단기적으로 추천을 “아직 안 가본 역 후보”로 표현해 이동시간 정확도를 암시하지 않는다. 역 순서·분기·순환선 데이터가 검증된 후 그래프 최단 경로로 바꾸는 것을 별도 범위로 잡는다. 근거 라벨과 다른 후보 보기는 실제 피드백이 있으면 추가한다.

노선도는 정합성 검사와 사용성 검사를 나눠야 한다. 역 참조가 맞아도 원·라벨·클릭 영역이 겹칠 수 있다. 전체 보기·도심 확대·환승역·호선 선택을 모바일에서 측정하고, 밀집 구간은 확대 수준별 라벨 표시와 환승역 합성 표현을 검토한다. 초기 로그인 번들에 모든 화면이 정적 import되어 있으므로 라우트별 lazy 로딩도 빌드 크기/첫 로딩 실측 후 적용한다.

**완료 기준:** 추천이 비활성·방문 역을 내지 않는다. 환승·분기·순환선 테스트가 추천 설명과 일치한다. 노선도 터치 대상·키보드 접근·프레임 시간·메모리를 실측한다. 문서의 “60fps” 목표를 측정 결과로 오인하지 않는다.

## 5. 추가 기능 제안과 보류 범위

### 5.1 전체 기록 내보내기 — P2 제안

장기 보관 가치와 커플 해제 시 접근 차단을 고려하면 JSON/CSV 기록 메타데이터와 사진을 묶는 사용자 백업이 유용하다. 현재 확정 스펙은 아니므로 별도 요구사항으로 작성한다. 대량 다운로드의 페이지네이션, 만료 URL 재발급, 진행률·재시도·개인정보 포함 범위를 정해야 한다. PNG 저장을 이 기능의 완료로 계산하지 않는다.

### 5.2 운영 진단 — 출시 전 준비

저장 성공률·사진 부분 실패·권한 거부·정리 잡 실패·최초 로딩 시간은 구분해 관측한다. 일기·사진·초대 코드·이메일·서명 URL은 로그에 담지 않고 기능명/오류 코드/소요시간 정도를 수집한다. 서비스 데이터 접근 권한과 별개로 운영 도구의 접근을 관리한다.

### 5.3 지금 확대하지 않을 것

공개 피드·소셜 관계·장소 리뷰·상업 추천·채팅은 현재 목적을 분산한다. PWA·푸시·사진첩 공유 진입은 기존 미도입/기각 결정을 임의로 뒤집지 않는다. 기념일 알림·연간 리포트·자동 병합·전국 노선 확대·목록 가상화는 사용자 요구나 성능 실측을 근거로 별도 계획한다.

## 7. 검증 가이드

### 7.1 우선 재현할 시나리오

1. 독립 커플 A/B를 구성하고 URL ID·RPC·Storage 경로를 바꿔도 상대 커플 데이터를 볼 수 없는지 확인한다.
2. 같은 커플의 두 세션에서 합류·작성·수정·삭제·해제를 수행하고 앱 복귀와 캐시 상태를 확인한다.
3. 사진 순서를 바꾸며 업로드 성공/DB 삽입 실패를 주입한다. 기존 사진 유지와 재시도 결과를 확인한다.
4. 사진 부분 실패 후 뒤로가기·새로고침 경고, 본문 보존, 재업로드를 확인한다.
5. 태그 필터 A/B를 빠르게 전환하고 이전 추가 페이지 응답을 늦춰 결과 혼합을 확인한다.
6. 1시간 이상 지난 카드 복귀, 만료 서명, 사진 삭제, 네트워크 복귀에서 표시를 확인한다.
7. 월 경계·동일 날짜 여러 기록·태그·기간 이동·삭제가 섞인 페이지네이션에서 중복/누락을 확인한다.
8. 범위 밖·폐역 방문을 포함해 총 방문 수와 MVP 커버리지 분자/분모를 각각 검증한다.
9. 360px 모바일·데스크톱 프레임·키보드·다크 모드에서 폼, 지도, 대화상자, 복귀 스크롤을 확인한다.

### 7.2 자동화와 실제 서비스 검증의 역할

- DB 테스트: 소유권·RPC 원자성·낙관적 잠금·초대 만료·월 집계·권한을 검증한다.
- 프론트 통합 테스트: 요청 경쟁·상태 전이·부분 실패·history 복귀·캐시 소유자를 검증한다.
- 실제 서비스 통합: 메일 인증/비밀번호 재설정, PostgREST 오류, 서명 만료·Storage 이미지 변환, 두 세션 동작을 검증한다.
- 배포 확인: Auth redirect URL·카카오 실제 배포 도메인·환경 변수·깊은 링크 새로고침·적용 마이그레이션을 확인한다. 과거 localhost 확인 기록을 운영 검증으로 대체하지 않는다.

CI가 확인되지 않았으므로 향후 lint·build·test:db를 PR 필수 체크로 구성한다. 경고는 의존성 의도를 검토해 수정하며, 스크롤 복원용 effect에 의존성을 기계적으로 추가해 동작을 바꾸지 않는다.

## 8. 문서 정리 기준

README의 “디자인 문서 아직 없음”, App.tsx·record-card-query.ts의 과거 구현 단계 주석, PROGRESS의 일부 DDL 적용 대기·역 수·진행률 표현이 최신 내용과 혼재한다. 문서를 완료 증거로 쓰기 전에 코드·적용 환경·검증 결과를 대조한다.

PROGRESS는 구현 완료, 로컬 자동 검증 완료, 실 서비스 검증 완료, 배포 완료를 별도 상태로 기록하도록 개선한다. 90% 같은 체감 수치보다 “사진 부분 실패 검증 미완료”처럼 출시를 막는 구체 조건을 우선 표시한다. 이 분석에서는 기존 문서를 덮어쓰지 않았다.

최종 출시 판단은 기능 개수보다 **두 사람이 기록을 잃지 않고 함께 축적하고 다시 찾을 수 있는가**에 둔다.
