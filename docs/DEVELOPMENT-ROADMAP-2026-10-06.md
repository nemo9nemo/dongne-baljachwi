**2026-10-15 진행 갱신:** D01–D04는 로컬 구현·검증 완료. 현재 스키마 167개/전환 전 이력 73개 DB 검사,

## 1. 개발 목표와 현재 기준

**노선도를 메인 화면으로 유지하고, 기록이 안전하게 저장되며 원하는 기록을 쉽게 찾고 다시 작성할 수 있게 만든다.**

사용자는 현재 노선도 방향을 승인했다. 이번 후속 개발에서 홈을 최근 기록 목록이나 일반 지도로 바꾸지 않는다. 노선도 배치·표현을 다시 만드는 작업도 우선 실행 목록에서 제외한다. 기존 노선도 개선과 관련 없는 기록·조회·복구 기능부터 순서대로 개발한다.

### 확정 사항과 미정 사항

| 구분 | 내용 | 개발 시 취급 |
|---|---|---|
| 확정 | 첫 화면과 핵심 탐색 수단은 노선도 | 기존 `/lines` 진입과 역 탐색을 유지 |
| 확정 | 현재 노선도의 시각 방향 유지 | [1차 구현 보고](design/line-map-implementation-2026-10-06.md)를 기준으로 회귀 검증 |
| 확정 | 나머지 개선을 순서대로 진행 | 저장 신뢰성 → 제품 계약·복구·검색 → 작성 편의 → 선택 기능 |
| 현재 구현 | 커플 공간에 기록·태그·사진이 귀속되고 공동 편집 가능 | 개인 전환이 적용되기 전까지 실제 권한 계약으로 취급 |
| 후속 목표 | 개인 사용을 기본으로 하고 공유는 선택 | 이전 개인 전환 문서의 목표이며, 아래 소유권 정책 확정 후 적용 |
| 미정 | 기존 공동 기록의 보존/복사 방식 | D05에서 결정. `author_id`를 개인 소유자로 자동 간주하지 않음 |
| 미정 | 선택 공유의 읽기/기여 권한 | D05에서 결정. 읽기 전용을 권장하지만 확정된 요구로 취급하지 않음 |
| 미정 | 기록 복구 기간·탈퇴 시 공동 기록 처리·공동 기록 내보내기 범위 | D20·D21 실행 전 결정 |

이전 대화에서 소유권·공유 정책에 대한 답변은 아직 확인되지 않았다. **문서 작성 요청이나 시간 경과를 정책 승인으로 해석하지 않는다.** 정책과 무관한 D01–D04는 바로 개발할 수 있다. 정책 미정으로 D06이 대기하더라도 D07–D14 중 기존 권한 모델에서 독립적으로 가능한 작업은 계속 진행한다.

### 기존 문서와의 관계

- 최신 사용자 결정인 **노선도 메인**을 적용한다. 이전 개인 전환 조사 문서의 ‘최근 기록 홈·일반 지도 기본’ 제안은 채택하지 않는다.
- [개선 백로그](IMPROVEMENT-BACKLOG-2026-10-06.md)는 문제와 근거를 보존한다. **실행 순서와 목표 동작은 본 문서**, 실제 적용 여부는 단계별 구현 보고에서 확인한다.
- 기존 스펙 05의 사진 직접 DELETE/INSERT, 사진 실패 후 상세 이동 등은 D03–D04의 개선 대상으로 명시한다. 구현 시 스펙 05·DB 타입·테스트를 함께 개정한다.
- 스펙 11–13은 기능 세부 근거로 재사용한다. 커플 전용 접근 범위는 개인 전환 결정 후 해당 기능과 함께 수정한다.
- 이전 문서에 적힌 테스트 통과나 현재 작업 트리의 수정 파일을 후속 작업의 완료 근거로 재사용하지 않는다.

| 상황 | 최종 동작 |
|---|---|
| 로그인 후 진입 | 노선도가 열림. 역 검색·선택 또는 기록 추가로 이동 |
| 기록 작성 | 역·방문일 필수. 사진·일기·감정·날씨·태그·장소 이름은 선택 |
| 사진 준비 중 | 글 입력은 가능. 저장과 사진 목록 변경은 준비 완료까지 제한하고 이유 표시 |
| 수정 초기 조회 일부 실패 | 불완전한 폼을 저장 가능한 상태로 열지 않음. 실패 안내와 재시도 제공 |
| 정상 저장 | 기록 상세로 이동. 목록·방문 집계·통계가 새 기록을 반영 |

| 개인 전환 적용 후 | 초대나 관계 정보 입력 없이 사용. 공유는 별도 선택. 기존 공동 기록은 확정한 보존 정책을 따름 |

개인 전환·선택 공유에 관한 행은 **D05 결정 후의 목표**이며 현재 동작을 설명하는 표가 아니다.

## 4. 1단계 — 저장 신뢰성

### D01 · P0 · 수정 데이터 로드 실패와 빈 값 구분

연결 항목: **R01**\
수정 대상: `src/screens/records/RecordEditorScreen.tsx`, `RecordDetailScreen.tsx`, 조회 계약·관련 테스트.

**개발 방향**

1. 본문·태그·사진 메타데이터는 수정에 필요한 필수 로드로 묶는다. 하나라도 조회 실패하면 저장 가능한 `ready`로 전환하지 않는다. 태그/사진 오류를 `[]`로 바꾸지 않는다.
2. 태그 자동완성·노선 배지·사진 서명 URL은 보조 로드로 분리한다. 서명 실패는 사진 자체가 없다는 뜻이 아니므로 메타데이터와 순서를 유지하고 이미지 자리만 대체한다.
3. 로드 재시도에는 요청 세대 또는 취소 처리를 둔다. 역/기록 ID·사용자·공간이 바뀐 뒤 이전 응답을 적용하지 않는다.
4. 최초 로딩은 전부 확인한 뒤 폼을 한 번에 초기화한다. 사용자가 이미 편집한 후의 재조회는 폼을 조용히 초기화하지 않고 새 서버 스냅샷으로 보관한다.
5. D03에서는 본문·태그·사진·버전을 한 DB 스냅샷으로 읽는 계약까지 완성한다. 서로 다른 시점의 세 조회에 최신 버전만 붙이면 충돌 검사를 우회하는 결과가 생길 수 있다.

**최종 동작 / 완료 기준**

- 태그 조회만 500으로 실패시켜도 기존 태그가 서버에서 사라지지 않는다. 실패 화면에서 저장 요청 자체가 발생하지 않는다.
- 재시도 성공 후 원래 태그와 사진 순서가 표시된다.
- 이미지 서명만 실패하면 사진 개수·순서는 유지되고 삭제로 해석하지 않는다.
- 기록 A의 늦은 응답이 기록 B의 수정 화면에 들어오지 않는다.

### D02 · P1 · 사진 준비 상태와 저장 상태 연결

연결 항목: **R04**\
수정 대상: `PhotoField.tsx`, `photo-pipeline.ts`, `RecordEditorScreen.tsx`.

**개발 방향**

- 사진 준비 건수를 부모에 전달해 저장 가능 여부와 이탈 보호에 포함한다. 버튼 비활성뿐 아니라 Enter 제출·재시도·드래그 핸들러에서도 검사한다.
- 사진 준비 또는 업로드 동안 추가 선택·삭제·순서 변경을 잠근다. 완료 시 오래된 `photos` 클로저로 최신 목록을 덮지 않도록 함수형 갱신 또는 최신 목록 참조를 사용한다.
- 작업 세대가 바뀌거나 화면이 사라지면 늦은 완료를 폐기하고 생성한 Blob URL을 해제한다. 실패한 파일 외의 준비된 사진은 보존한다.
- 현재 한도인 **사진 10장**, 원본 선택 파일당 10MiB, 긴 변 2048px의 처리 기준을 참고한다. 목표 인코딩 용량과 강제 업로드 제한은 구분하고 서버/버킷 기준과 대조한다.

**최종 동작 / 완료 기준**

- 사진 선택 직후 ‘사진 준비 중…’이며 저장되지 않는다. 준비가 끝나면 실제 반영된 목록으로만 저장한다.
- 준비 중 삭제/이동·연속 선택·화면 이탈을 시도해도 사진이 다시 나타나거나 중복되지 않는다.
- 파일 하나의 디코딩 실패가 나머지 사진이나 글을 지우지 않는다.

### D03 · P0 · 원자적 저장·버전 검사 서버 계약

연결 항목: **R02·R03**, D04의 **R06** 기반\
수정 대상: 새 `supabase/migrations/*.sql`, `src/lib/database.types.ts`, `record-rpc.ts`, `photo-storage.ts`, `supabase/tests/`, 스펙 05.

아래 이름은 **구현할 계약의 제안**이며 아직 존재하는 API가 아니다. 구현 시 이름을 바꾸더라도 의미와 실패 동작을 유지하고 타입·호출부·스펙을 함께 고친다.

| 계약 | 입력 | 성공 결과 | 보장 |
|---|---|---|---|
| 수정 스냅샷 조회 | 기록 ID | 본문·태그·사진 메타데이터·`revision` | 같은 DB 스냅샷의 완전한 편집 기준 |
| 본문·태그 저장 v2 | 신규/수정 구분, 기록 ID, `expected_revision`, `operation_id`, 폼 값 | 기록 ID, 새 버전, 저장 결과 | 본문·태그·버전·처리 영수증이 같은 트랜잭션 |
| 사진 목록 교체 `sync_record_photos` | 기록 ID, `expected_revision`, `operation_id`, 최종 사진 목록 | 확정 목록, 새 버전, 제거 대상 경로 | 목록 전체 성공 또는 이전 목록 유지 |

**서버 개발 순서**

1. 증가형 `revision`을 도입한다. 본문·태그 변경과 사진 목록 확정 모두 같은 기록의 버전을 증가시킨다. 화면용 `updated_at`은 유지하되 JavaScript 날짜 변환 결과를 동시성 토큰으로 사용하지 않는다.
2. 권한을 확인한 기록 행을 잠근 뒤 기대 버전을 검사하고 갱신한다. 조회→비교→수정을 독립 요청으로 나누지 않는다. 불일치는 `RECORD_CONFLICT`, 삭제/접근 불가는 기존 정보 노출 원칙에 맞는 `RECORD_NOT_FOUND`로 반환한다.
3. 사진 최종 목록의 개수·중복 ID·정렬·치수·파일 타입·크기·경로 귀속을 서버에서 검증한다. 기존 다른 기록의 사진 ID/경로를 끌어오지 못하게 한다. 허용 목록은 화면의 현재 한도와 일치시킨다.
4. 사진 순서를 바꾸기 위한 DELETE/INSERT가 필요하면 **한 RPC의 한 트랜잭션** 안에서 처리한다. 기존 `(record_id, sort_order)` UNIQUE 제약을 만족하도록 교체한다. 오류 주입 시 이전 목록이 온전히 남아야 한다.
5. 동일 작업의 재시도를 식별할 처리 영수증을 저장한다. `(호출자, 권한 범위, 작업 종류, operation_id)`를 유일하게 하고 요청 내용의 식별값·성공 결과를 함께 보관한다. 같은 키/같은 내용은 이미 처리한 결과를 반환하고, 같은 키/다른 내용은 거부한다.
6. 영수증 조회와 반환 전에도 현재 권한을 확인한다. 동시 중복 요청은 DB 유일성/잠금으로 하나만 처리한다. 성공했던 요청의 재시도는 이미 증가한 버전 때문에 단순 충돌로 처리되지 않아야 한다.
7. 읽기는 RLS가 적용되는 단일 조회를 사용한다. 쓰기에 `SECURITY DEFINER`를 사용한다면 고정 `search_path`, 함수 실행 권한, 호출자·범위·행 귀속 검사를 함수 안에 모두 둔다. 직접 테이블 쓰기나 구버전 RPC가 새 버전 검사를 우회하지 못하도록 전환 계획에 포함한다.

**Storage 경계**

- 바이너리 업로드는 DB 트랜잭션 밖이다. 본문 확정 → 새 파일 업로드 → 사진 목록 RPC의 순서를 유지한다. **DB와 Storage까지 원자적이라는 설명은 하지 않는다.**
- 준비한 파일이 하나라도 업로드 실패하면 이번 최종 목록 교체를 보류한다. 기존 사진 목록은 그대로이고 성공한 업로드는 재시도용으로 기억한다. 모두 준비되면 목록을 한 번에 확정한다.
- 새 사진은 새 ID/경로를 사용한다. 동일 경로 재업로드는 같은 준비 파일의 재시도에만 허용해 기존 참조 파일을 변경하지 않게 한다.
- 사진 제거 대상 객체는 DB 목록 교체 성공 확인 후 정리한다. 응답이 유실되면 객체를 먼저 지우지 않고 동일 작업 결과부터 확인한다.
- 미참조 업로드·삭제 실패 객체는 D07의 유예/재검증 대상이다. 현재 저장이 진행 중인 객체를 고아로 판정하지 않는다.

**완료 기준**

- 사진 3장의 순서 교체에서 INSERT 오류를 발생시켜도 이전 3장과 순서가 유지된다.
- 두 클라이언트가 같은 버전으로 수정하면 하나만 성공하고 나머지는 충돌한다. 본문 대 본문뿐 아니라 본문 대 사진·사진 대 사진도 검사한다.
- 같은 신규/사진 확정 요청을 동시 또는 반복 전송해도 결과가 하나다. 같은 작업 ID에 다른 내용을 보내면 기존 기록을 덮지 않는다.
- 다른 사용자/공간/기록의 ID와 경로, 직접 쓰기 우회, 권한 해제 후 재시도를 모두 검사한다.

### D04 · P0/P1 · 충돌·부분 실패·응답 유실 복구

연결 항목: **R03·R06**, R02의 화면 연동\
수정 대상: `RecordEditorScreen.tsx`, `record-rpc.ts`, 오류 타입·캐시·브라우저 테스트.

**개발 방향**

- 편집 폼과 서버 저장 기준을 구분한다. 본문 저장 성공 시 본문 기준·버전만 갱신하고, 사진 성공 시 사진 기준·버전을 갱신한다.
- 신규 작성 세션에 기록 ID와 저장 요청 ID를 미리 만든다. 자동 재시도·응답 유실 복구에서는 같은 ID와 같은 요청 내용을 유지한다. 성공 확인 전에는 새 ID로 같은 기록을 다시 만들지 않는다. 새 RPC는 생성/수정을 명시적으로 구분하고 기존의 `p_record_id = null` 생성 방식과 혼용하지 않는다.
- 진행 중 작업 ID와 전송 스냅샷은 사용자·접근 범위별로 보관해 새로고침 후에도 결과를 확인한다. 이 최소 저장 범위 분리는 D04에 포함하고 일반 초안 UX는 D12에서 완성한다. 영수증 보존 기간이 끝나도 같은 신규 기록 ID를 다른 기록으로 재생성하지 않도록 유일성·재사용 거부 정책을 둔다.
- 전송한 값은 불변 스냅샷으로 보관한다. 응답 불명 상태에서 새 입력을 이전 요청 ID로 보내지 않는다. 결과 확인 후 변경된 입력은 새 작업으로 저장한다.
- ‘사진 다시 올리기’는 본문 저장 RPC를 다시 호출하지 않는다. 본문 변경이 추가로 남아 있으면 그 상태를 별도 안내하고, 전체 저장 버튼에서만 새 본문 작업을 수행한다.
- 충돌 시 최신 버전만 갈아 끼워 자동 재전송하지 않는다. 내 입력을 보존한 채 최신 내용을 확인하고 다시 적용할 수 있게 한다. 삭제된 기록을 새로 저장하는 기능은 명시적 사용자 선택으로만 실행한다.
- 모든 비동기 저장 경로에 예외 처리와 잠금 해제를 보장한다. 로컬 초안 삭제 실패 때문에 서버 저장 성공을 실패로 바꾸거나 사진 단계가 중단되지 않게 한다.

| 화면 상태 | 보여줄 내용 | 가능한 동작 |
|---|---|---|
| 수정 로드 실패 | 기존 내용을 모두 확인하지 못함 | 다시 불러오기, 안전한 뒤로가기 |
| 사진 준비 중 | 준비 중인 사진 수 | 글 입력, 이탈 확인. 저장·사진 목록 변경 제한 |
| 본문 저장 중 | 저장 중 | 중복 제출 제한 |
| 사진 업로드/확정 중 | 글 저장됨, 사진 진행률 | 중복 제출 제한. 이탈 시 미완료 설명 |
| 응답 유실 | 저장 결과 확인 필요 | 같은 작업 결과 확인/재시도 |
| 사진 실패 | 글 저장 완료, 사진 목록 미완료 | 사진만 재시도, 입력 보존 |
| 버전 충돌 | 다른 곳에서 변경됨 | 내 입력 유지, 최신 내용 확인·재적용 |
| 모두 성공 | 저장 완료 | 상세로 이동, 원래 탐색 맥락 보존 |

**완료 기준**: 저장 응답 차단 후 재시도에서 기록 수가 증가하지 않는다. 사진만 재시도하는 동안 다른 기기의 본문을 덮지 않는다. 연속 클릭·Enter로 중복 저장이 시작되지 않는다. 사진 실패 상태에서 나가면 경고하며 돌아와 남아 있는 초안의 범위를 정확히 설명한다.

### D06 · P0 · 개인 소유권·세션·가입 흐름

연결 항목: **F01**, 일부 **F02·M08**\
수정 대상: 새 마이그레이션, RLS·집계 뷰·Storage 정책, `App.tsx`, `auth/guards.tsx`, `SessionProvider.tsx`, 온보딩·프로필·저장/조회·캐시.

- 권장 모델은 개인 원본 소유자와 기존 공동 공간을 구분하는 구조다. 예를 들어 `owner_id`와 기존 공동 범위를 구분하되, 실제 필드·제약은 D05 결과에 맞춰 확정한다. 기존 `author_id`는 최초 작성자 정보로 보존한다.
- 가입 후 주요 화면의 필수 조건을 인증으로 바꾼다. 상대 연결·사귄 날 입력을 개인 기록의 선행 조건에서 제거한다. 가드만 제거하지 않고 RPC/RLS/사진 저장 경로/조회/통계까지 함께 적용한다.

- 캐시·초안·사진 서명·내보내기의 키에 사용자와 접근 범위를 포함한다. 로그아웃/범위 변경/권한 해제에서 이전 내용이 한 프레임도 재노출되지 않는지 확인한다.
- 기존 Storage 경로를 일괄 이름 변경하지 않는다. 새 개인 경로와 기존 공동 경로의 접근 정책을 병행하고, 필요 시 별도 검증된 이전 작업으로 처리한다.

**완료 기준**: 멤버십 없는 새 계정이 노선도에서 기록 작성·사진 업로드·조회·수정을 완료한다. 기존 두 사용자의 공동 기록과 사진은 확정한 정책대로 보존된다. 제3자·초대 미수락자·해제된 사용자 접근을 직접 API 수준에서 거부한다.

### D07 · P0 · 보존 기간·정리 작업의 실제 운영 계약

연결 항목: **R09**\
수정 대상: 운영 작업 정의/서버 실행 코드, 필요 시 정리 큐·실행 이력 SQL, `DissolveCoupleDialog.tsx`, Storage 정리 호출과 운영 문서.

1. 운영에 실제 정리 잡이 있는지, 스케줄·마지막 성공·실패·대상 범위를 읽기 전용으로 확인한다. 리포지토리에 없다는 이유만으로 미운영이라고 단정하지 않는다.
2. 해제 즉시 접근 차단과 보존 기간 이후 영구 삭제를 구분한다. 현재 ‘30일’ 안내가 실제 정책·작업과 일치하는지 검증한다.
3. 정리 작업은 대상 산출 → 보존 기간/참조 재확인 → Storage API 삭제 → DB 정리/상태 기록 순서를 재시도 가능하게 설계한다. 파일 경로를 확보하기 전에 DB 행을 지워 추적을 잃지 않는다. Storage 메타데이터 직접 SQL 삭제를 파일 삭제로 취급하지 않는다.
4. 정상 참조 사진·업로드 진행 중 파일·다른 공간 데이터는 제외한다. D03의 미확정 업로드는 유예 기간과 처리 영수증을 확인한다.
5. 실행 횟수·대상 수·성공/실패·재시도 시점을 기록한다. 로그에 사진 서명 URL·본문·자격 증명을 남기지 않는다.

**완료 기준**: 테스트 공간의 만료 대상만 정리되고, 중간 실패 후 재실행해도 정상 데이터가 손상되지 않는다. dry-run 목록과 실제 처리 결과가 일치한다. 운영 적용 여부와 로컬 검증 여부를 별도로 보고한다. 실제 영구 삭제 실행은 대상·정책·복구 가능성을 검토한 별도 운영 단계다.

### D08 · P1 · 화면 복귀·재연결·늦은 응답 보호

연결 항목: **R07**, 일반 지도의 **M07**\
수정 대상: `SessionProvider.tsx`, `screen-cache.ts`, `line-map-data.ts`, `StationDetailScreen.tsx`, `TimelineScreen.tsx`, `MapViewScreen.tsx`.

- 탭 복귀·네트워크 재연결·사용자/범위 변경에서 세션 권한과 현재 화면 데이터를 재검증한다. 중복 이벤트를 묶고 요청 중복을 제한한다. Realtime 도입은 필수로 두지 않는다.
- 요청에 사용자·범위·필터·세대 정보를 묶어 늦은 응답과 이전 캐시 쓰기를 무시한다. 권한이 사라지면 과거 목록을 stale 상태로 계속 보여주지 않는다.
- 같은 범위의 재검증에서는 기존 목록을 유지하며 갱신 상태를 알리고, 필터·스크롤·노선도 위치를 보존한다. 현재 편집 중인 폼을 자동 덮어쓰지 않는다.
- 일반 지도에서도 방문 로딩/실패를 ‘방문 0건’으로 표시하지 않는다. SDK 오류는 같은 화면에서 재시도와 노선도 이동을 제공한다. 자동 이동만으로 끝내지 않는다.

**완료 기준**: A→B 역을 빠르게 바꾸고 A 응답을 늦춰도 B만 표시된다. 계정 전환 후 이전 방문 집계가 캐시에 남지 않는다. 다른 기기의 저장이 복귀 시 반영된다. 진짜 빈 상태와 조회 실패가 다르게 보인다.

### D09 · P1 · 사진 서명 만료·오류 복구

연결 항목: **R08**\
수정 대상: `photo-storage.ts`, `RecordCard.tsx`, `RecordDetailScreen.tsx`, `PhotoField.tsx`, `PhotoViewer.tsx`.

- 사진 경로·표시 크기·접근 범위별로 URL과 만료 시각을 관리한다. 같은 경로의 갱신 요청은 합치고, 실패 후 무한 `onError` 재서명을 막는다.
- 자동 재서명은 같은 로드 주기에서 1회로 제한하는 안을 기본으로 한다. 다시 실패하면 대체 이미지와 명시적 재시도를 제공한다. 범위가 바뀌면 실패/서명 캐시도 분리한다.
- 카드·상세·뷰어·편집에서 같은 오류 의미를 사용한다. URL 만료나 네트워크 오류를 원본 사진 삭제로 해석하지 않는다.

**완료 기준**: 만료·404·오프라인·권한 해제를 주입해 요청이 무한 반복되지 않는지 검사한다. 다른 사용자의 캐시 URL을 재사용하지 않는다. 권한 해제 후 새 서명 발급은 거부되며 이미 발급된 URL은 만료 전까지 유효할 수 있다는 한계도 설계에 기록한다.

### D10 · P1 · 기록 검색·필터·누락 없는 페이지 조회

연결 항목: **F03·E03**\
수정 대상: `record-card-query.ts`, `TimelineScreen.tsx`, 목록 조회용 SQL/RPC·타입·테스트.

- 첫 검색 범위는 역명·장소 이름(D14 이후)·일기 본문이다. 태그는 `tag_norm` 기반 정확 일치 필터로 제공한다. 여러 태그를 지원할 경우 AND/OR 의미를 화면과 서버 계약에 명시한다.
- 조회 입력에 검색어·역·태그·시작일/종료일·현재 접근 범위·키셋 커서를 둔다. 목록과 월 집계는 같은 검색/필터 조건을 사용한다.
- 태그에 맞는 모든 ID를 브라우저로 먼저 가져오는 방식을 서버 `EXISTS`/조인 필터로 바꾼다. 검색 조건과 `(visited_on DESC, id DESC)` 커서를 같은 조회에 적용한다.
- 검색 문자열은 파라미터로 전달하고 와일드카드 의미를 결정한다. 한국어 검색을 영어 형태소 검색만으로 대체하지 않는다. 인덱스 방식은 대표 데이터와 실행 계획을 측정해 결정한다.
- 필터를 URL에 보존하고 변경 시 커서를 초기화한다. 접힌 필터에서도 활성 조건과 해제 버튼은 보인다. ‘전체 기록 없음’과 ‘검색 결과 없음’을 구분한다.
- 목록의 일기는 기존처럼 발췌문만 반환한다. 페이지별 대표 사진·태그·서명 호출 수를 측정하고, 실제 SDK 지원 없이 변환 이미지 서명 배치가 가능하다고 가정하지 않는다.

**완료 기준**: 같은 태그의 기록을 1,000건 이상 넣어 끝까지 탐색해도 누락·중복이 없다. 같은 날짜의 여러 기록도 안정적으로 이어진다. 필터 변경 중 이전 응답이 섞이지 않는다. 타 계정/범위의 검색 결과와 월 건수가 새지 않는다.

### D11 · P1 · 연월 이동

연결 항목: **F04**, [스펙 13](specs/13-timeline-time-jump.md)\
수정 대상: `TimelineScreen.tsx`, 월 집계 함수·목록 조회 타입/커서.

- ‘기간 이동’을 열 때 현재 검색·태그·날짜 조건에서 기록이 있는 연월과 건수만 조회한다. 서버 집계에도 목록과 동일한 RLS/범위 조건을 적용한다.
- 달 선택은 **그 달부터 과거로 읽기 시작하는 점프**다. 특정 월만 남기는 기간 필터와 구분한다. 선택한 월 말일을 첫 페이지 상한으로 사용한다.
- 점프 지점을 URL에 보존하고 ‘최근 기록으로 돌아가기’를 제공한다. 검색/태그/기간 조건 변경 시 점프를 해제한다.

**완료 기준**: 오래된 달로 한 번에 이동하고 이후에는 과거 방향으로 이어진다. 중간 달의 기록이 삭제돼도 다음 과거 기록을 표시한다. 목록과 월 집계가 같은 조건을 사용한다. 기록 수가 적을 때의 진입점 노출은 스펙 13의 기준과 함께 확정한다.

## 6. 3단계 — 작성 편의·화면 정리

### D12 · P1 · 초안 범위와 복원 안내

연결 항목: **R05**\
수정 대상: `RecordEditorScreen.tsx`, `app-storage.ts`, 초안 저장/복원 책임을 분리한 모듈, 로그아웃 정리.

- 초안 키는 사용자 ID·접근 범위·신규 작성 세션 또는 기록 ID·초안 버전을 포함한다. 기존 소유자 정보 없는 전역 `new` 초안은 새 계정에 자동 복원하지 않는다.
- 폼·기준 기록 버전·저장 시각·미완료 작업 ID를 보관한다. D04에서 성공한 본문과 사진 미완료 상태를 구분하며, 새 글이 입력되면 그 변경을 다시 초안으로 남긴다.
- 1차 초안에는 사진 Blob을 넣지 않는다. ‘글 임시 저장 / 사진은 다시 선택 필요’를 명확히 알린다. Blob 복원은 별도 기능이며 D18의 열람 캐시와 같지 않다.
- 저장소 읽기·쓰기·삭제 실패를 모두 처리한다. 초안 제안이 남아 있는 동안 초기 빈 폼의 자동 저장이 기존 초안을 덮지 않게 한다. 다른 탭 초안 경합도 감지한다.

**완료 기준**: 계정 전환 시 다른 초안이 보이지 않는다. 저장소 차단·용량 초과에도 서버 저장은 정상 처리된다. 새로고침 후 복원되는 내용과 복원되지 않는 사진을 사용자가 구분한다.

### D13 · P1 · 연속 작성·원래 화면 복귀·재방문 참고

연결 항목: **F05**, [스펙 12](specs/12-record-entry-flow.md)\
수정 대상: `RecordEditorScreen.tsx`, `RecordDetailScreen.tsx`, 역 상세·타임라인 진입 정보.

- 목록/역 상세의 필터·월 점프·스크롤을 복귀 맥락으로 전달한다. 상세→수정→저장 사이에도 유지한다. 복귀 주소는 앱 내부 허용 경로로 제한한다.
- 저장으로 도달한 상세에만 ‘이어서 기록 추가’를 제공한다. 다음 폼은 날짜만 이월하고 역·본문·사진·태그·감정·날씨를 비운다.
- 연속 작성 진입과 저장 완료는 `replace`로 처리해 기록 수만큼 히스토리를 쌓지 않는다. 뒤로 가면 연속 작성 전 화면으로 복귀한다.
- 선택한 역의 과거 기록이 있으면 접힌 재방문 요약과 최근 최대 3건을 제공한다. 수정 중인 기록 자신은 제외한다. 조회 실패는 저장을 막지 않고 이전 역 요약도 남기지 않는다.

**완료 기준**: 같은 날짜 기록 3건을 이어 쓰고 뒤로 가면 원래 필터/위치로 돌아온다. 일반 열람 진입에는 저장 직후 배너가 없다. 기록 없는 역에서는 빈 재방문 패널을 표시하지 않는다.

### D14 · P1 · 선택형 장소 이름

연결 항목: **F06**\
수정 대상: 기록 테이블·저장 RPC·목록 뷰·타입, 작성/상세/카드/검색.

- 역은 계속 필수 기준 위치다. 장소 이름은 nullable 문자열로 추가하고 빈 문자열은 null로 정규화한다. 길이 상한은 스펙에 하나로 확정해 UI와 서버에 같이 적용한다.
- 값이 있으면 카드에 장소 이름과 역명을 함께 보여주고, 없으면 기존 역명 표시를 유지한다. 기존 기록의 장소 이름을 자동 추정해 채우지 않는다.
- D10 검색에 필드를 추가한다. 일반 지도 핀은 여전히 역 좌표이므로 ‘역 기준 위치’임을 표시한다. 실제 가게 좌표·외부 장소 검색은 이 단계에 포함하지 않는다.

**완료 기준**: 같은 역의 ‘카페 A’와 ‘공원 산책’ 기록을 구별하고 검색할 수 있다. 장소 이름 없는 기존 기록도 수정 없이 정상 표시된다.

### D15 · P1 · 문구·통계·보조 정보 정리

연결 항목: **F02·M08**, 일부 **E01**\
수정 대상: `AppShell.tsx`, 프로필·카드·공유 진입부·통계 조회/표시·README·제품 문서.

- D06 적용 이후 개인 화면의 커플 생성 유도·초대 대기·사귄 날·‘총 데이트 수’를 정리한다. 커플 기능을 실제로 사용하는 기존 공동 공간의 문맥은 보존한다.
- 개인 목록의 반복 작성자 표시는 줄이고 공유/공동 맥락에는 작성자를 표시한다. 감정·날씨·태그는 상세/선택 입력에 남긴다.
- ‘기록 수’와 ‘방문 역 수’를 구분한다. 방문 커버리지는 선택한 표시 범위와 방문 집합의 교집합으로 계산한다. 개인/공동/공유받은 범위가 섞이지 않게 한다.
- 노선도는 계속 메인이다. 현재 승인된 지도 공간·배치·탐색 UI를 이 문구 정리 작업에서 다시 바꾸지 않는다.
- 방문일의 ‘오늘’은 한국 날짜 기준으로 UI/서버를 일치시킨다. 서버의 현재 `current_date + 1` 여유와 프론트 `todayKst()`가 서로 다른 미래 날짜를 허용하는지 검사하고 계약을 맞춘다. 이모지 포함 글자 수도 UI/SQL에서 대조한다. 현재 일기 1,000자·태그 최대 10개/각 20자·사진 10장 기준을 오래된 스펙 수치와 정합시킨다.

**완료 기준**: 화면의 소유권·건수·사용 가능한 동작이 실제 서버 권한과 일치한다. 상대 연결 없이 사용하는 로그인 사용자의 개인 상태와 기존 공동 공간 상태를 각각 검증한다.

## 7. 4단계 — 선택 기능

### D16 · P2 · 선택 공유 모음

연결 항목: **F07**. 선행: D05–D06의 소유권과 역할 확정.

- 개인 원본과 모음 참조를 분리한다. 제안 모델은 모음·멤버·모음-기록 연결·초대다. 개인 전체 기록을 자동 공유하지 않는다.
- 권장 초기 권한은 읽기 전용이다. 기여 권한을 선택하면 ‘본인 기록 추가/수정’과 ‘다른 사람 원본 수정’을 구분해 SQL 권한 표를 작성한다.
- 공유 해제/탈퇴는 참조와 접근 권한을 제거하고 개인 원본을 삭제하지 않는다. 원본 수정이 공유 화면에 반영되는지, 복사본인지도 UI에 명시한다.
- 사진·검색·집계·내보내기도 동일 권한을 적용한다. 초대 만료·취소·중복 사용을 테스트한다.

**완료 기준**: 선택한 기록만 상대에게 보이며, 공유 해제 후 새 조회·서명 요청은 거부된다. 원본과 다른 모음의 접근은 보존된다. 기존 발급 URL·로컬 캐시의 권한 해제 시차를 사용자 안내와 맞춘다.

### D17 · P2 · 가보고 싶은 역·장소

연결 항목: **X01**. 수정 대상: 프로필 추천, 역 상세, 사용자별 찜 저장/조회.

방문 기록과 별도 찜 데이터를 만들고 추천 진입을 상세/찜으로 연결한다. ‘방문 기록으로 남기기’를 명시적으로 선택할 때만 작성한다. 찜은 방문 횟수·기록 수를 늘리지 않는다. `station_lines.seq` 차이를 실제 거리·소요시간으로 안내하지 않는다.

**완료 기준**: 미방문 찜 5개를 추가해도 방문 통계는 변하지 않는다. 중복 찜을 막고 해제 가능하다. 찜에서 작성 후 실제 저장 성공 때만 방문 상태가 바뀐다.

### D18 · P2 · 제한된 오프라인 사진 캐시

연결 항목: **X02**, [스펙 11](specs/11-offline-photo-cache.md).

성공적으로 표시한 사진 Blob을 IndexedDB에 제한적으로 저장한다. 스펙 11의 변형별 상한(썸네일 1,000개 또는 40MB, 원본 60개 또는 60MB 중 먼저 도달하는 조건)·LRU·30일 TTL을 기준으로 삼고, 실제 바이트 단위와 기기 제약을 구현 시 명시한다. 프로필에 사용량/비우기를 제공한다. 사용자·접근 범위를 키에 포함하며 로그아웃·권한 해제·삭제 확인 시 관련 캐시를 폐기한다. 저장 공간 부족이나 IndexedDB 차단은 사진 표시를 막지 않는다.

**완료 기준**: 실행 중인 앱에서 연결을 끊어도 캐시된 허용 사진은 열리고, 미캐시 사진은 대체 표시된다. 계정 전환 시 캐시가 재노출되지 않는다. 완전 오프라인 앱 시작·오프라인 서버 저장·네트워크 단절 중 즉각적인 원격 권한 철회를 보장한다고 설명하지 않는다.

### D19 · P2 · 사진 확대·형식 지원·촬영일 제안

연결 항목: **X03**, 스펙 12의 EXIF 제안.

- 뷰어의 핀치/더블탭 확대·축소·초기화와 사진 넘기기 제스처 충돌을 먼저 해결한다. 키보드 버튼과 닫기 후 포커스 복원도 제공한다.
- HEIC는 변환 라이브러리의 호환성·용량·라이선스·실제 기기 동작을 확인한 뒤 지연 로딩으로 도입한다. 미지원/실패는 선택 단계에서 알리고 기존 사진은 보존한다.
- EXIF 날짜는 재인코딩 전에 읽어 ‘촬영일로 바꾸기’ 제안만 제공한다. 자동 변경하지 않는다. 유효한 과거/오늘 날짜 중 가장 이른 날짜를 제안하고 여러 날이면 그 사실을 알린다. 날짜 없음·미래 값은 제외하고, 타임존이 없는 값을 임의로 UTC 변환해 날짜를 바꾸지 않는다. 서버 업로드 사진에서는 기존 EXIF 제거를 유지한다.

**완료 기준**: 확대 상태에서 사진 전환/닫기가 예측 가능하다. HEIC 실패가 폼 전체 실패가 되지 않는다. 촬영일 제안을 누르기 전에는 방문일이 바뀌지 않는다.

### D20 · P2 · 기록·사진 백업 내보내기

연결 항목: **X04**. 선행: 개인/공동/공유받은 기록의 내보내기 권한 결정.

버전이 있는 manifest와 JSON/CSV 기록, 실제 접근 가능한 사진 파일을 묶는다. 서명 URL만 적은 파일을 사진 백업으로 간주하지 않는다. 페이지 조회·진행률·취소·메모리 제한·사진 실패 목록을 처리한다. CSV 수식 실행 문자와 파일명 경로 탈출도 처리한다. 개별 PNG 저장은 유지한다.

**완료 기준**: 표본 기록의 날짜·역·장소·글·태그·사진 수를 원본과 대조하고, 실패 파일은 누락 목록으로 확인할 수 있다. 공유 권한 밖 데이터는 포함하지 않는다. 가져오기 기능까지 구현·검증하지 않았다면 자동 복원 가능한 백업이라고 약속하지 않는다.

### D21 · P2 · 삭제 복구·계정 탈퇴

연결 항목: **X05**. 선행: 복구 기간·공유 원본 삭제 결과·탈퇴 처리 정책 결정, D07.

권장 방향은 논리 삭제와 휴지통이다. 일반 목록·방문 집계·지도에서는 제외하고, 기간 안 복원하면 사진과 통계까지 되살린다. 영구 정리는 D07과 연결한다. 클라이언트의 짧은 타이머만으로 휴지통 보존을 구현하지 않는다. 계정 탈퇴는 공유 모음 탈퇴·커플 해제와 별도 흐름으로 제공한다.

**완료 기준**: 삭제→복원에서 사진 순서와 태그가 보존된다. 타 계정의 휴지통은 조회/복원할 수 없다. 기간 경계의 복원과 영구 정리가 경쟁해도 한 결과로 확정된다. 탈퇴 후 남는 공동 기록과 삭제되는 개인 기록을 확정 정책과 대조한다.

## 8. D22 — 모든 단계의 코드·검증 기준

연결 항목: **E01·E02·E04**. 테스트는 별도의 마지막 단계로 미루지 않는다.

### 구현 단위

1. 작업 ID와 최종 동작을 해당 기능 스펙에 반영한다.
2. DB 변경이 있으면 새 마이그레이션과 권한/오류/재시도 테스트를 먼저 만든다. 과거 적용된 마이그레이션 파일을 수정해 이력을 바꾸지 않는다.
3. TypeScript 계약·RPC 경계·프론트 상태 처리를 함께 연결한다. 서버의 원문 오류를 그대로 노출하지 않고 의미 있는 코드와 안내로 바꾼다.
4. 같은 문제를 담당하는 저장·초안·조회 코드를 필요한 범위에서 분리한다. 사용처 없는 일반화나 화면 전체 재작성은 피한다.
5. 정상 흐름뿐 아니라 해당 작업의 실제 실패 경로를 검사한다. 구현을 그대로 복제한 테스트 대신 데이터 보존·권한·사용자 결과를 검증한다.
6. 적용한 파일·마이그레이션·테스트 명령/결과·미검증 범위·운영 적용 여부를 구현 보고에 기록한다.

### 검사 행렬

| 영역 | 반드시 확인할 항목 |
|---|---|
| 저장 | 본문/태그/사진 조회 실패, 사진 준비 중 제출, 원자적 순서 교체, 버전 충돌, 동일 요청 재시도, 응답 유실 |
| 권한 | 개인/기존 공동/공유받은 범위, 제3자 접근, 직접 API 우회, 권한 해제 후 응답·캐시·서명 |
| 탐색 | 검색·태그·기간·월 점프의 조합, 동일 날짜 키셋, 1,000건 초과, 이전 요청 응답 차단 |
| 입력 | 새로고침·초안 복원·저장소 실패, 이모지 1,000자 경계, 한국 날짜 경계, 긴 역/장소 이름 |
| 사진 | URL 만료·업로드 실패·깨진 파일·재시도 상한·용량 제한·계정 전환 |

| 운영 | 정리 대상 dry-run, 실패 재시도, 만료 전/후, 기존 자료 보존, 배포 순서와 구버전 쓰기 우회 |

### 현재 실행할 수 있는 명령과 준비할 검증

```sh
npm run build
npm run lint
npm run test:db
npm run test:line-map
npm run line-map:check
```

- `test:db`는 PGlite의 SQL/RLS/RPC 계약 검사다. 실제 Auth·PostgREST·Storage 동작을 대신하지 않는다.
- `tests/browser/run.mjs`는 기존 모킹 브라우저 검사다. 기본 `TEST_BASE_URL`은 `http://127.0.0.1:5174`이며 브라우저/Playwright 준비가 필요하다. 개발 시 새 실패 시나리오를 추가하고 실제 서비스 검사와 분리한다. 현재 `package.json`에 `test:browser` 명령이 있다고 가정하지 않는다.
- 운영 마스터 읽기용 `verify:line-map`은 노선도 기준 검사에만 사용한다. 기록 개선 테스트에서 서비스 키로 사용자 기록을 임의로 읽거나 변경하지 않는다.
- 프론트 strict는 관련 모듈부터 오류를 확인하며 단계적으로 적용한다. 기존 코드의 대량 수정과 기능 변경을 한 검토 단위에 섞지 않는다.
- 라우트 지연 로딩·사진 서명 요청 최적화는 전후 번들 크기·초기 표시·요청 수를 측정한다. 성능 목표를 측정 없이 달성했다고 기록하지 않는다.

## 9. 배포와 완료 판정

### 저장 계약 변경의 배포 순서

1. 테스트 환경에 새 컬럼·RPC·처리 영수증 등 호환 가능한 서버 기반을 적용한다.
2. 새 클라이언트로 전체 저장/사진/충돌/재시도를 검증한다. 개발 DB와 실제 Storage가 있는 테스트 환경 검증을 구별해 기록한다.
3. 구버전 쓰기가 새 계약을 우회하지 않도록 전환 시점에 레거시 RPC/직접 쓰기 권한을 제한한다. 오래 열린 탭에는 입력 보존과 새로고침 안내를 제공한다. UI 배포만으로 R03 완료를 선언하지 않는다.
4. 클라이언트가 새 서버 계약에 의존한다면 서버 배포 확인 후 프론트를 배포한다. 새 RPC가 없을 때 구 DELETE/INSERT 경로로 조용히 폴백하지 않는다.
5. 실패 시 읽기와 입력 보존을 우선하고 영향 기능의 쓰기를 제한한다. 추가 데이터를 삭제하는 방식의 롤백이나 이전의 무조건 덮어쓰기 경로 재개를 기본 복구책으로 쓰지 않는다.

### 단계 상태 표기

| 상태 | 의미 |
|---|---|
| 계획 | 구현 방향과 완료 기준만 작성 |
| 정책 대기 | 필요한 제품 결정 미확정. 독립 작업은 계속 가능 |
| 구현 중 | 코드/SQL 수정 중 |
| 로컬 검증 완료 | 빌드·해당 자동 검사·모킹/로컬 화면 검증 완료 |
| 테스트 환경 검증 완료 | 실제 API·Storage·권한·복수 세션 동작 확인 |
| 운영 적용 완료 | 운영 배포와 실제 적용 확인까지 완료 |

‘파일을 작성함’, ‘로컬 테스트 통과’, ‘운영 적용 완료’를 구별한다. 저장소의 기존 수정 파일은 먼저 diff를 확인하고 보존하며, 다른 작업의 결과를 되돌리거나 자신의 완료 항목으로 중복 기록하지 않는다.
