# 브랜치 운영 규칙

이 저장소에서 브랜치를 만들거나 갱신하고, PR을 열고, 병합·정리할 때 적용한다.

## 브랜치 규칙

- `develop`를 통합 브랜치로 사용한다. 새 작업 브랜치는 가능한 최신 `develop`에서 만들고 `master`에서 시작하지 않는다.
- 작업 목적을 나타내는 접두사와 짧은 kebab-case 주제로 브랜치 이름을 만든다. 예: `feature/station-search`, `fix/record-date`, `hotfix/login-loop`, `docs/setup-guide`. 작업에 맞으면 `refactor/`, `test/` 같은 명확한 유형 접두사도 사용할 수 있다.
- 작업 브랜치의 PR 대상은 `develop`이다. 리뷰 완료 후 병합하고, 병합이 확인되면 작업 브랜치를 삭제한다. 호스팅 서비스가 원격 브랜치를 이미 삭제했다면 남아 있는 로컬 브랜치만 정리한다.
- 굵직한 기능 단위로 `develop`의 변경을 `master`에 반영한다. 이때 `develop`에서 `master`로 PR을 열고, 일반 작업 브랜치의 PR을 `master`로 직접 보내지 않는다.
- `hotfix/*`도 기본적으로 같은 흐름에 따라 `develop`으로 PR한다. 사용자가 별도의 운영 배포 경로를 지정하면 그 경로를 따르되, 수정 사항이 이후 `develop`에도 포함되도록 한다.

## 브랜치 변경 전

- 먼저 현재 브랜치, upstream, 작업 트리 상태를 확인한다. 기존 수정과 미추적 파일을 보존하고, 관련 없는 변경을 초기화·폐기하거나 조용히 다른 브랜치로 옮기지 않는다.
- 새 작업에서는 로컬 또는 설정된 원격에 `develop`이 있는지 확인한다. 없으면 `master`에서 임의로 만들지 말고 상황을 알린 뒤 진행 방법을 묻는다.
- 기존 브랜치의 작업이나 PR을 이어가는 것이 분명하면 해당 브랜치를 계속 사용한다. 그 외에는 적절한 접두사를 붙여 `develop`에서 새 브랜치를 만든다.
- 각 브랜치는 리뷰할 수 있는 하나의 변경에 집중한다. 기존의 무관한 변경을 커밋이나 PR에 포함하지 않는다.

## 리뷰와 정리

- PR 본문 작성과 코드 리뷰의 상세 절차는 [pull-request-review](../pull-request-review/SKILL.md)를 따른다.
- 병합 전에 PR 대상이 `develop`인지, 리뷰가 끝났는지 확인한다.
- PR 병합 성공을 확인한 뒤 로컬 브랜치와, 아직 남아 있다면 원격 브랜치를 삭제한다. 일반적인 정리 과정에서 force-push하거나 미병합 브랜치를 삭제하지 않는다.
- 완료 시 브랜치 이름, PR 대상, 병합 여부, 정리한 항목을 알린다. 리뷰·병합·원격 접근을 할 수 없으면 브랜치를 유지하고 남은 작업을 설명한다.
